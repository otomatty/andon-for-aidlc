# バージョン確認の設計

プロジェクトまたはエンジンの aidlc-workflows のバージョンが Guide の対応版と一致しない場合、Guide は更新画面を表示し、更新が終わるまで主要機能を使えなくする。読み取り処理は対応版の形式だけを前提にでき、複数のバージョンの解釈を抱えずに済む。

## 決定事項（2026-10-09）

| 項目                   | 決定                                                                                                                                                         |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 基準のバージョン       | Guide の対応版 `WORKFLOWS_TARGET_VERSION`。公式の最新リリースは見ない（起動時の通信も不要）                                                                  |
| 対応版より古い         | 更新画面を表示してブロックする                                                                                                                               |
| 対応版より新しい       | 拡張の更新（または対応待ち）を案内してブロックする。Guide はダウングレードしない                                                                             |
| ブロック中も使えるもの | 更新・セットアップ画面、同梱の公式ドキュメントの閲覧、Doctor の診断と修復・再試行                                                                            |
| ブロックするもの       | ダッシュボードのワークフロー表示、カスタマイズ、回答の書き込み、ドキュメントの質問（チャット）、MCP の全ツール（文書検索を含む）、ステータスバーの現在地表示 |
| 回避手段               | 設けない。Doctor と修復だけを使える                                                                                                                          |
| チームでの更新の UX    | 共有ファイルの変更を迫られる場面を本人が選べるようにし、他のメンバーは1クリックで追いつけるようにする（下記「更新画面」）                                    |

## 判定

純関数 `inspectVersionGate(root, target)` を reader-core に置き、拡張・ブラウザ版・MCP の3経路が同じ判定を使う。reader-core は3経路すべてが依存しているパッケージである。これまでの判定は拡張の `inspectWorkflowsManagement`（プロジェクト側）と `inspectCliManagement`（エンジン側）に分かれ、Doctor の `workflowsVersionCheck` は docs manifest のバージョンと比べて新しいバージョンを正常とみなすなど、基準がばらばらだった。これを1つにまとめる。

- **プロジェクトのバージョン:** 各ハーネスの `tools/data/aidlc-stamp.json` の `frameworkVersion`、`tools/aidlc-version.ts`、`.aidlc-version`（pin）。
- **エンジンのバージョン:** native 導入のプロジェクト（stamp がある）では、この PC で pin を解決した実行ファイルのバージョン。pin がなければ既定の実行ファイルのバージョン。copy 版（stamp がない）ではハーネスのファイルがエンジンそのものなので、プロジェクトのバージョンと同じ。
- **版の書式:** 上流の `aidlc-channel.ts` と同じく、安定版 `x.y.z` とプレビュー版 `<x.y.(z+1)>-preview.<YYYYMMDD>.<N>` を版として読み、上流と同じ順序で比べる（同じ基底では安定版がプレビュー版より新しい）。それ以外の文字列は読めない版として扱う（`packages/reader-core/src/version/release-id.ts`）。
- **費用:** 判定は同期の fs 読み取りだけで行う。実行ファイル全体の sha256 は判定に含めず、更新・修復のときだけ計算する。

判定結果と、更新画面が示す1つの操作:

| 結果              | 条件（上から順に評価）                                               | 操作                       | 共有ファイルの変更     |
| ----------------- | -------------------------------------------------------------------- | -------------------------- | ---------------------- |
| `not-installed`   | ハーネスも pin もない                                                | セットアップ               | —                      |
| `unknown`         | ハーネスの衝突、読めないバージョン、バージョンのないハーネス         | Doctor と修復              | —                      |
| `project-newer`   | 対応版より新しいバージョンが1つでもある                              | Guide を更新               | なし                   |
| `project-older`   | 対応版より古いバージョンが1つでもある                                | プロジェクトを対応版に更新 | あり（コミットが必要） |
| `engine-newer`    | プロジェクトは対応版で pin がなく、この PC の既定エンジンが新しい    | プロジェクトを対応版に固定 | あり（コミットが必要） |
| `engine-mismatch` | プロジェクトは対応版だが、この PC のエンジンが未導入か別のバージョン | この PC に対応版を導入     | なし                   |
| `ok`              | 上記のいずれでもない                                                 | —                          | —                      |

`ok` 以外はブロックする。リポジトリを上げた人が1人いれば、他のメンバーは pull した後に `engine-mismatch` となり、この PC への導入だけで揃う。

## 強制する場所

| 経路                                       | 強制の方法                                                                                                                                                 |
| ------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 拡張のコマンド（開く・ようこそ・更新情報） | ダッシュボードを開く前に判定し、`ok` 以外は更新画面を開く。セットアップ完了済みでも素通りさせない                                                          |
| ダッシュボード webview                     | ホストが `version-gate` を送る。ブロック中は `docs` / `guides` のルートだけ表示し、ナビとワークフロー表示を差し替える。ドキュメント画面の質問欄は出さない  |
| api-core（拡張内・ブラウザ版の共通）       | `routeRead` / `routePost` の入口で判定し、許可リスト（同梱ドキュメントの閲覧系）以外を「更新が必要」のエラーで拒否する。画面の分岐が漏れても、ここで止まる |
| ブラウザ版 `dashboard-server`              | api-core の入口判定で同じく止まる                                                                                                                          |
| MCP サーバー                               | 全ツールの呼び出しごとに判定し、`ok` 以外は更新が必要な旨と操作を返す。共有の `.mcp.json` / `SKILL.md` の登録は書き換えない                                |
| ステータスバー                             | 現在地の代わりに「更新が必要」を表示し、クリックで更新画面を開く                                                                                           |
| 起動時の通知                               | 「後で」（snooze）は廃止する。ブロック中は毎回更新画面へ誘導する                                                                                           |

## 更新画面

既存の更新パネル（`aidlcGuide.updateWorkflows`）を使い、判定結果に応じた操作を1つだけ大きく示す。各ハーネスのバージョン・pin・エンジンのバージョンと対応版も並べる。

- **プロジェクトを更新（`project-older`）:** 実行前に、変更されるファイル（`.claude/`、`.cursor/`、`.aidlc-version`、`.gitignore` など）を一覧で見せる。作業中でも続けられる（2.11 の決定事項1）。管理者権限の扱いは上流に合わせる（同2）。実行後は変わったファイルの一覧と、コピーできるコミットメッセージ（例: `chore: aidlc-workflows を 2.11.0 に更新`）を出し、「チームのメンバーは pull すると、Guide の案内に従って揃えられます」と案内する。
- **Guide を更新（`project-newer`）:** 拡張の更新確認（`aidlc-guide.checkUpdate`）を開く。最新の Guide でも対応していない場合は、その旨を表示する。
- **プロジェクトを固定（`engine-newer`）:** 確認ダイアログの後、対応版の実行ファイルで `aidlc config --pin <対応版>` を実行し、`.aidlc-version` を作成・登録する。対応版がこの PC になければ先に追加導入し、既定バージョンは元に戻す。実行後は変わったファイルと、コピーできるコミットメッセージ（例: `chore: aidlc-workflows を 2.11.1 に固定`）を出す。予備の操作として「この PC の既定を対応版に戻す」（`aidlc use <対応版>`）も確認付きで置く。こちらは共有ファイルを変えないが、固定していない他のプロジェクトにも効く。
- **この PC に導入（`engine-mismatch`）:** 対応版のエンジンを導入し、プロジェクトの pin に合わせる。共有ファイルは変えない。クローン直後など、プロジェクトの pin がこの PC に登録されていない場合は、エンジンが導入済みでも「このマシンに登録」で pin を登録する（`prepareProjectCli`）。マシンの既定 CLI と共有ファイルは変えない。
- **Doctor と修復（`unknown`）:** 既存の診断と修復を案内する。
- いずれの場合も同梱の公式ドキュメントへのリンクを置く。

### 画面の組み立て（2026-10-27）

更新画面はセットアップ画面と同じ組み立てにした。判定結果とパネルの経過から `updatePhase`（`workflows-update-phase.ts`）が状態を 1 つ選び、`workflows-update-html.ts` がその状態だけを描く。状態が進むとホストが画面を描き直す。

- **上部:** 状態を 1 行（見出しと補足）で示し、「この PC」（ネイティブ導入ではこのプロジェクトで解決されるエンジン、それ以外は既定）「このプロジェクト」（古いときは最も古い版、それ以外は最も新しい版）「Guide の対応版」の 3 つを並べる。対応版と比べた印（対応版・古い・新しい・未導入・未登録・固定なし・未コミット）を付ける。
- **やること:** 手順の番号付きリストか 1 枚のカードで、主ボタンは 1 つだけ。ほかの操作は文字のリンクにする。ツールごとの版・固定バージョン・この PC の既定・実行ログは「詳しく見る」にたたむ。
- **プロジェクトの更新（`project-older` と、判定は通るが固定や再実行が要る場合）:** 「更新前のチェック」「プロジェクトを（対応版）に更新」「コミットして共有」の 3 手順。更新ボタンは、この PC に対応版の実行環境がなければ先に入れ（`prepareTargetRuntime`、既定は変えない）、チェックがまだなら実行し、問題がなければ更新まで続ける。チェックで問題が見つかれば 1 つめの手順で止め、ファイルごとの直し方と「N 件を直して（対応版）に更新」を示す（下の「更新を止めたファイルの直し方」）。チェックを完了できなかった場合は理由を示し、もう一度押すとチェックなしで更新する（更新処理自身の事前確認は働く）。
- **コミット:** このパネルで更新・固定した後は、判定が `ok` でも「コミットして共有」を先に示す。変わったファイルはフォルダーごとに件数でまとめ、「コミットメッセージをコピー」を主ボタンに、「ソース管理を開く」を添える。
- 「CLI を更新」は単独の操作としては置かない。この PC の既定を対応版にしたい場合は公式の `aidlc use` を使う。

### 更新を止めたファイルの直し方（2026-10-27）

更新前のチェックで問題が見つかったとき、以前の画面は上流の英語の `detail` と「確認できません」「特定できません」で終わる案内を並べ、直せる問題があるかに関係なく「AI で直して更新」を主ボタンにしていた。AI の回答は Guide が計算した正解との一致で判定しており、AI は同意するだけだった。そこで、直し方を Guide が決め、AI は答えが決まらない所にだけ使う形に改めた。

| 項目               | 決定                                                                                                                                                                                                                                                                                                                                                    |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 問題の読み方       | 上流の `detail` を種類（`ProblemKind`、`workflows-conflicts.ts`）に分けて日本語の案内を付ける。上流の `remediation` と原文は「原文」にたたんで残す                                                                                                                                                                                                      |
| 直し方の区分       | ファイルごとに「自動」「確認」「AI」「手で直す」に分ける（`RepairItem`、`workflows-repair-plan.ts`）。複数のツールが同じファイルを挙げた場合は 1 件にまとめ、ツールで食い違う場合は「手で直す」にする                                                                                                                                                   |
| 主ボタン           | 「手で直す」がなければ「N 件を直して（対応版）に更新」。あれば「直したので再チェック」にし、残りが 1 ボタンで直せることを示す。部分的な反映はしない（全ツールの設定を作業用コピーで通してから反映する前提を守る）                                                                                                                                       |
| AI を使わない修正  | 公式ファイルと同じ内容の作り直し、3-way マージによる変更の当て直し、古い区切りの `.gitignore`・Markdown の移行、`.gitignore` の管理ブロックの付け直し（同じ位置に付け直し、ブロック内の独自ルールはまとめてすぐ後ろか前に置いて、重なる公式ルールとの優先順位を保つ。保てなければ止める）、ツールの順番の入れ替え。いずれも以前は AI の同意を待っていた |
| 確認する修正       | 公式版への置き換え（今のファイルをバックアップへ移して作り直す。上流が案内する手順で、`--force` は使わない）、新しい版でなくなったファイルの削除・別名での保存、文字コードの変換、以前の版の取り寄せ。おすすめを既定で選び、選び直しはホストが覚える（画面は描き直さない）                                                                              |
| 以前の版の取り寄せ | 変更部分を見分けるために以前の版の公式配布物が要る場合、公式インストーラーで保持版として入れ、既定のバージョンは戻す（`installRetainedNative`）。利用者が主ボタンを押したときだけ行う                                                                                                                                                                   |
| AI の修正          | 壊れた JSON と、以前の版がない・変更が重なるファイルの当て直しだけ。1 ファイルずつ依頼し、送るのはそのファイル（当て直しでは新旧の公式ファイル）だけ。Guide の規則（JSON は読めること、キー・値・コメントを同じ順番で残し記号と空白だけを変えること。当て直しは両方にない行を書かないこと）を満たさない案は使わない                                     |
| 承認               | AI の修正が 1 件でもあれば、作業用コピーで全ツールを通した後に差分・AI の説明・Guide の確認結果を示して止まる。承認すると、AI に頼み直さずにその内容で同じ手順をやり直して反映する。頼んだ後に元のファイルが変わっていれば止まる                                                                                                                        |
| AI に聞く          | ファイルの中身を送らず、問題の種類・上流の説明・Guide の案内から、理由と選び方を説明させる。ファイルは変えない                                                                                                                                                                                                                                          |
| 更新が止まった後   | 更新処理の事前確認で止まった場合は、チェックをやり直して同じ区分で示す。Doctor の項目はツールごとに一覧にし、Guide が実行できる対処（`aidlc engine plugin sync`）だけにボタンを付ける                                                                                                                                                                   |

上流 2.11 の `mergeBlock` は区切りのない文章をチームのものとして残すため、2.11.1 への更新では `legacy root integration ambiguous` は出ない。区切りのない古い文章を AI で消す修正は作らず、出た場合は「手で直す」にする。

## Guide を更新する前の知らせ

新しい Guide が対応する aidlc のバージョンを上げる場合、拡張の更新確認ダイアログに「この更新後は、プロジェクトの aidlc を X から Y に更新するまで Guide を使えません。更新したファイルはリポジトリへのコミットが必要です」と表示する。都合が悪ければ「今はしない」を選べる。このため、リリースに対応する aidlc のバージョンを載せた添付ファイル（`aidlc-guide-release.json`）を加える。

## 手動で新しくした場合（2026-10-22）

利用者が公式の `aidlc update` / `aidlc use` / インストーラー、またはプレビューのチャネルで、Guide の対応版より新しいエンジンやプロジェクトにした場合の挙動。どこまで新しくしたかで分ける。

### 決定事項

| 状況                                                             | 判定            | 挙動                                                                                                              |
| ---------------------------------------------------------------- | --------------- | ----------------------------------------------------------------------------------------------------------------- |
| この PC の既定だけが新しい。プロジェクトは対応版に固定・登録済み | `ok`            | そのまま使える。上流のランチャーは固定版で動かし、`aidlc update` は登録済みの固定版を消さない                     |
| この PC の既定だけが新しい。プロジェクトは固定していない         | `engine-newer`  | ブロックする（AI ツールも新しいエンジンで動き、新しい形式の記録を書くおそれがある）。プロジェクトの固定を案内する |
| この PC の既定をプレビュー版にした。プロジェクトは固定・登録済み | `ok`            | プレビュー版の番号を版として読む。以前はエンジンなしと誤判定していた                                              |
| プロジェクトのファイル・固定版まで新しい（プレビュー版を含む）   | `project-newer` | ブロックを続け、Guide の更新と、対応版に戻す方法を示す                                                            |

- **Guide は利用者が選んだ既定バージョンを自動で戻さない。** 固定を主な操作にするのは、既定を保ったまま対応版で動かせるため。
- **戻す処理は案内にとどめ、Guide は実行しない。** 戻すと共有ファイルが変わり、チームで上げた更新を個人の判断で戻すことになりうる。「Guide はダウングレードしない」（2026-10-09）を維持する。
- **互換モードは設けない。** 新しい版の記録を推測で読むと、現在地を黙って誤表示する。「回避手段を設けない」（2026-10-09）を維持する。

### 戻し方の案内（`project-newer`）

判定結果の `rollback` に、対応版へ戻す方法を載せる。ダッシュボードの案内画面と更新画面に同じ文面（`versionGateRollbackGuide`）で表示し、更新画面ではコマンドをコピーできる。

| `rollback.kind` | 条件                                                                                           | 表示                                                                                                                                                                                                              |
| --------------- | ---------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `state-newer`   | いずれかの作業記録の State Version が Guide の `CURRENT_STATE_VERSION` より新しい              | 戻せない旨。上流の古いリリースは新しい形式の記録を開かないため、対応した Guide を待つ                                                                                                                             |
| `commands`      | native 導入、またはツール未設定で固定版だけが新しい                                            | `aidlc config --pin <対応版> --yes` と、設定済みのツールごとの `aidlc config --harness <ツール> --yes`。上流は複数ツールのプロジェクトで `--harness` のない `aidlc config` を拒否する（ツール未設定なら前者だけ） |
| `leftovers`     | ツール未設定で、導入が途中で止まったファイルに対応版以外の版（読めないものを含む）が残っている | そのファイルを Git で元に戻すか削除して、セットアップをやり直す。固定版を戻すだけではファイルが残るため、コマンドは示さない                                                                                       |
| `copy`          | copy 版                                                                                        | 公式手順の「更新の安全」でコピー用ランタイムから戻すか、Git で更新前のコミットに戻す                                                                                                                              |

コマンドは自分の未コミットの更新にも、コミット済みの更新にも同じものが使える。違うのはチームへの影響だけなので、未コミットかどうかは判定しない（判定は同期の fs 読み取りだけにする方針で、`git` を実行しない）。文面で「すでにコミットして共有していた場合は、戻す前にチームで相談し、戻した変更もコミットする」と案内する。State Version は各スペースの `intents/*/aidlc-state.md` の `State Version` 欄だけを読む（`readStateVersion`）。

### Guide の更新確認

最初のフォルダーが `project-newer` のとき、拡張の更新確認（`aidlc-guide.checkUpdate`）はプロジェクトの版を基準に案内する。

- 新しい Guide がない: 「最新版です」ではなく「最新の AIDLC Guide はまだ X に対応していません」と警告し、「更新の案内を開く」でダッシュボードの戻し方へ誘導する。プレビュー版なら、プレビュー版には対応しない旨を伝える。
- 新しい Guide を入れたらどうなるかは、その対応版を対象に同じ判定（`inspectVersionGate`）を実行して決める。判定の規則を拡張側でなぞらないので、版の混在、検出されないツールが残したファイル、読めないファイルも判定と同じに扱える。
  - `ok`・`engine-mismatch`・`engine-newer`・`not-installed`: 「この更新で、プロジェクトの aidlc-workflows X に対応します」と表示する。残りはこの PC かセットアップの操作で、新しい Guide が案内する。プロジェクトの更新とコミットを求める従来の警告は出さない。
  - `project-older`・`unknown`: 更新後もプロジェクトを整えるまで使えない旨を表示する。
  - `project-newer`: 更新後も使えない旨を表示する。
- 添付の対応版を読めない場合は、更新後の画面で確認できると伝える。

### 実装

## 既知の制約

- **Guide の更新は常に最新版を入れる。** チームが 2.11 のまま、Guide だけ 2.12 対応版が出た場合、Guide を更新した人は再びプロジェクトの更新を求められる。事前の知らせで判断してもらい、特定の古い Guide を選んで入れる機能は設けない。
- **信頼されていないワークスペース:** 更新できないので、ドキュメント閲覧以外は使えない。
- **フォルダーを開いていない:** 判定対象がないため、これまでどおりダッシュボードは開かない。
- **マルチルート:** これまでどおり最初のフォルダーを対象に判定する。

## 2.11 対応との関係

- reader は対応版の形式だけを読めばよくなる。2.11 で解釈が変わった規則（STAGE_JUMPED の範囲、記録 JSON がない場合の Verdict、memory の relaxed / off、run floor）は、バージョンを切り替えずに 2.11 の規則へ置き換える。
- バージョン確認と 2.11 対応を同じリリースで出す。バージョン確認を先に main へ入れる場合は `release:skip` を付け、対応版 2.10.0 のまま配布しない（2.11 に上げた利用者が拡張の更新待ちでブロックされるのを避ける）。

ブランチ `claude/laughing-archimedes-h6lo25` に実装した。対応版はまだ 2.10.0 のままで、2.11 対応と同じリリースで出す。

| 部分           | 実装                                                                                                                                                                                                                                                                                                                            |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 判定           | `packages/reader-core/src/version/gate.ts` の `inspectVersionGate`。ハーネス検出・バージョン読み取り・この PC のエンジン解決は拡張から reader-core へ移し、拡張の既存モジュールは再エクスポートする                                                                                                                             |
| API            | `packages/api-core/src/version-gate.ts`。`routeRead` / `routePost` / `handlePost` の入口で 409 `reason: "version-gate"` と判定結果を返す。判定は1秒だけキャッシュする。ブロック中はプッシュ通知も送らない。`createGuideService` は既定で判定を有効にし、無効化は `versionGate: null` の明示（素のフィクスチャを使うテスト）だけ |
| MCP            | `packages/mcp-server/src/version-gate.ts` の `gated` で全7ツールを包む。判定そのものが失敗した場合も閉じる側に倒す                                                                                                                                                                                                              |
| ダッシュボード | API の拒否を検知すると `VersionGateShell` に切り替える（拡張とブラウザ版で同じ仕組み）。再確認ボタンとウィンドウのフォーカスで再判定し、通れば新しい状態で開き直す。ドキュメント画面は質問欄の代わりに案内を出し、質問の API を呼ばない                                                                                         |
| 拡張           | 起動時の通知は「後で」を廃止し、状況に応じた操作を1つだけ示す。ステータスバーは「更新が必要」と表示する。簡易 Doctor のバージョン行も同じ判定を使う                                                                                                                                                                             |
| 更新パネル     | 冒頭に判定の案内、プロジェクト更新の前に変わる共有ファイル（ツールのディレクトリ・`.aidlc-version`・`.gitignore`）を表示する。更新が成功したら `git status` の前後比較で実際に変わったファイルとコミットメッセージを表示し、コピーできるようにする                                                                              |
| 事前の知らせ   | リリースに `aidlc-guide-release.json` を添付し（`scripts/release-metadata.ts`）、拡張の更新確認ダイアログで対応版の変更を先に表示する。添付のない過去のリリースは従来どおり。添付があるのに読めない場合（タイムアウト・HTTP エラー・不正な JSON・別の版の内容）は、対応版を確認できなかったことをダイアログで知らせる           |

設計からの差分:

- ブロック中にダッシュボードを開くと、ダッシュボード自体が更新の案内画面になる。そこからの操作で更新パネルを開く。
- 実行前に示す共有ファイルは、ツールのディレクトリ単位の一覧。`aidlc config --dry-run --json` によるファイル単位の計画表示は、複数ハーネスの更新フローを確認付きに組み替える必要があるため今回は行っていない。実行後の一覧は実際の差分である。
