# aidlc-workflows の版更新と Doctor 互換性の検証設計

状態: 検証スクリプト、版別レジストリ、3 OS の実採取 CI、docs / shell の統合同期を実装。main の required checks の有効化は、専用 Release App の設定待ち。

目的は、次の版へ更新するたびにテスト内の版番号を書き換えなくても、更新漏れと Doctor の互換性不足を検出すること。PR #114 のレビューにある agent-map の緩い版検証と、旧版の出力だけで Doctor の新版対応を宣言できる問題を対象にする。

## 現状と変更方針

現在の `check-workflows-drift.ts` は主に調査用で、不一致があっても検査を実行できれば終了コード 0 を返す。導入対象と Doctor 対応版のずれは advisory であり、通常の `bun run check` にはこの検査自体が含まれていない。agent-map のテストは版の書式だけを確認し、Doctor の対応版一覧と版別の実出力データも別管理になっている。

調査用レポートは残し、出荷の可否を決める検査を追加する。通常の検査はリポジトリ内のファイルだけで完結させ、公式配布物からの採取は更新作業と専用 CI に分ける。検査コマンドがファイルを自動修正することは避け、更新コマンドが作った候補を検査する。

## 1. 版の基準と整合性

更新対象の版と公式 SHA は、既存の `docs/official-docs.manifest.json` を基準にする。新しい版管理ファイルを重ねて作らない。同期前には公式タグがその SHA を指し、対象配布物の `AIDLC_VERSION` が manifest の版と一致することを確認する。作業用 upstream checkout の HEAD や main の版表記だけで正式版と判定しない。

新設する `scripts/check-workflows-compatibility.ts` は、次を完全一致で確認し、不一致・欠落・読取失敗で終了コード 1 を返す。

| 対象                        | 比較する値                                                                                 |
| --------------------------- | ------------------------------------------------------------------------------------------ |
| docs の manifest と検索索引 | sourceVersion と upstreamSha                                                               |
| bridge-map と agent-map     | `aidlc <manifest の版> (State Version <同梱エンジンの状態版>)`                             |
| artifact-map                | 既存の再生成チェックと sourceVersion                                                       |
| Claude / Cursor シェル      | 両方の AIDLC_VERSION・stamp・状態版。公式 SHA から生成した同期結果との対応も専用 CI で確認 |
| GUI の導入先                | WORKFLOWS_TARGET_VERSION が manifest の版と一致                                            |
| reader の状態版             | エンジンの現行状態版が CURRENT_STATE_VERSION と一致し、SUPPORTED_STATE_VERSIONS に含まれる |
| Doctor                      | 対象版と対象 SHA に対応する検証記録があり、必要な採取ケースがすべて存在する                |
| README / AGENTS             | 現行の対応版宣言が一致。過去版の説明は検査対象から区別する                                 |

data-lint は上の比較処理を利用する。期待値に `2.9.0` を直書きせず、agent-map 自身から期待値を作ることもしない。例えば docs の pin だけが次の版になれば、古い agent-map と GUI の導入先を検出する。すべてが旧版のままならローカルだけでは新リリースの存在を知れないため、その検出は公式リリースを調べる同期処理の役割とする。

版の一致は内容の互換性を保証しない。既存のステージ・エージェント・入出力・リンクの照合は残す。bridge-map の説明を確認せず、版の文字列だけ更新して対応完了としない。

更新・ロールバックのテストでは、比較上の「導入対象より新しい版」を固定文字列で表さない。対象版からテスト用の前後関係を生成し、過去の実リリースを確認するケースは明示的に分ける。これにより将来その固定文字列が導入対象と同じ版になって、テストの前提が崩れることも防ぐ。

## 2. Doctor の対応宣言と検証データを結び付ける

`packages/vscode-extension/data/doctor-compatibility.json` を新設し、確認済みの版ごとに次を記録する。これは更新対象を決めるファイルではなく、その版を検証した証拠を管理するファイルとする。

- 公式版、upstreamSha、解析形式の ID。
- 対応を確認した OS・配布形式・ハーネス・シナリオ。
- 採取した stdout / stderr、終了コード、期待する解析結果へのパスとハッシュ。
- 採取コマンド、実行したランタイムの版と SHA-256、生成スクリプトの版。
- 実プロセスからの採取か、単体テスト用に組み立てた例かの区別。

`doctor-output.ts` の独立した対応版リストはこのレジストリから導出する。CI は、対応版にデータがない、fixture の版・SHA が対象と違う、必要なケースが欠ける、ハッシュが合わない場合に失敗する。古い fixture のファイル名や版番号だけを変えて対応済みにはできないよう、専用 CI でも公式対象から再採取する。

既存 2.8.x の組み立てた fixture は回帰テストとして保持し、実採取だったとは記録しない。旧版の未採取部分は移行時に明示し、新しい導入対象に必要な実採取を旧データで代用する例外は設けない。

### 採取と解析の検証

新設する `scripts/capture-doctor-fixtures.ts --upstream <公式 checkout> --out <候補ディレクトリ>` が、使い捨てのプロジェクトと設定ディレクトリを作り、対象版の `doctor --verbose --no-color` を実行する。ネイティブ版は公式配布物、コピー版はその公式 SHA から生成した Bun 用配布物を使い、両者の証拠を混同しない。

基本ケースは正常・警告・異常。追加ケースとして、JSON 出力に載らない analysis の警告、未知の診断、コピー版の Bun 案内、Kiro の provider 不要、空白・日本語を含むパスを扱う。Windows・macOS・Linux で収集し、必要な OS・配布形式の組み合わせを検証ポリシーで固定する。実行できなかった組み合わせを成功扱いにしない。

環境の違いによる揺れを抑えるため、HOME・設定先・PATH とツールの有無を採取ケース側で制御する。利用中の設定やインストール先は変更しない。タイムスタンプ・一時ディレクトリ・ユーザー名だけを明示的な規則で正規化し、診断文・ステータス・件数・対処コマンドを消して差分を隠さない。

各ケースで次を検証する。

1. 全診断行と対処行を解析でき、未解析行がない。
2. 合格・警告・異常の件数、セクション、終了コードとの関係が期待値に一致する。
3. 既知の診断と対処が日本語になり、パス・コマンド・数値が保持される。
4. 未知の診断を含むケースでは、原文と未対応の表示が残り、黙って行が消えない。

期待値を Andon の `parseDoctorOutput` の実行結果から自動生成してはいけない。初回の期待値は上流の診断データと実出力を照合して確定し、変更のないケースでは前版の契約を使う。解析した結果をそのまま期待値に書く方式では、誤解析まで正解になる。

### 出力に現れない変更も検出する

実行ケースはすべての環境分岐を通らないため、ソースの変更検出を補助として使う。対象は `aidlc-doctor.ts` だけでなく、診断を生成する utility・config diagnostics・doctor bundle・モデル設定・ソース境界診断なども含める。対象一覧は明示して管理し、専用 CI の全 upstream 差分から Doctor に関係する新しい依存ファイルが増えていないかも確認する。

実装では `core/tools` 以下の全 TypeScript / JSON をハッシュで比較する。版定数の値だけは版の検査で別途確認する。これにより既知の診断ファイル以外への変更や新しい依存の追加も要確認になる。動的な文言を静的抽出で網羅できるとは扱わない。関連ソースが変わった場合は診断コードと表示の変更を人が確認する。ハッシュが一致していても、実採取と parser・日本語訳の照合を省略しない。

## 3. 自動更新できる範囲

| 検出した差分                                     | 処理                                                            |
| ------------------------------------------------ | --------------------------------------------------------------- |
| 版・SHA・索引などの機械的な値                    | 内容の照合後、同期コマンドで更新候補を生成                      |
| 実採取結果が既存の解析・翻訳契約を満たす         | 新しい版の fixture と検証記録を候補へ追加                       |
| 新しい診断文、セクション、対処方法、件数の不一致 | CI を失敗させ、原文・未解析行・不足訳・関連ソース差分をレポート |
| 修正が必要な parser・日本語訳                    | 人または AI が修正案を作り、同じ検査を再実行して PR で確認      |
| State Version やステージ構成の変更               | 実装・説明の互換性確認を要求し、版番号だけ自動修正しない        |

AI が修正する場合も、検査の無効化、期待値の丸ごと置換、未知行の無視で通過させない。変更後の成果物・出力を確認したうえでレビューする。自動修正候補の作成と、自動マージ・公開は別の操作とする。

## 4. ローカル検査・同期・CI への組み込み

- 通常の `bun run check` に `check:workflows-compatibility` を加える。コミット済みの版・検証記録・fixture を使うため、upstream checkout やネットワークがなくても更新漏れを検出できる。欠落時の skip は認めない。
- 公式更新の検出 → 固定 SHA の取得 → 配布物生成／取得 → docs と shell の同期候補 → Doctor 採取 → 解析・訳の検査 → 索引再生成 → 全体 check、の順で実行する。
- 現在の docs 同期と shell 同期は別ワークフローなので、片方だけを更新して版が混ざらないよう、共通の候補準備処理にまとめるか、同じ候補ブランチへ統合する。検査を追加するだけでは既存の自動同期が毎回止まるため、この変更を同時に行う。
- 未対応差分があれば採取物とレポートを残す。調査用の Draft PR を作る場合も、出荷検査は失敗のままとし、`release:skip` だけで互換性未確認の main への混入を許可しない。
- `check:workflows-compatibility` と専用 Doctor 契約検証を、リポジトリの required status check に設定する。ワークフローを置くだけではマージ防止にならないため、GitHub 側の ruleset 設定も実装の完了条件に含める。
- 自動同期が使うトークンによって後続 CI が起動しない構成では、同期の実行側で必須検証を完了するか、適切な GitHub App で通常の PR 検証を起動する。既存の「読み取り権限で上流コードを実行し、書き込み権限のジョブは公開処理だけを行う」分離は維持する。

## 5. JSON 化は上流の完全な出力契約ができてから

2.9.0 の `--json` は `data: report` を出力するが、humanReport は別途 `analysis.findings` を警告として追加し、フッターの警告数にも加算する。したがって、現時点で JSON だけに切り替えると画面から診断が欠ける。`--export` のデータも重複統合などの変換を受けるので、表示件数の無条件な正解データにはしない。

長期的には上流へ、安定した check ID、section、status、message ID、引数、fix、analysis findings、表示と一致する counts を持つ版付き JSON schema を提案する。実現後は schema の版ごとに解析し、未知の schema と ID を検出する。JSON 化後も診断内容の変更と日本語訳の対応確認は必要になる。

## 実装順と受け入れ条件

1. ローカルの版整合性チェックと data-lint の共通化を実装する。架空の次版で manifest だけ、map だけ、GUI 導入先だけを更新したテストがそれぞれ失敗することを確認する。
2. 2.9.0 の実出力を採取し、Doctor 検証レジストリを導入する。新版の fixture 欠落、古い SHA、手作り例による実採取の代用を拒否する。PR #114 の指摘 2 件をここで解消する。
3. 正常・警告・異常と特殊ケースの採取を CI 化する。未知セクション・未知診断・件数不一致を意図的に入れたケースが失敗し、出力の変更がレポートに残ることを確認する。
4. docs / shell 同期を統合し、採取・検証・更新候補作成を接続する。互換性のある次版は候補を自動生成でき、未対応の次版は出荷ゲートで止まることを検証する。
5. required status check の設定と失敗時の運用まで確認し、更新チェックリストへ正式なコマンドを反映する。

手順 1〜4 を PR #114 に実装した。v2.9.0 は Windows・macOS・Linux の各 9 ケースを公式配布物から採取し、上流データとの照合、全行の日本語対応、終了コードと件数を確認した。専用 CI では再採取した stdout・stderr・期待値・ランタイムのハッシュも登録済みの記録と比較する。同梱シェルは公式生成物と照合し、Cursor の既存パッチだけを確認済みのハッシュで許容する。

手順 5 の設定テンプレートには必須チェックを追加したが、GitHub 側の有効化は未完了。既存の自動リリースは main へ直接 push するため、[専用 Release App の設定](dependency-quality.md#main-の保護を有効にする)を先に行う。2026-09-16 の確認では App 用の Actions variable と secret は未登録、main の ruleset も未設定だった。App を設定し、実際のリリースが成功したあとでルールを適用する。上流への JSON 契約提案はこの実装の前提にしない。
