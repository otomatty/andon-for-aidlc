# aidlc-workflows 2.11.2

[更新履歴一覧](../changelog.md) · [改善点の日本語ガイド](../release-highlights.md)

## [2.11.2] - 2026-10-28

互換性: スクリプトに影響する変更があります

AI-DLC 2.11.2 は、2.11.1 以降にマージされた利用者に見える変更をまとめたリリースです。主な変更は次のとおりです。

- 本人の返答は、どの質問でも、どのチャットからでも本人の言葉のまま読み取り、記録には各決定のもとになった返答が残ります。
- 学びのステップは、本人がエージェントを正したときにだけ尋ねます。
- 先へ進む方法のない質問で終わるゲートが、Guard Policy strict でも大幅に減りました。
- 計画の切り替え、スキップ、取り消し、ジャンプ、単独のステージ実行は、今いる場所から続きます。
- 多数のリポジトリを持つワークスペースも Reverse Engineering のゲートまで届き、どのステージでも新しいリポジトリを加えられます。
- 並行ビルドは本人のブランチから始まり、そのブランチに取り込まれ、記録への編集を持ち帰ります。
- Code Generation は、本人が持ち込んだファイルのうち変更したものを、元に戻す方法とともに名指しします。
- `aidlc config --yes` は端末で何も尋ねません。
- Windows を含むすべてのハーネスで修正を行いました。

影響を受けるのは、次のスクリプトや CI ジョブだけです。詳しくは後述の「スクリプトの互換性」を参照してください。

- ネイティブの `aidlc` もあるマシンで、コピーしたプロジェクトを更新するもの。
- `AIDLC_UNATTENDED=1` を設定せずに AI-DLC を動かすもの。
- Claude Code の Amazon Bedrock の設定を、コミット済みのプロジェクトから取得するもの。

### 本人の言葉と回答

* ステージの承認の質問と AI-DLC 自身の質問（コード計画の質問、Unit とバッチのチェックポイント、検証コマンド、ガードの回復の質問）では、本人の返答をどんな言葉でも表示された選択肢と照らし合わせて読み取り、記録にはその選択を本人の言葉全体とともに残します。
  * "3. Approve, and add User Stories next" に対して `3` と入力すると、そのとおりに動作します。
  * "finished" や "ok I'm done" は完了として扱います。
  * "Nothing to add. Approve, and move on" は、その一つのメッセージで承認します。
  * ブロッキングのチェックで "fix them first" と答えると、Fix findings を選びます。
  * コード計画の質問で Request Changes の `2` を選ぶと、"2" から計画を修正するのではなく、何を変えるべきかを一度尋ねます。
  * ガイド付きの実行では、回答は最初の一回で記録され、読み返しはありません。
  * 番号付きまたは欄の中で示された質問に一文字だけ（"a"、"b"）答えると、本人の選択として扱わず、一度だけ確認します（`Did you mean Approve or Request Changes?`）。
* 本人の返答は、その作業のどのチャットからでも有効です。
  * 一つ目のチャットで尋ねた質問に、二つ目のチャットで `/aidlc postgres` と答えると、新しい作業を始めずに回答として記録します。
  * 再開後のガードの回復の質問での `/aidlc 2` や `/aidlc request changes: ...` は、そのとおりに実行されます。
  * AI-DLC の別の質問が画面に出ている間に入力した承認は、エージェントがそのメッセージを名指しすれば有効です。
  * "looks good, build it, and turn the specialist reviewers off for the rest of this work" は両方を行います。
  * "Continue automatically" の下では、回答として入力した `/aidlc Guide me` はその回答として扱います。"use bun test, and stop for today" は回答したうえで作業を保留します。"let's stop here for today" は、最初からフックがオフだった Claude Code や Codex のチャットでも作業を一時停止します。新しいチャットでは、開いている質問を一言一句そのまま再び示して待ちます。
* 進行中の作業がある状態での新しい言葉の扱いの変更は次のとおりです。
  * その言葉がどこに属するかを尋ねる質問で "yes" とだけ答えると、別の新しい作業を始めずに、三つのうちどれを意図したかを尋ねます。
  * "Separate new piece of work" は、それが始める計画の大きさ、または次に本人がその計画を選ぶことを示します。そこで "2" と答えると、エージェントが計画を選ぶのではなく、その計画の質問へ進みます（Kiro で、作業を選択していない clone の場合も、`Unknown scope` のエラーにはなりません）。"2, as express work" には、その計画を大きさとともに一度だけ確認します。
  * "Separate work, but use the classic plan" は classic で作業を始めます。そこで名指しした計画は、本人が依頼とともにスキップまたは追加したステージのうち、取り込めるものをそれぞれ取り込みます。その計画がすでに実行するステージや、作業がもともと含まないステージについては、拒否したり黙って落としたりせず、一度だけその旨を伝えます。
  * チームメイトの clone では、依頼に対する質問は二つではなく一つで、計画を名指しして、どの作業に属するかを尋ねます。
  * Other の回答には、本人の言葉に合わせた計画の組み替えを提案し、何かを動かす前に本人に諮ります。
  * 別の計画の名前だけを入力した場合（`/aidlc workshop`）も読み取ります。その計画での新しい作業を意図したのか、この作業をその計画へ移すことを意図したのかをエージェントが判断できない場合は、一つだけ質問します。
* 本人が操作している実行では、エージェントが本人を待つところでターンが終わり、"AI-DLC is carrying on with <stage>." の行は追加されません。エージェントが尋ねることもないままステージの途中で止まった場合は、"go on" と伝えてください。自律実行の Construction と無人の実行では、AI-DLC は引き続き自ら作業を続けます。
* "Use the recommended answer for every question and finish the stage now. Do not ask me anything." と伝えると、その作業について要約の確認と学びのステップをオフにし（本人が戻すよう求めるまで学びは残しません）、その旨を戻し方とともに一行で伝え、プロジェクト全体については何も尋ねず、ステージの承認ゲートで止まります。質問で本人が求めた変更は、チームが記録した実践と異なる場合でも行います（エージェントがその旨を一行で伝えることがあります）。チームがロックした strict の Guard Policy は引き続き有効で、その行はファイルを名指しします。
* 要約の確認は、本人に示した要約への本人の返答でだけ成立します。エージェントは要約を示してターンを終えるため、先に入力した "approve" や、同じターンで記録された "Looks correct" が、本人の名前で要約を確認することはなくなりました。本人の返答の後に質問ファイルが書かれた場合は、もう一度確認を求められることがありますが、ループすることはありません。
* 承認の前の学びのステップは、そのステージで本人がエージェントを正した場合（Request Changes、または本人の言葉で）にだけ、残す価値のある訂正ごとに一度尋ねます: `You asked me to <your change>. Keep that for next time?`（Yes, for this project、Yes, for the team、No）。
  * 何も訂正していなければ、要約からそのまま Approve か Request Changes に進みます。
  * "approve, and next time use the shared fixtures" は質問なしで残し、エージェントがどこに残したかを伝えます。
  * エージェント自身のメモが提示されることはありません。
  * 本人が残さなかったものがプロジェクトのメモリに書かれることはありません。設定の形で書かれた訂正を残す場合（`Methodology: tdd`）は、拒否せずにその設定として読み取ります。
* 質問はそれぞれのツールに合わせて尋ねます。
  * Claude Code では、ステージの質問ファイルが各質問の選択肢に A から D と X（Other）を振るため、質問欄に収まり、拒否されたり、選択肢が欠けたり、二つに分かれたりすることはありません。選択肢が一つの質問は、`Invalid tool parameters` と表示する欄ではなく、チャットで番号を付けて尋ねます。
  * Claude Code と Codex では、欄に入る数より選択肢の多い質問は、二つに分けずに番号付きの一覧として一度に尋ねます（`Reply with all numbers that apply (e.g. 1, 3).`）。
  * Codex では、答えないまま閉じた質問欄は、同じ質問として番号付きの文章で戻ります。
  * カンマを含む選択肢は、新しいチャットでも欠けることなく戻ります。
  * チャットで尋ねる質問は、誰が答えるかを示します（`Q1. [Product owner] ...`）。
* 記録には、本人が決めたことについて本人が言ったことが残ります。
  * 本人が始める作業は、エージェントが打ち直したり言い換えたりしても、本人の言葉と空白のまま記録されます。
  * 各回答、要約の確認、承認は、それに対して示された返答を保持します。再開後のコード計画の承認は、それが示されたメッセージを名指しします。
  * 複数の質問を含む質問欄は、すべての選択を保持します（Codex では一つが空欄の場合も）。空のまま送信した場合は言葉を記録しません。`$` を含む選択肢（"Show $0.00"）は書かれたとおりに記録されます（Claude Code では許可を求めません）。
  * コード計画の質問ファイルの `[Answer]:` の後の回答は、条件も含め、書かれたとおりに承認の記録に残ります。
  * エージェントが本人のメッセージから選んだ回答は、その旨を示します。本人の返答が別の質問に答えた後にエージェントが記録した質問は、その返答を持たなくなりました。AI-DLC 自身の回復でやり直した Unit は、本人の依頼ではなく、やり直しとして記録されます。
  * 本人のメッセージだけが本人のものとして扱われます。Claude Code のヘルパーの引き渡し、Copilot による AI-DLC の Stop の注記の反響、エディターで開いているファイルについての opencode の注記、失敗または停止した Kiro のワークフローは、本人の返答として扱われなくなりました。
  * AI-DLC の言葉を繰り返す本人のメッセージは、本人のものです。Kiro CLI では、エージェントの作業中に入力したメッセージ（"stop for today"）は本人のものなので、停止すると本人の言葉で作業が保留されます。Copilot CLI では、ヘルパーが始まった直後に送ったメッセージも本人のものとして扱われます。
* チャットで入力したキー、トークン、パスワードは、AI-DLC がコミットする作業の記録ではマスクされます（`password=[masked]`）。AI-DLC がそれを見つけると、チャットはそれを受け取っているため、本物であれば発行元で変更するよう一度だけ伝えます。照合は形だけで行い（平易な "my password is hunter2" は入力したとおりに残ります）、エージェントが本人のメッセージから書く文書はマスクされず、このリリースより前に書かれた記録は書き換えられません。
* エージェントは、AI-DLC 自身の管理情報（フィールドやステップの名前、最初の行の前の余計なラベル）を読み上げなくなりました。collaborators がオフの場合は、開発者が一人で作業することを伝えます。
  * 本人が聞く必要のある行（作業がどこから再開するかや、入力したキーを変更することなど）は、本人が返答する前のエージェントの最後のメッセージで伝えるため、`claude -p`、`copilot -p`、ヘッドレスの Kiro CLI でも本人に届きます。
  * 最初の要約は、作業が実際に実行する深さとテスト戦略を示します。
  * Kiro では、"4"（Other）とだけ答えた後、エージェントが代わりに何を望むかを尋ねます。
  * 変わっていないプロジェクトのルールを後日に再確認しても、そのルールは一つだけ残ります。

### ゲート、レビュー、計画の承認

* 先へ進む方法のない "<Stage> can't go ahead as things stand: which way would you like to go on?" の質問を大幅に減らしました。
  * 要約の確認がオンになったときに開いていたゲートでの Approve は通ります。
  * この作業がレビューなしで実行するステージでは、エージェントが自らゲートを開きます。
  * 再試行したレビューが再び完全なレビューを書かなかった場合は、未完了として記録し、作業は先へ進みます（Claude Code では、バックグラウンドで実行中のレビュアーがいなくなった時点で）。
  * Request Changes の後、完了したレビューは、レビュアーが書いたラウンド番号にかかわらず、最初の一回で記録されます。
  * エージェントがレビューの前に報告した改訂には、ステージをやり直す提案ではなくレビューが行われます。一方、レビュー以降に何も変えずに指摘を却下すると、二度目のレビューや "Start the stage over" ではなく、同じゲートがすぐに戻ります。
  * relaxed または off では、本人の変更の後にエージェントが自ら始めたレビューが、Unit は先へ進めないと言うことはなくなりました。
  * ビルダーが質問を飛ばした並行の Functional Design は、その質問を本人に尋ねます。
  * strict では、自身のフォルダー（プロジェクトのもの、または記録済みのチェックアウトのもの）の `.aidlc-source-paths.json` で除外したテストキャッシュが、Unit のない計画で承認を妨げることはなくなりました。拒否は、何が変わったかと、除外をどのファイルに書くかを示します。
* Guard Policy strict（enterprise の既定）での変更は次のとおりです。
  * チェックポイントで差し戻した Unit や、ビルド済みの Unit の Code Generation のやり直しでは、毎回拒否するのではなく、変更したコードをレビューして再び尋ねます。
  * 新しい clone や別のマシンで再開した作業は、承認済みの計画をすべて尋ね直すやり直しではなく、一行で Code Generation を完了します。
  * 計画の承認がオフの場合、並行のバッチを割り当ててからセットアップするまでの間にプロジェクトが変わっても、誰にも尋ねていない計画の承認をセットアップが求めることはなくなりました（ガイドにあるとおり、最初の Unit の取り込みでは引き続きそこで止まります）。
  * レビューが最終となった文書をエージェントが自ら編集しようとしても、その編集は行われません。エージェントは次のゲートで何を変えるつもりだったかを伝え、本人が判断します。
  * 質問をファイルで尋ねるステージでの本人の Approve は受け付けられます。
  * 回復のレビューが合格した後は、本人がすでに行った承認を記録し、再び求めません。
  * ステージを承認する返答の後、本人の次のメッセージまでの間にそのステージの文書が変わった場合は、その承認とともに受け付けます（そこでエージェントが求められずに行った編集は、別の行で伝えます）。
  * Reverse Engineering の開いているゲートは、チームの clone、プロジェクトフォルダーのコピー、ブランチの切り替えをまたいでも、全体の再スキャンにならず、本人が離れたところに留まります。
  * 最後のレビューの後にどの Unit も自分のものとしていない編集は最初に名指しされるため、その編集をした Unit がそれを一覧に載せ、承認が完了します。
  * 文書ができた後に本人が要約を再び確認すると、本人に再確認を求めるのではなく、エージェントが残りを自ら保存します。
  * Unit を一つずつビルドする場合、完了済みの Unit の設計についての Request Changes は、その Unit のステップだけを差し戻します。
* 承認の前のレビューの要約は、レビューで見つかったことを一度だけ伝えます。
  * 軽微な点だけの準備完了のレビューは、変更の提案を伴う準備完了として示します。
  * ステージのゲートは、Approve がどの未解決の指摘をリスクとして受け入れるかを示し、いずれかの修正を求めることも、理由を添えて却下することもできると伝えます。
  * 作業を変えて直した指摘は `Changed after review` と示します（Guard Policy が off または relaxed の場合。strict では変更したファイルを再びレビューします）。
  * レビュー後の変更は一度だけ伝えます。
  * 記録には誰が決めたかが残ります。それらの指摘は `Changed after review` として記録されます。本人に示されなかった指摘（"Continue automatically" の下で承認した Unit、または Unit の承認後に挙がった指摘）は、`Accepted risk` ではなく `Approved autonomously` として記録され、次のレビューのために未解決のまま残ります。
  * "approve, but make sure R-03 gets handled" は、ゲートでも Unit のチェックポイントでも `Fix requested` を記録するため、次のレビューで再び確認されます。チェックポイントで本人が却下した指摘は、再び現れることなく本人の理由を保持します。
  * 誤ったレビュアーが署名したレビューは、本人に伝えられたレビュアーのものを求めてエージェントを差し戻します。別のヘルパーがレビュアーの代わりに書いたレビューは、レビュアーの名前で署名されていても、Cursor CLI を除くすべてのツールで本人に伝えます。
  * 本人に一度も示されていないゲートについて報告された承認は、そのチャットに本人の返答がなければ記録されず、質問が本人に届きます。
  * コード計画の質問が待っている間、計画の承認がオフになるのは、計画が示された後に送られたメッセージによる場合だけです（それより前に "approve, and turn plan approval off" と伝えた場合は、その計画を一度だけ、理由を示す一行とともに尋ねます）。
  * 設定が変わるのは、それを求めたメッセージによる場合だけです。そのため、別のことに対する以前の "Approve" や "that's right" が、本人の名前で学びや要約の確認をオフにすることはなくなりました。"approve, and turn plan approval off" は一つの返答で両方を行います。
  * ステージの文書が書かれる前に本人が答えた回答で、そのゲートが承認されることはなくなり、代わりにゲートが本人に示されます。
  * 前のフェーズへ戻っても、離れたフェーズが完了として記録されることはなくなりました。一方、フェーズ全体を飛び越えるジャンプは、そのフェーズをスキップとして記録します。
* Code Generation のゲートとコード計画の変更は次のとおりです。
  * Code Generation のゲートで、本人が答える前にレビュー済みのファイルが変わった場合（エージェントが示したばかりの指摘を直した場合）は、修正を取り消してしまう無言のループではなく、変更を伝えたうえでゲートを一度だけ再び示します。
  * Claude Code で計画の承認後に圧縮が起きても、最初の報告でゲートが開きます。
  * コード計画が待っている間も、プロジェクトフォルダーへの移動から始まるコマンドライン（`cd <project> && aidlc doctor`）で doctor、status、next を実行できます（PowerShell では、パスを引用符で囲むか `;` でつなぎます）。
  * `/aidlc --status` は、そのままでも `--intent` や `--space` を付けても、`Running` ではなく、作業が本人のコード計画の承認（または本人の編集の完了）を待っていることを示します。
  * コード計画の質問で今日は終わりにしても、直前に求めた変更が記録から失われることはなくなりました（新しいチャットで単に再開すると、引き続き計画を示さずに計画の質問を尋ねます）。
  * 同じ返答で変更を添えてコード計画を承認すると（"A, approved. one condition: ..."）、先にその変更を計画に入れるため、二度目の質問なしで承認がその変更を含みます。
  * 計画が待っている間も、シェル変数を通じて作業自身のファイルを読む操作は実行されます。
  * 計画の承認がオフの場合、計画の行は、ビルドがすでに進んでいる間に尋ねるのではなく、計画に目を通すよう頼めることを伝えます。
  * relaxed では、承認済みのコード計画が変わると、各ビルドステップの横の行は、計画の承認がオフだとは言わず、relaxed が緩めるチェックである計画の再承認を名指しします。
* 同じステージで三回変更を求めると、保留や新しいチャットをまたいで数えて、Accept as-is が選択肢に加わります。`/aidlc --status` はそのステージ自身の改訂回数を示します。Requirements Analysis と Domain Design では、スキップしたステージが合う場合にゲートが "Approve, and add <Stage> next" を提示できます。bugfix、express、poc、infra、refactor、security-patch の実行での "Approve, and add User Stories next" は、User Stories を加えて同じターンで始めます。
* ゲートでのチェックの変更は次のとおりです。
  * advisory のチェックは、レビューの前に完成した文書に対して実行されます（並行でビルドした Unit はまだ対象外です）。そのため、エージェントはソースタグの欠落などの自分のミスを直し、ゲートは残ったものだけを名指しします。
  * トレーサビリティのチェックは、Requirements Analysis が書いたとおりに要件 ID を読むため、実際の抜けがないのにトレーサビリティの指摘を報告するゲートが大幅に減りました。
  * ステージの指示どおりに書いたファイルは、見出しの指摘を報告しません。チームのテンプレートの見出しは、先頭の絵文字の有無にかかわらず一致します。チームの `test-results.md` のテンプレートは、Build and Test と Performance Validation でチェックされます。
  * エージェントは、自分のタグを直すと提案するのではなく、Intent Capture の `[scope]` タグを Initial Scope Signal の行にだけ書きます。
  * ブロッキングのチェックで Fix findings を選ぶと、エージェントが文書を直して再びレビューを受けます。Override は、エージェントをステージに戻すのではなく、本人のゲートを開きます。
  * 開いているゲートで直した文書は、同じターンでその質問を再び示します。
  * Unit ごとにビルドする作業では、Fix findings はチェックが名指しした Unit だけを再びレビューします。別の質問の後に示した選択も有効です。
  * 実行できなかったチェック（クラッシュしたスクリプトや、`tsconfig.json` のない型チェック）は、ゲートで一度だけ伝え、合格ではなく実行できなかったものとして記録します。

### 計画、ジャンプ、スキップ

* 計画を切り替えても作業は続きます。
  * ステージの実行中にスコープを切り替えると、同じターンで作業が続きます。"switch this to the express plan" は、計画のコンポーザーへ進むのではなく、`--scope` と同じようにその場で切り替えます。
  * 承認と切り替えを一緒に行う返答は、同じターンで承認を記録します（新しい計画でもそのステージを実行する場合）。要約を確認して、そのステージのない計画へ切り替える返答は、先に確認済みの文書を書き出します。
  * 一度も実行していない Units Generation を越えて、より大きなスコープへ切り替えても、開いているゲートとその Approve は保持されます。
  * より小さなスコープへ切り替えた後に戻ると、切り替えで外れたステージは未開始のまま残るため、そのステージを加え直すか切り替え直すと実行されます。
  * 加えたばかり、またはスキップしたばかりのステージを取り消すと、計画は元に戻ります。
  * スキップしたステージを後から本人の言葉やジャンプで戻すよう求めると、計画に戻ります。その場でスキップしたステージを、作業が先へ進んだ直後に戻すよう求めると、次に実行されます。
  * スキップは、その取り消しがいつまで有効かを示します（"until the work moves past it"）。
  * 今のステージのスキップを伴うスコープの切り替えは、切り替えたうえでそのステージをその場でスキップし、作業を続けます。
  * Practices Discovery のゲートでの "approve, and skip user stories" は、エンジンの言葉で拒否せず、ステージをスキップして Practices Discovery の質問を再び尋ねます。
  * "Continue automatically" の下でも、本人の `/aidlc --skip` や `--add` はすぐに反映されます。
  * 作業の途中で絞り込んだ計画を承認すると、次のステップへ進みます。
  * 質問を書いている間に入力した設定は、その質問に反映されます。
* ジャンプの変更は次のとおりです。
  * Code Generation 以外の実行中の作業での `/aidlc --stage <stage>` や `--phase <phase>` は、一つのステップでジャンプしてステージを始めます。
  * `/aidlc --scope enterprise --stage code-generation` は、先に切り替えてからジャンプします。ジャンプと一緒に入力した設定は保持されます。
  * Code Generation の回復の質問で求めたジャンプは、最初の依頼で通ります。
  * 要約を確認済みのステージへ戻ると、その要約を一度だけ尋ね、その文書について Keep を選ぶとレビューへ進みます。ステージは先へ進めないと言うことはありません（Kiro IDE の strict では、何度もそう言っていました）。
  * 初期化のステージや、計画に含まれないステージへ戻るジャンプには、先に "Jump accepted." を示すのではなく、すぐに拒否または質問（コードを再びスキャンする提案、またはそのステージを単独で実行する提案）を示します。
* "It's existing code, but skip the reverse engineering" は、Reverse Engineering をスキップし、コードを文書化すると約束することなく、本人がいたところから作業を続けます。Requirements Analysis を承認する返答で Reverse Engineering を戻すよう求めると、その承認の直後、Code Generation の前に実行します。
* 作業に合わせた計画の変更は次のとおりです。
  * 既存のコードでは、`/aidlc compose` による計画は、フォルダーにまだコードがない場合も含め、すべての実行で Reverse Engineering を残します（ステージは、まだ最新のコードマップを再利用するかを尋ねます）。それを外すことを提案するのは、準備済みのコードマップがそれを許す場合だけで、ゲートでその旨を伝えて本人が判断します。
  * 承認した計画は、示したすべてのステージ、深さ、設定、Guard Policy で作成されます。そのゲートで本人が求めたステージの変更はコンポーザーへ戻され、本人が承認する計画に反映されます。エージェントが行ったと言いながら落とされることはありません。
  * 残したステージが使うステージを計画がスキップする場合、提案はその旨を一度だけ伝えます。
  * "Approve and save as scope" は、作業の作成とともに必ず計画を保存します。
  * 計画の提案、作成時の行、`/aidlc --help`、保存したスコープは、同じステージ数を示します。計画を切り替えた後の各ステージの開始、進捗の行、status も同じです。
* `--single` で一つのステージを単独で実行する場合の変更は次のとおりです。
  * 本人の作業はそのままの場所に残ります。上書きする作業の文書はコピーを保管してその場所を伝えます。入力した `--depth` や `--test-strategy` はその実行にだけ適用します。`--guard-policy` や `--guard.<fence>` は、それらなしで実行する手順を添えて拒否します。
  * strict では、そこで Unit の文書について Keep を選ぶと、再び保存を求めるループではなくレビューへ進みます。
  * 作業の完了後に単独で実行したステージは、本人の回答、要約、そのレビューを記録します。まだ作業がない場合は、一緒に入力した内容を依頼として受け取り、それらと本人のコード計画の承認を記録して完了します。
  * 分離した Code Generation の実行の各ステップは自身の次のステップを示すため、本人の計画の質問が戻り、ワークフローには手が加わりません。
* 作業の開始と再開の変更は次のとおりです。
  * 依頼とともにスキップまたは追加したステージ（`/aidlc --skip requirements-analysis <request>`）は、そのまま進めても計画を作業に合わせても計画に残り、計画の質問はそれを数に入れます。
  * 作業のないプロジェクトで `/aidlc` だけを入力すると、エラーではなく "Tell me what to build and I'll start it." と伝えます。新しいチャットでは、開いたままにした検証コマンドや要約の質問を最初に戻します。
  * `/aidlc --resume` は、clone で唯一の進行中の作業を、続けるかどうかを尋ねずに再開します。一緒に入力した言葉は、作業を選択していない clone の場合も、開いているステージがそれなしで進むのではなく作業に届きます。一緒に入力した設定は、本人が選ぶ作業のために保持されます。
  * ゲートに戻ったときにやり直しを求めると、ステージをやり直します。ステージのレビュー完了から承認までの間に戻ると、ステージを再び実行するのではなく承認を示します。新しいチャットで再開した Code Generation の改訂は、本人が変えるべきだと伝えた内容を保持します。
  * pull によって AI-DLC の作業記録に git の競合が残った場合は、本人の側から作業を続け、相手側の状態を一度だけ伝え、代わりに相手側を採用する git コマンドを示します。
  * 値を取らないスイッチの後に続くもの（`/aidlc --new-intent fix --project-dir handling`）はすべて本人の依頼として扱うため、求めていないフォルダーや status が書かれたり表示されたりすることはありません。

### Construction

* ハーネスのフォルダー内（`.claude/worktrees/<name>` など）やプロジェクトの外の worktree に置いたコードも、Code Generation のレビューの対象になります。エージェントがチェックアウトを記録し（`/aidlc intent add-checkout <path>`。取り消しは `/aidlc intent remove-checkout <path>`）、承認はコードが見つかった場所を示し、レビュー後のそこでの編集も検出されます。
* Unit の変更は次のとおりです。
  * Unit のステップ（進行中の Unit、またはビルド済みの Unit の Code Generation）の Redo は、他の Unit の完了済みの作業を残したままそのステップをやり直し、改訂のループではなく、その計画を一度だけ本人に戻します（計画の承認がオフの場合はすぐにビルドします）。Redo と一緒に求めた変更は、その計画の質問への回答になります。
  * Unit のチェックポイントでの本人の Request Changes は、エージェント自身の質問を経ても有効なままです。
  * 作業にない Unit を名指ししたジャンプややり直しは、どの Unit を意図したかを尋ねます。
  * Unit を一つずつビルドしている間の `/aidlc --skip functional-design` は、拒否せず、ここから先のすべての Unit でそのステージをスキップします（"for this unit" を付けると、そのステージに取り組んでいる Unit だけ）。
  * 完了の記録だけが残っていた Unit がループすることはなくなりました。
  * チーム所有の Unit では、Unit のレビューから完了までの間に再開したり二つ目のチャットを使ったりしても、Unit のゲートへ進みます。
* 並行ビルドの変更は次のとおりです。
  * Unit を並行でビルドすることに yes と答えると、一つの変更として伝えたうえで適用します。GitHub Copilot では、各ターンがサイズのエラーで終わるのではなく、ウェーブが割り当てられます。
  * チームの clone のように本人のブランチからビルドすると、すべての Unit が始まり、それぞれがそのブランチに取り込まれます。
  * プロジェクトの外のファイルへのコミット済みのリンクや、Git が無視する `.env` やログのファイルによって、ビルドが始まらないことはなくなりました。
  * Unit を並行で設計する場合は、先に本人のチャットで各 Unit の質問を尋ねるため、設計は本人の回答に従います。
  * 各ワーカーは、AI-DLC が読む場所に自分の Unit の記録を書き、余計な `construction/` フォルダーは作りません。
  * Claude Code では、Unit のレビュアーが完了しているのに、どのレビュアーも完了していないと Unit のレビューが言うことはなくなりました。
  * 各 Unit は、コミット済みかどうかにかかわらず、プロジェクトにあるとおりの設計の記録から始まります。Unit がそれらに加えた編集は、取り込み時に行単位でマージされて持ち帰られます。同じ行での衝突は、その Unit の Code Generation のフォルダーに保存され、一行で名指しされます。
  * Unit のフォルダーに取り残されたエージェントは、フックがオフだと言うのではなく、プロジェクトのフォルダーへ戻ります。
  * strict では、ビルド中に保留された本人のメインのチェックアウトへの書き込みについて、その理由と、Code Generation が終われば書き込めることを伝えます。取り込み時に本人の git フックが拒否したファイルは、直して取り込めます。
  * ビルド中に変更されて再び承認された Unit の計画は引き継がれ、ビルドは続きます（差し戻したバッチを再ビルドしている間も同様です）。一方、ワーカーがすでにコードを書いた Unit には、ループしていた提案ではなく、その作業を脇に置いてビルドし直す選択肢だけを提示します。
* 本人のファイルは本人のものとして扱われます。
  * 本人の README、LICENSE、ドキュメント、設定がすでにある新しいプロジェクトフォルダーでは、本人が求めるかビルドに必要な場合を除き、それらをそのままにするよう Code Generation に指示し、計画にもそれらを示します。ビルドの承認の質問（または各 Unit のチェックポイント）は、作業の前から本人が持っていたファイルのうち、ビルドが変更または削除したものを名指しし（既存のコードでは、コードではないファイルだけ）、git がコピーを持っていれば元に戻す git コマンドを添えます。
  * 委任したエージェントへのブリーフは、本人の作業ツリーの stash、reset、上書きのチェックアウト、clean、および計画が名指ししていないもののインストールを禁じます。
  * タイムアウトしたり中断されたりしたチェックポイントのチェックは、自分が起動したプロセスを止めます（`--timeout-ms` で既定の 30 分を延ばせます）。
  * `src/app/items/[itemId]/` のようなルートフォルダーに対する Unit の主張が、その横にある無視されたファイルのために拒否されることはなくなりました。
  * 一つのチェックアウトで二つの作業が開いている場合、各ビルドは、もう一方の作業の Unit のファイルを削除したり指摘したりせず、そのままにします。
  * パスに `audit` を含むプロジェクトでのコマンド（または日付付きのレポートへの `npm audit`）は、AI-DLC の監査証跡への書き込みとして拒否されずに実行されます。
* Code Generation の前に（計画の質問が開いている間や、AI-DLC の記録だけを書くステージで）エージェントが本人のファイルを編集した場合は、本人の選択の後の最初のステップ、または次の承認で、それらを戻し方とともに一度だけ名指しします（`Before this work started, src/app.js was changed; git checkout HEAD -- src/app.js puts it back as last committed.`、または `During Requirements Analysis, ...`）。あるいは、ファイルが新しいことや、その変更を元に戻せないこと（本人のコミットしていない変更を含んでいた、または git にない）を伝えます。何も止められることはなく、その方法で元に戻したファイルは、ビルドのレビューで誰の変更でもないものとして扱われます。
* Build and Test は、プロジェクト全体のカバレッジの下限を、一つの Unit のテスト（すべてのテストが合格しても失敗していました）ではなく、テストの全体の実行で判定します。ブラウザーのチェックは実際のブラウザーで実行するまで `Unverified` のままにし、その抜けをゲートで一度だけ伝えます。毎回の実行で必要なファイルは四つで、結合、性能、セキュリティのテスト手順は、それを求めるテスト戦略の場合だけです。Code Generation は、必要のない要約の確認を求めなくなりました。

### Reverse Engineering と多数のリポジトリ

* 多数のリポジトリを持つワークスペースでも、Reverse Engineering はステップのサイズのエラーで止まらずに始まり、ゲートまで届きます。
  * AI-DLC がディスク上で見つけ、本人が一度も名指ししていないリポジトリが十以上作業の対象になる場合は、本人の依頼ですでにどれかを示していない限り、どれかを読む前に一度だけ尋ねます（`Read all 190, or only the ones this work needs?`。git の行数を添えます）。
  * ゲートはすべてのリポジトリのファイルを、進捗を示しながら一度にチェックし、欠けているファイルをそのリポジトリ付きで名指しします。
  * 190 のリポジトリでは、Linux での各ステップとゲート前の待ち時間が、数秒から約一秒に短くなります。
  * スペース、アクセント記号、アポストロフィを含む名前のリポジトリフォルダーも、作業が始まる前に止まることなく、本人が名指ししたとおりに作業に含まれます。
* `/aidlc intent add-repo <name> [--url <address>]` は、どのステージでも作業にリポジトリを追加します。まだ手元にない場合は本人の git と認証情報で clone し、一行と戻し方を示します。strict で Units Generation がすでに承認済みの場合は、その Unit がまだ有効かを一度だけ尋ねます。`/aidlc intent set-repos <name,...>` は一つのコマンドで対象を絞り込みます。`aidlc system workspace-sync` は、clone のアドレスに含まれる認証情報を `***` と表示します。
* Reverse Engineering の変更は次のとおりです。
  * Guard Policy が relaxed または off の場合、Request Changes はスキャン全体ではなく、本人が求めた部分だけを再実行します。
  * コードナレッジベースの再利用は、本人がその質問に答えて初めて本人の選択として記録されます。
  * 最後の質問に新しいチャットで答えた回答は記録され、その承認へ進みます。
  * 名前にスペース、アクセント記号、`&` を含むプロジェクトフォルダーでもスキャンが実行され、フォルダーの名前はそのまま保たれます。

### セットアップ、設定、ライフサイクル

* 七つのハーネスすべてで `aidlc version` が `2.11.2` を表示します。
* 端末での `aidlc config --yes` は何も尋ねません。プロジェクトをセットアップまたは更新した後、セットアップのチェックと、まだ本人の対応が必要なものを、それぞれのコマンドとともに示します（`aidlc config` だけを実行すると、引き続き手順を案内します）。
  * Windows の改行コードのチームメイトの clone も、七つのハーネスすべてで git がクリーンな状態のまま更新されます。
  * git リポジトリではないプロジェクトフォルダーは、そこで AI-DLC をセットアップするかを尋ねずに更新されます。
  * ネイティブの `aidlc` もあるマシンでのコピーしたプロジェクト自身の config は、ネイティブ導入のものを黙って使うのではなく、自身のリリースとフックを保持し、そのリリースのダウンロードを提案します。
* チャットからチェックをオフにしたりオンに戻したりする場合の変更は次のとおりです。
  * 本人の設定ファイルでの切り替えは、スイッチ名、ファイル、コマンド、ワークフロー ID を含まず、本人の言葉で平易な一行を伝えます。
  * 新しいチャットでの "turn the review freeze check back on for this project" は、一つのステップで実行されます。
  * 別の設定ファイルがまだチェックをオフにしている場合は、オンに戻すどの方法でもその旨を伝え、そのファイルと、そこで解除するコマンドを名指しします。ファイルを名指しせずにチャットから戻した場合は、本人自身の項目だけを解除します。
  * どのツールでも、本人の名前でチャットからオフにしたチェックは、それだけの行で一度だけ本人に伝えます。Codex と opencode のツールパネルにはほかに何も表示しません。
* Claude Code では、`aidlc config` での Amazon Bedrock の回答は、git で無視される本人自身の `.claude/settings.local.json` に書かれるため、チームメイトが本人の AWS プロファイルを引き継ぐことはありません。チームメイトの clone には、`aidlc config providers` を名指しする警告が一度だけ表示されます（2.11.1 でセットアップしたプロジェクトについては「スクリプトの互換性」を参照してください）。
* `aidlc doctor` の変更は次のとおりです。
  * クリーンなプロジェクトに、doctor 自身の監査エントリをコミットするよう伝えることはなくなりました。
  * 別の clone から pull した作業は、フックのエラーではなく、そのマシンを名指しする警告になります。
  * 待機中の作業のフックが、凍結しているように読み取られることはなくなりました。
  * 古い更新チェックは、いつチェックしたかを示します。
  * エクスポートは、スキップしたステージをスキップとして示します。
  * Claude Code のネイティブ導入で、`aidlc engine hook <name>` として配線され、ファイルがプロジェクトにしかないチームのフックは、そのコマンドが一度もそれを実行していなかったため、その行が失敗になりました。自身のファイルを実行するコマンドで登録する修正の行を示します。
* ロックを取っている間に強制終了されたフックが、後の書き込みと doctor を 5 分間止めることはなくなりました。ハードリンクのないドライブで、ロックを取っている間に（Ctrl-C で）止めた config、update、plugin のコマンドが、後のすべてのコマンドを妨げることはなくなり、次のコマンドが一行でそれを解除します。保護された AI-DLC のファイルへの書き込みの拒否は、一致したパスを名指しします。本人が手で編集した作業の一覧（末尾のカンマ、コメント）は読み取られます。何も読み取れない一覧は、上書きせずに新しい一覧の横に保管し、一行で伝えます。
* ガイドの変更は次のとおりです。
  * インストールガイドは、チーム自身のハーネスの設定を残したまま、プロジェクトから AI-DLC を削除する方法を説明します。
  * classic スコープは、Construction での承認が Unit ごとにどこにあるかを示します。

### プラグイン

* Kiro IDE と Kiro CLI v3 では、プラグインが追加するエージェントが AI-DLC 自身のエージェントと同じツール、MCP サーバー、ルールを得て、自身のエージェントに作業を渡すプラグインのステージが実行されます。プラグインのエージェントに初めて作業を渡す前に、Kiro は確認します。この修正は、作者がこのリリースでプラグインを再ビルドし、それを再び配置した時点で反映されます。Kiro CLI V2 では引き続き手書きのエージェントファイルと信頼の項目が必要で、その方法を文書化しました。
* プラグインの Markdown で `{{INVOKE}}` と `{{TOOL_PREFIX}}` を使えるようになりました。これらは構成時と plugin sync 時にインストールの経路に合わせて埋められるため、これらを使って書いたプラグインのステージは、Bun のないネイティブ導入でも実行されます。リファレンスのプラグインの二つのステージは、`bun: command not found` で失敗せずに `aidlc engine ...` を実行するようになりました。`bun ...` を自分で書くプラグインには、引き続き Bun が必要です。
* コアのステージを自身のスコープに加えたプラグインを削除すると、同梱のステージが元に戻るため、次の `aidlc config` が通ります。プラグインの削除や更新、またはプロジェクトの更新でも、プラグイン自身の行の横に本人が書いたステージの行は保持されます（その場合、プロジェクトの更新はそのステージを本人が変更したものとして扱い、通常の競合の行とその直し方を示します）。`plugin select --harness-dir <dir>` は、名指ししたインストールを変更します。

### スクリプトの互換性

* スクリプトに影響する変更: `.aidlc-version` による固定のないプロジェクトで、ネイティブの `aidlc` もあり `AIDLC_RUNTIME_ROOT` が設定されていないマシン上で、`--from` なしで実行するコピーしたプロジェクト自身の `config`（たとえば `bun .claude/tools/aidlc.ts config --force` や `--yes`）は、ネイティブ導入のリリースから更新しなくなりました。端末なしで実行すると、2.11.1 では終了コード 0 で終わっていたところ、`refreshing .claude needs the <version> release files` とともに終了コード 4 で終わるようになりました。プロジェクト自身のリリースを取得するには `--download` を、引き続きネイティブ導入のファイルを使うには `--from <install root>/versions/<version>/runtime` を追加します。
* スクリプトに影響する変更: `AIDLC_UNATTENDED=1` を設定せず、自律実行の Construction でもない実行は、人が操作しているものとして扱われます。エージェントが止まると、AI-DLC の Stop フックが作業を続けるのではなく、ターンが終わります。AI-DLC を動かすスクリプトや CI ジョブは、対話モードのガイドがすでに自動化に求めているとおり、`AIDLC_UNATTENDED=1` を設定します。
* スクリプトに影響する変更: Claude Code では、Amazon Bedrock の回答は git で無視される `.claude/settings.local.json` に書かれ、`.claude/tools/data/harness.json` は AWS プロファイルを保持しなくなりました。2.11.1 でセットアップしたプロジェクトは、`aidlc update` と更新を経ても共有の `.claude/settings.json` に値を保持し、その値を設定した人が `aidlc config providers` に再び答えると、値はそこから取り除かれます。コミット済みの設定から Bedrock を取得していた CI ジョブは、その環境を共有の `settings.json` に自ら設定し、keep current と答えます。`harness.json` からプロファイルを読んでいたスクリプトは、`aidlc config providers --show --json` を読みます。
