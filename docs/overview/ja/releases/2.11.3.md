# aidlc-workflows 2.11.3

[更新履歴一覧](../changelog.md) · [改善点の日本語ガイド](../release-highlights.md)

## [2.11.3] - 2026-11-04

互換性: スクリプトに影響する変更があります

AI-DLC 2.11.3 は、Bun 1.4.4 でビルドしたネイティブの `aidlc` を含むリリースです。これは、Bun が同梱する Brotli デコーダーの CVE-2026-111497 を修正します。あわせて、2.11.2 以降にマージされた、利用者に見える変更をまとめています。主な変更は次のとおりです。

- チームの Unit は、エージェントとともに最後まで動作します。チームメイトの clone からでも、リード自身のチェックアウトからでも、publish、pin、一つのマージの質問と取り込みを経て、通常の pull まで届きます。
- 依頼は、引用符、`$`、バッククォートを記録に残します。
- Request Changes の後の再レビューと二回目のラウンドは、最初の一回で通ります。計画にチェックを入れることや、テストの実践を残すことは、計画の再承認を求めなくなりました。
- Code Generation で保留した作業が、そのプロジェクトでのほかの依頼を止めることはなくなりました。
- 並行ビルドは、メインのチェックアウトで求めた変更を取り込み、Git が無視するファイルは対象にしません。
- 誰も求めていないシステムパッケージのインストールは、本人の了承を待ちます。
- AI-DLC は OpenCode 2 で動作し、セットアップすれば exFAT ドライブでも動作します。Windows では、入力した引数をそのまま `aidlc` に渡します。
- Kiro CLI を起動する行は、そのエンジンを名指しします。
- すべてのハーネスで修正を行いました。

影響を受けるのは、次のものだけです。詳しくは後述の「スクリプトの互換性」を参照してください。

- 2.11.3 が `aidlc.exe` を書いたマシンで、以前のリリース自身の `install.ps1` によりそのリリースをインストールする、またはそのリリースの `aidlc uninstall` で削除する Windows のスクリプト。
- エージェントが自分でシステムパッケージをインストールする無人の実行。
- 1.18.29 より古い opencode 1 で、opencode 向けに `aidlc config runtime --check` を実行するスクリプト。

**opencode:** AI-DLC は、opencode 1.18.29 以降、または OpenCode 2 を求めるようになりました（以前のリリースは 1.17 を求めていました）。プロジェクトを更新するときに、opencode も更新してください。`aidlc doctor` は、古い opencode 1 を警告します（`Harness CLI: opencode <version> is below 1.18.29`）。

### セキュリティ

* ネイティブの `aidlc` は Bun 1.4.4 でビルドされています。これは、Bun が同梱する Brotli デコーダーの境界外書き込みである CVE-2026-111497 を修正します。CISA は、この脆弱性が実際に悪用されていると掲載しています。
  * ネイティブの `aidlc` 2.11.2 以前には、影響を受けるデコーダーが組み込まれています（`aidlc version` はこのマシンのリリースを示します。ピンしたプロジェクトでは、`aidlc doctor` がプロジェクトの版を `Project pin: <version> is installed` と示します）。Bun を別に更新しても、それは置き換わりません。`aidlc update` を実行し、古いリリースにピンしたプロジェクトは `aidlc config --pin 2.11.3` で移してください。
  * 既定の設定では、AI-DLC がそのデコーダーに渡すのは、HTTPS 経由の自身のリリースのダウンロードだけです。チームがメトリクスを `http://` のコレクターへ送っている場合（`AIDLC_METRICS_ENDPOINT`）、そのネットワーク経路上の誰かがコレクターの応答を偽造でき、その応答はデコーダーに届きます。更新し、コレクターを `https://` へ移してください。
  * コピーの経路では、自身の Bun を 1.4.4 以降に更新してください。

### 本人の言葉と回答

* 本人の言葉は、入力したとおりに AI-DLC とその記録へ届きます。
  * 計画の質問と作業の記録は、依頼の中の引用符とバックスラッシュを保持します（以前は、`/aidlc slugit "" prints an empty line, ...` が `slugit  prints an empty line, ...` として戻っていました）。
  * 理由、選択、依頼の中の `$` やバッククォート（`$0.00` のような価格、バッククォートで囲んだコマンド）は、シェルに変えられることなく、書かれたとおりに記録されます。Claude Code は、そのために AI-DLC 自身のコマンドを許可するよう求めなくなりました。
  * カンマと価格の両方を含む質問の選択肢は、欠けることなく戻ります。
  * Windows で Claude Code の Git Bash を使う場合、`!`、`$`、引用符、バッククォートの隣にあるアポストロフィも保持されます（"Don't merge, it's unsafe!" が "Dont merge, its unsafe!" として届くことはなくなりました）。これは、AI-DLC が引き渡すステップでも、質問の選択肢でも同じです。
* Claude のデスクトップアプリの Claude Code では、別の Claude セッションがチャットへ送ったメッセージは、本人の返答として数えなくなりました。そのため、その "Approve" や "Request Changes" がゲートに答えることはありません。エージェントがそれを読んでいる間に本人が入力したメッセージは、引き続き本人のものです。
* 番号付きの選択肢は、`1. **Approve** - Continue to ...` および `**Other** - describe what you want instead` と表示され、長いダッシュではなく平易な ` - ` を使います。対象は Kiro CLI、Kiro IDE、Cursor、opencode、GitHub Copilot です。AI-DLC が同じ記号で表示していたほかの行も同様で、拒否や doctor の行から、スラッシュコマンドの選択画面にあるスコープの一覧、Claude Code のウェルカムカードまでが含まれます。
* 確認した要約がもう一度質問を受ける場合（求めた変更の後、または承認の後に再び開いたステップ）、エージェントはそれらを続きの番号付きの質問として加え、確認するための要約を一つに書き直して、最初の一回で示します。AI-DLC が拒否する形を試すことはありません。
* `aidlc engine audit turns` は、本人の各ターンを、送った内容とともに一覧します。内容は、このマシンが一日だけ保持するメッセージの記録から読みます。コミットされる監査には言葉が残らないためです。このマシンに言葉がないターンはその旨を伝え、このコマンドは何も書きません。

### ゲート、レビュー、計画の承認

* Request Changes の後の動作は次のとおりです。
  * レビューのあるステージのゲートでは、改訂のためのレビュー依頼をそのままエージェントに渡すため、再レビューが最初に拒否されて（`Cannot start review iteration 2 ... Retry with --iteration 1`）、再び尋ねられることはなくなりました。
  * Guard Policy が relaxed または off のとき、Code Generation のゲートで Request Changes が二回続くと、最初の回と同じように、計画を直すための新しい言葉がエージェントに渡されます。言葉を落として同じ計画を再びビルドすることはありません。
  * そこでは、改訂した計画のビルドが、行う変更の前に毎回チェックを消すのではなく、計画上の自身のチェックを保持します。
* 承認したコード計画が再び尋ねられるのは、本当に変わったときだけです。
  * ビルド中にステップへチェックを入れる操作は、その箱がラベルの後、見出しの中、または表のセルにある場合（`Step 1. [x]`）、strict でも再承認を求めず、relaxed または off でも "Your approved plan changed after the build started" とは言いません。
  * 更新より前に承認した計画が、リスト項目の先頭以外に、すでにチェック済みの箱、`[-]`、または文章の箱を持っていた場合は、strict でもう一度尋ねます。
  * strict では、Code Generation の学びのステップで残すテストの実践は、次の計画から適用されます。そのため、ビルドとそのレビューが到達したゲートは開きます。完了したビルドが計画へ戻り、再び承認され、ビルドされ、レビューされることはありません。
* ほかの依頼は、Code Generation で待っている作業には止められません。
  * 作業がそこで保留されている間（"let's stop here for today"）、プロジェクトでほかに求めるもの（スクリプト、コミット、計画が名指ししていないファイルへの編集、すでにビルドした Unit の修正）は、どの Guard Policy でも実行されます。それぞれが `Code Generation cannot start: ...` で拒否されることはありません。
  * Claude Code、Codex CLI、opencode、および `--harness kiro` でセットアップしたプロジェクトの Kiro CLI では、同じフォルダーで別のことに開いた二つ目のチャットは、そこでの最初の AI-DLC のステップから、作業のチェック（コード計画、レビューの凍結）に止められます。それまでは、そのチャットが行う書き込みもそれらには止められません。そのチャットでの `/aidlc` は、引き続き作業を続けます。
  * 計画のチェックが読めないシェルコマンド（`python3 -c`、ループ）は、読めていないものとして拒否され、平易な読み取りが通る方法を示します。
* ゲートの各選択肢は、表示のとおりに動作します。Approval & Handoff と Feedback & Optimization のゲートは、何も実行していなかった "Reject Initiative (end workflow)" と "Start New Ideation Cycle" を提示しなくなりました（作業を終える、または新しい作業を始めるには、自分の言葉で伝えてください）。Accept as-is は "Approve it as it is and move on" と表示します。何もアーカイブされないためです。
* 実行しても結果がなかったゲートのチェック（スクリプトがないチームのチェック、タイムアウトしたもの、結果を出す前に止まったもの）は、クラッシュしたチェックがすでにそうしていたように、ゲートで一度だけ伝え、実行できなかったものとして記録します。何も伝えずにゲートが開くことはありません。

### 計画、ジャンプ、スキップ

* 完了した作業での変更は次のとおりです。
  * さらにステージを求めると（poc の後の "I want to add the operation phase"）、エージェントは、最後のステージの後にそれらを実行する計画を、それぞれが加えるものと推奨とともに名指しします。本人が選ぶと、作業はその計画へ切り替わり、承認済みのものをすべて保持したまま、その新しい最初のステージを始めます。どの方法でも "start a new workflow instead" で終わることはありません。
  * 計画の切り替えと同じ依頼で、その切り替えが再び開くステージをスキップする場合（完了した poc に対する `/aidlc --scope feature --skip ci-pipeline`）、そのステージはスキップされます。スキップしたことと、それを単独で実行する方法を一行で示します。ステージが始まって、スキップが拒否されることはありません。
* `/aidlc compose` から、作業に合わせた計画を承認すると、示した計画が、その深さと設定とともに作成されます。返答の後にエージェントが計画を再び組み立てた場合（Codex で `codex exec` のターンの間にそうなる場合）も同じです。"the plan you approved" として別の計画が作られることはありません。見た計画が失われている場合、エージェントはその旨を伝え、承認のために新しい計画を示します。
* ステージのルールが部分に分かれて届き、ある部分のコードがダッシュで始まる場合、エージェントの `continue -- <code>` は次の部分を持ってきます。GitHub Copilot でも同じです。読み込みを部分 1 へ戻すことはありません。以前はそこで、ステージの質問や承認が遅れるか、届かないことがありました（Kiro CLI では部分 1 が何百回も取得されていました）。
* 始まった後の最後のステージを、計画の組み替えを通じてスキップすると、その場でスキップするための `/aidlc --skip <stage>` を名指しします。"Continue automatically" の下では、拒否された計画やスコープの変更が、そこにいる間、承認する人がいないとは言わなくなりました（無人の実行では引き続きその旨を伝えます）。作業の状態ファイルの Stages to Execute の行は、Stages to Skip と同じように各ステージを名指しします（`2.3 (requirements-analysis)`）。すでに開いている作業は、スコープの変更か再構成がその行を書き換えるまで、今の行を保持します。

### Construction

* 並行ビルドの変更は次のとおりです。
  * Guard Policy strict では、Unit をビルドしている間にメインのチェックアウトで求めた変更（"also fix the typo in the README"）は入り、取り込み時にも保持され、本人の言葉とともに記録されます。Code Generation が終わるまで保留されることはありません。
  * ビルド中の Unit の計画が名指しするファイルは、引き続きその Unit のチェックポイントを通ります。チームがメモリでロックした strict の Guard Policy は、設定されている場所を示します。
  * Git が無視し、追跡していないファイル（テスト実行のログ、開発サーバーのログ、`.env`）が、計画の再承認を求めたり、取り込みやステージの完了を止めたり、本人の変更として伝えられたりすることはなくなりました。プロジェクトの外のフォルダーへの無視されたリンクや、サブモジュールの横にある無視されたファイルが、ビルドの開始を止めることもなくなりました。
* ウォーキングスケルトンがオンで、ほかの Unit を並行でビルドしている場合の変更は次のとおりです。
  * 最初の取り込みは、チェックポイントで承認したスケルトン（またはそれが削除したファイル）を、本人の変更として読まなくなりました。
  * スケルトンのチェックポイントとバッチのチェックポイントの後に Code Generation を承認すると、何も越えられなかったスケルトンを名指しする拒否ではなく、Build and Test へ進みます（すでに止まっている作業は、次の承認で通ります）。
  * Unit のソースを持ち、`.gitmodules` の項目がないネストしたリポジトリは、どの Unit のフォルダーを作るよりも前に名指しされ、Git のサブモジュールとして登録する手順、またはその Unit を直列にビルドする手順を示します。空のフォルダーと、理由を言わない失敗にはなりません。
  * 再び承認した計画が、Unit の既存のビルドへ届かない場合は、再び承認しなければならないとは言わず、そのビルドが自分のものとして持っているもの（コミットしていない作業、またはメインのコードの履歴にないコミット）を伝えます。
* チームの Unit は、エージェントとともに最後まで動作します（Claude Code と GitHub Copilot CLI では、そのように実行します）。
  * チームメイトの新しい clone、またはリード自身のチェックアウトで、どちらの承認のリズムでもクレームした Unit は、そのステージ、`/aidlc unit publish`、`/aidlc unit pin`、一つのマージの質問とその取り込みを通ります。クレームしたチェックアウトは、その後、通常の `git pull` で取り込まれた main を受け取り、記録のすべての行を保持し、次のクレームに使えます。
  * その途中で、pin は Unit を、実際の clone が保持するとおりに受け取ります（AI-DLC 自身のステージの日記とレビューの記録、Plan Approval の行、その Unit の種類が何も負わないステージ、または未解決の懸念があっても承認したステージ、1 MiB を超える記録）。理由を一つずつ挙げて拒否することはありません。
  * publish と land は、`.gitignore`、`AGENTS.md`、`opencode.json` の AI-DLC 自身の部分によって止まることはなくなりました。取り込みは、Unit Progress の表がまだない main でも、もう一方の承認のリズムでも完了します。land は、git がコミットを拒否した理由を伝えます。
  * AI-DLC が Unit の完了を伝えた後のコミットは、拒否のループではなく通ります。`/aidlc unit pin <unit>` とほかの `unit` コマンドは、新しい作業として読まれずに実行されます。AI-DLC が Unit をクレームするのは、本人が求めたときだけです（`/aidlc --claim <unit>`）。
* チームの Unit のゲートとボードの変更は次のとおりです。
  * pin は、Unit をピンするそのターンで、マージの質問を一度だけ本人に出します。最初の回答は、その言葉、またはそれが届いたメッセージとともに、本人のものとして記録されます。Approve はそのターンで Unit を取り込みます。
  * Unit の終わりのリズムでは、一つのゲートが、それより前の各ステージの未解決の指摘をステージのラベル付きで示し、完了しなかったレビューも示します。Approve は、示した内容だけを受け入れます。
  * Request Changes の後に再び示したゲートは、次の回答を受け取ります。
  * Unit に当てはまらないステップ（プロビジョニングするものがない Infrastructure Design）は、本人またはエージェントがスキップするとスキップされます。毎ターン拒否されることはありません。マージの質問は、その旨を一度だけ伝えます。
  * クレームしたチェックアウトでの "Reopen the approved stage" は、その Unit のためにそのステージを再び開きます。そのチェックアウトは、main にすでにマージされた Unit を完了として示します。
  * ボードは、取り込まれた Unit が取り込まれたことを示します。すべての Unit がクレームされている間は、メインのチェックアウトからは何も実行されないことと、各 Unit がどこで作業されているかを示します。
  * Unit の終わりの通知は、ここで publish し、その後、Unit のクレームを持たないプロジェクトのチェックアウトから pin、ゲート、land を行い、取り込まれたらここで main を pull するよう伝えます。
* チームの Unit で、このリリースでも開いたままの既知の抜けは次のとおりです。
  * Unit の終わりのリズムでは、Unit がスキップしたステージが、その Unit の終わりの承認を止めます。その承認は、そのステージの文書と、持つことのできないレビューを求めます。
  * マージの質問は、未解決の指摘を残したまま承認したステージについて、レビューをきれいに通過したと言うことがあります。
  * Unit をクレームしたチェックアウトで、承認済みのステージへの変更を求めると、そのステージは再び開きますが、入力していないジャンプのコマンドとして記録され、本人の言葉は残りません。
* エージェントが、誰も求めていないシステムパッケージをインストールしようとする場合（Build and Test での `sudo apt-get install -y python3-pytest` など）は、どのステージでも、どの Guard Policy でも、コマンドとその目的を伝えて待ちます。了承すると、一度だけ実行され、本人の言葉とともに記録されます。独立したメッセージで求めたインストール、または承認した計画が名指しするインストールは、これまでどおり実行されます。
* ATDD の方法論では、コード計画の Acceptance Red のステップが、機能をビルドする前に受け入れテストを実行し、失敗した出力を記録するよう求めます。TDD の Red のステップと同じです。更新より前に承認した ATDD のコード計画で、ビルドがまだレビューされていないものは、Guard Policy strict でもう一度尋ねます。

### Reverse Engineering と多数のリポジトリ

* 括弧、角括弧、波括弧、`;`、`$`、バッククォートを名前に含むリポジトリフォルダー（`lib (copy)` など）は、ほかと同じように作業の一部になります。名前が "stops AI-DLC's commands on Cursor" であるとして外されることはありません。Cursor では、そのフォルダーに対する Reverse Engineering のヘルパーのコマンドが、Guard Policy strict と relaxed の下で実行されます。`!`、`$`、バッククォートの隣にアポストロフィがある名前は、引き続き外されます。

### セットアップ、設定、ライフサイクル

* 七つのハーネスすべてで、`aidlc version` が `2.11.3` を表示します。
* AI-DLC はハードリンクを作らなくなりました。そのため、exFAT ドライブ（Linux または Windows）でも、`aidlc config --harness <name> --yes`、`/aidlc knowledge onboard`、`aidlc system workspace-sync`、`/aidlc intent add-repo` は、ローカルディスクと同じように動作します。config が拒否されたり、ワークスペースの同期が生の `EPERM` や `EISDIR` のエラーで止まったりすることはありません（端末では、Linux の exFAT と WSL の `/mnt/c` での初回セットアップは、これまでどおりファイル権限のチェックで止まります）。一つのプロジェクトで同時に始めた二つの AI-DLC のコマンドは、どのドライブでも何も失いません。二つ目は、`another AI-DLC command is still working in <project>.` と次のステップを伝えます（二つのワークスペース同期では、ステージング中に clone が現れたこと）。別のコンピューターが残したロックは、削除するフォルダーを名指しします。
* `aidlc update --help`、および `use`、`uninstall`、`doctor`、`version` のヘルプは、そのコマンドが取るすべてのオプションを、一行の意味とともに名指しします。`update --channel` は、そのチャンネルから一回の実行分のリリースを取ることを伝えます。一方、`aidlc config --channel` は、このマシンが従うチャンネルを設定します。
* モデルをそのままにすることが、Claude Code、Codex、opencode、Kiro CLI での回答になりました。モデルの質問での Enter、初回セットアップでの `unchanged`、または新しい `aidlc config models --keep` が、取り消し方とともにそれを記録します。そのため、モデルの方針がないプロジェクトの更新が、モデルについて再び尋ねることはありません（`aidlc config models --reset` がそれを消します）。
* `aidlc doctor` の変更は次のとおりです。
  * 一度も更新を確認していないマシンで、自身の簡単な確認が失敗した場合（リリースのサイトが遅い、または到達できない）、更新の行は警告ではなく、`not checked yet` として合格し、`aidlc update --check` を名指しします（`aidlc doctor --check-updates` は、失敗した確認を引き続き報告します）。
  * doctor が自ら解除した古いロックは、その行を失敗させて終了コード 1 で終わるのではなく、合格します。
* AI-DLC のチェックの一つをオフにするとき（センサー、学び、利用状況の追跡は除きます）、その変数が環境で 1 以外に設定されている場合（`AIDLC_DISABLE_REVIEW_FREEZE_HOOK=0` など）は、スイッチは記録されたものの、その変数が設定されている間はチェックをオフにしないこと、およびエディターまたは CLI をその変数なしで起動することを伝えます。チェックがオフであるとは言いません。
* 50 ページを超える PDF で、AI-DLC が最初の 50 ページを読むものは、全体を読んだものとして記録されなくなりました。`/aidlc knowledge show` は、本文の上に `truncated  yes after page 50` と表示します。依頼の中でそのような PDF を名指しすると、エージェントは `Only its first 50 pages were read.` と伝えます。

### プラグイン

* ネイティブ導入のプラグイン作者は、`aidlc plugin validate` と `aidlc plugin build` に加えて、`aidlc plugin test [path] --install <project-root>` で構成のテストを実行します。名指ししたプロジェクトの、変更されることのない使い捨てコピーで、プラグインをテストします。`unknown command 'plugin'` にはなりません。そのプロジェクトでプラグインがオフの場合、その行は、その導入向けの select を名指しします（ネイティブ導入では `aidlc engine plugin select aidlc,<plugin>`）。まだインストールされていない場合は、先にそこにプラグインをインストールするよう伝えます。
* Kiro IDE では、このリリースでビルドしたプラグインが、セッション開始のステップを、AI-DLC 自身のセッション開始フックが得る 1800 秒で登録します。Kiro の既定の 60 秒ではありません。以前は、別の同期を待ったり、遅いマシンで実行したりするプラグインの構成が、メッセージなしで止まっていました。プロジェクトにすでにある登録は、プラグインをビルドして再び配置するまで、以前のビルドが書いたものを保持します。
* ステージまたはスコープを加えるプラグインを同期した後、どのハーネスでも、`aidlc doctor` の AI-DLC のファイルの行は、`/aidlc` スキルの横にあるスコープとステージの表（`tables.md`）を、`aidlc config` が保持してそこで止まるファイルとして名指ししたり、それらに対して `aidlc config --force` を提案したりしなくなりました。更新が、プラグインの行を含めて、それらを自ら再び描画します。

### ハーネスごとの変更

* Claude Code の変更は次のとおりです。
  * 名前付きのエージェントの下で始めたセッション（`claude --agent <name>`、バックグラウンドのセッション、または Claude のエージェントがオンの場合）は、最初の `/aidlc` のステップを実行し、計画を提案します。`Delegated agent "<name>" cannot run ...` で拒否されることはありません。
  * プロジェクトの git worktree で作業するデスクトップアプリのセッションでは、ネイティブ導入のフックが、セッション、本人の言葉、その監査を、その worktree に記録します。メインのチェックアウトの記録に書いたり、すべてのフックが `this project's <version> pin is not registered on this machine` で失敗したりすることはありません。
  * `aidlc config` は、`.claude/worktrees` が本人の worktree を持ち、その中にシンボリックリンクがあるプロジェクト（追跡されている `AGENTS.md -> CLAUDE.md` など）をセットアップし、それをそのまま残します。`transaction tree contains a link or special file` で止まることはありません。
  * ウェルカムメッセージの Scopes の表は、各計画が実行するステージを一覧します（infra の Inception の `PD, RA`、security-patch の `RE, RA`）。スコープは本人のコマンドから設定されるか、確認のために提案されることを伝えます。どの行も、その表を越えて続きません。
* GitHub Copilot の変更は次のとおりです。
  * Windows の Copilot CLI では、すべてのステージの文書が最初の試行で書かれます。AI-DLC は、ステップを引き渡すときに、各ステージと Unit の記録フォルダー、および Reverse Engineering の引き渡しとコードナレッジベースのフォルダーを作るためです。ステージが新しいフォルダーを始めるたびに、チャットで書き込みが拒否されて再試行することはありません。
  * アダプターは、Copilot のデスクトップアプリが送ると報告された形を読みます（パッチがプレーンテキストとして、または `toolArgs` の中に届く `apply_patch`、`powershell` または `pwsh` という名前のシェル呼び出し、`paths` を持つ `grep`）。そのため、その方法で編集したステージは、Running のままではなく、確認した要約の後に承認できます。このアプリは、まだ対応している面ではありません。
* Kiro CLI と Kiro IDE の変更は次のとおりです。
  * Kiro CLI 2.33.0 以降は、エンジンをコマンドラインか、本人自身の Kiro の設定からのみ受け取ります。そのため、`aidlc config --harness kiro-ide` でセットアップしたプロジェクトでは、何も付けない `kiro-cli` が v2 のエンジンを開き、`agent "aidlc" not found` と伝えて、AI-DLC のフックを一つも実行しないことがありました。AI-DLC が表示する行と、ガイドが示す行のうち、Kiro CLI を起動または再起動するものは、すべてエンジンを名指しするようになりました。そこでは `kiro-cli --v3` です（Kiro がフォルダーを信頼するかを尋ねたら **Trust, continue** を選びます）。`--harness kiro` でセットアップしたプロジェクトでは `kiro-cli --v2` です（Kiro CLI 2.21.4 以降）。
  * `--harness kiro` でセットアップしたプロジェクトでは、Kiro CLI での並行ビルドが、ワーカーが Unit のチェックアウト `.aidlc/worktrees/<unit>/` に書く各ファイルの承認を求めなくなりました（その `.git`、`.gitignore`、ほかのドットファイル、プロジェクトのドットフォルダー、プロジェクトの外のものは、引き続き承認を求めます。Kiro CLI の v2 エンジンでは、チェックアウト自身のドットフォルダーも通ります。エージェントのファイルを Kiro が 3.0 エンジン向けに更新したプロジェクトは、更新が名指しする `aidlc config --harness kiro --force` でこの動作になります）。
  * Kiro IDE では、Kiro の Default エージェントのチャットで `/aidlc` と依頼すると、そのチャットで一度だけ、Kiro が AI-DLC の各コマンドの承認を求める理由と、チャット欄の下のエージェントメニューで aidlc を選ぶとそのカードが止まることを伝えます。判定が出る前に承認したときに残った Unit のレビュアーのコピー（Kiro のエージェント一覧の "<reviewer> (this review)"）は、その作業の次のチャットが始まるとき、または次のレビューが求められるときに削除されます。本人が削除するまで残ることはありません。
  * doctor の ignore-source の行（今は `Kiro ignore sources:`）は、Kiro CLI v3 も拒否されることと、各ファイルがどこに適用されるかを伝えます。Kiro CLI v3 は、設定なしで `.kiroignore` を適用し、`.gitignore` は適用しません。
* opencode の変更は次のとおりです。
  * AI-DLC は OpenCode 2 で動作するため、ゲートはすべての返答を拒否するのではなく、本人の返答を受け取ります。そこでは、OpenCode 2 にそのためのツールがない、To-Do による進捗の同期の代わりに、`/aidlc --status` を使います。チャットは、入力したスイッチを保持したまま、`/aidlc` コマンドのテンプレートを表示します。
  * opencode 1 では、AI-DLC が 1.18.29 以降を求めるようになりました（以前のリリースは 1.17 を求めていました）。`aidlc doctor` は、それより古いものについて警告します。
* Windows の変更は次のとおりです。
  * ネイティブ導入では、`aidlc` が入力した引数をそのまま渡します。インストールは bin フォルダーに `aidlc.exe` を加えるため、PowerShell、CMD、Git Bash は `aidlc.cmd` より先にそれを実行します。そのため、`aidlc use 'R&D'`、`^`、`|`、`>`、`%NAME%` が、先に cmd.exe に読まれることはなくなりました。各コマンドの開始も少し早くなります（以前のリリースからの更新の後は、最初のコマンドがそれを書きます）。
  * 作業が Code Generation にある間、Git Bash の `cd /c/<project>;` の後に続く AI-DLC 自身のコマンドは、`Code Generation cannot start: ...` で拒否されずに実行されます。本人の言葉を伴って拒否されたステップは、その先でもその言葉を保持します。

### スクリプトの互換性

* スクリプトに影響する変更: Windows では、2.11.3 がネイティブ導入の bin フォルダーに `aidlc.exe` を書いた後、以前のリリースの `install.ps1` は、そのリリースをインストールせず、`existing aidlc at ... is outside the native install destination` のチェックで止まります（終了コード 4）。以前のリリースの `aidlc uninstall` は `aidlc.exe` を残し、それを名指しします。以前のリリースへ切り替えるには、`aidlc use <version>` を使います。
* スクリプトに影響する変更: 承認した計画が名指ししていないシステムパッケージのインストールは、無人の実行（`AIDLC_UNATTENDED=1`）でも保留されます。そのため、エージェントが自身のツールをインストールしていた CI ジョブ（`sudo apt-get install`、`brew install`、`winget install`）では、コマンドが実行されるのではなく名指しされます。AI-DLC を始める前に、ジョブの中でそれらのツールをインストールしてください。
* スクリプトに影響する変更: opencode 向けの `aidlc config runtime --check` は、1.18.29 より古い opencode 1 で失敗するようになりました（`opencode <version> is below 1.18.29`）。2.11.2 では通過していました。先にジョブの中で opencode を更新してください。平易な `aidlc config --harness opencode --yes` は、これでは止まりません。`aidlc doctor` は警告するだけです。
