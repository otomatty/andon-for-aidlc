# ハーネスエンジニアガイド

> [AI-DLC ドキュメント](../README.md) の一部 · [ユーザーガイド](../guide/00-introduction.md) · **ハーネスエンジニアガイド** · [開発者リファレンス](../reference/00-overview.md)

AI-DLC は手法であり、この実装はそれを、あなたが使うハーネス — Claude Code、Kiro CLI、Kiro IDE、Codex CLI、Cursor、opencode、GitHub Copilot — の上で、すぐ動く形で出荷します。14 のエージェント（11 の領域専門家、2 のレビュアー、そしてコンポーザー）、33 のステージ、11 のスコープ、そしてルールとセンサーの一式です。このガイドは、その手法を**作り替えたい**人のためのものです — どのステージを実行するかを変える、フレームワークが扱っていない領域のためにエージェントを追加する、スコープを絞る、常設のルールをフレームワークに教える、決定論的な検査をステージへ配線する、といったことです。

これらはすべて、**コードを書かずに**行えます。

---

## 3 人の読み手、3 つのガイド

AI-DLC のドキュメントは、話題ではなく「何をしようとしているか」で分かれています。

| ガイド | あなたは… | 変えるのは… |
|-------|----------|------------|
| [ユーザーガイド](../guide/00-introduction.md) | AI-DLC を*使って*ソフトウェアを作る | `.claude/` は何も変えません — `/aidlc` を実行し、ゲートで回答し、成果物をレビューします |
| **ハーネスエンジニアガイド**（本ガイド） | チームに合わせて AI-DLC の*振る舞い方*を形づくる | フレームワークが読む**データ**: ステージ、エージェント、スコープ、ルール、センサー、ナレッジ |
| [開発者リファレンス](../reference/00-overview.md) | AI-DLC *そのもの*を変える | そのデータを読む**コード**: オーケストレーター、フック、CLI ツール、コンパイルパイプライン、テストスイート |

本ガイドと開発者リファレンスの境界は**データかコードか**です。ハーネスエンジニアが触れるものはすべて、YAML フロントマターを持つ Markdown ファイルか JSON の設定 — フレームワークが実行時に読み込む宣言的なデータです。ステージを追加する、エージェントを追加する、スコープを定義する。これらに *TypeScript の編集が不要*であることは、フレームワーク自身の設計原則です。変更が `.ts` の編集 — オーケストレーター、フック、ツール — を意味した瞬間に、あなたは開発者リファレンスの領域へ踏み込んでいます。

## メンタルモデル: ステージが*何を*、エージェントが*誰が*

2 つのプリミティブがフレームワークの大部分を担っており、この 2 つを取り違えないことが仕事のすべてです。

- **ステージ**は作業の単位です — *何が*起きるか。消費・生成する成果物、それをリードするエージェント、そして実行方法を宣言します。ステージはワークフローグラフのノードです。
- **エージェント**はペルソナです — *誰が*作業するか。領域の専門性、ツールの許可リスト、モデルを持ちます。エージェントはステージ*の中へ*読み込まれます。

ステージはリードエージェントを名指ししますが、エージェントが自分のステージを名指しすることはありません。この非対称性は意図的です。作業の再割り当て（ステージの編集）を、働き手を書き直さずに行えますし、働き手の追加（エージェントファイルの追加）を、どこかのステージがそれを使うと決めるまでワークフローを乱さずに行えます。

2 つの機構が、これらのステージを通して作業を進めます。ハーネスエンジニアとして、あなたはその両方が読む**データ**を形づくります。決定論的な**エンジン**（`core/tools/aidlc-orchestrate.ts`。サブコマンドは `next`、`continue`、`report`、`park`、`team-board`、`wait` のちょうど 6 つで、`continue` は内部のステアリング転送用、`team-board` は Team Construction の読み取り専用クエリ）は、`aidlc-state.md` とコンパイル済みの `stage-graph.json` を読み、次に何を実行するかを決め、型付きのディレクティブを 1 つ出力します。**コンダクター**（`skills/aidlc/SKILL.md`）は、各ディレクティブを実行に移す薄い転送ループです。経路選択はエンジンにあり、あなたのステージファイル・スコープ・ルールは、それを操る入力です。

ハーネスエンジニアが設定する他のすべては、この 2 つにぶら下がります。

- **スコープ**は、ある種類の作業に対して*どの*ステージを実行するかを決めます（バグ修正はセットアップ後の 30 ステージのうち 6 ステージ、エンタープライズの機能開発は全部を実行します）。
- **ルール**は、すべてのワークフローへ持ち込まれる常設の決定です — あなたのチームの「いつもこうする」。
- **センサー**は、ステージに結び付いた決定論的な検査です — 一致する書き込み時か承認ゲートで実行され、バインディングは助言的にも、ブロッキングにもなります。
- **ナレッジ**は、エージェントが作業前に読み込む領域の文脈です。

## コードなしで変えられること

これらはすべて、手作業で書かれたハーネス非依存のソースである `core/` で作成し、その後ハーネスごとのツリーを再生成します（下記の [ビルドモデル](#ビルドモデル-core-で作成しハーネスを再生成する) を参照）。

| 変更 | 作成する場所 | 章 |
|--------|-------|---------|
| ステージが何をするかを編集する | `core/aidlc-common/stages/<phase>/<slug>.md` | [ステージの構造](01-anatomy-of-a-stage.md) |
| まったく新しいステージを追加する | 適切なフェーズディレクトリの新規ファイル + グラフの配線 | [ステージを追加する](02-adding-a-stage.md) |
| エージェントを追加・変更する | `core/agents/<name>-agent.md` | [エージェントを追加する](03-adding-an-agent.md) |
| スコープを定義する | `core/scopes/aidlc-<name>.md` + ステージごとの `scopes:` タグ | [スコープ](04-scopes.md) |
| 常設のルールを教える | `core/memory/{team,project}.md` | [ルールと学習ループ](05-rules-and-the-loop.md) |
| 決定論的な検査を配線する | `core/sensors/` 配下のセンサーマニフェスト + ステージの `sensors:` インポート | [センサー](06-sensors.md) |
| チームの領域ナレッジを加える | `aidlc/knowledge/<agent>-agent/`（スペースレベルのナレッジディレクトリ。実行時） | [チームナレッジ](07-team-knowledge.md) |
| Construction とスウォームの姿勢を形づくる | `core/memory/` + `units-generation` ステージ | [Construction とスウォーム](08-construction-and-swarm.md) |

各章は*どうやるか*を語り、網羅的なスキーマについては [開発者リファレンス](../reference/00-overview.md) へリンクします — リファレンスが規範となる契約であり、本ガイドは実践の物語です。

1 行だけ例外があります。**チームの領域ナレッジ**は、*あなた*が自分のプロジェクトのスペースレベル（`aidlc/knowledge/`。スペースの `memory/`、`codekb/`、`intents/` の兄弟）に、実行時に加える文脈です — `core/` の一部ではなく、フレームワークがそれを上書きすることは決してありません。上記のそれ以外はすべて、`core/` で作成するフレームワークのソースです。

## 命名規則と、それがどこで強制されるか

ステージのファイル名の語幹は、フロントマターの `slug` と一致していなければなりません。`aidlc-graph compile` は、語幹の不一致、ステージ slug の重複、そして消費されるいずれかの成果物に対する複数の生成者を、ハードエラーとして拒否します。重複プロデューサーのエラーは、生成側のステージファイルと消費者を 1 つ名指しします。どのステージも消費していない場合、成果物名の共有は依然として妥当です。センサーのファイル名／ID の検査はコンパイル時のハードエラーです。スコープとエージェントで宣言名が重複する場合はローダーのエラーとなり、両方のファイルを名指しします。スコープ／エージェントのファイル名と名前の乖離は `/aidlc --doctor` が助言として報告するため、作成者はファイル名を変えるか `name` を直せます。

## ビルドモデル: `core/` で作成し、ハーネスを再生成する

ハーネスエンジニアが作成するソースは `core/` にあります。ステージは `core/aidlc-common/stages/`、エージェントは `core/agents/` に置き、スコープ、ルール、センサー、ナレッジ、ツール、フックもここで管理します。ソース開発用の `dist/<harness>/` ツリー（`dist/claude/.claude/`、`dist/kiro/.kiro/`、`dist/kiro-ide/.kiro/`、`dist/codex/`、`dist/cursor/`、`dist/opencode/`、`dist/copilot/`）は、`core/` とハーネス固有の `harness/<name>/` から生成します。これらは Git の管理対象外のローカル出力であり、コミットや手動編集はしません。

```bash
# 1. core/ のソースを編集する（dist/ は決して編集しない）
$EDITOR core/aidlc-common/stages/inception/my-stage.md

# 2. core/ + harness/ から全ハーネスの両配布形式を再生成する
bun scripts/package.ts

# 3. 生成結果の再現性を検証する（CI のガード）
bun scripts/package.ts --check
```

コミットするのは `core/` または `harness/` のソース変更です。`--check` はコピー形式、ネイティブ形式、プラグインの全配布物を別々の一時ディレクトリで2回生成し、バイト単位で比較します。
以降の章の `aidlc engine graph compile` などのコマンドは、プロジェクトで有効なインストール済みハーネスに対してツールを実行します。生成されたコピー形式の文書は Bun ディスパッチャーを、ネイティブ形式の文書は `aidlc` を使います。ソースの作成者は配布形式に依存しない呼び出しを使います。ソースは `core/` で編集し、ディスパッチャーはインストール済み配布物に対して実行する、という区別を保ってください。
ビルド契約の全体は [新しいハーネスへの移植](09-porting-to-a-new-harness.md) と、[アーキテクチャ § ソースと配布物](../reference/01-architecture.md#ソース対ディストリビューション1-つのコア複数のハーネス) を参照してください。

## 開発者リファレンスへ踏み込むとき

変更がフレームワークのデータではなくコードに及ぶときは、[開発者リファレンス](../reference/00-overview.md) を開いてください。

- オーケストレーターの経路選択や状態機械（[オーケストレーター](../reference/03-orchestrator.md)、[状態機械](../reference/12-state-machine.md)） — 規範となるエンジン／コンダクター／ディレクティブ／ランナー／スコープ形状／スウォームの契約は [スキルシステム](../reference/17-skill-system.md) を参照
- フックや CLI ツール（[フックとツール](../reference/06-hooks-and-tools.md)）
- ステージグラフのコンパイルパイプライン、または監査イベントの分類体系
- テストスイート（[テスト](../reference/09-testing.md)）

ステージやエージェントの追加はワークフローグラフに*触れ*ますが、それを読むコードは変えません — だからこそ本ガイドにあります。グラフのコンパイル方法を変えたり、新しい監査イベントを追加したりするのはコードの変更であり、そちらに属します。

## 本ガイドの構成

初回は順番に読んでください。

1. **[ステージの構造](01-anatomy-of-a-stage.md)** — ステージファイルのフォーマット。フロントマターの契約、3 区画の本文、グラフのコンパイル方法。何かを変える前に理解しておくべき、もっとも重要な 1 つ。
2. **[ステージを追加する](02-adding-a-stage.md)** — 最初から最後まで: ファイルを作成し、依存エッジを配線し、コンパイルし、スコープに現れるのを見る。
3. **[エージェントを追加する](03-adding-an-agent.md)** — ペルソナを作成し、それがリードまたは支援するステージへ結び付ける。
4. **[スコープ](04-scopes.md)** — スコープからステージへの対応を定義し、調整する。
5. **[ルールと学習ループ](05-rules-and-the-loop.md)** — 層のチェーンにまたがってルールを作成し、ループが訂正をルールへ昇格させるようにする。
6. **[センサー](06-sensors.md)** — 決定論的な検査を作成し、ステージへ結び付ける。
7. **[チームナレッジ](07-team-knowledge.md)** — エージェントにあなたの領域の文脈を与える。
8. **[Construction とスウォーム](08-construction-and-swarm.md)** — チームの Construction 自律姿勢をルール層で設定し、自律スウォームにおける Unit ごとの Bolt が何を並行実行できるかを `units-generation` で形づくる。
9. **[新しいハーネスへの移植](09-porting-to-a-new-harness.md)** — `harness/<name>/` ディレクトリ 1 つとマニフェストの 1 行で、`core/` を編集せずに別の CLI ハーネスを追加する: マニフェストの契約、フックアダプター、`emit.ts`。
10. **[プラグインを作成する](10-authoring-a-plugin.md)** — 再利用可能で任意の **AIDLC プラグイン**を `plugins/<name>/` にパッケージする: 新しいステージ／エージェント／スコープ／センサー／doctor 検査 + 既存のコアステージへの加法的なコントリビューションを、ハーネスごとに本物のホストプラグインとして出力する。設計は開発者リファレンスの単一の章（[18 機構](../reference/18-plugin-mechanism.md)）にあります。
