# ステージの構造

ステージは AI-DLC ワークフローの原子です — 1 ステップで*何が*起きるか。ハーネスエンジニアが行う他のあらゆる変更はステージファイルの上に積み上がるため、最初に読むべき章がここです。読み終える頃には、任意のステージ `.md` ファイルを開き、その各部分を誰が読むのかを把握し、ファイルを編集して変えられるフィールドと、フレームワークのコードによって固定されている振る舞いを見分けられるようになるはずです。

ステージファイルは、YAML フロントマターを持つ 1 つの Markdown ファイルです。フロントマターはグラフのノード — そのステージが消費・生成する成果物、リードエージェント、実行方法 — を宣言します。本文は、エージェントが従う散文です。両方が 1 ファイルにあるのは意図的であり、この章の残りはその理由を解きほぐします。

---

## 2 人の読み手、1 つのファイル

ステージファイルには 2 人の読み手がいて、両者が重なることはありません。

- **パーサー**は YAML フロントマターだけを読みます。構造化されたグラフのエントリ — エッジ、リードエージェント、実行モード — を生成し、本文は完全に無視します。
- ステージを実行する**エージェント**は本文だけを読みます。散文の手順に従い、成果物を生成し、フロントマターには決して触れません。

両方を 1 ファイルに置くということは、ファイルを開いたときにグラフのエッジと実行手順が並んで見えるということです。ステージを読むレビュアーは、どの成果物を生成するのか*と*それを生成する指示の両方を、一度に目にします。両者を分けてしまう — グラフ用の YAML ファイルと、エージェント用の散文ファイル — と、そのインラインでの可視性が壊れます。それこそが、ステージをレビュー可能にしている性質です。

この分離は、自分が何を編集しているのかを知るための鍵です。フロントマターのフィールドを変えれば*グラフ*（依存エッジ、リードするエージェント、実行モード）を変えたことになり、本文を変えれば*作業*（エージェントが実際に何をするか）を変えたことになります。この 2 つは独立しています。

実際のステージは `core/aidlc-common/stages/<phase>/<slug>.md` に作成されます — 例えば `stages/inception/domain-design.md` です。この章と並べて 1 つ開いてみてください。読み終える頃には、その形は馴染みのあるものになっているはずです。

## フロントマターの概観

フロントマターは、YAML キーのフラットなブロックです。`slug` や `phase` のように機械的で、隣のステージからコピーしてくるものもあります。ひと握りは本当の判断を伴い、ステージを作成・編集する前に理解しておく価値があるのはそれらです。

| フィールド | 何を決めるか | 判断のポイント |
|-------|-----------------|-------------------|
| `requires_stage` | 依存と順序のエッジ | このステージは本当に他のステージの出力を消費するのか、それとも単にその後に走ればよいだけか？ |
| `consumes` | このステージが読む成果物 | 成果物ごとに: `required` か、brownfield／greenfield の `conditional_on` か、そして `cited` か。 |
| `consumes[].cited` | 存在するときに出力が引用しなければならない任意入力 | 存在するときはいつも出力がその上に組み立てられる任意入力があるか？ あればそれに `cited: true` を付けます。すると `upstream-coverage` チェックがその引用を求めます。 |
| `produces` | このステージが書く成果物 | これらは、他のステージが発見する前向きのエッジになります。 |
| `lead_agent` / `support_agents` | 誰がステージを実行するか | 1 つのペルソナが所有し、サポーターが視点を加えます。 |
| `mode` | コミュニケーションのトポロジー | `inline`（コンダクターの文脈内の声）、`subagent`（ハブ&スポークのディスパッチ）、`pipeline`（連鎖）、`mob`（区切られたラウンドでのメッシュ）。 |
| `for_each` | 反復するかどうか | インスタンスごとに 1 回の実行を駆動する成果物を名指しします。 |
| `reviewer` / `review_artifact` | 独立した品質レビュー | レビュアーを宣言する場合、レビュー対象となる必須の Markdown 出力を1つ指定します。レビュー記録はその成果物に紐付き、ゲートにも対象が表示されます。`produces` の順序には依存しません。 |

とくに間違えやすい判断について、いくつか注記します。

- **`consumes[].required` は有効な計画に対するスコープであり、グローバルではありません。** `required: true` は「生成側のステージが*この*ワークフローで実行されるなら、この consume は満たされていなければならない」という意味であって、「生成側が常に実行される」ではありません。スコープは意図的に上流ステージをスキップするため、一律のグローバル要求では、それらのスコープが構造的に無効になってしまいます。入力が無い場合はステージ本文が適切に処理します（「生成されていれば」といった散文で）。
- **`consumes[].conditional_on` は brownfield／greenfield の分岐を表します。** `conditional_on: brownfield` が付いた consume は、ワークフローが brownfield のときにだけ必須になります。無条件の consume では、このフィールドを完全に省略します — `always` という値はありません。
- **`mode` はコミュニケーションのトポロジー**です — 本文の実行中に誰が誰と話すか。`inline` は短いステージをコンダクター自身の文脈で実行し、サポーターは取り込まれた声になります。`subagent` はリードを新しい文脈へ委譲し（Construction のコード生成のような長いステージ）、サポーターが宣言されていれば、それぞれを相互に見えないスポークとしてディスパッチします。`pipeline` はサポーターを宣言順に連鎖させ、各自が上流の作業すべてを見ます。`mob` はすべてのサポーターをリードの下書きに対して並行に走らせ、異議申し立てのラウンドを 1 回だけ区切って行います。誰が参加するかは `support_agents`、どう参加するかは `mode` です。`pipeline` と `mob` は空でない `support_agents` を必要とします。
- **`for_each` は反復対象の成果物を名指しします。** Unit ごとに 1 回実行される 5 つの Construction ステージは `for_each: unit-of-work` を宣言します。他のステージはこのフィールドを省略し、1 回だけ実行されます。集約は宣言ではなくグラフから推論されます。
- **`lead_agent` と `support_agents` は `core/agents/*.md` に対して検証されます。** ハードコードされた一覧はありません — エージェントを追加するとは、そのディレクトリにファイルを置くことです（[エージェントを追加する](03-adding-an-agent.md) を参照）。

これは方向付けであって、契約ではありません。型・制約・AI-DLC が後で追加する予約名前空間のフィールドを含む完全なフィールド表は、開発者リファレンスの [フィールドリファレンス — いつ使うか](../reference/15-stage-definition.md#フィールドリファレンス--いつ使うか) を読んでください。

## 3 区画の本文

フロントマターの下で、本文は 3 つの区画を持ち、順序は常に `## Steps`、`## Sensors`、`## Learn` です。`domain-design.md` を見ると、3 つすべてが埋まっています。

- **`## Steps`** は、エージェントが従う命令的な散文です — ペルソナの読み込み、事前の文脈の読み取り、質問ファイルの作成、成果物の生成、承認ゲートの提示。ステージの領域固有の作業が住むのはここであり、グラフに触れずに*ステージが何をするか*を変えるとき、最もよく編集する区画です。
- **`## Sensors`** は、簡潔なローカル要約を与えます。出力の着地先、フロントマターの `sensors:` 一覧を映す `Imports:` 行、そして `upstream-coverage` をインポートしている場合に `consumes:` を映す `Upstream targets:` 行です。意図的に省いたセンサーや、構造化出力の所有権といったステージ固有の例外はここに置きます。共通の振る舞いは `stage-protocol-sensors.md` にあり、センサーの全体像は [センサー](06-sensors.md) で扱います。
- **`## Learn`** は、`stage-protocol-learnings.md` セクション 13 の学習ループ契約を指します。`directive.protocol_modules` に `learnings` がある場合だけ、作業中は `directive.memory_path` にある 4 見出しの日誌を維持し、人間のゲートの前に学びのステップを行います。このステップは、そのステージで本人がエージェントを正した後にだけ本人に質問し、本人が残すものを永続化します。いつ質問するか、そしてブートストラップ、単独実行、Unit ごとの各例外はこのモジュールが所有します。`learnings` が無い場合は日誌を保たず、このステップも省きます。ワークフロー実行時の学習がステージ本文を書き換えることはありません。

3 つの区画が固定されているので、ステージのセンサーのバインディングと学習ループへのポインタには常にそれぞれの置き場所があり、それらを追加しても本文が再構成されることはありません。本文モデルの全体と各区画が持てる内容は [3 区画の本文モデル](../reference/15-stage-definition.md#本文の-3-区画モデル) にあります。

内面化しておく価値のある境界が 1 つあります。ステージファイルはフレームワークの成果物であり、その形は不変です。本文の `## Steps` / `## Sensors` / `## Learn` という構造が、ワークフローによって書き換えられることは決してありません。ワークフロー中に認められている唯一の編集は、学習ループがフロントマターの `sensors:` インポート一覧へ新しいセンサー ID を追記することだけです。ステージファイルのそれ以外は、ハーネスエンジニアとして意図的に変えるものです。

## グラフから見た consumes と produces

依存グラフは、どこにも直接は書かれていません。すべてのステージにまたがる `consumes` と `produces` の宣言から立ち現れます。あるステージの `produces` 一覧は、その前向きのエッジです。別のステージが「`scope-document` を生成するのは誰か」と尋ねたとき、答えはそれを宣言しているステージになります。あるステージの `consumes` 一覧は、その後ろ向きのエッジです。`required` の成果物は、その生成側がこの計画に含まれていれば、このステージの実行時に存在していなければなりません。任意の成果物は、存在すれば読まれます（上で述べた計画スコープの規則です）。

`requires_stage` は依存関係を明示し、同時に純粋な順序も表します。2 つの役割を担います。

1. **意味的なデータ依存** — 「私は成果物 X を消費し、それはステージ Y が生成する」ので、Y を `requires_stage` に置きます。
2. **表示順のエッジ** — 同じフェーズにあり、データ依存は無いが順序が決まっている 2 つのステージ。アルファベット順のタイブレークに頼るのではなく、この弱いエッジを書くことで、計算された表示順が安定して定まります。

ステージを作成したり移動したりするとき、それをワークフローへ配線するのはこの 3 つの一覧です。正しく書けば、ステージは正しいスコープに、正しい順序で、入力が満たされた状態で現れます。まったく新しいステージを配線する手順は [ステージを追加する](02-adding-a-stage.md) で段階を追って扱います。

## stage-graph.json はコンパイル結果です — 決して手で編集しないこと

ソースビルドでは、生成された Claude 配布物が `dist/claude/.claude/tools/data/stage-graph.json` からグラフを読みます。`dist/` は `bun scripts/package.ts` で生成するローカル出力で、Git の管理対象外です。インストール済みランタイムでは、同じ相対ファイルが `.claude/tools/data/` の下にあります。この JSON はビルド成果物です。正本は各ステージの YAML フロントマターであり、JSON はそのコンパイル結果です。

流れはこうです。

```
ステージ .md の YAML を編集  →  コンパイル  →  stage-graph.json  →  ランタイムが読む
```

`core/` でステージのフロントマターを編集した後は、`bun scripts/package.ts` を実行します。これはすべての生成ツリーへグラフをコンパイルします。コミットするのは `core/` の編集だけです。生成ツリーは管理対象外で、CI がソースからもう一度ビルドします（`bun scripts/package.ts --check` は 2 回ビルドしてバイト単位で比較します）。インストール済みのプロジェクトツリーでは、`aidlc engine graph compile` がそのツリーの `stage-graph.json` を再生成し、`aidlc engine graph compile --check` はそれが古くなっているときに知らせます。

```text
$ aidlc engine graph compile --check
stage-graph.json is out of date. Run `aidlc engine graph compile` to regenerate.
```

そこから導かれる規則が、**`stage-graph.json` を手で編集しない**ことです。YAML を編集し、再コンパイルしてください。手による編集は、次のコンパイルで潰されるか、乖離チェックに引っかかるかのどちらかです。コンパイルコマンドと乖離ガードは [作成フロー](../reference/15-stage-definition.md#作成フロー) に文書化されています。

## ステージが*含むもの*と、ステージが*すること*

この章は、ステージファイルが*含むもの* — そのフォーマット — についてのものです。ステージが実行時に*すること*については、対になる契約があります。承認ゲート、質問の流れ、状態のチェックボックス、完了メッセージです。その振る舞いの契約は、領域にかかわらずどのステージでも同じであり、[ステージプロトコル](../reference/04-stage-protocol.md) に住んでいます。ステージ本文が「承認ゲートについては stage-protocol.md に従う」と述べているとき、それが指しているのはこの契約です。

頭の中で 2 つを分けておいてください。ステージの*定義*（この章、[リファレンス 15](../reference/15-stage-definition.md)）はファイルフォーマットであり、ステージの*プロトコル*（[リファレンス 04](../reference/04-stage-protocol.md)）は、すべてのステージの作業を包む実行時の振る舞いです。あなたが編集するのは定義です。プロトコルはたいてい、そのままにしておきます。

フロントマターと本文を結び付けた、注釈付きの完全な例は [実例](../reference/15-stage-definition.md#実例) を参照してください。
