# エージェントを追加する

エージェントはフレームワークの*誰が*にあたります — 領域、ツールの許可リスト、ティアを持つペルソナです。出荷される 14 のエージェントは、プロダクト・デザイン・デリバリー・アーキテクチャ・AWS プラットフォーム・コンプライアンス・DevSecOps・開発・品質・パイプラインデプロイ・運用をカバーする 11 の領域専門家、レビュー専用の 2 エージェント、そしてアダプティブワークフローのコンポーザーから成ります。チームが、フレームワークの扱っていない領域（たとえばデータガバナンスのレビュアーやモバイルの専門家）を必要としたら、Markdown ファイルを 1 つ `core/agents/` へ置くことでペルソナを追加します。TypeScript は不要です。

この章はその作業の流れを辿ります。ペルソナファイルとは何か、そのフロントマターにおける判断、そして*見えている*エージェントはまだ*動いている*わけではない、という 2 段階の真実です。フィールドごとの契約については開発者リファレンスへリンクします。ユーザーの席から見たこれらのエージェントについては [ユーザーガイド — エージェント](../guide/06-agents.md) を参照してください。

---

## ペルソナファイルとは何か、どこに住むか

すべてのエージェントは `core/agents/<slug>-agent.md` にあるフラットな 1 ファイルです。上部に YAML フロントマター、その下に Markdown の本文があります。出荷されるファイルはいずれも `aidlc-` の接頭辞を持ちますが（`aidlc-architect-agent.md`、`aidlc-developer-agent.md`）、あなたが追加するファイルはあなたのものであり、その接頭辞を使う必要はありません。出荷される 14 個はフレームワークのファイルとして扱ってください。インストール済みのプロジェクトでは、そのいずれかをローカルで編集すると、あなたのコピーを別の場所へ移すか `--force` で出荷版を取り込むまで、次の `aidlc config` による更新が止まります。そのため、*既存のエージェントが何を知っているか*のカスタマイズは、ファイルを編集するのではなくチームナレッジを通じて行います（[チームナレッジ](07-team-knowledge.md) を参照）。更新はそのことを次のように伝えます。

```text
$ aidlc config --harness claude --yes
error: 1 config conflict(s): .claude/agents/aidlc-architect-agent.md (locally modified or unowned)
fix: to keep your version, move .claude/agents/aidlc-architect-agent.md somewhere else and run the same command again; to take the shipped version over it, run it again with --force.
```

本当に新しいペルソナは別の話です。あなたが所有し、アップグレードを生き延びる新しいファイルになります。

フロントマターは、フレームワークがパースする部分です。本文は、エージェントが起動時に自分自身について読む散文です — 責務、協働、記憶の焦点、働き方の原則。機械が読むのはフロントマターだけで、本文はエージェント自身の枠付けのためのものであり、出荷ファイルの構造に合わせて書きます。パッケージャーは、必須の委譲ナレッジ事前確認を、すべてのハーネス投影に追加します。

以下は、`core/agents/aidlc-architect-agent.md` に作成された、実際のエージェントのフロントマターです。

```yaml
---
name: aidlc-architect-agent
display_name: Architect Agent
examples:
  - tech-stack.md
  - infrastructure-preferences.md
description: >
  Solutions architect responsible for domain design, contract design, NFR patterns, and component decomposition.
  Leads Feasibility, Domain Design, Units Generation, Contract Design, Functional Design, NFR Requirements, and NFR Design stages,
  and serves as the dispatched last link of the Reverse Engineering pipeline.
disallowedTools: Task
tier: judgment
---
```

## フロントマターの契約と、あなたが下す判断

フィールドごとの完全なスキーマはリファレンスにあります。ここでは、実際に作成するときにあなたが下す判断を挙げます。

**`name` はファイル名の語幹と一致していなければなりません。** `aidlc-data-governance-agent.md` というファイルは `name: aidlc-data-governance-agent` を宣言します。パーサーはこれをキーにするため、不一致は「決して解決されないエージェント」を作ってしまうもっとも簡単な方法です。ローダーは、ファイルをまたいでエージェントの `name` が重複することを拒否し、エラーで両方のファイルを名指しします。

**エージェントは既定で、セッションのツール一式を継承します。** 出荷される 14 個のどれも `tools:` の許可リストを宣言していないため、それぞれがセッションの提供するすべてのツール — `Read`、`Edit`、`Write`、`Glob`、`Grep`、`AskUserQuestion`、`Bash`、`WebSearch`、そして継承された MCP ツール — に到達できます。ペルソナを絞るには、使ってよいツールだけを名指しする任意の `tools:` 許可リストを追加します。`tools:` を列挙すると、ペルソナは名指しした正確なツールだけに絞られ、完全修飾の `mcp__<server>__<tool>` の ID も名指ししない限り、継承された MCP ツールは落ちます（下の MCP 継承の注記を参照）。ある領域が本当に小さな面を必要とするときにだけ手を伸ばしてください。ほとんどのペルソナは、すべてを継承させておくのが最善です。

**MCP サーバーは継承されるものであり、エージェントごとに付与されるものではありません。** プロジェクトルートの `.mcp.json` で宣言された 5 つの MCP サーバーはセッションへ供給され、すべてのエージェントがそれらを自動的に継承します — 作成すべきエージェントごとの付与はありません。あるペルソナをあるサーバーから*遠ざける*には、その `tools:` 許可リストを、そのサーバーを含まない完全修飾の `mcp__<server>__<tool>` 一覧へ絞ります（裸の `mcp__<server>` トークンは no-op であり、サーバーレベルの付与ではありません）。この継承と制限のモデルは `t110` のレジストリ整合性テストで動かされています（[テスト](../reference/09-testing.md) を参照）。

**`disallowedTools` は `Task` を含まなければなりません。** これは任意ではありません。エージェントは委譲された働き手として動きます。エンジンの `run-stage` ディレクティブが `mode: subagent` を運ぶとき、`Task` 呼び出しを行うのはコンダクター（生きた `/aidlc` セッション）です。`Task` を許すと、エージェントが自分のサブエージェントを生み出し、フレームワークが防ぐために作られている委譲の連鎖が起きてしまいます。出荷されるすべてのエージェントが `Task` を禁止しており、あなたのものもそうしなければなりません。Kiro の投影は、この Claude 専用のフロントマターキーを取り除き、Kiro ネイティブのエージェントツール設定を通じて同じ「入れ子の委譲なし」の境界を強制します。それ以外の `disallowedTools` の値は、パッケージングを失敗させるか、プラグイン合成時にドロップとして記録されます。

**`tier` は作業の種類を表し、パッケージャーがそれをハーネスごとのモデル / effort のキーへ投影します。** コアのエージェントのフロントマターに生の `model:` や `effort:` を書くことはありません。それらは Git 管理外のローカルな `dist/<harness>/` ツリーと版付きのリリースランタイムにある投影の出力であり、`core/tools/aidlc-tiers.ts` のティア表から導出されます。曖昧な意図の解釈や、密な文脈の下でのアーキテクチャのトレードオフの比較衡量のように、下流へ波及する多制約の推論を仕事とするペルソナには `judgment` を選んでください。judgment エージェントは、明示的なモデル方針が上書きしない限り、セッションのモデルと effort の両方を継承します。明示された基準に照らして新しい入力を判断する、レビュアー型のペルソナには `balanced` を選んでください。`templated` は、出力が主にパターンに沿ったもので、手法がすでにエージェントのナレッジファイルに書き込まれている場合（デリバリー計画、CI/CD YAML、ランブックの足場など）に限って選んでください。方針が記録されていなければ、`balanced` のレビュアーティアは Claude Code では Sonnet を `medium` effort で使い、Codex と opencode ではセッションモデルを継承して medium の推論 effort を指定します。`judgment` と `templated` はセッションのモデルと effort を継承します。ウィザード既定の `balanced` プリセットはレビュアーティアとは別物で、Deciding・Reviewing・Writing up のモデルを変えずに、medium の effort を明示的に設定します。Kiro IDE、Cursor、Copilot はセッションを継承するので、ウィザードはそこではプリセットを記録せず、記録済みのプリセットはそのグループ effort の設定を表現できないと報告します。Kiro CLI のエージェントは、セッションモデルとプリセットの 1 つのセッション effort を継承します。迷ったら `judgment` を使ってください。投影表（とプロジェクトの `tier_cap`）であとからいつでもコストを下げられますが、低すぎるティアで作成したペルソナは、気づかないうちに推論が足りなくなります。完全な投影表と上限の上書きは [エージェントシステム](../reference/05-agent-system.md) を参照してください。

あと 2 つのフィールドは、振る舞いではなく表示を左右します。`display_name` は、ステータスラインが表示する人間可読のラベルです（アーキテクトは "Architect Agent" と表示されます）。`examples` は、エージェント→例の表に文書化された、推奨されるナレッジファイル名を列挙します — これらは*ユーザーに提示される提案*であり、ランタイムが読み込むことも、エンジンがディスクへ書くこともありません。

必須／任意の正確な表と共有設定のマトリクスは、[エージェントシステム: フロントマター契約](../reference/05-agent-system.md#frontmatter-契約) を参照してください。

## 見えていることと動いていることは別: 2 段階の真実

内面化すべきことが 1 つあります。ファイルを置くとエージェントは*見える*ようになり、ステージへ配線すると*動く*ようになります。両方の手順が必要で、片方だけだと、存在するのに一度も実行されないエージェントができあがります。

- **発見が「見える」を作ります。** `.claude/tools/aidlc-lib.ts` の `loadAgents()` が、次の呼び出し時に `.claude/agents/` のすべてのペルソナ `.md` ファイル（`aidlc-*` という名前か、`display_name`、`examples`、`tier`、`plugin` のいずれかを持つもの）を読み、メタデータのマップを導出します。コードの編集も登録の手順もありません — ファイルの存在が登録です。この時点からステータスラインはその表示名を描画でき、チームはスペースレベルの `aidlc/knowledge/<slug>-agent/` ディレクトリの下に標準を追加できます。
- **ステージへの結び付けが「動く」を作ります。** ステージは、フロントマターの `lead_agent` / `support_agents` フィールドで、リードと支援のエージェントを slug で名指しします（`.claude/tools/data/stage-graph.json` へコンパイルされます）。どこかのステージがあなたの slug を参照するまで、`run-stage` ディレクティブがそれを名指しすることはなく、したがってコンダクターがそのペルソナへ委譲することもありません。

これはフレームワークの中核にある非対称性を映しています — ステージがエージェントを名指しし、エージェントが自分のステージを名指しすることはありません。したがって、エージェントファイルだけでは設計上、不活性です。新しいペルソナを働かせるには、それを使うべきステージを編集してください。結び付けの仕組みは [ステージを追加する](02-adding-a-stage.md) にあります。

各エージェントは、`core/knowledge/aidlc-<slug>-agent/`（フレームワークの手法）に作成するナレッジディレクトリと、任意でスペースレベルのチーム側オーバーレイ `aidlc/knowledge/<slug>-agent/`（あなたの標準）とも対になります。スペースレベルの `aidlc/knowledge/` ディレクトリは自由形式で、ブートストラップ時点では空です。中身ができたときに、チームがエージェントごとのサブディレクトリを作ります — エンジンが雛形を作ることはありません。2 層のナレッジの流れは [チームナレッジ](07-team-knowledge.md) で扱います。

## 手順

リファレンスのレシピをなぞって、最初から最後までの流れを示します。

1. **エージェントファイルを作る** — 必須のフロントマターを備えた `core/agents/<slug>-agent.md`: `name`、`display_name`、`examples`、`description`、`disallowedTools`（`Task` を含む）、`tier`。任意の `tools:` 許可リストはペルソナを絞ります。省略すればセッションのツール一式を継承します。任意の `maxTurns: <n>` はエージェントのターン予算を上限付けます — Claude Code では拘束力があり、opencode ではネイティブの `steps:` キーへ投影され、Codex CLI・Cursor・GitHub Copilot・Kiro の両サーフェスでは不活性（ペルソナの散文のみ）です。これらはエージェントごとの上限キーを公開していません（Codex の TOML の出力はペルソナのフロントマターの引用を書き換え、kiro のエージェント JSON はそのキーを決して受け取りません — スキーマが未知フィールドでフェイルクローズします）。今日それを出荷しているのは、レビュー専用の 2 エージェントです（対の慣習はレビュアーペルソナの `## Turn Budget` 節を参照）。本文は出荷ファイルの構造（Core Responsibilities、Collaboration、任意の Memory Focus、Key Principles）に合わせて書いてください。
2. **ナレッジファイルを追加する** — ペルソナが起動時に読み込むべき手法を、`core/knowledge/aidlc-<slug>-agent/` の下に置きます。
3. **ステージへ配線する** — それがリードまたは支援する各ステージファイル（`core/aidlc-common/stages/<phase>/<slug>.md`）のフロントマター `lead_agent` / `support_agents` へ slug を追加し、`bun scripts/package.ts`（インストール済みのツリーでは `aidlc engine graph compile`）で再生成して `stage-graph.json` を作り直します。`stage-graph.json` を手で編集してはいけません。ビルド成果物であり、次のコンパイルが手作業の変更を上書きします（[ステージを追加する](02-adding-a-stage.md#4-ハーネスを再生成して-stage-graphjson-を再コンパイルする) を参照）。この手順が、エージェントを動くようにします。
4. **チームナレッジのディレクトリを文書化する** — チームが自分の標準をスペースレベルの `aidlc/knowledge/<slug>-agent/` の下に追加することを書き添えます。エンジンはこのディレクトリを作りません。中身ができたときにチームが作ります（スペースの `aidlc/knowledge/` は自由形式で、ブートストラップ時点では空です）。
5. **手で保守されているドキュメントの表を更新する** — フェーズ参加マトリクスとエージェント→例の表は、自分では再生成されません（下記「自動では検証されないこと」を参照）。

発見・intent-create・ステータスラインの確認コマンドを含む完全なレシピは [貢献: エージェントを追加する](../reference/11-contributing.md#エージェントの追加) にあります。エージェントを追加するのではなく、既存のエージェントのツール・ティア・ステージ割り当てを変えるには、[エージェントシステム: エージェントを変更する方法](../reference/05-agent-system.md#エージェントの直し方) を参照してください。

### 自動で検証されること

- `loadAgents()` は、次の呼び出し時に `.claude/agents/` の新しいペルソナ `.md` ファイルを発見します — コードの編集も登録も不要です。ペルソナとは、`aidlc-*` という名前のファイルか、フロントマターに `display_name`、`examples`、`tier`、`plugin` のいずれかを持つファイルです。そこにあるそれ以外のファイルはホスト自身のエージェントであり、手を付けません。
- ペルソナの `name` または `display_name` が欠けていると、パーサーはファイル、欠けているフィールド、そして（`aidlc-*` という名前でないファイルでは）それをペルソナとみなしたキーを名指しして例外を投げます。
- エージェントは slug のアルファベット順に返されるため、発見の順序はどのプラットフォームでも同一です。
- インテントの作成が、空のスペースレベル `aidlc/knowledge/` ディレクトリを作ります。エージェントごとのサブディレクトリや README をシードすることはありません。
- ステータスラインは、導出されたメタデータから表示名を描画します。

### 自動では検証されないこと

- **ステージグラフへの参加。** `stage-graph.json` はエージェントを slug で参照します。そこへ配線せずにエージェントを追加すると、存在はするが決して実行されません。発見と有効化は別の手順です。
- **ナレッジファイルの存在。** `examples` は、エージェント→例の表に文書化された推奨ファイル名です — 何かがそれを作ったり確認したりすることはありません。実際の内容は `aidlc/knowledge/<slug>-agent/`（スペースレベルのナレッジディレクトリ）の下に置きます。
- **手で保守されているドキュメントの表。** [エージェントシステム](../reference/05-agent-system.md#フェーズ参加) のフェーズ参加マトリクスと、ナレッジ README テンプレートのエージェント→例の表は、手で編集します。エージェントを追加するのと同じ変更の中で更新してください。
- **エージェントファイルの本文。** パースされるのはフロントマターだけです。本文の散文はエージェント自身が起動時に読むため、出荷される 14 個に合わせて丁寧に書いてください。
