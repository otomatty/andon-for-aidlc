# ルールと学習ループ

ルールは、あなたのチームがすべてのワークフローへ持ち込む常設の決定です — それが無ければ実行のたびに説明し直すことになる「いつもこうする」です。ハーネスエンジニアとして、ルールの作成方法は 2 つあります。ルールファイルを直接編集するか、**学習ループ**にワークフロー中の訂正を永続的なルールへ昇格させてもらうかです。この章は、ユーザーガイドの [ルールと学習ループ](../guide/09-rules-and-the-learning-loop.md) の章に対する、作成側の相棒です。あちらはループを概念として扱い、銀行の例を最初から最後まで辿ります。ここでの焦点は運用面です。何のためにどのファイルを編集するのか、ルールを重ねたとき厳密加算モデルはどう振る舞うのか、そして一度きりの修正が常設のルールになるようループをどう回すのか。

ルールは制御ループのフィードフォワード側です — エージェントが作業する*前に*読む散文です。[センサー](06-sensors.md) はフィードバック側 — 書き込みの*後に*発火する決定論的な検査です。ルールは自分の相棒としてセンサーを名指しできます。この 2 つの半分は、対になるよう設計されています。

## 5 つの層と、編集するファイル

ルールは `core/memory/`（スペースメモリ層に対する、作成されるソース）配下の Markdown ファイルとして、スコープごとに 1 ファイル存在します。`scope:` というフロントマターのフィールドはありません — この実装はスコープをファイル名から導出するため、あなたが選ぶファイル*こそ*が、作成対象のスコープです。

| こういう範囲に適用したいルール… | 編集するファイル | スコープ |
|---|---|---|
| 組織のすべてのプロジェクト | `org.md` | org（フレームワーク既定） |
| チームが動かすすべてのプロジェクト | `team.md` | team |
| このプロジェクトだけ | `project.md` | project |
| 1 つのフェーズのすべてのステージ | `phases/<phase>.md` | phase |

4 つのフェーズファイルは `phases/ideation.md`、`phases/inception.md`、`phases/construction.md`、`phases/operation.md` です（initialization はブートストラップ専用で、ルールファイルを出荷しません）。5 つ目の層 — ステージごとのルール（`aidlc-stage-<slug>.md`）— は将来のリリースのために予約されており、まだ作成できません。

どのファイルへ手を伸ばすかは、2 つの判断で決まります。

- **`org.md` はフレームワークが出荷するものです。** すべてのプロジェクトが継承する既定 — trunk ベース開発、ウォーキングスケルトンの方針、スコープごとのテスト姿勢 — を担います。上流のものとして扱ってください。ほとんどのハーネスエンジニアはこれに手を触れず、team か project で作成します。
- **project スコープは永続的な逸脱のためのものであって、何でも置く場所ではありません。** `project.md` へ手を伸ばすのは、*このプロジェクト*がチーム全体の実践から安定して外れるときだけにしてください — チームが squash するところをリベースする monorepo、テスト下限を飛ばすレガシープロジェクトなど。そのルールがチームの動かすすべてのプロジェクトで役に立つなら、それは `team.md` に属します。

各ファイルは、話題ごとの見出し — `## Way of Working`、`## Testing Posture`、`## Deployment`、`## Code Style` など — の下に置かれた素の散文です。ルールを追加するには、それが属する見出しの下に箇条書きを 1 つ足します。ファイル名からスコープへの完全な対応表と解決器の仕組みが規範となる契約です: [ルールシステム § ファイル名から導出するスコープ](../reference/08-rule-system.md#ファイル名から導出するスコープ) と [§ 配置](../reference/08-rule-system.md#配置)。

### リポジトリ全体で Guard Policy を固定する

これらのファイルの見出しのうち 1 つは、散文ではなく構造化された設定として読まれます: `## Guard Policy` です。これは、このスペースでの作業に対してガードがどこまで退くかを、2 つの面で決めます。1 つ目は、人が何かを承認または確認したあとに入力が変わったとき（承認後に編集された計画、レビュー後に編集されたレビュー済みの文書、現在の要約確認なしに保存された出力）に何が起きるかです。`strict` はその承認をやり直させ、`relaxed` と `off` は変更を一度記録し、人に 1 行で伝えて続行します。計画の承認後に動いたワークスペースのソースは、どの値でも記録して続行します。2 つ目は、どの権限フェンスを維持するかです。`strict` は何も下げず、`relaxed` は `plan-approval` と `review-freeze` を下げ、`off` はその 2 つに加えて `state-transition` と `reviewer-scope` を下げます。`human-presence` がこの値で下がることはありません。既定では、各インテントはそのスコープの値を取ります。チャットから下げるには、本人が自分の言葉で頼んでコンダクターが設定コマンドを実行するか、切り替え（`/aidlc --guard-policy relaxed` や `guard policy off`）を入力し、その行に対してエージェントが同じ設定コマンドを実行します。全員に対して `strict` を固定するには、`team.md`（または `org.md`、1 つのプロジェクトだけなら `project.md`）の見出しの下に 1 行置きます。

```markdown
## Guard Policy

Mode: strict
```

どこかの層にある `Mode: strict` は、スコープの既定値とインテント自身の行より優先します。そのうえでチャットやフラグによる `relaxed` や `off` への切り替えは、このファイルを名指しする一文とともに拒否され、実行中のインテントに対する次の管理対象の検査が、このファイルを出所とする `GUARD_POLICY_SET` 行として変更を記録します。ここでの `Mode: relaxed` と `Mode: off` は、値がスコープから来ているすべてのインテントのポリシーを設定し、宣言している層のうちもっとも狭いものが勝ちます（`project.md`、次に `team.md`、次に `org.md`）。本人が 1 つのインテントに設定した値は、そのまま保たれます。セクションを空のままにしても何も変わりません。それ以外の値は、ファイルと許される 3 つの値を名指しする検証エラーになります。この行は `## Testing Posture` と同じ `Field: value` の文法で読まれ、コメントアウトされた行も対象です。HTML コメントの中の `Mode:` は何も宣言しません。

`strict` を保持する層は `/aidlc config set guard.<fence> off` を拒否し、その拒否でメモリファイルを名指しします。また、その行がある間は、以前に下げたフェンスを強制的に元に戻します。保存された `Guards Off` の項目は残り、メモリの行が strict でなくなってから再び効きます。マシン全体のキルスイッチは引き続き優先し、フェンスを `on` にすることは常に許されます。

廃止された見出し `## Change Control` も 1 リリースの間は読まれるので、メモリファイルが改名より前のスペースもそのまま動きます。1 つのファイルに両方があるときは、新しい見出しのセクションが優先します。

## 厳密加算: 層は積み上がり、どれも黙って上書きしない

チェーンは現在 4 つの層を通して解決され、5 つ目は予約されています。

```
org -> team -> project -> phase      (stage: reserved, not authorable yet)
```

モデルは**厳密加算**です。適用されるすべてのルールが、エージェントの文脈に一度に現れます — 実行時に落とされたり抑制されたりするものはありません。org の既定、team の実践、project の特殊化が連結され、対応するフェーズのルールは、ステージが既にフロントマターで `phase:` を宣言しているために付随します（ステージが他のあらゆるものをインポートするのと同じ、プル型の作成方向です）。各ステージにどのファイルが適用されるかは、グラフのコンパイル時にそのグラフノードへ焼き込まれ、ランタイムがチェーンを歩き直すことは決してありません。選ばれたファイルの現在のテキストは、各ステージの配信の前に読まれます（[学びは次のステージの配信から効く](#学びは次のステージの配信から効く) を参照）。[ルールシステム § 厳密加算の実行時モデル](../reference/08-rule-system.md#厳密加算の実行時モデル) と [§ 5 層の継承](../reference/08-rule-system.md#5-層継承) を参照してください。

作成者としてのあなたにとって、これが意味するのは次のことです。`overrides:` ブロックも、設定すべき `enforcement:` キーワードもありません。狭い層が広い層に対して静かに勝つことはありません。代わりに、あなたが書いたすべての層が、エージェントの視界に同時に存在します。これは作成の仕方を変えます — ルールは、適用されるべきスコープで肯定的に述べ、上位の層を抑制するスイッチへ手を伸ばすのではなく、それらと積み上がることを信頼します。

### 競合は、学習の書き込み前に検査されるのであって、実行時に解決されるのではない

実行時に何も上書きしないため、より広いスコープのルールと*矛盾する*ルールは、解決器がほどけない問題になってしまいます。学習ループのプロトコルは、選択が決定論的なライターへ到達する前に、オーケストレーターへセクション単位の LLM 検査を実行させることでこれに対処します。ある `## 見出し` の下に team または project スコープの学習が追加されようとしているとき、オーケストレーターは提案されたテキストを `org.md` の同じ見出しと比較します。矛盾を見つけると、org の文を提示し、3 つの選択肢 — **修正**、**スキップ**、org ルールの所有者への**エスカレーション** — を示します。競合が無いか、ユーザーがエスカレーションした選択だけが先へ進みます。project 層の書き込みは org に対してのみ検査します。team と project の差は正当なプロジェクト特殊化であって、方針違反ではないからです。

決定論的な `aidlc-learnings.ts persist` ライターは `org.md` を読みませんし、この比較を独自に強制することもありません。受け取った選択をそのまま受け入れます。この検査は監査上の補助であって、強制の境界ではありません。もう 1 つの受け入れゲートは practices-discovery ですが、そちらは org 競合の検査を実行しません。その昇格は、ユーザーの確認によって正当化される、決定論的なセクション置換だからです。project のルールが `Mandated` または `Forbidden` の下に追記されるのは、生成される `(affirmed YYYY-MM-DD)` の接尾辞を無視したうえで、同じテキストがそのセクションに無い場合だけです。変わっていないルールを再確認しても、既存のテキストと日付は保たれます。事後の状態は、読み取り専用の `/aidlc --doctor` の 2 行が可視化します。**rule-drift** の行は、team または project の内容が、内容のある org の見出しと重なる箇所を（人間が確認すべき矛盾候補として）示し、ライフサイクル上 stale なファイルは stale-suppressed として別途報告されます。**paired-coverage** の行は、実際に解決されるセンサーを名指ししているルールの数を報告します。どちらも助言であり、終了コードを変えることはありません。[ルールシステム § ルールドリフト検出](../reference/08-rule-system.md#ルールドリフト検出) を参照してください。

## 学習ループを回す

ルールが作成されるもう 1 つの道では、あなたはファイルを一度も開きません — ワークフロー中にエージェントを訂正し、ゲートでその訂正を確認すると、フレームワークが代わりに書いてくれます。それが学習ループです。ほとんどのステージ実行は何も追加しませんが、それが健全です。ループが関わるのは、本人があるステージでエージェントを正したとき、または次回のために何かを残すようエージェントに頼んだときだけです。

仕組みは [ユーザーガイドの章](../guide/09-rules-and-the-learning-loop.md) で扱っています。ハーネスエンジニアの視点では、ループが何を生み、それがどこへ着地するかが要点です。

1. **ステージ中、日誌が記録する。** コンダクター（有効なステージを実行している、生きた `/aidlc` セッション）は、`<record>/<phase>/<stage>/memory.md`（インテントの記録ディレクトリ `aidlc/spaces/<space>/intents/<YYMMDD>-<label>/` の下）に観察ログを保ち、Interpretations、Deviations、Tradeoffs、Open questions の 4 見出しの下にエントリを置きます。これは自動で作成・維持されるものであり、手で編集してはいけません。これはエージェントの推論についてのステージの記録であり、その中身が本人に提示されることはありません。
2. **訂正については 1 回だけ尋ねる。** 本人が次回も通用するような形でエージェントを正したステージ（Request Changes、またはエージェントの作業中に本人の言葉で訂正したもの）では、承認ゲートの前に、エージェントが `Yes, for this project`、`Yes, for the team`、`No` を添えて「You asked me to <their change>. Keep that for next time?」と尋ねます。何も訂正されていなければ、何も尋ねません。本人がはっきり残すよう頼んだメモは、質問なしで残されます。ユーザーガイドに [その見た目](../guide/09-rules-and-the-learning-loop.md) があります。
3. **本人が残すものを書き込む。** 残された訂正は、日付付きの実践の行として着地します。本人がファイルパスや見出しを選ぶことはありません。本人の選択がファイルを決め、エージェントが見出しを振り分けます。

### 残した学びの着地先

確認された学びは実践*そのもの*です。practices-discovery が確認するのと同じスペースメモリのファイル（`aidlc/spaces/<active-space>/memory/team.md` / `memory/project.md`）に着地し、別途 `*-learnings.md` という面はありません。本人の選択がファイルを決めます。

| 本人の選択 | 着地先 | 監査イベント |
|---|---|---|
| Yes, for this project（および本人が残すよう頼んだメモ） | `aidlc/spaces/<active-space>/memory/project.md` | `RULE_LEARNED` |
| Yes, for the team | `aidlc/spaces/<active-space>/memory/team.md` | `RULE_LEARNED` |
| No | 何も書かれません | なし |

既定のスコープは、もっとも狭い **project** です。**Yes, for the team** は、その学びがこのプロジェクトを越えて当てはまるときに `memory/team.md` へ広げます。org へ広げる道はありません。org の実践はフレームワークが出荷するか、別のプロセスで組織が作成するものであり、ループが org スコープへ書くことは決してありません。既定を狭く保つことで、1 つのプロジェクトでの驚きが、うっかり組織全体のルールになるのを防ぎます。学習ループと practices-discovery は、2 つの異なるライフサイクルでこれら同じファイルへ書き込みます。ループは日付付きのエントリを 1 件ずつ追記し、practices-discovery はセクションまるごとを確認します。解決器は、org → team → project → phase というきれいな整数のチェーン上でファイルを並べます。

### 学びがルールではなく検査であるとき（`SENSOR_PROPOSED`）

取っておく価値があるものが、*繰り返し行っている手作業の検査*であることもあります — あるステージの出力について、同じ抜けをずっと目視で確かめている、というような場合です。ゲートでその種の学びを確認すると、フレームワークはそれをルールではなくセンサーのバインディングとして扱います。2 つの書き込みをアトミックにインストールします。`.claude/sensors/` の下にセンサーマニフェストの雛形を作り、発端となったステージの `sensors:` インポート一覧へ新しいセンサーの ID を追記し、`SENSOR_PROPOSED` の監査行を残します。これが、フレームワークのリリース以外でステージファイルに対して認められている唯一の編集です — 増えるのはインポート一覧だけで、ステージ本文には決して触れません。そこから先は、[センサー](06-sensors.md) を使って手でマニフェストを肉付けします — ループはバインディングの雛形を作り、検査はあなたが作成します。

### 学びは次のステージの配信から効く

ゲートで捕まえた学びは、すでに選ばれているルールファイル（`project.md` または `team.md`）に着地し、エンジンは各ステージの配信の前に、選ばれたファイルのテキストを読み直します。そのためルールは、現在の実行の次の該当ステージと、それ以降のすべてのワークフローでエージェントに届きます。待たされるのは選択そのものです。まったく新しいルールファイルがディレクトリ走査に入り、新しいセンサーがバインドされるのは、次にステージグラフがコンパイルされたときだけです。

手で作成する場合も同じです。ワークフローの途中で `team.md` を編集すると、進行中の実行の次のステージの配信に届きます（すでに実行したステージに遡って変えることはありません）。センサーの構成はルールのテキストとは異なります。その一部はコンパイル済みのグラフにあり、一部は発火時に読み直されます。その分かれ方は、書き込みフック、ゲートの経路、インストール形態によって違います。センサーの編集（新しいセンサー、またはすでにバインドされたものへの変更）を予測どおりに効かせるには、ステージグラフを再コンパイルしてください。再コンパイルでも届かない例外が 1 つあります。ネイティブインストールでは同梱センサーのワーカーが ID で選ばれるため、同梱マニフェストの `command` を編集しても実行される内容は変わりません。そこで検査を変えたいなら、独自のセンサー ID が必要です。
