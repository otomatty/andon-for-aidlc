# Construction とスウォーム

Construction は、AI-DLC が実際にものを作る場所です — ユニット単位のステージが走り、**スウォーム**がその作業を多数の Unit へ一度に展開しうる場所です。同時にここは、「何を、どう形づくれるのか」というもっともきれいな答えのために、どのつまみが誰のものかを正直に見分ける必要がある部分でもあります。ここにあるレバーのいくつかは、他のあらゆる章が教えるのと同じくデータとして作成する、ハーネスエンジニアであるあなたのものです。他のつまみは、ゲートに立つ人間と、実行を起動する作業者のものです。この章はそのすべてを辿り、線を正確に引きます。おかげであなたは正しい面へ手を伸ばし、あなたのものではないつまみを押し続けずに済みます。

貫く筋は、本ガイドの他の部分と同じです。あなたは `core/` 配下の**データ** — ルール、ステージ、センサーの検査コマンド — を編集して Construction を作り替えるのであって、コードを編集することは決してありません。Construction が違って感じられる理由は、もっとも目に見える 2 つの振る舞い（自律の付与、スウォームのドライバー）が、意図的にデータファイル*ではない*関心事に支配されているからです。それを認識することが、存在しない設定を書いてしまうのを防ぎます。

---

## 3 つの関心事、3 人の所有者

フレームワークの設計原則は、あらゆる決定を「それがどんな種類のものか」で分けます。決定性はツールに属し、知識はエージェントに属し、判断は人間に属します。Construction のスウォームは、その分割を具体にしたものであり、どれか 1 つのつまみに触れる前に全体像を持っておく価値があります。

| Construction における関心事 | 所有者 | どこに住むか |
|---|---|---|
| チームの自律**姿勢**（常設の既定） | あなた（ハーネスエンジニア） | `core/memory/{team,project}.md` のルール（データ） |
| どの Unit が並列**可能**か | あなた（ハーネスエンジニア） | `units-generation` ステージとその依存 DAG（データ） |
| スウォームが信頼する**収束の検査** | あなた（ハーネスエンジニア） | あなたのプロジェクト自身のビルド／テストコマンドと、保護された仕様（データとプロジェクト設定） |
| このプロジェクトに対する実際の自律の**付与** | 人間 | 実行時の明示的な提示、またはオンデマンドの依頼 |
| スウォームの**ドライバー**選択 | 作業者 | `AIDLC_USE_SWARM` 環境変数 |
| 収束の**判定**、マージバック、監査 | ツール | `aidlc-swarm.ts`（コード → 開発者リファレンス） |

「あなた」と記された 3 行が、この章の本体です。残りの 3 つは、あなたのデータが形づくるランタイムを理解する必要があるために扱いますが、どれもあなたが作成するものではありません。

## 自律の姿勢 — ルールとして書く、あなたの本当のレバー

常設の推奨は `core/memory/org.md` の `## Walking Skeleton` の見出しの下にあり、`team.md` と `project.md` で精緻化されます。ソースを生成する新しいソロ Unit のワークフローは、互いに独立した 3 つの設定を記録します。

| 設定 | 新しいワークフローの既定 | 意味 |
| --- | --- | --- |
| `Construction Checkpoints` | `enabled` | 完了したソロ Unit を、現在の証跡を使って検証・承認する |
| `Construction Iteration` | `unit-major` | 1 つの Unit の適用対象ステージを終えてから次の Unit へ進む |
| `Construction Execution` | `serial` | 直列にビルドする。明示的なスウォーム実行には stage-major が必要 |

`Construction Verification Command` は、インテント単位の別の Runtime State フィールドで、自動の既定値はありません。Delivery Planning が実際のプロジェクト検査を提案し、型付きのセッターが書き込む前に人間の承認レシートを記録します。実行できる検査をまだ持たないグリーンフィールドのプロジェクトは、最初のチェックポイントまで延期できます。同じコマンドがすべての Unit／バッチのチェックポイントで再利用されます。選択や変更には[記録済みコマンドの手順](../guide/12-cli-commands.md#construction-verification-command-record-human-authorization)が必要で、汎用の `state set` や自律の付与では決して行いません。
コマンドを提示する前に、ハーネスのファイル書き込みツール（Write/edit）で `<record>/verification-command.txt` へ書き込みます。シェルの `echo` や heredoc は決して使いません。リポジトリ由来のコマンド文字列をシェルの行へ埋め込んではなりません。承認前に置換が実行されうるからです。`log decision`、`log answer`、`state set-construction-verification-command` には `--command-file verification-command.txt` を使います。2 つのログ呼び出しはどちらも自分のセッションを見つけるため、`--session` は渡さず、セッションを調べることもしません。`decision` ツールの JSON 出力の `command` フィールドから、正規化された完全なコマンドをそのまま検証コマンドの質問のコードスパンへ写します。決して省略しません。コマンド内のバッククォートを保てる区切りを選びます。人間は `<record>/verification-command.txt` を開くこともできます。正規化されたコマンドは、空白でない 1 行・最大 1024 文字です。制御文字と表示を偽装する文字（ゼロ幅文字や双方向制御を含む Unicode の書式文字、行／段落区切り、ノーブレークスペース U+00A0）は拒否されます。
人間の **Approve** / **Request Changes** の回答を記録します。回答はそのチャットでも、それが最新の質問である間は新しいチャットでもかまいません。レシートを許可するのは **Approve** だけで、無関係な回答、**Request Changes**、別の質問への回答は許可になりません。人間が選んでいない限り、`--details "Approve"` を書いてはなりません。

チェックポイント方針には、ソロのオーナーシップ、実際に空でない Unit DAG、そしてソースを生成するユニット単位ステージが含まれていることが必要です。設計のみの作業と Unit の無い作業は、既存のステージの流れを保ちます。skeleton-on では、最初の DAG Unit を、動作する最小の統合スライスとして計画します。この Unit は適用対象のユニット単位の設計ステージとコード生成をすべて終え、実際のエンドツーエンドの検査に通り、人間のスケルトン承認を受けてから後続の Unit が始まります。stage-major が選ばれていても同じです。最初の設計ステージのレビューだけでは、動作するスケルトンにはなりません。`bolt-plan.md` の計画上のマーカーは、実際の DAG の順序を変えません。

skeleton-off では、エンジンは Construction の開始時に **Continue automatically** / **Review each checkpoint** を提示します。skeleton-on では、実際のスケルトンのチェックポイントの後にその選択を提示します。コンダクターは `offer_autonomy` に従い、人間の選択を `bolt set-autonomy` で記録し、選択が分かった後ではしごを繰り返し尋ねることはしません。オンデマンドの付与／取り消しの依頼は引き続き使えます。自律は通常の完了承認を変えるものであり、人間の Plan Approval、検証コマンドの選択、有効な要約確認を肩代わりすることも、失敗した検査を通すこともありません。
要約確認が適用されるのは `directive.ceremony.summary_confirmation === "on"` の場合だけです。

スウォーム実行を選ぶには、明示的に stage-major を選び、そのうえで `Construction Execution: swarm` を選びます。ガイド付き（`gated`）と自動（`autonomous`）のバッチ完了はどちらもサポートされます。自律を付与しても順序や実行方式は変わりません。unit-major は直列のままで、矛盾するスウォーム設定を拒否します。新しいフィールドを持たない旧来のワークフローは、既存の最初のステージのレビューと、自律に基づくスウォームのルーティングを保ちます。unit-major の下では、それらの遅延したステージ承認は 1 つの質問になります。チーム所有の作業は `unit_gate` と、独自の per-stage または unit-end の承認のリズムを保ちます。

推奨は、[ルールと学習ループ](05-rules-and-the-loop.md) のルールの層を通じて形づくります。実際の付与を選ぶのは引き続き人間です。たとえばチームは次のように推奨できます。

```markdown
## Walking Skeleton

Until our integrated checks have proved reliable, recommend **Review each
checkpoint**. Review the working first slice and each ordinary completed Unit
or swarm batch before proceeding. Plan Approval, verification command selection,
and any enabled summary confirmation remain human decisions even when we later select
**Continue automatically**.
```

信頼できるプロジェクトでは、同じ見出しで、スケルトンが検証された後に **Continue automatically** を推奨できます。ルールが提供するのは案内であって、記録された自律の付与や、スウォーム実行への暗黙の切り替えではありません。

## チェックポイントと承認の証跡

`run-stage` が `construction_checkpoint` を運ぶとき、Unit の本体とレビューはすでに実行されています。`rereview` フィールドは、レビュー後に変更されたコードや文書の再確認 1 回を指し、尋ねずに最初に実行します（Guard Policy が `strict` の場合だけ。`relaxed` と `off` では変更は受け入れられ、承認はそのまま有効です）。これを本体／レビュアー／ゲートのロジックより前にルーティングします。`command_authorized: false` の場合は、どの `verify` よりも前に検証コマンドの質問を尋ね、人間の decision／answer／セッターの手順を完了してから、`next` を再実行します。
それ以外の場合は `bolt checkpoint --action verify --unit <unit> --kind <unit|skeleton>` を実行します。これは記録済みの、人間が許可したコマンドを実行するもので、verify 時に選ばれた文字列を実行するのではありません。承認するのは現在の検証済みの証跡だけとし、承認の質問には「Verified with `<full command>` (exit 0)」を表示します。その際、ツール出力の正規化された完全な `verification_command` を省略せずに使います。スケルトンは常に人間を必要とし、通常の Unit は `human_required` に従います。
`swarm_checkpoint` も同様に、次のバッチの前に完了したバッチをルーティングします。
`verify` が `verified: true` を報告し、現在のチェックポイントが `ready: true` になった後でだけ、`aidlc engine bolt checkpoint --action ask --unit "<unit>" --kind <unit|skeleton>` で人間の Unit／スケルトン承認の質問を開きます。`ask` は準備できていない、または未検証のチェックポイントを拒否します。人間に尋ねるバッチの質問では、status が `ready: true` を報告した後でだけ `aidlc engine bolt swarm-checkpoint --action ask --batch <N> --units "<Units>"` を実行します。
そのうえで **Approve** / **Request Changes** を提示して待ちます。このチェックポイントの質問に対する人間の正確な回答が、対応する操作を許可します。そのチャットでも新しいチャットでもかまいません。自分の質問を持たない新しいチャットの回答は、別のチャットが尋ねたチェックポイントの質問への回答として保持されます。ただし、それが最新の質問で、まだ開いている間に限ります。無関係な回答、エージェント自身の言葉、別の質問への回答は許可になりません。これらのコマンドは自分のセッションを見つけます。人間が選んでいない `--user-input` は決して渡しません。同意は 1 回限りで、現在のチェックポイントのフィンガープリント、検証証明の ID、許可されたコマンドのダイジェストに結び付きます（バッチの質問はフィンガープリントと Unit ごとの `Command SHA-256` の集合に結び付きます）。
`verify` やスウォームの `finalize` を再実行すると、このインテントの開いているチェックポイントの質問と、取り込まれたチェックポイントの回答が、どのセッションのものでもすべて撤回されます。再検証し、`verified: true`（バッチではソースの着地後に `ready: true`）を確認してから、もう一度尋ねます。古い回答で新しい証跡を承認することはできません。自動承認（`human_required: false`）には `ask` も `--user-input` も不要です。人間による却下には、常にこの検証済みの質問と回答の手順が必要です。
承認／却下は `next` へ戻ります。1 つの Unit やバッチのために、コード生成ステージ全体を承認することは決してありません。完全な操作の形は[チェックポイントのコマンド](../guide/12-cli-commands.md#aidlc-engine-bolt-checkpoint--unitの検証と判断)を参照してください。

バージョン 3 のチェックポイント証明は、コマンドの SHA-256 と、表示ラベルとしての正規化された完全なコマンドを、生の出力ではなく出力のバイト数とダイジェストとともに保存します。それより前のバージョンの証明は、許可されたコマンドでの再検証が必要です。
検証ツールは、証明ファイルとともにツール所有の `CHECKPOINT_VERIFICATION_RECORDED` レシートを記録し、承認にはそのレシートが必要です。手書きの証明ファイルで Unit を検証済みにすることはできません。証明ファイルがまったく無いチェックアウト（新しいクローンや別のマシン）では、すでに承認済みで証跡が変わっていない Unit について、そのレシートが証明の代わりになるため、何も再実行されません。

`construction_policy.completion_only: true` と `human_completion_required: false` を運ぶ最終ステージのディレクティブは、記録済みの承認を整合させるだけです。本体、質問、レビュアー、学習のプロンプトを飛ばし、ユーザー入力なしで `awaiting-approval`、続いて `approved` を報告し、`next` を呼びます。証跡のエラーには、指定されたレビュー／レシートの修復が必要で、必要に応じて人間に相談します。検証をでっち上げたり、未検証のチェックポイントの承認質問をしたりは決してしません。

Plan Approval は、提示がまとめられていても個別に結び付いたままです。複数の Unit の計画が同時に準備できたとき、`next` はそれらを 1 つのエンジンの質問で尋ね、エージェントは人の選択を Unit ごとに記録します（`log answer --checkpoint plan-approval --units`）。各承認は、その Unit 自身の計画に結び付きます。「すべて承認」はすべての Unit を承認し、1 つの Unit を名指しした変更はその Unit だけを差し戻します。[CLI リファレンス](../guide/12-cli-commands.md#コード生成の計画をまとめて承認)を参照してください。

部分的な着地の後、`next` は残りの Unit を示し、有効な準備済みワーカーは元のグループの承認とワークツリーを保持します。続行する前に、その親とワークツリーの実行許可を確認します。`testing-posture verify` は、現在の承認、または下げられた plan-approval のフェンスの下での内容変更の継続に対して `execution_allowed: true`（exit 0）を使います。`ok: false` は、編集された内容が承認されていないことを引き続き意味します。元の承認の証跡は保持します。
許可された継続では、`reason` が作業を続けられる理由を説明し、`approval_reason` が診断の詳細を保持します。委任されたワーカーは、検証済みの親インテントのライブなフェンスを使うため、それを下げたり上げたりすると、すでに準備済みのワーカーにも次の確認時に適用されます。
出力された Unit の集合が小さくなったというだけで、最初の準備を繰り返してはなりません。失敗したときは引き続き人間の Retry／Abort の判断のために停止し、チェックポイントの Request Changes は新しい改訂を始めます。その改訂のネイティブな準備が記録されると、以降のディレクティブは追加の承認なしにそのワーカーを続行します。中断したセットアップの回復は、ワーカーに結び付いたレシートを置き換えるのではなく、現在の承認を再利用します。
1 つのワーカーを明示的に破棄するネイティブのレビュアーの Retry では、準備によって、記録されたコミット済みの承認済みベースラインを復元できます。別のワーカーの承認や保留中の作業は変わりません。破棄は現在のワーカーを特定していなければなりません。欠落しているだけでは回復の許可になりません。チェックポイントの改訂は `--resume-existing` の経路を保ち、最初のバッチは通常の準備を使います。

## 何が並列に走れるかを形づくる — Bolt-DAG

スウォームは作業を Unit へ展開するため、「何が同時に走れるか」は上流の inception において `units-generation` ステージが決めます。そのステージは `unit-of-work-dependency.md` を生成し（`core/aidlc-common/stages/inception/units-generation.md` が `produces: unit-of-work-dependency` を宣言します）、その成果物の中の必須の `yaml` フェンスブロックが、各 Unit とその `depends_on` 一覧を列挙します。

コンパイラはそのブロックを `runtime-graph.json` の `bolt_dag` ノードへ読み込みます。このノードは、エッジブロックが整形式かつ非循環である**ときにだけ**存在します。ブロックが無い、不正、循環している場合、ノードは丸ごと省かれます（[実行時グラフ](../reference/13-runtime-graph.md)、44 行目のスキーマ注記）。`bolt_dag` ノードは `batches` も運びます — すべての Unit の依存が先行するレベルで満たされるトポロジー的なレベルであり、あるバッチ内の Unit 同士にはエッジが無く、まとめて展開できます。

5 つの**ユニット単位**の Construction ステージは、それぞれフロントマターで `for_each: unit-of-work` を宣言します。

人間のチーム所有については、デリバリー計画で `Construction Iteration: unit-major` と `Unit Ownership: team` を組み合わせられます。その場合エンジンは、同じ DAG／成果物／レシートの証跡から `## Unit Progress` を導出し、ソロの経路の遅延した 1 回の承認の代わりに、per-stage または unit-end の Unit ゲートを使います。このチーム所有の経路は独自の方針を保ちます。ソロのオーナーシップは、記録された状態によって選ばれるチェックポイント有効の経路、または旧来の経路を使います。

| ステージ | 実行 |
|---|---|
| `nfr-requirements` | Unit ごとに 1 回 |
| `functional-design` | Unit ごとに 1 回 |
| `nfr-design` | Unit ごとに 1 回 |
| `infrastructure-design` | Unit ごとに 1 回 |
| `code-generation` | Unit ごとに 1 回 |

4 つの設計ステージについては、ユニット単位のカバレッジがさらに**種別でフィルタ**されます。各 Unit の `kind`（2.7 のエッジブロックでタグ付け）が、ステージの `produces_kinds` マップを通じて、その Unit が実際に負う produces 成果物を選びます。エンジンは run-stage ディレクティブの produces パスとカバレッジ検査の両方をその集合へ刈り込むため、`spec` の Unit はデプロイ文書なしで infrastructure-design を完了でき、`packaging` の Unit はファイル 0 個で functional-design を完了できます。タグの無い Unit は完全なマトリクスを保ちます。

（残る 2 つの Construction ステージ、`build-and-test` と `ci-pipeline` は、最後にすべてを対象として 1 回だけ実行されるため、ユニット単位の展開の一部ではありません。）

**この並列の面が存在するのは、`units-generation` が実行されるスコープだけです** — `enterprise`、`feature`、`mvp`、`classic`、`workshop` です。増分的なスコープ（`bugfix`、`refactor`、`security-patch`）と `poc` / `infra` / `express` は `units-generation` を決して実行しないため、エッジブロックを生成せず、`bolt_dag` を持たず、スウォームが展開する対象の無いまま Construction を単一パスで実行します。スウォームは、作業に実際の Unit DAG がある場所で形づくってください。Unit がゼロの実行は通常のステージ実行を保ちます。オンデマンドの承認の好みが DAG やスウォームを生み出すことはありません。

ここでのハーネスのレバーは間接的ですが、確かに存在します。**`units-generation` が捉える依存構造を形づくることで、何が並列化されるかを形づくります。** 相互依存の少ない粗い Unit を好むチーム向けの案内を書けば、より多くの Unit が同じバッチへ入り、同時に走ります。密で深く連鎖した依存は、作業を多数の小さなバッチへ直列化します。これに影響を与えるのは、`units-generation` ステージの散文と、アーキテクトエージェントが分解の際に読むルールを通じてです — 分解そのものは、エージェントが人間とともに行う知識の判断であり、それが書くトポロジーを、コンパイラがバッチへ変えます。

エッジブロックを `bolt_dag` へ変えるコンパイルとパースはコードであり、あなたが作成するものではありません。そのパーサーを形づくるのはコードの変更です → [開発者リファレンス](../reference/13-runtime-graph.md) を参照してください。

## 収束の配線 — 信頼される信号は、あなたのプロジェクト自身の検査

コード生成のスウォームが計画を迂回することはありません。`prepare` の前に、出力されるすべての Unit は、構造化された Testing Contract、Unit にスコープされたテスト指示、そして一致する承認フィンガープリントを含む、人間が承認した最新の計画を持っていなければなりません。最初の保護された prepare の前には、承認済みの親アプリケーションのソースもコミット済みで再現可能でなければなりません。ツールは、旧来の自律でも新しいチェックポイント方針でも、最初のワークツリーを作る前にすべての Unit を読み取り専用で検証します。承認済みのソースが未コミットなら、コミットして再試行する修復策を示して拒否し、その拒否による子は残しません。コミットは明示的な許可がある場合だけ行います。prepare も自律の付与も、あなたの代わりにコミットすることはありません。承認済みのインラインのスケルトンのソースは、後の並列バッチの前にこの明示的なコミットが必要です。各ワーカーは引き続き、承認された Unit のマーカー、契約のハッシュ、計画、指示を受け取ります。

却下されたバッチは、その却下の改訂に対する新しい Plan Approval の後、`prepare --resume-existing` で再開します。既存のワークツリーはソースを保持し、古いメタデータをアーカイブします。ネイティブなソースの着地で子が取り除かれた場合、ツールは検証済みの着地の証跡をもとに、すでに着地した親のソースから子を再作成できます。却下の改訂は保持され、古い承認で置き換えられることはありません。その証跡の無い子の欠落は拒否されます。マージされたすべての子が存在し続けると約束してはなりません。

スウォームのワーカーは、自分の Unit が収束したと主張できます。フレームワークがその主張を鵜呑みにすることは決してありません。権威ある信号は、審判が実行する、あなたのプロジェクト**自身の検査コマンド**です。終了コード `0` は本当に収束したことを意味し、それ以外の終了コードはまだであることを意味します。自律的な Construction のためにハーネスエンジニアが確保すべき、もっとも重要なことがこれです — プロジェクトが本当に実のある検査コマンドと保護された仕様を*持っている*こと。それによって初めて、スウォームは信頼して収束できる対象を得ます。

信号を担う面は 2 つあります。

- **検査コマンド。** あなたの Unit が完了したことを証明するもの — `npm test`、`pytest`、ビルドと lint のスクリプト、CI のローカル同等物など。審判はループ中に Unit ごとにそれを実行し、finalize でもう一度実行します。green の終了だけが、その Unit の作業をマージさせます。
- **保護された仕様ファイル。** 審判は、指定された `--test-file` を、フォークされた git のベースラインと比較する改ざん検知を行えます。したがってワーカーが、red の検査を green にするために「完了」を定義するテストを静かに弱めることはできません。Guard Policy が relaxed または off の場合、変更された保護ファイルは Unit を失敗させる代わりに `change_notices` で報告されます。受け入れ基準を符号化した仕様が存在し、それが指し示されているファイルであることを、あなたが担保します。

あなたのハーネスとしての貢献は、その両方を実のあるものにすることです。常に通る検査や、空の仕様は、スウォームに形だけの印を渡すことになります。`org.md` の `## Testing Posture` ルールは、選択された Test Strategy に、スコープごとの加法的な下限を組み合わせています（たとえば `mvp` / `feature` はカバレッジ 80% を加えます）。それらの下限を捨てずに実行のリズムを変えるには、`team.md` でより厳しい構造化された方法論／順序を作成します。

散文の側では、センサーが検査を補完します。`units-generation` が既にインポートしている `required-sections` と `upstream-coverage` のセンサーは、ゲートで成果物の形とカバレッジを検証します。[センサー](06-sensors.md) の筋力を使えば、プロジェクト固有の収束や必須セクションのセンサーを作成し、同じ抜けをずっと目視で確かめている Construction ステージへ結び付けられます。この 2 つはゲートで発火し、助言的です。追加したセンサーは、その `fire_on` の指定に従って書き込みのたびまたはゲートで発火します。ブロッキングのゲートセンサーは、指摘が修正されるか人が上書きするまでゲートを止めます（[センサー](06-sensors.md) を参照）。プロジェクトの検査コマンドは厳格な収束のゲートです。両者は 2 つの半分を担います。センサーは成果物の形を見張り、検査は Unit がマージしてよいかを決めます。

## ドライバーの継ぎ目 - `AIDLC_USE_SWARM`

スウォームが物理的にどう展開するかは環境変数で選ばれます。そしてこれが**作業者のつまみ**であることは、はっきりさせておく価値があります。`.claude/` のデータファイルではなく、`settings.json` にもありません（展開時にコンダクター側で読まれます）。あなたがこれを作成することはありません。あなたのデータが形づくるランタイムを知るために理解しておくのです。

| `AIDLC_USE_SWARM` | ドライバー | 振る舞い |
|---|---|---|
| 未設定、または `"1"` 以外 | サブエージェントの下限 | コンダクターが 1 メッセージの中で、Unit ごとに 1 つずつ、N 個の並列 `Task` 呼び出しを発行します。 |
| `"1"` | インラインの Dynamic Workflow | コンダクターが、Unit ごとのパイプラインと反復上限を JS が所有する `Workflow` を作成します。 |
| `"1"` だが Workflow ツールが利用不可 | 明示的に下限へ劣化 | コンダクターは下限へフォールバックし、`--degraded-from ultracode` を渡すため、審判が `SWARM_DEGRADED` を発行します。 |

どちらのドライバーも各 Unit の Code Generation（サブエージェントとして動く唯一のユニット単位ステージで、スウォームがディスパッチするのはこれです。ユニット単位の設計ステージはスウォームに含まれません）を実行し、同じプロジェクトの検査に対して収束します。違いは、並列の作業がどうディスパッチされるかだけです。暴走のバックストップは、スウォームツールの外側、ハーネスの **Stop フックの上限**（`core/hooks/aidlc-continue-workflow.ts` の `blockCap()` / `defaultBlockCap()` の対。`CLAUDE_CODE_STOP_HOOK_BLOCK_CAP` として公開）にあります。この自律 Construction の経路では既定の上限は **8 ブロック**です（対話時の既定は 2。明示的な `CLAUDE_CODE_STOP_HOOK_BLOCK_CAP` は両方を上書きします）。ドライバーの継ぎ目の契約は [スキルシステム § 6](../reference/17-skill-system.md#6-スウォームのレフェリードライバー継ぎ目ボルト-dag) にあります。

ドライバーとともに動くことのない判断が 1 つあります。失敗は自律モードにかかわらず、**常に停止して人間を再関与させます**（`aidlc-common/protocols/stage-protocol-construction.md` の「失敗時は停止して尋ねる」）。審判の `finalize` が終了コード 2 の封筒を返すと、コンダクターはバトンを人間へ返します。手放しモードは正常系のゲートを取り除きますが、失敗時の停止は大きく鳴らしたままにします。

## どこからがコードの変更になるか

線はきれいです。ここまでのすべて — 自律姿勢のルール、エッジブロックを生む Unit の分解、プロジェクトの検査コマンドと保護された仕様、補完するセンサー — は、`core/` またはプロジェクトの設定の下であなたが作成するデータです。コードに触れずに Construction を形づくれます。

スウォームの機構はコードであり、それを形づくるのは開発者リファレンスの領分です。

- **審判** `aidlc-swarm.ts` — 状態を持たない `prepare` / `check` / `finalize` の各サブコマンド。保護されたコード生成の prepare は、旧来の自律でも新しいチェックポイントでも、まず各 Unit の承認済み Testing Contract、フィンガープリント、コミット済みの親のソースを検証し、そのうえでワークツリーをフォークします。新しいワークツリーはそれぞれ、コミット済みかどうかにかかわらず、プロジェクトにあるとおりのインテントの記録（finalize が持ち帰る記録）から始まるため、ワーカーは自分の Unit の機能設計を読めます。`--resume-existing` は、子が残っている場合も、検証済みのネイティブなソースの着地の後に再作成が必要な場合も、却下された改訂を保持します。残りのコマンドは判定を実行し、マージ前に主張されたすべての Unit を再検証し（虚偽コンダクター防護）、レビュー済みのレコード成果物と束縛済みソースマニフェストをスナップショットして着地させ、ワーカーによる記録へのその他の編集（計画が更新する契約やビジネスルール）を、インラインのビルドが残すのと同じように行単位で主の記録へ取り込み、AIDLC メタデータのマージバックを直列化し、審判が所有する 6 つの `SWARM_*` イベントを発行します。git がマージできない記録の編集は、プロジェクト側のコピーをそのまま残し、その Unit のステージフォルダの `not-merged/` の下に保存され、1 行で伝えられます。その後コンダクターが、収束した各 Unit について `aidlc-worktree merge` を呼び出します。この別立ての不変なソースの着地が `SWARM_SOURCE_MERGED` を発行します。
- **エンジン** `aidlc-orchestrate.ts` — サブコマンドがちょうど 6 つ（`next`、`continue`、`report`、`park`、`team-board`、`wait`。`continue` は内部のステアリング転送用、`team-board` は Team Construction の読み取り専用クエリ、`wait` はディスパッチした作業を待つ、時間制限付きの読み取り専用の待機）の決定論的なルーターです。Construction のバッチがスウォームの対象になるかを決めます。
- **Bolt-DAG のパーサー** — エッジブロックを `runtime-graph.json` へ読み込むコンパイルの手順です。

3 つすべての規範となる契約は [スキルシステム § 6](../reference/17-skill-system.md#6-スウォームのレフェリードライバー継ぎ目ボルト-dag) にあり、`bolt_dag` ノードのスキーマは [実行時グラフ](../reference/13-runtime-graph.md) にあります。コンダクター自身の章は [オーケストレーター](../reference/03-orchestrator.md) です。

ユーザーガイドの [Construction の流れ](../guide/04-phases-and-stages.md#フェーズ-3-コンストラクション-construction) は、対象となるソースを生成するソロの経路を示します。実際に統合された Unit の検査と人間のスケルトン承認があり、提示された場合は **Continue automatically** / **Review each checkpoint** が続きます。また、旧来の最初のステージのレビューと、保持される設計のみ・Unit なし・チーム所有の経路も区別しています。自律の選択は、実行方式とは独立に、通常の完了承認を制御します。7 つの `SWARM_*` 監査イベント（審判からの 6 つと、ソースの着地からの `SWARM_SOURCE_MERGED`）は [状態と監査](../guide/10-state-and-audit.md) に整理されています。
