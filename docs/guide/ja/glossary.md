# 用語集

User Guide と Developer Reference で揃えている定義です。

---

| 用語 | 定義 |
| ---- | ---- |
| **エージェント (Agent)** | 配布されているペルソナ 14 体。領域の専門家 11、レビュー専用 2、適応型ワークフローのコンポーザー 1。コンダクターが、担当ステージ・レビュー・編成の役で起動する。 |
| **承認ゲート (Approval gate)** | 完了した作業（ステージ、検証済み Unit、完了した swarm バッチ）に対する判断。人間が必要なゲートは実際の回答を待つ。チェックポイント対応のワークフローでは、記録済みの許可のもとで通常の完了を自動承認できるが、Plan Approval、有効な要約確認、検証コマンドの選択、スケルトンの承認は人間の判断のまま残る。要約確認が適用されるのは `directive.ceremony.summary_confirmation === "on"` のときだけ。初期化と completion-only の記録処理は、人間への承認質問を増やさない。 |
| **自律モード (Autonomy mode)** | `Construction Autonomy Mode` に保存するunset / gated / autonomous。対象ワークフローのContinue automaticallyはautonomous、Review each checkpointはgated。通常の完了承認を制御し、実行順とswarmの選択とは別。Plan Approval、有効な要約確認、検証コマンド、スケルトン、失敗の判断は人間に残る。既存作業は従来の方針を維持。 |
| **ボルト (Bolt)** | 依存関係でつながる 1 つ以上の Unit にまたがる、Construction の計画上のデリバリースライス。Unit、その worktree、swarm バッチとは別物。Delivery Planning がグループ化、完了の定義（Definition of Done）、確信の仮説、所有者を記録する。実行時の順序は Unit DAG と記録済みの反復の選択に従い、`bolt-plan.md` はそれらを置き換えない。Build and Test と CI Pipeline は、完了した Unit の作業全体に対して 1 回だけ実行する。 |
| **成果物 (Artifact)** | ステージが作り、インテントのレコードディレクトリ（`aidlc/spaces/<space>/intents/<YYMMDD>-<label>/`）に置くファイル。大半は `requirements.md`、`code-summary.md`、`initiative-brief.md` のような Markdown 文書で、`traceability.json` のような JSON も少しある。 |
| **監査証跡 (Audit trail)** | レコードディレクトリの `audit/` にある追記専用ログ。クローンごとのシャード（`<host>-<clone>.md`）を、読む側がグロブして時刻順にマージする。イベント種別は 126。ISO 時刻付きで、意図から本番まで追える。 |
| **CLI ツール (CLI tool)** | この実装が実行する外部コマンド。ネイティブインストールでは何も要らない（**ネイティブチャネル** を参照）。コピー経路には `bun` が要る。Claude Code のツールとは区別する。 |
| **Claude Code ツール (Claude Code tool)** | Read、Write、Edit、Bash、Glob、Grep、Task、AskUserQuestion など、Claude Code 本体の能力。エージェントは既定でセッションのツール一式を継ぐ。任意の `tools:` 許可リストで狭められる。配布で禁じているのは `disallowedTools: Task` だけ。 |
| **Codex** | OpenAI Codex CLI ハーネス。現在の AI-DLC ハーネス配布の一つ。ソースビルドは `core/` + `harness/codex/` から無視されるローカル投影 `dist/codex/` を生成する。リリースは `runtime/codex/` に載せる。起動は `$aidlc`。[AI-DLC on Codex CLI](harnesses/codex-cli.md) を参照。 |
| **コマンド (Command)** | 人が打つ AI-DLC の起動。ハーネスのチャットコマンドはワークフローに `/aidlc`（Codex は `$aidlc`）。ネイティブの `aidlc` コマンドはプロジェクト、診断、プラグイン、マシンライフサイクルの経路を持つ。 |
| **コンパクション (Compaction)** | コンテキストが埋まったとき、Claude Code が古い会話を要約する処理。状態は `aidlc-state.md` と監査証跡で越える。 |
| **コンダクター (Conductor)** | `/aidlc` セッションそのもの（`SKILL.md`）。薄い転送ループで、**エンジン**に次を聞き、実行し（ステージ、質問、スウォームの展開）、結果を報告して繰り返す。実行の質は持つ。ルーティングは持たない。[Engine and Skill System](../reference/17-skill-system.md) を参照。 |
| **Construction Verification Command** | すべての Unit／バッチのチェックポイントで再利用する、インテント単位のプロジェクト検査。ツールが所有する `VERIFICATION_COMMAND_RECORDED` レシートが、人間の **Approve**（エージェントが読んだその人の返答で、正確な文言を保持する。尋ねたチャット、または新しいチャットでもそれが最後に尋ねた質問である間の返答）を、正規化・トリムした 1 行コマンドの SHA-256 に結び付け、その後に型付きの状態設定コマンドが記録する。無関係な返答、**Request Changes**、別の質問への返答はレシートを認可しない。状態フィールドだけでは実行は認可されない。Delivery Planning が提案するか、グリーンフィールドで先送りした場合は最初のチェックポイントで尋ねる。以後の変更にはすべて新しい人間のレシートが必要。証明に残すのはダイジェストと表示ラベルで、生のコマンド文字列は残さない。 |
| **制御ループ (Control loop)** | **ルール**（作業前に効く立ち振る舞い）と **センサー**（出力に対する決定論的検査）の対。ステージを操舵し、検証する。（**ハーネス**＝CLI 配布の意味とは別。昔はどちらも harness と呼んでいた。） |
| **コピー経路 (Copy channel)** | `aidlc-copy-runtime-X.Y.Z.tar.gz` の `runtime/<harness>/` 全体を手動コピーする導入方法。Bun が必要で、ネイティブの aidlc 実行ファイルは不要。 |
| **コア (Core)** | 手で書く、ハーネス非依存の正本 `core/`。エンジン、ステージ、エージェント、ルール、スコープ、センサー、ナレッジ、フック、セッションスキル。各ハーネス配布はここから生成する。直すのはここ。`dist/` は触らない。 |
| **Cursor** | Cursor（cursor.com）ハーネス。現在の AI-DLC ハーネス配布の一つ。ソースビルドは `core/` + `harness/cursor/` から無視されるローカル投影 `dist/cursor/` を生成する。リリースは `runtime/cursor/` に載せる。IDE と CLI（`agent`）が同じ木を読む。14 ペルソナは `.cursor/agents/` のネイティブサブエージェント。オーケストレータ、ランナー、ユーティリティショートカットは `.cursor/skills/` のネイティブスキル。Cursor は `@`-import を展開しないので、`.cursor/rules/aidlc.mdc` が常設の方法論層を指し、4 本の `aidlc-phase-*.mdc` ルールがフェーズ層を指す。起動は `/aidlc`。ショートカットは `/aidlc-status`、`/aidlc-jump`、`/aidlc-scope`。[AI-DLC on Cursor](harnesses/cursor.md) を参照。 |
| **深度 (Depth)** | 成果物の詳しさ。Minimal / Standard / Comprehensive の 3 段。スコープに既定があり、どの承認ゲートでも上書きできる。[スコープ・深度・テスト戦略](05-scopes-and-depth.md) を参照。 |
| **ディレクティブ (Directive)** | エンジンが各 `next` で出す型付き指示（`run-stage`、`ask`、`print`、`done`、`invoke-swarm` など）。コンダクターが次にすることを決める。[Engine and Skill System](../reference/17-skill-system.md) を参照。 |
| **配布 (Distribution)** | **コア**から**パッケージャ**が生成する、1 つのハーネス向けの投影。ソースビルドは、Git 管理外のローカルの `dist/claude/`、`dist/codex/`、`dist/copilot/`、`dist/cursor/`、`dist/kiro/`、`dist/kiro-ide/`、`dist/opencode/` ツリーと、ネイティブ用の対応する `dist-release/<harness>/` を生成する。リリースでは、`dist/` の投影を手動コピー用に帯域外の `aidlc-copy-runtime-X.Y.Z.tar.gz` で、`dist-release/` の投影をネイティブインストール用にマニフェスト記載の `aidlc-runtime-X.Y.Z.tar.gz` で配布する。メンテナーは生成物を手で編集しない。 |
| **エンジン (Engine)** | `aidlc-orchestrate.ts` の決定的な経路選択ツール。`next`、`continue`、`report`、`park`、`team-board`、`wait` の 6 サブコマンドを持つ。continue は内部転送、team-board は読み取り専用の Team Construction 照会、wait は委任作業の上限付き待機。scope・順序・jump・再開・gate を決めてディレクティブを出す。[スキルシステム](../reference/17-skill-system.md)を参照。 |
| **外部ツール (External tool)** | ステージが使う第三者の道具（AWS CLI、Maven、npm など）。Claude Code のツールとは区別する。 |
| **ガード (Fence)** | 実行中のワークフローのどのステップも求めていない操作を拒否するガード。plan approval、review freeze、state transition、reviewer read scope、human presence の 5 つがある。最初の 4 つは `/aidlc config set guard.<fence> off\|on` で 1 件の作業ごとに切り替えられ、`on` はポリシーで下げられたガードを上げられる。reviewer-scope の切り替えが影響するのは委譲レビュアーの読取り／検索の境界であり、クレーム済みのチーム checkout が別 Unit の `construction/` サブツリーへ書き込めないという必須ルールには影響しない。人が入力した弱化スイッチは、エージェントが `--intent`/`--space` またはチャットのワークフロー選択を使って設定コマンドを実行する。設定コマンドは状態と監査行を書き込み、何が変わったかを伝える。存在しない名前のインテントは拒否する。状態ファイルがない場合、行に入力した設定（Guard Policy、plan approval、ガードのスイッチ、その他のインテント設定）は、このチャットが次に始める作業のために保持される。人が自分の言葉で求めたとき、またはガードの `lower-fence` の選択肢を選んだときは、エージェントが代わりに設定コマンドを実行する。CLI の設定コマンドは、直前の判断以降に人のターンが記録されていれば弱化する。すでに off のガードや、設定元が `you` の同一ポリシー語にはキーが不要で、そのターンがなくても、人が自分の端末で入力したコマンドは本人の操作として弱化する。それ以外では `fenceKeyBypassed` だけが、フィクスチャ／ハーネス起動時の在席バイパス経由で CLI の弱化を許可する。memory が保持する strict が最初に拒否し、以前の `Guards Off` エントリより優先する。無人実行ではプロンプト時の適用を止め、CLI の弱化を拒否する。フックは Windows でも動くため、プロンプトを転送するすべてのハーネスが入力によるスイッチに対応する。モデルのツールはフックを起動できず、`aidlc/.aidlc-sessions/` やどの `.aidlc-plan-approval/` ディレクトリにも書き込めない。これは [state-transition ガード](../reference/06-hooks-and-tools.md#pretooluse-aidlc-state-transition-guardts) が強制する。Codex では `/aidlc` の代わりに `$aidlc` を使う。human presence には作業ごとのスイッチがなく、`AIDLC_SKIP_HUMAN_PRESENCE_GUARD=1` でのみ下がる。道を譲ったガードは、監査台帳があれば `GUARD_STOOD_ASIDE` 監査行を記録する。通知の届き方はハーネスによる。**Guard Policy** を参照。 |
| **Guard Policy** | 1 件の作業でガードがどこまで道を譲るかを決めるインテントごとの設定（`strict`、`relaxed`、`off`）。変更された入力が承認を開き直すかどうかと、どのガードを維持するかを決める。スコープの既定値（スコープファイルが宣言しなければ off）、次にインテント自身の状態行から解決し、`Mode: strict` を宣言する memory 層があれば両方より優先する。memory 層の `Mode: relaxed` または `Mode: off` は、スコープ由来の値を置き換える。状態に `Guard Policy` と廃止済みの `Change Control` の両方が異なる語で書かれている場合、設定元 `conflicting state lines` として strict を適用し、次の `next` が、記録上最後に設定された方（なければ本人のもの、スコープのもの、またはより厳しい方）を唯一の行として残すまでそれが続く。両者が一致する場合は `Guard Policy` を使い、次のポリシー書込みで旧行を取り除く。`/aidlc --guard-policy relaxed\|off` または平易な言葉での同じ依頼に対しては、エージェントが設定コマンドを実行する。strict はコンダクターが直接設定できる。チャットからの明示的な `intent create --guard-policy relaxed\|off` は、スコープ既定値より低い場合は拒否する。作業を作成し、人が低い値を求めたときにエージェントが設定コマンドを実行する。スコープ既定値は確認なしで適用する。compose による作成では、計画が実行されるストックスコープ（一致した計画のスコープ、またはカスタム計画のベース）から Guard Policy を読み、スコープファイルは書かない。コンダクターは `strict` または `relaxed` のときに `--guard-policy` を渡し（これで低いスコープ既定値を引き上げる）、`off` では決して渡さない。一致した提案の Guard Policy を下げると、選んだ値を持つストックスコープ上のカスタム計画に変わり、上げた場合は一致した計画のままになる。どちらの場合もインテント作成時に適用され、後から設定コマンドを実行する必要はない。コンポーザーは進行中インテントの値を変えず、代わりにサポートされているポリシー変更の経路を示す。旧称は Change Control で、旧表記は 1 リリースの間だけ読み取る。**ガード (Fence)** を参照。 |
| **ガードレール (Guardrail)** | ルールファイル内の規定セクション（`## Forbidden`、`## Mandated`、フェーズルールの見出し）。振る舞いの拘束を書く。入れ物はルール。「ガードレール」はその中身の名前。**ルール** を参照。 |
| **ハーネス (Harness)** | AI-DLC コアの CLI 配布。ハーネス非依存の **コア** を載せる、一つの有能なコマンドラインエージェント。集合は開いている（現在は Claude Code、Kiro CLI、Kiro IDE、Codex CLI、Cursor、opencode、GitHub Copilot）。*注: このリポジトリでは「harness」に 4 義がある。* (1) **この CLI 配布の意味（正）**。(2) ルール＋センサーの **制御ループ**（古い呼び方。**制御ループ** を参照）。(3) `harness/<name>/` のソース面。(4) `tests/harness/` のテストヘルパ。利用者向け文書で「ハーネス」と言えば (1) だけ。 |
| **フック (Hook)** | Claude Code がイベントに応じて自動で実行する TypeScript スクリプト。この実装は 17 本のフックを使い、すべて `settings.json` にプロジェクト全体で登録する。ワークフローの背骨（監査ログ、センサーのディスパッチ、ランタイムグラフのコンパイル、ステータスラインの同期、トークン使用量の畳み込み、コンパクション時の状態検証、サブエージェントの追跡、ターン終了時のループ強制）に加え、セッションのライフサイクル、人のターンの発行、ディスパッチルールの正確な配送、state-transition・reviewer-scope・review-freeze・plan-approval の各ガード、ステータスラインコマンドからなる。ワークフロー固有の処理は自己ゲートする。session-start はプロセスの祖先を記録し、エージェントが実行する設定コマンドは、入力された弱化スイッチを選択中の作業へ適用するか、チャットが次に始める作業のために保持する。 |
| **インライン実行 (Inline execution)** | 既定の実行。オーケストレータがエージェントのペルソナを載せ、会話の中でステージを進める。人とのやりとりがそのままできる。 |
| **インテント (Intent)** | スペースの `intents.json` に 1 行で載る作業（`{uuid, slug, dirName, scope, repos, status}`）。専用の [レコードディレクトリ] は `aidlc/spaces/<space>/intents/<YYMMDD>-<label>/`。`<YYMMDD>` は UTC の短い日付（例: `260624` = 2026-06-24）なので並びが時系列になる。`<label>` は依頼の短い kebab-case。同日同ラベルが被ったら `-2`、`-3`…。衝突しない正式 ID はレジストリ行の時系列 UUIDv7 で、ディレクトリ末尾ではない。最初の `/aidlc` でエンジンが最初のインテントを作る。明示セレクタかセッション紐づけが、共有の `active-intent` カーソルより先に効く。**スペース**、**レコードディレクトリ** を参照。 |
| **Kiro** | Kiro ハーネス。現在の AI-DLC ハーネス配布の一つ。ソースビルドは無視されるローカル投影を `dist/kiro/`（CLI）と `dist/kiro-ide/`（IDE）に生成する。リリースは `runtime/` に載せる。方法論は `aidlc/spaces/<active-space>/memory/` を、CLI の agent resources か IDE の常時含む steering ライブ参照から読む。起動は `/aidlc`。[Kiro IDE](harnesses/kiro-ide.md)、[Kiro CLI](harnesses/kiro-cli.md) を参照。 |
| **ナレッジ (Knowledge)** | ステージ開始時にエージェントが読む参照。二層。方法論ナレッジはフレームワーク同梱（`.claude/knowledge/`）。チームナレッジは利用者が管理し、スペース単位（`aidlc/spaces/<space>/knowledge/`）。自由形式。初期は空。そのスペースの全インテントで共有する。 |
| **ラダープロンプト (Ladder prompt)** | Continue automatically / Review each checkpointの選択。対象作業で方針が未設定なら、skeleton-offではConstruction開始時、skeleton-onでは実際のスケルトンチェックポイント後に提示。後からの許可・取消も可能。旧形式の最初のステージ承認は、統合スケルトンの完成を証明しない。 |
| **ラーニングループ (Learning loop)** | ステージ中の訂正を、残るプラクティスとセンサーにする。ステージ中はオーケストレータが `memory.md` に観察を書き、承認ゲートで見せ、残すものを人が確認する。確認した学びは `aidlc/spaces/<active-space>/memory/project.md` のプラクティスになる（ワンクリックで `team.md` へ昇格）。現在のワークフローの次の該当ステージから効く。または新しいセンサーの下書きになり、次のステージグラフのコンパイルで結び付く。[ルールとラーニングループ](09-rules-and-the-learning-loop.md) を参照。 |
| **ライフサイクル (Lifecycle)** | AI-DLC 方法論全体。その 1 回の実行がワークフロー。公開ネイティブ面は `config`、`doctor`、`version`、`update`、`use`、`uninstall`。 |
| **マシンライフサイクルコマンド (Machine lifecycle command)** | 利用者単位のリリースや設定を扱うネイティブ `aidlc` 経路。プロジェクトの `.aidlc-version` ピンには従わず、いつもアクティブなバイナリから実行される。プロジェクトのワークフローデータは変えない。 |
| **マニフェスト (Manifest)** | ハーネスの `harness/<name>/manifest.ts`。**パッケージャ** に、**コア** をそのハーネスの **配布** へどう投影するかを宣言する（ディレクトリ対応、ルール名の付け替え、手書きファイル、任意の `emit` プラグイン）。ハーネス追加の大半はマニフェスト 1 本。 |
| **MCP サーバー (MCP server)** | プロジェクトルートの `.mcp.json`（`.claude/` の隣）で宣言し、Claude Code セッションに載せる外部ツールサーバ。配布は 5 つ。`context7` と AWS 系 4 つ（`aws-mcp`、`aws-pricing`、`aws-iac`、`aws-serverless`）。エージェントはセッションの MCP を全部継ぐ。エージェント単位の許可はない。使わせないときは `tools:` を `mcp__<server>__<tool>` まで狭める。認証がないサーバは単に使えない。ワークフローは止まらない。[Harness Primitives Mapping — MCP Servers](../reference/14-claude-features.md#mcp-servers)、[導入](01-getting-started.md#mcp-サーバーの任意設定) を参照。 |
| **memory.md** | ステージごとの観察日記。`<record>/<phase>/<stage>/memory.md`。Learnings が on の場合だけ、エンジンが run-stage ディレクティブを出すときに作り、オーケストレータが維持する（手編集しない）。Interpretations、Deviations、Tradeoffs、Open questions を書く。ラーニングループが承認ゲートで読む入力。 |
| **モブ実行 (Mob execution)** | 委譲メッシュ（`mode: mob`）。回数に上限がある。リードが下書きし、互いに見えない協力者が並行で寄与ファイルを書き、リードが統合し、判断が残れば人に出す。配布のモブは User Stories (2.4)。コラボレーターがオフ（`enterprise` 以外の配布スコープすべて）の場合、リードが単独で実行し、モブのラウンドはない。 |
| **複数リポジトリインテント (Multi-repo intent)** | 兄弟のコードリポジトリをまたぐ作業。作成時にリポジトリ集合を取る。`--repos a,b` か、ワークスペース直下の `.git` を持つ子の自動発見。`intents.json` の `repos` に残る。Construction の git 操作は `--repo <name>` で対象リポジトリを指定する。`repos` がないインテントは昔の単一リポジトリ（プロジェクトディレクトリで git する）。[成果物リファレンス](14-artifacts-reference.md) を参照。 |
| **ネイティブチャネル (Native channel)** | 推奨の利用者単位の導入経路。ネイティブの `aidlc` バイナリと、マシンの versions ディレクトリ下の版一致ハーネスランタイム。インストーラとプロジェクトの足場に Bun、Node.js、Git は不要。Alpine musl ホストは先に、Bun と Node.js が共有するランタイム前提を `apk add libgcc libstdc++` で入れる。 |
| **オフラインパッケージ (Offline package)** | ネットワーク無しで入れるため、そのまま運ぶリリース成果物一式。プラットフォームバイナリ、ランタイムペイロード、インストーラ、`version.json`、`checksums.txt`、出自束 `aidlc-release.intoto.jsonl` が入る。 |
| **opencode** | opencode（opencode.ai）ハーネス。現在の AI-DLC ハーネス配布の一つ。ソースビルドは `core/` + `harness/opencode/` から無視されるローカル投影 `dist/opencode/` を生成する。リリースは `runtime/opencode/` に載せる。エンジンは `.aidlc/`。opencode は `.opencode/tools/*.ts` をカスタムツールとして読むので、エンジンは置けない。`.opencode/` はネイティブシェル（サブエージェント、`/aidlc`、フックアダプタプラグイン）だけ。方法論はプロジェクトルート `opencode.json` の `instructions` グロブ。起動は `/aidlc`。[AI-DLC on opencode](harnesses/opencode.md) を参照。 |
| **GitHub Copilot** | GitHub Copilot ハーネス。現在の AI-DLC ハーネス配布の一つ。ソースビルドは `core/` + `harness/copilot/` から無視されるローカル投影 `dist/copilot/` を生成する。リリースは `runtime/copilot/` に載せる。1 回の導入で CLI と VS Code agent mode の両方（読むプロジェクトファイルは同じ）。エンジンは `.aidlc/`。`.github/` には aidlc 名のネイティブ出力だけ（フック配線 `hooks/aidlc.json`、ペルソナのカスタムエージェント、スキルツリー）。既存の `.github/` にマージし、置き換えない。方法論はルート `AGENTS.md` の `@`-import。起動は `/aidlc`。[AI-DLC on GitHub Copilot](harnesses/copilot.md) を参照。 |
| **オーケストレータ (Orchestrator)** | ワークフローの回し方の総称。次を決める決定論的 **エンジン** と、実行する **コンダクター**（`SKILL.md`）。起動は `/aidlc`。[Engine and Skill System](../reference/17-skill-system.md) を参照。 |
| **パッケージャ (Packager)** | `scripts/package.ts`。**コア** + 各 **マニフェスト** から、無視されるローカル `dist/<harness>/`、`dist-release/<harness>/`、プラグイン投影をすべて実体化する。`bun scripts/package.ts` が全部。`--check` は独立した一時ルートで二度ビルドし、結果をバイト比較する CI の決定論ガード。 |
| **並行バッチ (Parallel batch)** | `unit-of-work-dependency.md`（2.7）から、互いに依存せず同時に走れるユニットの実行時グループ。ボルト計画のまとまりではない。自律スウォームではエンジンが各 DAG バッチを収束させ、Code Generation のステージゲートは 1 回（中間バッチごとではない）。`SWARM_COMPLETED` が実行時バッチを閉じる。 |
| **パイプライン実行 (Pipeline execution)** | 委譲チェーン（`mode: pipeline`）。宣言順にリンクが実行され、上流の成果を全部見る。戻るたびに今の試行のレシートを残し、最後のリンクが成果物を揃える。配布のパイプラインは Reverse Engineering (2.1)。登録リポジトリごとにレシート鎖が 1 本完走する必要がある。 |
| **フェーズ (Phase)** | ライフサイクルの大きな区切り 5 つ。Initialization (0)、Ideation (1)、Inception (2)、Construction (3)、Operation (4)。ステージ数は Initialization 3、Ideation 7、Inception 9、Construction 7、Operation 7。 |
| **フェーズ境界検証 (Phase boundary verification)** | Ideation、Inception、Construction の最後のステージ（Approval and Handoff、Delivery Planning、CI Pipeline）が `<record>/verification/` に書くトレーサビリティ検査。欠けたリンク、孤立した成果物、不整合を、下流が積み上げる前に拾う。これらのステージのどれかを飛ばす計画では、そのフェーズの検査はない。[成果物リファレンス](14-artifacts-reference.md#フェーズ境界検証) を参照。 |
| **プレーン (Plane)** | フレームワークが分ける 3 つの関心。ネットワーク構成から借りた言い方。**コントロールプレーン**（ステージ定義、ルール、センサー。何が実行されるべきかのスキーマ。コンパイル時に解決）、**データプレーン**（実際のステージ実行、ボルト、監査テレメトリ）、**マネジメントプレーン**（`/aidlc --doctor`、監査照会、`CLAUDE.md`）。利用者向けの向きは [ルールとラーニングループ](09-rules-and-the-learning-loop.md)。全体像は `docs/reference/02-plane-architecture.md`。 |
| **プロジェクトピン (Project pin)** | コミットする `.aidlc-version`（strict-semver）。エンジンコマンドが使う保持済みネイティブエンジンを選ぶ。`aidlc config --pin` が完全なバイナリと一致するプロジェクトハーネスを検証し、マシンローカルの解決先を記録し、`pins.json` にピンを登録してそのリリースを刈り込みから守る。安定したコマンドランチャは、現在有効な完全性検査ディスパッチャを起動し、プロジェクト操作の前にピンしたランタイムを検証して選ぶ。 |
| **投影スタンプ (Projection stamp)** | 生成される `tools/data/aidlc-stamp.json`。投影した木のフレームワーク版、配布、ハーネスディレクトリを記録する識別情報。起動と doctor が版のずれを見つける。 |
| **レコードディレクトリ (Record dir)** | 1 インテントの成果物、ステージごとの `memory.md`、`aidlc-state.md`、`audit/` シャードを持つ場所。`aidlc/spaces/<space>/intents/<YYMMDD>-<label>/`（文中では `<record>/`）。インテントごとに 1 つ。明示セレクタかセッション紐づけが、共有の `active-intent` より先に勝つ。**スペース**、**インテント** を参照。 |
| **リフレッシュ基準 (Refresh baseline)** | init が所有する `tools/data/aidlc-manifest.json`。フレームワーク所有ファイルと型付きルート寄与のハッシュを記録する。`aidlc config` がリフレッシュ操作の分類、ローカル編集の検出、廃止された所有コンテンツの安全な削除、プロジェクト所有データの保全に使う。 |
| **リリースチャネル (Release channel)** | **ネイティブチャネル** を参照。ネイティブ用 `aidlc-runtime-X.Y.Z.tar.gz` は、その場で再生成したローカル `dist-release/<harness>/` 投影から組み立て、TLS と SHA-256 で認証し、リリースワークフローが出自を証明する。 |
| **保持版 (Retained version)** | 利用者単位の versions ディレクトリに並べて置く、完全なネイティブバイナリ、リリースマニフェスト、0 個以上のハーネスランタイム。アクティブ、ロールバック、登録済みピン版は刈り込みから守られる。 |
| **ルート統合 (Root integration)** | `aidlc config` が宣言ポリシー（managed block、JSON map、JSON array、whole file）の下で突き合わせる、プロジェクトルートのファイル寄与。所有は明示で、無関係なプロジェクトの中身は残すか、衝突になる。 |
| **レビュアー (Reviewer)** | 品質ゲートのエージェント。`aidlc-product-lead-agent`（要件・ストーリー・モック）か `aidlc-architecture-reviewer-agent`（技術設計）。ステージ本体が成果物を出したあと、ステージが `reviewer:` と必須の Markdown `review_artifact:` を宣言しているときに、別サブエージェントとして実行される。1 本のレビュー（READY / NOT-READY と所見）を、依頼が指名したレビューファイルへ書く。成果物へは書かない。エンジンはそれをその成果物に鍵づけたレビュー記録として残す。依頼時の成果物／ソースフィンガープリント、Verdict / Reviewer / Iteration の厳格フィールド、安定した完了スナップショットで、変わった仕事が認証されないようにする。adversarial な NOT-READY ではビルダーが再実行し、`reviewer_max_iterations`（既定 2）まで回して、残件を人の承認ゲートに出す。レビュアーにはターン上限がある（Claude Code は `maxTurns: 60`、opencode は `steps: 60`、ほかは散文）。未完了レビューは一度再試行し、だめなら終端 NOT-READY。ブロックはしない。決めるのは常に人。[エージェント](06-agents.md) を参照。 |
| **ルール (Rule)** | 継続して適用する行動規則。アクティブスペースのメモリ層（`aidlc/spaces/<active-space>/memory/`）に一度書き、各ハーネスのネイティブ include（Claude の `@`-import、Kiro CLI resources / IDE steering、Codex ではエンジンのステップごとのルール配送、opencode の `instructions` グロブ、Copilot の `AGENTS.md` `@`-import）で毎回の対象ステージに載る。解決は厳格加算の 5 層（org → team → project → phase → stage）。当たるルールは全部コンテキストに出る。広い層を上書きはせず、足すだけ。**制御ループ** のフィードフォワード側。センサーと組んで決定論的検証もできる。[ルールとラーニングループ](09-rules-and-the-learning-loop.md) を参照。 |
| **ランタイムグラフ (Runtime graph)** | インテントの `runtime-graph.json`。構造ステージグラフのデータプレーン鏡。承認ゲートのたびに監査ログから実体化する。どのステージが実行されたか、どのボルトが分岐したか、どのセンサーが発火したか、`memory.md` の件数。doctor とラーニングループが読む実行ビュー。 |
| **スコープ (Scope)** | 名前付き設定 11 種（enterprise、feature、mvp、poc、bugfix、refactor、infra、security-patch、classic、workshop、express）。どのステージをどの深度で実行するかを決める。自由文の意図からエージェントが提案し、人が確認する。 |
| **センサー (Sensor)** | `.claude/sensors/` のマニフェストで定義する決定論的検査（例: `aidlc-linter.md`、`aidlc-type-check.md`）。一致する Write/Edit、または人が答える承認ゲートで既存成果物ごとに一度（ステージ全体を読む検査なら出力フォルダごとに一度）実行され（Construction の自律モードで承認されるゲートでは blocking センサーだけが走る）、`SENSOR_*` 監査行を残す。ゲート発火の結びは advisory か blocking。blocking は直すか、監査付きの明示オーバーライドが要る。ステージは frontmatter の `sensors:` で何が発火するかを宣言する。**制御ループ** のフィードバック側。フィードフォワード側はルール。[ルールとラーニングループ](09-rules-and-the-learning-loop.md) を参照。 |
| **テスト戦略 (Test strategy)** | テスト量の 3 段（Minimal / Standard / Comprehensive）。生成するテスト数と種類。深度とは独立。スコープが上書きを宣言しなければ、アクティブな深度に従う。[スコープ・深度・テスト戦略](05-scopes-and-depth.md#the-3-test-strategy-levels) を参照。 |
| **トランザクション (Transaction)** | 行き先のファイルシステムへステージし、想定する生きた状態と照合し、アトミックなリネームでコミットする、プロジェクトまたはマシンの変更。失敗したコミットはロールバックする。回収できない証拠は、doctor が報告する `.aidlc-recovery-*` 隔離に残る。 |
| **セッション (Session)** | ハーネスでの 1 回の会話（Claude Code のセッション、Kiro IDE のチャット、Codex CLI のセッションなど）で、そこで `/aidlc`（Codex では `$aidlc`）を実行する。再開機構で、ワークフローは複数セッションにまたがれる。 |
| **スキル (Skill)** | ハーネスがコマンドとして提供する、YAML frontmatter 付きの Markdown ファイル。Claude Code では `.claude/skills/` にあり `/` で入力する。Codex では `.agents/skills/` にあり `$` で入力する。ハーネスごとに専用のフォルダがある（[スキルとランナーコマンド](17-skills.md) を参照）。AI-DLC のオーケストレータは `aidlc` スキル。利用者向け文書では「スキル」より「コマンド」を使う。 |
| **スペース (Space)** | チームごとのワークスペース内の区画 `aidlc/spaces/<space>/`。独自の `memory/`、`knowledge/`、インテント記録（`intents/`）を持つ。明示セレクタかセッション紐づけが、gitignore された `aidlc/active-space`（既定 `default`）より先に勝つ。一人チームは `spaces/default/` しか見ない。**インテント**、**ナレッジ** を参照。 |
| **ステージ (Stage)** | ライフサイクルの discrete な 33 ステップ。リードエージェント、入出力、ステージプロトコルを持つ。番号はフェーズ付き（1.1、2.4、3.5）。 |
| **状態ファイル (State file)** | インテントごとの永続状態。`aidlc/spaces/<space>/intents/<YYMMDD>-<label>/aidlc-state.md`。ステージ進捗、スコープ、ワークスペース文脈、再開情報。チェックボックスは 6 状態（`[ ]` / `[-]` / `[?]` / `[R]` / `[x]` / `[S]`）。 |
| **サブエージェント実行 (Subagent execution)** | 委譲ハブ（`mode: subagent`）。コンダクターがハーネスのディスパッチツールで別エージェント文脈を呼ぶ。Code Generation (3.5) は 1 エージェントの集中実行。Practices Discovery (2.2) はハブ＆スポーク。リード下書き、互いに見えない 3 つの寄与、人へのインタビュー、リード統合。コラボレーターがオフの場合、リードはスポークなしで実行する。 |
| **作業ユニット (Unit of work)** | WHAT。独立して実装できる塊。2.7（Units Generation）で分解し、`unit-of-work-dependency.md` に載る。依存でつながったユニットが 1 ボルトの範囲になる。 |
| **ウォーク順 (Walk order)** | ソース生成とUnit分解を含む新規ソロ作業の既定はunit-major。1つのUnitの適用対象ステージを終えてから次へ進む。stage-majorも明示選択できる。対象のskeleton-on作業ではどちらの順序でも最初の統合Unitを後続より先に完了する。既存・設計のみ・チーム所有作業は従来の経路を維持。実行順はUnit DAG、Boltは計画。 |
| **ウォーキングスケルトン (Walking skeleton)** | 最小の動作する統合スライス。skeleton-on のときに最初の DAG Unit として計画する。対象となるチェックポイント対応のソロ作業では、その Unit が適用対象の設計ステージと Code Generation を完了し、人間が認可して記録したエンドツーエンドの検証コマンドを通過し、人間の承認を受けてから後続の Unit を始める。旧形式の最初の Construction ステージのレビューはステージゲートであり、動作するスケルトンの証拠ではない。 |
| **ユーティリティコマンド (Utility command)** | ワークフローステージを走らせない `/aidlc` フラグ。`--status`、`--config`、`--doctor`、`--version`、`--stage`、`--phase`、`--scope` など。照会、設定変更、移動をする。 |
| **ワークツリー (Worktree)** | swarm 実行で Unit に使う Git の隔離機構。そのディレクトリと `bolt-<id8>_<slug>` ブランチが Unit の作業を保持し、Unit のクレームと同様にインテントレジストリの UUID でスコープされる。[Bolt identity](https://github.com/awslabs/aidlc-workflows/blob/6a378b53c0a4fe0641ed7d8de8dfff94264d5b6a/core/knowledge/aidlc-shared/worktree-info-schema.md#bolt-identity) を参照。実行では、ガイド付きまたは自動の完了承認を使える。ワークツリーは計画上の Bolt でも swarm バッチでもない。 |
| **ワークスペース (Workspace)** | `aidlc config` がインストールするフォルダ（実行したフォルダ、または `--project-dir` で指定したフォルダ）。ハーネスフォルダ、`aidlc/`、そしてコードリポジトリ 1 つ（フォルダ自体がリポジトリ）か、`aidlc/` の隣に並ぶ複数のコードリポジトリを持つ。AI-DLC は git ルートを上方向へ探さないので、そのフォルダがワークスペースになる。プロジェクトフォルダ、プロジェクトディレクトリ、ワークスペースルートとも呼ぶ。[`aidlc/` の置き場所](03-spaces-and-intents.md#aidlc-の置き場所) を参照。 |
| **ワークフロー (Workflow)** | AI-DLC ライフサイクルの 1 回の通し。`/aidlc` からステージ完了まで。特定の作業（機能、バグ修正など）にスコープされる。 |
| **ワークフロープロファイル (Workflow profile)** | 利用者向けの、スコープの呼び名。Classic、Express、Feature、Bugfix など、作業の種類に合わせたライフサイクル。選んだプロファイルがステージ経路と既定値になり、`aidlc-state.md` の `Scope` に残る。[ワークフロープロファイル](workflow-profiles.md) を参照。 |
