# ステージ定義

この章では、AI-DLC ステージ定義の**ファイル形式**、すなわち YAML フロントマター
契約、本文の 3 区画モデル、およびそれらのソースを `stage-graph.json` へ変換する
コンパイル・パイプラインを説明します。実行時の振る舞い契約（承認ゲート、質問
フロー、状態追跡）を扱う[ステージ・プロトコル](04-stage-protocol.md)を補完します。
本章はステージファイルが*含むもの*について、ステージ・プロトコル章はステージが
*行うこと*についての説明です。

貢献者は形式を理解するためにこれを読みます。ステージファイルを書くまたは編集
するときは、`core/aidlc-common/protocols/stage-definition.md` にある
正規の契約を参照してください。このファイルが正式な仕様であり、この章では説明と
「いつ使うか」のガイダンスを補います。

---

## 2 つの読者、1 つのファイル

各ステージ `.md` ファイルには 2 種類の読者がいます。

- **パーサー**（`core/tools/aidlc-lib.ts` の `parseStageFrontmatter`）。YAML フロントマターをプレーンなレコードへ読み込み、それを `validateStageFrontmatter`（`core/tools/aidlc-stage-schema.ts`）が検査します。本文には触れません。
- ステージを実行する **LLM エージェント**。本文を読み、散文の指示に従って成果物を生成します。フロントマターには触れません。

両方を 1 ファイルに置くことで、貢献者はグラフの辺と実行手順を並べて見られます。
ファイルを分ける（グラフ用の YAML とエージェント用の散文）と、ステージを
レビュー可能にするインラインの可視性が失われます。

---

## バリアント A3 である理由

この形式は「バリアント A3」と呼ばれます。この形式のために検討された、
3 つの記述方式の 3 番目です。

- **分割ファイルより 1 ファイル。** フロントマターと散文を 1 つの `.md` に置くことで、グラフ構造と実行手順をまとめます。ステージを読むレビュアーは両方を見られます。
- **`grep` しやすい。** プレーンテキストです。バイナリー形式も、作成時の YAML と JSON 間の変換もありません。
- **差分を確認しやすい。** フィールド追加、リネーム、本文編集はいずれもコードレビューに明瞭に現れます。

採用しなかった案は、中心グラフ・ファイル（手編集の `stage-graph.json`）と散文だけの
ステージを組み合わせるものでした。散文を編集しながら、ステージがどの成果物を
生成するかを知るインライン可視性を失います。

## 作成フロー

```
Edit stage YAML
      |
      v
bun scripts/package.ts
      |
      +--> ignored dist/<harness>/<harness-dir>/tools/data/stage-graph.json
      |
      +--> ignored dist-release/<harness>/<harness-dir>/tools/data/stage-graph.json
                    |
                    v
             loadStageGraph()
```

YAML が正本で、JSON は生成されたビルド成果物です。リポジトリのパッケージ処理がソースから再生成し、インストール済みランタイムもプラグイン合成後に再コンパイルできます。

`aidlc-graph compile` と `compile --check` は実行時・診断用のサブコマンドとして残りますが、コントリビューターはコンパイル済み JSON をバージョン管理しません。YAML を編集して `bun scripts/package.ts` を実行すると、gitignore 対象の生成物を作成します。`bun scripts/package.ts --check` は一時ルートで 2 回再生成して決定性を検証します。

## フィールド・リファレンス — いつ使うか

正規仕様には型と制約を含む完全なフィールド表があります。この節では、判断を
要するフィールドについて説明を加えます。

### `requires_stage`

依存関係の辺をコード化します。役割は 2 つです。

1. **意味上のデータ依存。** 「ステージ Y が生成する成果物 X を消費する」→ `requires_stage` に `Y` を追加します。
2. **表示順の辺。** 同じフェーズ内で意味上の依存はないが順序が固定の 2 ステージ（例: 着想フェーズの `market-research` は `feasibility` より前）。計算されるステージの `number` を安定させるため弱い辺を追加します。

コンパイル時の `slug` アルファベット順のタイブレークは安全網です。特定の順で
配置しなければならないステージは、アルファベット順の偶然に頼らず明示的に辺を
記述してください。

### `for_each`

インスタンスが反復を駆動する成果物を指定します。ステージはインスタンスごとに
一度実行されます。

現在のユースケース: 5 つの構築ステージ（`functional-design`、
`nfr-requirements`、`nfr-design`、`infrastructure-design`、`code-generation`）
はユニットごとに一度実行されます。それぞれが
`for_each: unit-of-work`（`units-generation` が生成する成果物）を宣言します。

将来のユースケース: 環境ごと、テナントごと、リージョンごと、コンプライアンス
管轄ごとに実行するステージです。このプリミティブはワークフロー・エンジン一般の
ものであり、たまたま構築フェーズが最初に利用します。

**集約は宣言せず推論されます。** `for_each` ステージが生成する成果物を消費し、
自身の `for_each` を宣言しないステージは、定義上の集約ステップです。
`build-and-test` が典型例です。5 つの構築 `for_each` ステージが全ユニットを
反復したあとに一度だけ実行され、集約された出力を消費します。明示的な
`fan_in` や集約フィールドは不要であり、グラフ走査が判断します。

### `summary_confirmation`

任意の列挙値です。ステージの質問フローで、成果物を生成する前の決定論的な確認を制御します。

- `required` は、毎回質問ファイルを作成し、成果物を生成する前に統合要約への **Looks correct** の確認を得ることを要求します。
- `if-present` は、条件付きの質問フローが質問ファイルを作成した場合に同じ確認を要求します。現在の試行で要約の決定または確認が記録されたあとは、そのファイルを削除しても確認の義務は消えません。質問と確認を復元するか、明示的なライフサイクルのリセットで新しい試行を始めてください。

受領記録を Markdown だけから推測してはいけません。`aidlc-log.ts` は、対応するプロンプト記録と、その記録より後の本人の返答を確認してから、予約済みの `SUMMARY_CONFIRMATION_RECORDED` イベントを記録します。エージェントがプロンプトを記録する前に要約を示していた場合は、その記録の前のそのチャットでの本人の最新の返答も、`--message` なしで同じように数えます。ただし、質問ファイルがステージの最後の質問または回答の後、かつその返答の前に書かれていて、その返答とプロンプトの間にほかの質問が記録されていない場合に限ります（本人の返答の後にエージェントがその選択を `[Answer]:` へ書き込むことは、要約の書き込みではありません）。エージェントは `--message <id>` でそのメッセージを指名することもできます（このクローンの監査がそのプロンプトより前、またはその返答より前に記録している質問ファイルの最後の書き込みよりも前に送られたメッセージは指名できません。そのとき要約はまだ見られる状態になかったためです。ステージゲートの承認も、ステージの出力に対して同じ規則を当てはめます）。受領記録は本人の言葉を `Person Reply` として残し、質問ファイルのダイジェストと、記録された `Hash Scope` に結び付きます。新しい受領記録は `confirmed-content-v2` を使います。変わらない生内容の SHA-256 アルゴリズムが、CRLF と単独の CR を LF に正規化し、セクションをファイル順に保ち、得られた内容の末尾の空白を一度だけ取り除きます。表示されるすべての Q<n> セクションとフィードバックセクションは引き続き結び付きます。要約の後にある `Assumption Confirmation` セクション 1 つは、トップレベルの `## Q<n>` またはフィードバックの見出しとして書かれた行の手前までを除外します。`Q<n>` や `Assumption Confirmation` の見出しは、claim-sources センサーの規則により、先頭の絵文字の装飾があってもなくても数えます。保持される内容にあるコメント、コード、HTML、先頭の BOM は引き続きダイジェストに影響します。見出しと回答の認識は、`markdownBlocks` と `visibleMarkdownLines` を通じて組み込みの `Bun.markdown` パーサを使うようになりました。生の HTML ブロックの内容が見出し、回答、タグになることはありません。`Looks correct` の受領記録には `Summary Authorization Id` も含まれます。これは試行、ステージ、Unit、ワークフロー、質問ファイルのパス、確認済みの内容、選択肢から算出するダイジェストで、そのスコープの有効な認可になります。書き込み監査フックは、その後のステージ出力に対する `ARTIFACT_CREATED` / `ARTIFACT_UPDATED` の各行へ、この ID を付けます。完了処理は、受領記録の欠落・陳腐化、確認済みセクションの変更、禁止された見出し、または最新のネイティブ書き込みに現在の受領記録の ID が付いていない宣言済み成果物を拒否します。最後の条件は、出力が現在の確認に基づいて保存されていないことを意味します。同じ内容の再確認では同じ ID が生成されます。そのため `Looks correct` を繰り返しても、既存の認可は取り消されず再確認されます。回答が変わると新しい ID になるため、その ID の下で出力を保存し直す必要があります。受領記録と書き込みのどちらが先に記録されたかでは判定しません。ID のない旧形式の受領記録は、引き続き受領記録より後のネイティブ書き込みを必要とします。スコープのない進行中の受領記録で許可された追記を受け付けるには、先に再確認してスコープ付き受領記録を作成する必要があります。Unit 単位のステージでは、対象 Unit ごとに Unit スコープの受領記録が 1 件必要です。隔離実行でも、`single-stage:<slug>` というワークフロー識別子で同じ確認を行います。

`confirmed-content-v1` は、同じダイジェストアルゴリズムと以前の手書きの可視性規則を持つ、サポート対象の旧形式スコープとして残ります。v1 の受領記録は、記録されたダイジェストが現在の v2 のダイジェストと等しければ受け付けます。そのため影響を受けない文書は、再確認なしでバイト単位で同一の識別を保ちます。v1 が一致しない場合は `SUMMARY_CONTENT_SEMANTICS_CHANGED` で拒否します。その受領記録は Markdown パーサの更新より前のものなので、確認済みの内容が確認後に変わったか、v1 が確認済みのテキストとして扱っていた生の HTML の内容がもはやその一部ではないかのどちらかです。生の HTML の見出しと制御タグは、現在 Markdown の認識から除外されます。要約を提示し直して再確認し、v2 を記録してください。この拒否は編集があったとは決して主張しません。v2 が一致しない場合は、既存の `SUMMARY_CONTENT_STALE`（確認後に変更された）による拒否のままです。スコープのない受領記録は、ファイル全体の SHA-256 と既存の復旧文を保ちます。未知のスコープは引き続き `SUMMARY_HASH_SCOPE_INVALID` で拒否します。以前の同一確認の経路でも、v1 の受領記録を v2 のハッシュ関数で比較します。保存済みの受領記録は書き換えません。

### `workspace_requires`

ブール値で、既定は `false` です。意図ごとの記録ディレクトリに計画文書を置くだけ
ではなく、**ワークスペースルートへソースコードを書かなければならない**ステージで
`true` に設定します。

存在する理由: ステージの `produces[]` 成果物は通常、記録ディレクトリ配下に解決されます。
例外は、リバースエンジニアリングのリポジトリ別 codekb のようなスペースレベルのストアです。
そのため「`produces` は存在するか？」
という検査は、`code-generation-plan.md`、`unit-test-instructions.md`、
`code-summary.md` を書いただけで実際のコードを 1 行も出さない `code-generation`
ステージでも満たされてしまいます（課題 #366）。
`workspace_requires: true` がその穴を閉じます。ステージ完了時の
成果物ガード（`aidlc-state.ts` の `approve` / `advance` / `finalize` /
`complete-workflow`）は、ステージ完了前に `aidlc/` ワークスペースツリーと
ハーネスディレクトリの外で実ソース作業の証拠を追加で要求します。

codekb ステージでは、同じガードがアクティブなインテントに記録されたリポジトリ集合に
従います。記録されたすべてのリポジトリが、正準の
`aidlc/spaces/<space>/codekb/<repo>/` ディレクトリに宣言済み成果物を少なくとも 1 つ
持たなければなりません。名前が違うディレクトリや未記録のディレクトリは数えません。
記録されたリポジトリを持たないインテントは、従来どおり任意のリポジトリディレクトリを
許すフォールバックを保ちます。

「ソース作業」の検出方法はワークスペースによって異なります。
- **Git ワークスペース** - ガードは Git に問い合わせるため、このセッションのコードと
  ブラウンフィールドリポジトリの既存 `src/` を区別できます。未コミットまたは未追跡の
  非ドキュメント変更（`git status --porcelain`）があるか、直近コミットが非ドキュメント
  パスに触れている（`git diff --name-only HEAD~1 HEAD`）ときに合格します。後者の条項により、
  コミットしてから承認する流れ（作業ツリーはクリーンで、コードは直近コミット内）でも
  合格し、#366 の第 3 更新でのクリーンツリー誤ブロックを閉じます。
- **非 Git ワークスペース**（または任意の Git エラー）- ガードはシェルを使わない
  ファイルシステム存在チェックにフォールバックします。`aidlc/` ワークスペースツリーと
  ハーネスディレクトリの外に、少なくとも 1 ファイルが存在する必要があります。
- **ワークスペース自身の Git の外に置かれたコード** - コードは、インテントの記録済み
  リポジトリ（レジストリ行の `repos`）のいずれか、作業開始後に作られた子リポジトリ・
  クローン・ワークツリー、それらのいずれかのリンクされたワークツリー（`git worktree list`
  が示すもの）、またはワークスペースの Git が追跡しないチェックアウトにあることがあります。
  最後の例は、プロジェクトの外にあるリポジトリのワークツリーを、プロジェクト内の
  gitignore 対象フォルダに置いたものです（追跡されていない、または無視されているフォルダ
  それぞれの 3 階層下まで、リンクをたどらずに探します）。ガードはそれぞれに、ワークスペースに
  対するのと同じ問いを投げるため、新しいコードのないブラウンフィールドのチェックアウトも
  合格しません。検査の実行時に見つかったチェックアウトが数えられるのは、レビューがその
  コード変更を見られる場所、つまりソース走査が AI-DLC 自身のもの以外としてその下の
  ファイルを列挙する場所だけです。Claude Code の `.claude/worktrees/` のようなハーネス
  フォルダ、プロジェクトの外、別のドライブに置かれたコードは数えられないため、下の文言と
  ともに人へ回ります。ただし、作業がそのチェックアウトを記録している場合（エージェントが
  レビューの前に実行する `intent add-checkout <path>`、またはハーネスフォルダのワークツリー
  内での Unit の申告で、レビューのリクエスト時に記録されるもの）は別です。記録済みの
  チェックアウトは、レビューによって独立したルートとして走査され、そのファイルは
  `<label>@checkout/<path>` として列挙されます。そのため問い合わせの対象になって見つかり、
  レビュー後にそこで変更があればレビューは陳腐化したものになります。Git に問い合わせるのは実際の `.git` エントリを持つフォルダ（人が
  作ったクローン、サブモジュール、init、ワークツリー）だけです。リポジトリの形をしているだけの
  コミット済みフォルダはファイルシステム検査を受けるため、そのコミット済みの Git 設定が
  実行されることはありません。`.aidlc/` 配下の AI-DLC 自身の Bolt ワークツリーは、
  スウォーム自身の証拠に任されます。
- **コードをコミットし、その後に記録をコミット** - 記録だけの直近コミットは、ステージ中に
  先にコミットされたコードを隠します。そのためガードは、ソースをステージ試行の
  `Source Baseline` とも比較します。ステージ開始以降の AI-DLC 自身のファイル以外での
  変更はソース作業です。

ガードが探したどこにもソース作業を見つけなかった場合、Guard Policy off では作業が
そのまま続き、人は一度だけ「AI-DLC found no source changes under <where it looked>」と
聞きます。strict または relaxed では、エージェント自身の最初の報告が拒否され、常に使える
先へ進む方法が示されます。もう一度報告すると、承認の質問がその文言
（「If your code is somewhere else, approve as usual; if it is missing, ask for changes.」）
とともに人へ回ります。人の承認は、その言葉と並べて `Source Work` として記録されます。
strict または relaxed で、承認がゲート後の人の返答にならない場合（自律的な Construction
ゲート、human-presence チェックをオフにした場合、無人実行）と、エージェント自身の
`advance`、`finalize`、`complete-workflow` では、拒否はそのまま残ります。各結果は
ステージ試行ごとに一度、`SOURCE_WORK_NOT_FOUND` 行として記録されます。

今日これを宣言するのは `code-generation` だけです。そのユニット単位のレビューは、
追加で `<record>/construction/<unit>/code-generation/source-manifest.json` を
要求します。これは、作成・変更・削除されたすべてのアプリケーションソースパスの
厳密な帰属インデックスです。エンジンはマニフェストのバイト列と申告された内容を
ユニットの受領記録に束縛し、新規のユニットをすべてコンテンツアドレス方式の
ステージ開始時ベースラインと比較し、新規申告の和集合の外にある変更パスを
拒否します。ディレクトリ申告は後からの追加を包含します。メインのマルチリポジトリ
ワークスペースでは各エントリが記録済みリポジトリを名指しし、Bolt のマニフェストは
選択された 1 つのリポジトリからの相対になります。リポジトリを記録しないワークスペースでは、
プロジェクト内に入れ子になったチェックアウト（その Git が追跡しないワークツリーやクローン）の
中のエントリは、そのチェックアウト自身の Git で判定されるため、そのフォルダに対する
ワークスペースの `.gitignore` がそれを拒否することはありません。プロジェクト外のチェック
アウトへのリンクやジャンクションを経由するエントリ（`wt-link/src/`、または全体なら
`wt-link/`）も同様で、ソース走査がそのリンク経由で列挙するものを包含します。
作業の記録済みチェックアウトの中にあるエントリも、そのチェックアウトの Git で判定され、
その列挙名をキーとします。プロジェクト外のチェックアウトはその形で名指しし
（`<label>@checkout/src/`）、リポジトリを記録する作業でも `repo` は付けません。作業が
記録していない列挙名は拒否され、それを記録する手順が示されます。
アップグレード前の欠落フィールドは、
文書化された移行証拠としてのみフェイルオープンします。存在するのに束縛できない、
または破壊された現行世代の証拠は、Guard Policy が strict のときフェイルクローズします。
relaxed または off では一度だけ記録して作業を続けます。コードや設定を出力する
独自ステージ（契約生成器、インフラコード実行器など）を追加するチームは、
ワークスペースガードが適用されるよう `workspace_requires: true` を設定してください。
継続的インテグレーションでは `AIDLC_SKIP_ARTIFACT_GUARD=1` でバイパスできます。
このスイッチはレビュー時の必須出力存在チェックもバイパスします。ソースの束縛と
帰属は、別途 `AIDLC_SKIP_SOURCE_FRESHNESS=1` でバイパスします。

### `produces_kinds`

`for_each: unit-of-work` ステージ上の任意マップです。各キーはステージの
`produces` または `optional_produces` 成果物名、各値はその成果物が適用される
ユニットの**種別**一覧です。種別は `units-generation` のエッジブロックでユニットごとに
宣言され（[ランタイムグラフ](13-runtime-graph.md) の
`bolt_dag.units[].kind` を参照）、次のいずれかです。
`service | spec | ui | packaging | library`。

```yaml
produces:
  - performance-requirements
  - security-requirements
  - scalability-requirements
  - observability-requirements
produces_kinds:
  performance-requirements: [service, ui]
  scalability-requirements: [service]
  observability-requirements: [service]
```

存在する理由: 4 つの構築設計ステージは、固定の `produces` 一覧を全ユニットに
同一適用していたため、仕様ユニットにもスケーラビリティ文書が、パッケージング
ユニットにもビジネスロジックモデルが課され、人手で N／A スタブを書く必要が
ありました。`produces_kinds` によりエンジンはユニットごとに行列を刈り込めます。
ユニットが `kind` を持つとき、エンジンはその種別一覧に含まれる `produces`
エントリーだけを残します。マップに**載っていない**成果物は全種別に適用されます
（種別固有のものだけ注釈してください）。種別が**ない**ユニット、または
`produces_kinds` マップ自体がないステージは全行列を保持します。したがって既存の
すべてのワークフローに対して不活性です。

刈り込みは対称です。`run-stage` ディレクティブの `produces` パス
（指揮者が書くもの）とユニット単位のカバレッジ検査（承認パスのガードが要求するもの）
の両方をフィルタします。`optional_produces` とも合成されます。ディレクティブのパスは
両リストの種別フィルタ済み和集合であり、カバレッジは必須の `produces` だけを
キーにします（任意成果物は適用されない種別ではディレクティブから刈られ、いずれにせよ
カバレッジ免除のままです）。必須集合が**空**に刈られるユニットは定義上カバー済み
です。ステージが適用されないためです。全ユニットが空に刈られるユニット単位
ステージは、成果物ガードでデッドロックせずノーオペレーションとして承認されます。
4 ステージの既定種別行列はステージフロントマターのデータであり、エントリーごとに
レビューと差し戻しが可能です。誤ったエントリーを削除すると、その成果物の全行列が
復元されます。

標準の NFR ステージは、`observability-requirements` と `observability-design` の
両方をサービス種別のユニットへ対応付けます。

信頼に関する注意: `kind:` 値は `units-generation` ゲートで列挙検査されます
（`required-sections` センサーは誤記で大きく失敗します）が、その後のコンパイル済み
ランタイムグラフは信頼されます。エンジンは `bolt_dag.units[].kind` を読むときに
種別の形状だけを検査します（コンパイル済みバッチを信頼するのと同じです）。
コンパイル済みグラフで手編集され、妥当だが誤った種別にされたユニットは、その誤った
種別の集合へ黙って刈られます。

### `consumes[].required`

消費エントリーごとのブール値です。意味上は**アクティブな計画にスコープ**され、
成果物がどこかに常に存在する、という大域アサーションではありません。

> `required: true` は「生成ステージがアクティブな計画で走るなら、この消費は
> 満たされなければならない」を意味します。「生成側が常に走る」意味では
> **ありません**。スコープが生成側を除外するとき（例: `bugfix` が
> `units-generation` をスキップ）、その生成側成果物に対するすべての
> `required: true` 消費は無意味になります。要求すべきものがありません。

**スコープ付き読みの理由。** すべてのステージを実行するのは `enterprise` と
`feature` だけです。他のすべてのスコープは、意図的に上流ステージをスキップします。平坦で大域的な
`required: true` はそれらのスコープを構造的に無効にし、それは誤りです。正当な
運用モードだからです。本当の契約は条件付きです。「上流が走るなら、下流に渡せ」。
ステージ本文は既に不在ケースを穏当に扱います（「利用可能なら」などの散文指示や、
コンテキストからのフォールバック）。

**診断リントへの意味。** リントは各アクティブ・スコープを歩き、「ステージ X の
成果物 Y に対する `required: true` 消費は、このスコープで Y の生成側が `SKIP`
のため無意味」と報告します。助言であり、ブロックしません。ユーザーはスコープ選択で
既に短縮を選んでいます。

**`when:`（受け付けるが、まだ評価しない）。** ステージは `when:` 述語を宣言できます。
現在スキーマが受け付けるのは `producer-in-plan` だけで、その形を検査しますが、まだ
何もそれに基づいて動作しません。そのためステージは、`when:` がない場合と同じく
`scopes:` に従って実行されます。`required: true` と
`conditional_on: brownfield|greenfield` の組が、エンジンが現在評価する 2 次元を
カバーし、`when:` はそれを一般化するためのものです。

### `consumes[].conditional_on`

ブラウンフィールド／グリーンフィールドの分岐を捉えます。例:
`reverse-engineering` はブラウンフィールド・モードでのみ成果物を生成します。
それらを消費するステージは、スコープ解決器へ「ブラウンフィールドのときだけ
この消費が必要」と伝えるため、消費に `conditional_on: brownfield` を付けます。

無条件の消費では、**フィールドを完全に省略**します。`always` 値はなく、
無条件の消費は単に `conditional_on` キーを持ちません。

### `consumes[].cited`

消費に付ける任意のブール値です。`cited: true` は、その入力が存在するときは常に
ステージの成果物がそれを引用することを示します。`upstream-coverage` 検査は、存在する
すべての必須の消費を成果物が引用するよう求めます。任意の消費（`required: false`）は
検査しません。任意の入力は出力に反映されていない可能性があるためです。ただし、その消費に
`cited: true` が付いている場合は検査します。要件分析は `intent-statement` と
`scope-document` に印を付けます。どちらもそこでは任意です。Ideation のないスコープは
どちらも生成しないからです。そして存在するときは、要件はそれらを土台にします。

コンパイルは、印の付いた消費をステージの `cites` として `stage-graph.json` に列挙し、
コンパイル済みの `consumes` エントリはそのまま保ちます。そのため印を付けても外しても、
すでに完了したステージの記録は変わりません。このフラグがトップレベルの一覧ではなく
消費の上にあるのは、2.8.0 から 2.11.0 のプロジェクトが自身のツールで新しいリリースへ
更新するためです。そのツールは消費の中のキーは受け付けますが、知らないトップレベルの
キーは拒否します。

```yaml
consumes:
  - artifact: intent-statement
    required: false
    cited: true
```

### `optional_produces`

`produces:` と並ぶ、プレーンなケバブケース文字列リストです。ステージがユニットごとに
**書いてよい**が**必須ではない**成果物を名付けます。不在はなしを意味します。
必要な 1 ステージだけ（`frontend-components` のための `functional-design`）が
宣言するため、コンパイル済み `stage-graph.json` は最小のままです。

存在する理由: ユニット単位の構築ステージ（`for_each: unit-of-work`）は、その
ユニットの記録ディレクトリ上にすべての `produces[]` 成果物があるときだけ、その
ユニットについてカバー済みになります（`aidlc-orchestrate.ts` 内のユニット単位
カバレッジ検査）。一部の成果物はユニットに対して本当に条件付きです。
`functional-design` はユニットに UI があるときだけ `frontend-components` を
書きます。これを `produces:` に載せると、バックエンド専用ユニットでもカバレッジを
満たすため N／A スタブを書かされ、書くまでステージゲートに到達できません
でした。`optional_produces:` へ移すと免除されます。

- **カバレッジ免除。** `optional_produces` エントリーはユニット単位カバレッジ
  ループで無視されます。ユニットは**必須**の `produces[]` 成果物が存在する時点で
  カバー済みです。任意のものは `next` の進行も `approve` のコミットも妨げません。
- **指揮者には依然として解決される。** `run-stage` ディレクティブの `produces`
  パスは `produces` + `optional_produces` の和です。ユニットが条件付き成果物を
  **実際に**書くとき、指揮者は配置先を知ったままです。ステージが
  `produces_kinds` も宣言している場合、その和は解決前に種別フィルタされます
  （上記の `produces_kinds` を参照）。任意成果物が適用されない種別にはパスが
  見えません。
- **語彙にも残る。** `artifactsRegistry()` と `producersOf()` は両リストを和集合
  にするため、成果物名とその生成ステージは登録されたままです。

**対の規約。** すべての `optional_produces` エントリーは、ステージ本文の散文
（および `outputs:` 文字列）に、いつ書くかをエージェントへ伝える
`(CONDITIONAL - ...)` マーカーを**必ず**持たなければなりません。フロントマター
キーはエンジンのカバレッジビュー、散文はエージェントへの指示です。同期を保って
ください。

**警告。** `optional_produces` と印された成果物はユニット単位カバレッジ台帳から
見えません。エンジンはユニットがそれを生成したことを証明できません。ユニットに
対して正当に条件付きの成果物にだけ使い、ステージがユニットごとに常に書くべき
成果物のカバレッジを静かに緩める用途には使わないでください。

### `mode`

ステージの**通信トポロジー**、すなわち本文の実行中に誰が誰と話すかです。
値は 5 つで、4 つが有効です。

- `inline` — 指揮者が自身のコンテキストでステージを実行します。サポート
  エージェントは指揮者が取り込む視点（声）です。ディスパッチはゼロ。短い
  ステージで、実行が速く、コンテキスト圧迫がありません。
- `subagent` — ハブ・アンド・スポーク。リードは新しいサブエージェント・
  コンテキストへディスパッチされます（指揮者のコンテキストを溢れさせる長い
  ステージ、例: 構築のコード生成）。ステージが `support_agents` も宣言する
  場合、各サポーターはリードが返したドラフトに対する実際のスポークとして
  ディスパッチされ（互いに盲目のブリーフが成果物をパスで運び、ステージのルールは
  `stage-protocol.md` § "For subagent stages" のステップ 2 に従って届けられます）、
  統合のためリードがもう一度ディスパッチされます。
- `pipeline` — チェーン。リードがドラフトし、各サポートエージェントが宣言順に
  充実させます。各リンクはドラフトとそれ以前のすべての貢献を見ます。順序
  こそが要点です。空でない `support_agents` が必要です。
- `mob` — メッシュを有界ラウンドとして実行します。全サポートエージェントが
  リードのドラフトに対して並行に貢献し（互いに盲目）、リードが統合し、未解決の
  異議者は他参加者の立場を提示されたうえで確認か維持かの 1 ラウンドを得ます。
  維持された異議はゲートで逐語的に引用されます。空でない `support_agents` が
  必要です。出荷済みのショーケースは `user-stories`（プロダクトマネージャーが
  リード、デザイン・開発者・品質が協働者、プロダクトリードがレビュアー —
  モブ詳細化の儀式）です。
- `agent-team` — **予約済み**。メッシュ協働の将来のネイティブバス・トランス
  ポートです。実験的な `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS` プリミティブが
  安定すれば、ライブのピアメッセージング・ルームが、指揮者が運搬するラウンド
  なしに `mob` の意味論を運べます。`mob` が可搬なモードであり、どのステージも
  `agent-team` を宣言しません。

どのトポロジーでも指揮者がバスです。エージェント同士は呼び合わず、委譲するのは
指揮者だけです。書き込みモデルは実際の作業セッションを映します。全員が自身の
作業を書き、所有者が集約して編集します。ディスパッチされた各サポート
エージェントは貢献ファイル（`contributions/<agent-slug>.md`、identity-marker の
先頭行を持つ `stage-protocol-collaborators.md` の形）を書き、ステージの `produces[]`
成果物を編集するのはリードだけです。パイプラインのリンクは代わりに成果物を
直接前進させます。mob およびサポーター付き subagent のステージでは、貢献
ファイルが完了の証拠であり、1 つでも欠けている間はエンジンが承認を拒否します。
レビュー・ループはモードでは**ありません**。`reviewer` +
`reviewer_max_iterations` が任意のモードの上に二者批評トポロジーを提供し、
NOT-READY はリードだけを再度呼び出します。

**消費者契約。** `mode` フィールドを読むオーケストレーターコードは
`agent-team` を明示的に扱わなければなりません。最低でも
「`agent-team` モードは未実装」を送出してください。既定の実行パスへ
フォールスルーしてはいけません。列挙拡張時の黙ったフォールスルーは既知の落とし穴です。

**スウォーム・トリガー結合。** 自律的な構築スウォームは
`for_each: unit-of-work` + `mode: subagent` で発火します。ユニット単位の
ビルドステージのモードを変更すると、黙ってスウォームパスから外れます。
`aidlc-graph compile` はその形状を見つけると stderr へ助言を出します。

### `lead_agent` と `support_agents`

リードエージェントがステージを所有します。リードのペルソナ（スキル、ナレッジ、
ツール許可リスト）はステージ開始時に読み込まれます。サポートエージェントは視点を
足します。要件作業では `aidlc-product-agent` をリードにし、容量の現実確認のため
`aidlc-delivery-agent` をサポートとして読む、といった具合です。

両フィールドは、アクティブなハーネスのエージェントディレクトリを読む `loadAgents()` 経由で
`.claude/agents/*.md` に対して動的検証されます。`aidlc-graph.ts compile` は
発見したエージェント `slug` を `validateStageFrontmatter` へ渡すため、一致する
ファイルがないエージェント名を持つ `lead_agent` または `support_agents` は、
実行時に未登録サブエージェントの `Task` エラーとして現れるのではなく、コンパイル時に
大きく失敗します（`lead_agent "<name>" has no matching .claude/agents/*.md`）。
唯一の例外は予約済みの `orchestrator` 擬似エージェント（指揮者自身で、ブートストラップ
初期化ステージの `lead_agent` として名付けられます）。設計上エージェントファイルは
ありません。スキーマにハードコード列挙はなく、エージェント追加は必要なフロントマター付き
`.md` ファイルを `.claude/agents/` に置くことです。
[貢献: エージェントの追加](11-contributing.md#エージェントの追加)を参照してください。

### `reviewer`、`review_artifact`、`reviewer_max_iterations`、`review_class`

任意です。`reviewer` は、ステージ本文が成果物を生成したあと、承認ゲートの前に
呼ばれる品質ゲート・エージェントを名付けます（[ステージ・プロトコル](04-stage-protocol.md)
を参照）。今日出荷されるレビュアーは 2 つ —
`aidlc-product-lead-agent` と `aidlc-architecture-reviewer-agent` — であり、
コンパイルは `lead_agent` と同じく、発見済みエージェント名簿に対して値を検証します。

レビュアーを持つステージは `review_artifact` も宣言し、`produces[]` にある必須の Markdown 成果物を 1 つ指定します。これはレビューの対象となる成果物です。レビュー記録はこの成果物をキーとし、ゲートにもこの名前を表示します。指摘事項は `--reject-finding` / `--reopen-finding` / `--fix-finding <artifact>#R-NN` で指定します。レビュアーが対象成果物へ書き込むことはありません。出力の並び順やプラグインが追加した出力によって、レビュー対象が変わることはありません。Unit 単位のステージでは、いずれかの必須出力が適用されるすべての Unit 種別で、レビュー対象も適用可能でなければなりません。満たさない場合はグラフのコンパイルが失敗します。`traceability.json` のような構造化出力はレビュー対象にできません。

`reviewer_max_iterations` は、未解決の指摘を抱えたままゲートへ進む前の
レビュー／改訂ループの上限です。`reviewer` が宣言されて上限が無いとき
**既定は 2** です。指定する値は正の整数でなければならず、それ以外の値はコンパイル前のスキーマ検証で失敗します。
`reviewer` を宣言しないステージではフィールドを省略してください。コンパイラは
`reviewer` なしの `reviewer_max_iterations` を拒否します（スキーマエラー
`reviewer_max_iterations requires a reviewer` がグラフコンパイルを失敗させる）ので、
黙って無視されることはありません。

`review_class` はレビュー契約を選びます。`adversarial`（上記の反証と修復のループ。`reviewer` がクラス無しで宣言されたときの既定）か、`advisory`（通常フローの 1 パスを実行し、その指摘事項を人間の承認ゲートでエンジンが管理する指摘リストから示す。修復ループなし、実効の反復予算は 1）です。後続の書き込みがその終端受領記録を無効化した場合は、次の序数での 1 回だけの有界な回復リクエストが許されます。本人が求めたレビューが拒否されることはありません。出荷時の割り当ては、人間ゲート付きの Ideation / Inception の文章系 8 ステージが `advisory` を宣言し、Construction の設計・実装 5 ステージが既定の `adversarial` です。`none` は意図的にステージの値ではありません。レビューを不要とするステージは `reviewer:` 行を削除します。`none` はスコープの `review_cap` と実行単位の `--review` 上書きに存在し、ステージを編集せずに宣言済みレビュアーを黙らせられます。実行時の実効クラスは、ステージ宣言を 1 つの上限で引き下げたものです。作業単位の `--review` 上書きが設定されていればそれを、なければアクティブなスコープの `review_cap`（出荷時の `bugfix`、`poc`、`classic`、`workshop` は `advisory` に制限し、`express` は `none` に制限）を上限とします。上限はクラスを引き下げられますが、ステージの宣言を超えて引き上げることは決してありません。作業単位に設定した上書きはスコープの上限を置き換えるので、上限のあるスコープで `--review adversarial` を指定すると、各ステージ自身のクラスで実行されます。自律スウォームのレビューは上限と上書きの対象外です。Bolt 内ではレビュアーがマージ前の唯一の検証手段であるため、そこでは常にステージ宣言のクラスが適用されます。上限と同様、`review_class` は `reviewer` を必要とします（スキーマエラー `review_class requires a reviewer`）。

スコープのフロントマターは、5 つのセレモニースイッチも受け付けます。いずれも `on` | `off` で、省略時は on です（ただし `collaborators` は、出荷時には `enterprise` でだけ on です）: `sensors`、`learnings`、`summary_confirmation`、`plan_approval`、`collaborators`（off ではすべてのステージをリードだけで実行します。レビュアーには影響しません）。スコープの `summary_confirmation` は、ステージの `summary_confirmation: required | if-present` とは別物です。スコープ / インテントの方針は、その確認ポイントをそもそも適用するかどうかを決めます。`/aidlc --sensors on|off`、`/aidlc --learnings on|off`、`/aidlc --summary-confirmation on|off`、`/aidlc --plan-approval on|off` は、インテントのスコープ既定値を上書きします（計画承認を off にできるのは本人だけです）。`AIDLC_DISABLE_SENSORS=1`、`AIDLC_DISABLE_LEARNINGS=1`、`AIDLC_DISABLE_SUMMARY_CONFIRMATION=1`、`AIDLC_DISABLE_PLAN_APPROVAL_GUARD=1` は、それぞれのセレモニーを強制的に off にします。Classic はセンサー、学習、計画承認を有効にし、要約確認を無効にします。bugfix は学習と要約確認を無効にします。express と poc は計画承認を無効にします。各コード計画を尋ねずに作る計画承認 off を除き、ステージ承認、人間のターンの権限、監査、チームの書き込み保護は引き続き有効です。

### `ars`

任意です。ステージの**コンポーザー選別の事前値**で、`tools/data/ars-priors.json` の
1 エントリと同じ 4 つの事実を、ステージ自身のフロントマターに書いたものです。

```yaml
ars:
  targets: [ve, r]            # ARS components the stage reduces: iae | csu | ve | r | ua
  cost: 4                     # 1 (trivial) .. 5 (heavy); null = never numerically screened
  role: structural            # optional: initialization | core | phase-gate | structural
  project_types: [brownfield] # optional: mirror a condition: that restricts the project kind
```

リストはインライン（`[a, b]`）です。ブロックは次のトップレベルキーまで続くため、
その中の空行や `#` コメント（末尾のものを含む）は許されます。

存在する理由: `aidlc-graph ars`（[CLI コマンド](../guide/12-cli-commands.md) を参照）は、
コストの事前値と対象とする構成要素から、各ステージを EXECUTE/SKIP に選別します。
出荷される事前値はコアステージだけを名指しし、プラグインはそのファイルを編集できない
ため、プラグインのステージは以前、コンポーザーが判断だけで決めるしかない `no-prior` 行に
なっていました。スキーマはこのブロックを事前値ファイルのエントリと同様に検証し、
`aidlc-graph compile` がそれをノードへコピーし、`ars` サブコマンドはファイルのエントリと
まったく同じように選別します。`role: core` は常に実行し、`structural` と `null` コストは
ゲートでの判断に任され、`project_types` は別のプロジェクト種別ではステージを選別から外し、
`--completed` のステージは何よりも優先します。事前値ファイルには、ステージブロックでは
宣言できない役割が 1 つあります。`project-type`（Reverse Engineering）です。これは
スコアにかかわらず、自分のプロジェクト種別でステージを実行します。そのため、その種別でも
プラグインステージの `project_types` は引き続き構成要素によって判定されます。

選別を予測可能に保つ規則が 3 つあります。

- **事前値ファイルが勝つ。** スラッグにファイルのエントリと `ars:` ブロックの両方が
  あるときはファイルのエントリを使うため、ステージ側の編集でコアの選別が変わることは
  ありません。コアステージは `ars:` を宣言しません。
- **空の `targets` が機械的に実行されることはない。** 数値コストを伴う `targets: []` は
  合法ですが、`role` がなければ何も閾値を越えられません。行は SKIP になり、その旨を述べる
  理由が付きます。
- **コストには閾値がなければならない。** `cost` はコンポーザーペルソナの `1..5` の尺度に
  留まり、読み込んだ事前値ファイルにその値の `evThresholds` エントリがない場合、
  `aidlc-graph ars` はそのステージを名指しして終了コード 1 で終わります。

各選別行の `priorSource`（`shipped`、`stage`、`null`）は、その事前値がどこから来たかを示します。

## エージェント・フロントマターとの関係

ステージとエージェントは同じ YAML 優先の規律に従います。エージェント・フロントマター
（[エージェント・システム](05-agent-system.md#frontmatter-契約)を参照）は
*誰が* — エージェント名、許可ツール、階層 — を宣言します。ステージ・フロントマターは
*何を* — ステージが生成・消費する成果物、委譲先エージェント、実行方法 — を宣言します。

両形式とも:

- 各領域の権威あるソースです（並行するハードコード写像はありません）。
- 型付き構造を返す `loadX()` ヘルパーと共に出荷されます。
- ハードコード列挙ではなく、ファイルシステムに対して動的に検証します。

新しいステージの追加は新しいエージェントの追加と同じ形です。`.md` ファイルを置き、
必要なフロントマターを追加すれば、ヘルパーが実行時に拾います。

## 実例

正規の例は `scope-definition` です。規範的な YAML ブロックは
`dist/claude/.claude/aidlc-common/protocols/stage-definition.md` にあります。
ここへ複製せず、そちらを参照してください。

この例は、今日の散文が述べる内容を構造化してコード化しています。

- `requires_stage: [intent-capture]` は、散文指示「意図の記録ディレクトリ配下の
  `ideation/intent-capture/` から意図表明を読む」をコード化します。パーサーは
  散文を気にせずグラフの辺だけを見ますが、人間の読者は両者を同期させておくべきです。
- `consumes: [{artifact: intent-statement, required: true}]` は、
  `intent-statement` が存在するまでこのステージがブロックされることを示します。
  スコープの解決器が `intent-statement` の生成側を見つけられない場合、診断の
  欠落生成側検査が失敗します。
- `produces: [scope-document, intent-backlog, scope-definition-questions]`
  は前方の辺です。「誰が `scope-document` を生成するか？」を探す他ステージは
  `aidlc-graph.ts producersOf()` 経由でこれを見つけます。
- `for_each` フィールドなし — `scope-definition` はワークフローごとに一度実行されます。

## 本文の 3 区画モデル

ステージファイルの本文には、この順で宣言される 3 区画があり、出荷されるすべての
ステージが 3 つとも埋めています。

| 区画 | ここに入るもの |
|-------------|----------------|
| `## Steps` | エージェントが従う命令形の散文 |
| `## Sensors` | 出力先・インポート済みセンサー・上流ターゲットの簡潔な要約。ステージ固有の例外はローカルに残す |
| `## Learn` | 共有のセクション 13 の学習ループ契約とそのブートストラップ例外への簡潔なポインター |

順序が固定されているため、ステージのセンサーのバインディングと学習ループへのポインターには
常にそれぞれの置き場所があります。`## Sensors` のバインディング意味論とプルインポートモデルは
[センサー・システム](07-sensor-system.md)を参照してください。センサーの共通挙動は
`stage-protocol-sensors.md` に一度だけ定義され、日誌と学びの手続きは `stage-protocol-learnings.md` のセクション 13 にあります。directive.protocol_modules に learnings がある場合だけ実施し、それ以外では両方を省きます。
`## Sensors` と `## Learn` の見出しは、33 の全ステージにわたって
`t87-stage-compartment-headers` が検査します。`## Steps` はすべてのステージにありますが、
専用のテストはありません。

## パーサーとエミッター

`parseStageFrontmatter` と `emitStageFrontmatter` は `core/tools/aidlc-lib.ts` にあり、
YAML のみです。`bun scripts/package.ts` が生成するすべてのツリーで実行する
`aidlc-graph.ts compile` が、YAML を `stage-graph.json` へコンパイルします。リポジトリは
そのファイルを無視される投影の中でだけ生成します。ソースツリーのゲートは、コミット済みの
コンパイル済みファイルのドリフト検査ではなく、パッケージの決定性です。

## 既知の制限

- **`for_each` を使うのは構築フェーズだけ。** ユニット単位の 5 つの構築ステージは
  `for_each: unit-of-work` を宣言し、他の 28 ステージはフィールドを省略します。
- **`when:` は受け付けるが評価しない。** 上のフィールドの注記を参照してください。
- **コンパイル時に検証されるのはフロントマターだけ。** 本文の散文は解析されません。
  その `## Sensors` と `## Learn` の見出しはテストスイートが検査し、エンジンの実行時
  ガード（たとえばステージの必須作業に対する完了検査）は、ステージの散文ではなく
  ステージが生成するものに作用します。

## 将来の拡張 — 予約名前空間

仕様は、後続リリースで AI-DLC が追加しそうなプリミティブの名前を予約します。
スキーマは未知キーを拒否します。ここでの予約は、将来の貢献が場当たり的な追加と
衝突するのを防ぎます。

| キー | 予約の対象 | 担う役割 |
|-----|----------------|-----------------|
| `on_failure` | ループドライバー | 宣言的エラー回復 — 「このステージが失敗したら X へ戻る」または「調整した入力で再試行」。改訂意味論を `stage-protocol-recovery.md` の散文から移すことになる |
| `blocks_on` | 構築のワークツリー | データ読みなしの完了依存 — 今日過負荷の `requires_stage`（「あなたの出力を消費する」と「あなたの後に走る」を混同）を分割することになる |
| `timeout` | センサー・バインディング | 実行予算（期限）。ステージ・フロントマターではなくセンサー・バインディングに置く |
| `retry` | ループドライバー | 失敗時の再試行方針。ステージ・フロントマターではなくループ設定に置く |

`when` はもう予約ではありません。スキーマは `producer-in-plan` 述語とともにそれを受け付けて
形を検査しますが、評価はまだこれからです（上の `consumes[].required` を参照）。

設計根拠: Claude Code 自身のタスク・プリミティブ（`TaskCreate` 系に加え
`/loop` と定期実行）は依存、ブロック、再試行、タイムアウトを省略し、多段階
オーケストレーションはすべてクライアント側コードへ押し出します。この実装は、
実行振る舞い（再試行、タイムアウト、失敗処理）をステージ仕様ではなくループと
センサーのサブシステムに置くことで、その選択を映します。上記フィールドは、
消費者が現れたときの控えめな構造拡張であり、新しいパラダイムではありません。

予約名前空間のパターンは監査分類（[状態機械](12-state-machine.md)）に先例が
あります。監査分類は、イベント名を出力するコードが出荷されるまで、出力元セルを
`Reserved` としてその名前を事前登録でき、廃止された名前は `Reserved (retired name)`
として保ちます（現在は `CHANGE_CONTROL_SET`）。
