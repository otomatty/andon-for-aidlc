# テスト

## 概要

AI-DLC のテストスイートは**完全に TypeScript 製**です。すべてのテストは `bun` で実行される `t*.test.ts` ファイルであり、シェル（`.sh`）のテストファイルは 0 です。これが、同じファイル群が macOS、Linux、ネイティブ Windows で同一に動くという、構造によるプラットフォーム不変性の保証です。

スイートは `tests/` 配下の 1 ディレクトリずつ、**4 つのレベル** `smoke`、`unit`、`integration`、`e2e` で構成されます。この 4 レベルは、速度と網羅性の釣り合いを取る古典的な 3 層テストピラミッドへ対応付けられます。

```
            /\
           /  \    ACCEPTANCE — full workflows, artifact + experience verification
          / L3 \   Level: e2e  ·  When: local --release/--all; pre-release confidence
         /------\
        /        \
       /   L2     \  STAGE — individual stages with stub input, verify artifacts
      /------------\ Level: integration  ·  When: local default/--ci; PR gates
     /              \
    /      L1        \  PROTOCOL — contracts, structure, cross-references
   /------------------\ Levels: smoke + unit  ·  When: local changes and PR CI
```

`--ci` プロファイルと、フラグなしの既定実行はどちらも **smoke + unit + integration** を走らせます。つまり integration レベルは毎回のローカル `bun tests/run-tests.ts` に含まれます。`--release` / `--all` はそこへ `e2e` を加えます。上のピラミッドは各レベルの概念上の位置付けであり、実際の選択方法は下のプロファイルフラグです。

### テストの境界と所有

ディレクトリは実行のセレクターであり、コストについての約束ではありません。特に、`unit` には現在、CLI、インストーラー、ネイティブビルド、ワークフロー全体のテストが含まれます。`--no-llm` はモデルのゲートを閉じますが、テストを隔離された単体テストにするわけではありません。テストは、そのアサーションが試す境界で分類してください。

| 種類 | 証明するもの | 既存の例 |
| --- | --- | --- |
| ユニット | 制御された入力による直接の関数呼び出しを通じた、規則や変換 | バージョンの文法、文書のスキーマ、シャードの選択 |
| プロセスまたはアダプターの契約 | 実際の境界における終了ステータス、stdin/stdout、ファイルシステムへの影響、ハーネスのペイロード | フックのアダプター、インストール、プロセスの後片付け |
| 決定論的なジャーニー | 複数のエンジンのステップ、返答、ガードが組み合わさって期待どおりの結果になること | Plan Approval、スコープ実行、ガードマトリクス |
| ライブのジャーニー | 本物のエージェントとハーネスが、人が期待する結果を届けること | SDK、ターミナル、IDE の受け入れジャーニー |

入力のバリエーションは、契約を忠実に試せる最も安い層に置いてください。プロセス、並行性、プラットフォームの検査は、その境界こそがテスト対象の振る舞いであるときに残します。ライブのジャーニーは正確な失敗注入の代わりにはならず、アダプターの配線を証明するために、すべてのユニット入力をすべてのハーネスで再生する必要もありません。

回帰テストを追加する前に、同じ振る舞いを所有するスイートを探してください。セットアップと境界が一致するなら、それを拡張します。2 つ目の `covers:` の主張があっても、同一の入力とアサーションを 2 回実行する必要はありません。1 つのケースで、コマンド、状態の変化、監査イベントをまとめて覆えます。繰り返されている本体を取り除く前に、フィクスチャ、フック、パラメーターの表、プラットフォームの実装を比較してください。

オンボーディングの契約は `t-tui-onboarding` に属し、IDE のプロセス／プロファイルの隔離のケースは `t-e2e-driver-isolation` が所有します。`t47-failure-injection` は 4 つの CLI の失敗とその `ERROR_LOGGED` の証拠を所有します。それらに固有のアサーションは、2 つ目のファイルで再生されるのではなく、それらのスイートに残ります。

リリースのフィクスチャは、生成されたコピー／ネイティブのツリーを読んで独立したアーカイブを組み立て、要求されたバージョンを各アーカイブのスタンプにメモリ上で適用します。すべての配布物について、ディスク上にもう 1 つコピーを作る必要はありません。各呼び出しは現在のソースを読み、自分の出力を所有します。後のソースの変更は見え、1 つのフィクスチャを壊しても、別のフィクスチャや生成されたツリーは変わりません。

より広い一覧が issue #2774 で再編される間、4 つのセレクターと現在の CI の行き先はそのまま残ります。ファイルを移動するときは、その検出、カバレッジの主張、プラットフォームの選択、シャードのアフィニティ、マージ前の必須実行を保たなければなりません。セットアップ時間、テスト時間、ランナーの使用量は別々に測ってください。ディレクトリの移動やケース数の減少だけでは、性能の成果にはなりません。

`tests/harness/test-budget.ts` の共有ポリシーは、タイムアウトを失敗の最終防御として扱います。コールドインポート、ウイルス対策ソフト、プロセス生成、プロバイダーのスケジューリングはランナーによって大きく異なり、速く終わった実行が適切なタイムアウトを決めるわけではありません。
指定のない決定論的なケースには、どの OS でも 10 分が与えられます。フィクスチャ全体に共有のプロファイルを選び、より小さな個別の上書きは取り除いてください。

| 作業負荷 | 既定の上限 |
| --- | --- |
| ネイティブのプロセスまたは CLI の起動 | 5 分 |
| ランタイム引き継ぎのフィクスチャ | 20 分 |
| コンパイルまたは配布物の生成 | 15 分 |
| フィクスチャのセットアップと CLI を多用するケース | 30 分 |
| 複数ワークツリーのケース全体 | 60 分 |
| ライブの起動 | 10 分 |
| ライブのコマンドまたは成果物生成の作業 | 30 分 |

これらは上限であり、成功した操作はすぐに戻ります。テストが意図的に検証するタイムアウトは、明示的で短いままにします。所有権、終了ステータス、再帰、人間の境界、その他の正しさのアサーションは引き続き強制されます。
経過した実時間はそれらのアサーションの代わりにはなりません。テストが性能ではなく振る舞いを証明する場合は、直接の状態または注入した時計を使ってください。

本番のツールと単体バイナリのゲートは、`core/tools/aidlc-runtime-budget.ts` の運用上の既定値を共有します。[ランタイムとネイティブフックの予算](06-hooks-and-tools.md#runtime-and-native-hook-budgets)を参照してください。
呼び出し側の明示的な予算と、意図的な応答性の契約は、既定の実行時の最終防御とは別物のままです。

予算のレビューには、入れ子のサブプロセス、セットアップ、ポーリングの期限、クリーンアップ、CI の上限が含まれます。Bun のケース上限だけを引き上げても、より短い子プロセスの上限は直せません。
ドライバーの操作は、親の実際の残り予算を使います。逐次的な操作はその予算を共有します。後のすべての操作の最大許容量を予約しないでください。
ライブケースのヘルパーは、作業、セットアップ、クリーンアップの各段階の周りに余裕のある Bun の上限を与えますが、ファイルの期限が引き続き権威です。前の作業がファイルの時間を使った後に、すべての段階にその最大値を約束するものではありません。

インフラも同じ共有ポリシーを使います。

| 操作 | 既定の上限 |
| --- | --- |
| プロセスの識別子の発見 | 10 分 |
| 1 回のプロセス照会または終了の呼び出し | 5 分 |
| プロセスツリーのクリーンアップ | 15 分 |
| スーパーバイザーの終了と状態の公開 | 17 分 |
| 最終的な端末出力の排出 | 2 分 |
| デーモンの退役を含む端末クライアントの終了 | 合計 19.5 分 |
| ワーカーのクリーンアップと確認 | 合計 20 分 |

これらは操作ごとの最大許容量です。ファイルのクリーンアップは最大 5 分を一度だけ予約し、親の期限が各操作の許容量を切り詰めます。
`remainingCleanupTimeoutMs` は、作業の予約分を再度差し引くことなく、予約した末尾を含む元のハードな期限を使います。ハードな期限切れの時点では、最小限の即時の退役の試行だけを許可します。端末クライアントは、RPC とデーモン退役の待機にまたがって 1 つの終了期限を共有します。ポーリングは必要な証拠が得られ次第戻ります。識別子や退役の証拠が欠けていれば、引き続き失敗します。

ディスパッチされる各ファイルは、通常の integration/SDK のファイルを含め、独立したスーパーバイザーの期限を持ちます。`--file-timeout N` はそれを秒単位で制限します（隔離された E2E 以外での既定は 2 時間）。`--run-timeout N` は、セットアップと選択したすべてのファイルにまたがって 1 つの作業期限を共有します。使い切った予算は目に見える形で失敗し、必須のアサーションを飛ばすことはありません。実行は 1 つのクリーンアップの締め切りを保つため、あるファイルのクリーンアップを早く終えても、その予約された時間に追加の作業が入ることはありません。
ドライバーは解体のためにファイルの枠のうち最大 5 分を残し、作業が協調しない場合でも、ランナーは所有するプロセスを退役させ失敗を記録します。これらのフラグはディスパッチされた作業を制限するもので、コーディネーターの退役、フィクスチャの保持、レポートの公開はその後に続きます。
それらのネイティブのクリーンアップ検査は引き続き制限され、CI の外側のステップ／ジョブの上限が、収集のための最終的な実時間の防御になります。プロセスのクリーンアップが不確かな場合は、フィクスチャを保持します。ログには、解決された許容量、絶対期限、クリーンアップの予約が記録されます。

配布に関するテストは、検証する契約ごとに分かれています。

- `t145-packaging-parity.test.ts` は、独立したクリーンなパッケージ生成を 2 回行い、コピー版、ネイティブ版、プラグインの生成結果が決定論的であることを検証します。
- `t238-build-binaries.test.ts` は、単体で動くバイナリ一式をコンパイルして検証します。ネイティブルート、フック／アダプター、プロジェクトの変更、`PATH` に `bun` がない最終インストール構成を含みます。
- `t242-plugin-state.test.ts` は、ホスト側の一覧の正規化、構成ハッシュ、同期トランザクションのロールバック、所有権を守った不要ファイルの削除を検証します。
- `t243-install-mechanism.test.ts` は、アーカイブの拒否、共有トランザクションエンジンと復旧経路、プロジェクトの init／refresh における所有権、チェックサム、ライフサイクル、バージョン固定、オフラインパッケージ、コピー版とネイティブ版の分離を検証します。
- `t244-install-management.test.ts` は、マシン設定、更新の検出、インストーラーのハーネス選択、Windows のライフサイクル操作、補完、リリースワークフローでの候補の継続性を検証します。
- `t330-release-channel-grammar.test.ts` は、stable／preview の閉じた version-id の文法、インストーラーとライフサイクル処理に埋め込まれたその文法、ランチャーシムを経由する preview のインストールを固定します。
- `t331-preview-channel-lifecycle.test.ts` は、`config --channel`、チャネルに応じた `update` と `update --check`、API 失敗時の unavailable 判定、stable への切り替え、preview の保持とバージョン固定を検証します。
- `t332-preview-release-pipeline.test.ts` は、注釈付きタグによるプレリリースの公開、preview の計画処理とノート、計画記録を検証します。1 つの UTC 日付に、定期公開後の手動実行を含め、ソースが変わった preview を複数回公開できることを確認します。未変更のソースや追い越されたソースはスキップし、下書きや孤立タグは占有されていない id での再試行の計画を許可します。ワークフローのアサーションは、`main` が進んだ後に実行が開始時のコミットを計画・公開すること、stable タグと定期／手動の preview の分離、共有の `release-preview` の同時実行制御、契約ゲートの祖先関係、チャネル別の来歴の署名者、ビルドの版の埋め込み、そして Full Suite が失敗しても preview のワークフローを失敗させずに preview をビルドすることを検証します。
- `t-ci-preview-test-report.test.ts` は、preview の Full Suite レポートを検証します。各成果物自身の実行（ランナーのフィクスチャの実行ではない）からの失敗したファイルとケース、失敗したジョブ、無害化されたマークアップ、レポートのサイズ予算、そして answers コーパスのセクション（合格時も失敗時もライブの成果物の最後の試行から読み、公開されるノートには入れない）です。
- `t-live-answers-nightly.test.ts` は、answers コーパスの毎晩の実行を検証します。日付によるローテーション、Claude SDK のライブジョブでそれを開くスイッチ、取りこぼしは報告されるが義務にはならず、例外を投げた駆動は引き続き失敗すること、そして毎晩のレポートが読み戻す要約です。
- `t-ci-full-suite-evidence.test.ts` は、任意の Full Suite の証拠の検査器と、正確なコミット／実行の照合を検証します。`t-release-promotion.test.ts` は本物の Git 履歴を使い、preview の選択、正確なソースの保持、メタデータ、制御のスナップショット、再試行、エントリから描画される stable のページ（2.11.1 のページがゴールデン）、スキャンした貢献者の一覧、main のメタデータの同期を検証します。

テストランナーは、テストを探索する前にプロセスロックの下ですべての配布ツリーを再生成します。そのため、新しいクローンは既存の `dist/` のバイト列に依存しません。CI も生成ツリーを使う各ジョブの前に明示的なパッケージのステップを実行します。バイナリとリリースのパッケージャーは、`dist-release/` を読む前に、自身でも再生成と決定性の検査を行います。

リリース CI は Linux、macOS、Windows でネイティブのスモークテストを追加し、7 対象の成果物を各ネイティブランナーのアーキテクチャでビルドし、Bun と Node.js に共通の、文書化された実行時の前提条件 `libgcc` と `libstdc++` を導入した使い捨ての Alpine コンテナーで musl の両プローブを実行します。musl マトリクスは
`fail-fast: false` を使うため、両アーキテクチャが結果を報告してから、CI がチェックサム検証済みの候補を 1 つ用意します。Unix と Windows のライフサイクルの検証は、署名権限を持たずにそのバイト列を使います。その後、ワークフローがそれらに証明を付け、1 つのワークフロー成果物としてアップロードします。`release` はタグとチェックサムを再確認し、`GITHUB_TOKEN` でソースリポジトリに GitHub Release を作成して、アップロードした資産の一覧を候補と照合します。
公開時に候補を再ビルド、再パッケージすることはありません。

`tests/harness/release-fixture.ts` は、生成された配布物のマニフェストから決定論的なリリースディレクトリを作成し、リダイレクト、遅延、途中切断、キャプティブポータル、過大なメタデータ、資産欠落の障害を付けてローカルで提供できます。フィクスチャを作成するには
`bun tests/harness/release-fixture.ts --output <dir>` を実行します。
通常のスイートはオフラインのままです。t243 の実行時に `AIDLC_RELEASE_CONTRACT_LIVE=1` を設定すると、公開リリースのメタデータとチェックサムの契約検査を追加できます。

決定論的な e2e スライス（`bash tests/run-tests.sh --debug -P 8 --e2e --filter "^t[0-9]"`）は CI で `--no-llm` 付きで走り、ローカルの開発ループの既定は smoke + unit + integration です。マージ、ワークツリー、スウォームの経路に触れるブランチでは、レビューラウンドの前にこのスライスもローカルで走らせてください。通常ボルトとスウォーム実行のあいだのモード境界のリグレッションは、既定の層からは見えないからです。

**ファイル名規約。** テストのファイル名は `t<NN>[-description].test.ts` です。含まれるのは、それが置かれるレベルディレクトリと任意の人向け説明だけです。名前に**方式を表す区分は存在しません**。テストの方式、つまり CLI を起動するのか、SDK を駆動するのか、ライブ TUI を描画するのかは、ファイル名で宣言されるのではなく、そのテスト本文が実際に呼ぶドライバーから計算される*導出された集合*です。各テストが何をカバーするかの機械検証済み索引は、`tests/gen-coverage-registry.ts` がディスク上の `covers:` ヘッダから毎回新しく構築します。ここに手書きの表として保持したりコミットしたりはしません。後述の [テストレジストリ](#テストレジストリ) を参照してください。

### Markdown アダプターのカバレッジ

`core/tools/aidlc-markdown.ts` の `markdownBlocks` は、可視性、コンテナー、定義、主張の分割を扱う唯一のブロック解釈器で、`visibleMarkdownLines` はそれを投影します。これは組み込みの `Bun.markdown` レンダラーに基づいています。テストは 2 つ目の CommonMark のオラクルを保守するのではなく、利用側の結果を守ります。別個の `Bun.markdown.render` によるレビューの権威の経路は、既存のセキュリティのカバレッジを保ちます。

- `t341-markdown-blocks.test.ts` は、作成した CommonMark/GFM のブロック境界の例、インラインコードと HTML スパンの正確な列、アダプターが補正する `Bun.markdown` の 4 つの逸脱（空のタスク項目、見出しやフェンスへ続く表、コンテナーから出るフェンス、段落の下でインデントされたタグ）、描画を変えてしまうため取り除かなければならないプローブ、英字も数字もない行、エンティティで綴られたプローブのマーカー、描画の予算、ダイジェストのフェイルクローズの質問境界、描画されたツリーを偽造してはならない制御文字を検証します。
- `t343-raw-html-consumer-contracts.test.ts` は、生の HTML の内外での要約のダイジェストと回答、Change Control のセクション、Plan Approval の選択と再ベースライン化を確認します。`t344-visible-markdown-goldens.test.ts` は影響を受けない可視性とダイジェストのバイト列を固定し、`t345-receipt-scope-migration.test.ts` は v1/v2 の受領記録の互換性とパーサー更新後の復旧を検証します。
- `t247-claim-sources-sensor.test.ts` は、可視性の安全性を両方向から守ります。隠れたテキストは主張の根拠にならず、隠れたフェンスに見えるテキストが本物の参照定義を消したり、確認済みの仮定を短くしたりすることはできません。同じ行で HTML コメント、処理命令、宣言、CDATA セクション、閉じる生のタグの後に続くテキストは主張です。

## レイヤー 1: プロトコル（すべての変更、LLM なし）

LLM を呼ばずに、オーケストレーターの構造的正しさを検証します。これが通れば、プロトコルは内部整合しています。つまり、ステージが有効なファイルを参照し、入力 / 出力が正しく連鎖し、ルーティング表がステージファイルと一致しています。

**レベル:** smoke、unit、integration

**何をテストするか:**
- ファイル存在、権限、命名規則（smoke）
- コピー版／ネイティブ版のディスパッチを経由する全 17 本のフックソース、ステージのフロントマター、ナレッジ一覧（unit）
- スコープとステージの対応付け、グラフの一貫性、ステージ I/O 契約の連鎖、プロトコル準拠（integration）
- ステージ出力から手順への検証。宣言済み出力がすべて指示手順で参照されているか（integration。`aidlc-validate.ts` CLI ツールにより決定論的）
- スコープ実行: 出荷されているすべてのスコープを、利用者の最初の要求から完了まで駆動する（integration、`tests/integration/t-scope-run-*`。後述）
- スコープとホストの実行: すべてのハーネスのツリー（Claude、Codex、Copilot CLI、Kiro CLI、Kiro IDE、Cursor、opencode）で、各ツリー自身のフックを通じて classic のジャーニーを 1 つ実行する（integration、`tests/integration/t-scope-host-*`。後述）
- ガードマトリクス: 承認済みの作業の下でファイルが変わったときに利用者が出会うものを、Guard Policy、レビュー上限、計画承認ごとに検証する（integration、`tests/integration/t-guard-matrix-*`。後述）

**実行:** `bun tests/run-tests.ts --no-llm`。既定のプロファイルは integration レベルを含むため、実行には LLM が必要で、`claude` CLI が PATH にあればライブモデルのゲートを開きます。`--no-llm` はそのゲートを閉じ、このレイヤーを LLM なしに保ちます。決定論的なテストは引き続き実行されます。`bash tests/run-tests.sh` は既存の POSIX コマンド向けの互換ラッパーです。スコープ実行、スコープとホストの実行、ガードマトリクスは、`--filter` がそれらを選んだ場合、または `--release`/`--all` の場合にだけ実行されます（CLI リファレンスを参照）。

### スコープ実行

`tests/harness/scope-run.ts` は、モデルなしで、出荷されているスコープを実際のエンジンで駆動します。スクリプト化された代役がエージェントを演じます。Claude のスキルと同じようにエンジンのコマンドを実行し、Claude Code が発火させるフックを発火させます。質問やゲートに答えるのは、人間ターンのフックを通じた別個の利用者スクリプトだけで、エンジンの呼び出しはすべて本番のガードプロファイルの下で実行されます。
各 `t-scope-run-<scope>.test.ts` ファイルは、文章ではなく、状態、監査記録、ディレクティブ、ファイルを確認します。

- 実行されるステージとスキップされるステージが、ステージファイルの `scopes:` の一覧と一致する。
- 利用者のものとして記録されたすべての判断が、利用者スクリプトが送ったターン（`tests/harness/person-turns.ts`）に裏付けられている。裏付けがない場合は、ターンの台帳と、各インテントの監査証跡と状態を、テストのログフォルダーの `unbacked-decisions-<id>/` の下に保持するため、フィクスチャの削除後もイベントの順序が残る。
- スコープファイルのスイッチが状態とディレクティブに現れる。
- 実行は完了で終わり、すべての出力がディスク上にある。

`t-scope-run-new-scopes.test.ts` は、専用のファイルを持たない出荷済みのスコープを駆動するため、新しいスコープは出荷されたその日からカバーされます。`t-scope-run-moves-*` は、利用者自身の言葉、新しい作業とともに入力された設定、実行途中のスイッチ、その日の停止と再開をカバーします。新しい種類の手順を持つステージは、代役がその手順を学ぶまで実行が失敗します。実行が免除する既知のエンジンのブロックは、その名前を付けた `test.todo` とともに `KNOWN_STOP_BLOCKS` に列挙されます。
`t-scope-run-moves-own-file-*` は、bugfix と、2 つの Unit をステージごとにビルドする classic を、各 Guard Policy の下で歩きます（`tests/harness/own-file-moves.ts`）。エージェントが利用者にターンを渡すあらゆる時点で、開いているステージが作ったファイルを 1 つ変更し、手順を再表示するか `next` を実行します。各変更は、利用者が再び尋ねられるか作業が先へ進み、その手順の後に拒否が戻ってこなければ合格です。CI はスコープ実行を独自の integration ジョブとして実行します。プルリクエストとマージキューでは Linux、毎晩の Full Suite（その `scope_runs` ジョブ）と `full_verification` の Full Suite では Linux、macOS、Windows です。classic の 3 つの own-file ファイルは `own-file-moves` として別に実行され、マージキューとそれらの Full Suite では実行されますが、プルリクエストでは実行されません。

### すべてのハーネスのツリーでのスコープ実行

`tests/harness/scope-hosts.ts` は、同じ代役と利用者スクリプトを、別のツールのツリー上で、そのツール自身のフックを通じて実行します。各ホストはツリーを出荷どおりにインストールし、そのツールがエージェントのシェルに与えるもの（Codex の `CODEX_THREAD_ID`、Kiro の `KIRO_SESSION_ID`）を与え、あらゆる時点（チャットの開始、利用者の入力や選択、シェルやファイルのツールの実行、補助の送出、ターンの終了）で、ツリーの配線が登録する各コマンドを、そのツールのペイロードを与えて実行します。対象は `.codex/hooks.json`、`.github/hooks/aidlc.json`、Kiro CLI のエージェント JSON（`.kiro/agents/<agent>.json`。ツールの名前とその別名に対するグロブのマッチャー。補助は自身のセッションの下で自身のエージェントのフックを実行する）、Kiro IDE のフックカード（`.kiro/hooks/*.json`。ファイル名順の正規表現のマッチャー。書き込みやコマンドの後に動くカードはないため、Kiro と同じく次のカードがその仕事を行う）、Cursor の `.cursor/hooks.json`（マッチャーなし。すべての回答は終了コード 0 の JSON で、ターンの終了は追加のメッセージを送ることしかできず、ジャーニーはそれをブロックされた引き継ぎとして読む）、opencode のプラグイン（1 つの opencode プロセス、つまりホストが待つワーカースレッドに読み込まれる。拒否はフックが投げたエラー）です。
`tests/unit/t-scope-hosts.test.ts` は、それらのペイロードを各ツールから記録したもの（`tests/fixtures/<tool>-hook-payloads`）に対して固定します。各ツールの回答はそれ自身の形で読みます。Codex と Kiro は終了コード 2 で拒否し、Copilot は deny の判断で拒否し、Copilot はフックが書き換えたコマンドを実行し、Kiro の人間ターンのフックはターンの最初の `next` を自分で実行することがあるので、エージェントはその返答に基づいて動きます。すべてのツール呼び出しがフックを発火させるため、拒否は実行を止め、失敗するフックのコマンドは問題です。ホストは、インストール済みのリリースがセットアップしたプロジェクト上でも動けます（`ScopeHost.launcher`）。その場合、エージェントのコマンドと配線のフックは利用者の `aidlc` を通じて実行され、代役はインストール済みのエンジンが示す `aidlc engine ...` のコマンドに基づいて動きます。リリースの更新検査がこれを使います。

各 `t-scope-host-<harness>.test.ts`（`claude`、`codex`、`copilot`、`kiro`、`kiro-ide`、`cursor`、`opencode`）は、1 つのジャーニーを駆動します。設計ステージを飛ばし、2 つの Unit を 1 つずつ、それぞれチェックポイント付きでビルドする classic です。最初の Unit のチェックポイントの後、利用者はその日の作業を止め、新しいクローン（クローンが持つものだけが残ったフォルダーで、最初のクローンの監査シャードが最後に並ぶ）から作業を拾い、2 つ目のチャットで `/aidlc --resume` によって続けます。ジャーニーはスコープ実行が確認するものに加えて、2 つの監査シャード、2 つのチャット、各 Unit のチェックポイントが 1 回だけ尋ねられること、利用者が出会うべきでない回り道（拾ったばかりの作業を再開するよう言われるなど）がないこと、そして代役自身の手順のどれかのために状態遷移ガードが脇へ退くことがないこと（classic はガードをオフにして実行するため、補助が取ってはならない手順はそこでしか現れない）を確認します。CI はこれらを独自の integration ジョブ（`scope-hosts`）として実行します。プルリクエストとマージキューでは Linux、毎晩の Full Suite（その `scope_runs` ジョブ）と `full_verification` の Full Suite では Linux、macOS、Windows です。

### ガードマトリクス

`tests/harness/guard-matrix.ts` は、同じ代役を使って、2 つの Unit を持つ classic（Requirements、Units Generation、Code Generation、Build and Test）を、各 Guard Policy（`off`、`relaxed`、`strict`）、レビュー上限、計画承認の設定の下で駆動します。各 `t-guard-matrix-<change>.test.ts` ファイルは、利用者が変更を行う時点で 1 つの変更を加えます。後の Unit が承認済みの Unit のファイルを編集する、手による編集、承認待ちの間の計画の編集、ステージ途中の pull、revert、利用者が求める 2 回目のレビュー、Unit 間でのエンジンの更新、利用者自身による off への切り替え、構成されたスコープ、出荷時の classic です。文書の変更では Functional Design も歩きます。Unit 2 がビルドしている間に、Unit 1 の承認済みの機能設計やコード計画が（Unit 2 のエージェントまたは利用者によって）編集されるか、設計が削除されます。その `-waves` のファイルは Functional Design をステージごとに実行し、その後で利用者が Unit を 1 つずつ求めます。実行が出会うすべての拒否は追跡されます。利用者がエンジンの提示する対処を選ぶか、エージェントがそれが示すコマンドを実行します。各ケースは次を確認します。

- Guard Policy が off の場合、何も利用者を拒否したり再び尋ねたりしない（変更された文書については relaxed でも同様。削除された文書は、それを作り直す 1 回の停止を伴うことがあり、作り直されなければならない）。
- 方針が on の場合、利用者が変更について尋ねられるのは最大 1 回。
- 手順を実行した後に拒否が戻ってくることはない（デッドロック）。
- 利用者のものとして記録されたすべての判断が利用者の送ったターンに裏付けられ、実行は完了で終わる。
- 記録は、変更された Unit ごとに最大 1 件の CHANGE_ACCEPTED 行と、利用者向けの 1 行を保持し、何が変わったかを示す。何も変わらなければ何も保持しない。

エンジンが現在ブロックするケースは、そのブロックの名前を付けた `test.todo` で、本体に実際の検査を持つため、修正するとそれが有効になります。CI はガードマトリクスを、スコープ実行を実行する場所で、所要時間を均衡させた 2 つのジョブとして実行します。どちらも `^t-guard-matrix-` を選び、`--shard 1/2` と `--shard 2/2` がその一覧を重複なく分割します。最も長い変更のマトリクスは、エージェントの編集と手による編集、Unit ごとの削除とステージごとの削除を、より小さなファイルに分けています。どのシナリオも引き続き新しいプロジェクトから始め、同じ利用者体験と記録の確認を伴ってワークフロー全体を実行します。
分割した各ファイルは、元のファイルの所要時間の半分を見積もりとして始め、通常の重みの更新が観測した時間で置き換えます。

## レイヤー 2: ステージ（CI へのプッシュ、LLM あり、分単位）

既知のワークスペースと状態フィクスチャを使い、個別ステージを分離実行します。決定論的な入力を与えたときに、各ステージが正しい成果物を生成することを検証します。

**レベル:** integration

**何をテストするか:**
- 事前検証の健全性ゲート: Claude CLI が PATH 上にあるか、AWS 認証情報が有効か、Claude が応答するか（終了コード 0）、応答が空でないか（preflight）
- CLI ツールのユーティリティハンドラー: intent-create、--doctor、--status、--stage、--phase（integration）
- グリーンフィールド / ブラウンフィールドのスタブを使った個別ステージと成果物検証（integration）

**実行:** `bun tests/run-tests.ts --ci`

## レイヤー 3: 受け入れテスト（リリース時、LLM あり、時間単位）

完全なワークフローを実行し、体験まで含めて検証します。状態遷移だけでなく、成果物の内容、ステージ間の整合性、ドメインの正しさを確認します。

**レベル:** e2e

**何をテストするか:**
- ブラウンフィールドのスタブと成果物アサーションを伴う完全なバグ修正ライフサイクル
- グリーンフィールドのスタブと成果物アサーションを伴う完全な POC ライフサイクル
- 状態の進行、スコープのルーティング、監査の完全性、ジャンプ機構
- ステージ指示の品質に対する LLM の意味論レビュー（明確さ、論理の流れ、曖昧性検出）

**実行:** `bun tests/run-tests.ts --release`

## クロスプラットフォーム対応

テストスイートはネイティブ Bun ランナーを通じて macOS、Linux、Windows で実行されます。

```bash
bun tests/run-tests.ts [--ci | --all --debug -P 8]
```

`bash tests/run-tests.sh ...` は POSIX 互換ラッパーとして残り、同じ TypeScript ランナーへ委譲します。リポジトリのテストとコピー版のフック／ツールには `bun` が必要です。ネイティブリリース版は、インストール済みの `aidlc` バイナリを経由してフック／ツールを呼び出します。Bash は主要な実行基盤ではありません。

端末セッションの既定は、3 つのプラットフォームすべてでネイティブの `bun` です。`tmux` は Linux/macOS での明示的な代替です。macOS では、封じ込めに開始時刻で検査したプロセスの識別子と継承された `AIDLC_TUI_CONTAINMENT` トークンを使い、launchd の配下に付け替えられた後の、切り離された二重 fork の子孫を見つけます。祖先関係から逃れ、かつ環境変数を消して exec する子孫は、macOS では検出できません。Linux の subreaper による封じ込めと Windows の Job Object には、この制限はありません。

**スイートへ織り込まれている可搬性制約:**

- **パス**: `tests/harness/fixtures.ts` の `createTestProject` が一時プロジェクトのパスを正規化し、JSON とネイティブ `bun` をきれいに往復できるようにします。
- **インプレース編集**: テスト内ではファイル更新に TypeScript の書き込みを優先します。シェルヘルパーが避けられない場合でも、BSD/GNU 固有の `sed -i` の形式は避けます。
- **`grep -qiF`**: Git Bash には `-i` と `-F` の組み合わせに既知の不具合があります。パターンに正規表現のメタ文字がなければ `-i` 単独を使います。テストは修正前に t16 でこの問題に当たりました。
- **`tar` アーカイブ**: macOS の `tar` は既定で `._*` AppleDouble サイドカーファイルを注入します。クロスプラットフォームのテスト実行用にソースを束ねるときは `COPYFILE_DISABLE=1 tar …` か `git archive` を使います。
- **Windows での LLM のタイミング**: Windows EC2 からの Bedrock 呼び出しは macOS からよりかなり遅いことがあります（初回のコールドスタート、MSYS のプロセス fork のオーバーヘッド）。SDK/tui テストはドライバーの結果のサーフェスに対してアサートし、ランナーの preflight／ファイル単位の Claude ゲートに、実行基盤の不在と本物の失敗を切り分けさせてください。

**Windows で手動実行する場合:**

1. Bun **1.3.14 以降**、スイートの他のツール用の Node.js、Claude Code CLI をインストールする。
2. フルスイートまたは POSIX ラッパー互換のスモークを実行する場合は Git for Windows をインストールする。ネイティブランナーの経路自体には Bash は不要。
3. Bun が `@xterm/headless` を解決できるよう、リポジトリの開発依存関係をインストールする。Windows の既定の TUI バックエンドは Bun のネイティブ PTY を使う。
4. ライブの Claude TUI カバレッジには `AIDLC_TUI_LIVE=1` を設定する。`AIDLC_TUI_BACKEND` は未設定のままにするか `auto`/`bun` に設定する。必要に応じて `AIDLC_BUN_BIN` で具体的な `bun.exe` を選ぶ。
5. Kiro IDE スライスでは、Kiro IDE をインストールしてサインインし、`AIDLC_KIRO_IDE_LIVE=1` を設定する。GUI のテストは、そのユーザーがログインしたデスクトップセッションで実行する。スケジュールされたタスクでは「ユーザーがログオンしているときのみ実行する」を使って、このセッションでランナーを起動できる。Windows の既定のバイナリは `%LOCALAPPDATA%\Programs\Kiro\Kiro.exe` で、`AIDLC_KIRO_IDE_BIN` で上書きできる。
6. `bun tests/run-tests.ts --all --debug -P 8` を実行する。

WSL も Docker も不要です。サポートされる検証の実行基盤はネイティブ Windows です。

Kiro CLI のカバレッジでは、サインイン済みのネイティブの `kiro-cli.exe` を `PATH` に置きます。
`AIDLC_BUN_BIN` を検証済みの Bun の実行ファイルに固定し、そのディレクトリを `PATH` の先頭に保ってください。Kiro のインストールには古い Bun が同梱されていることがあります。
ACP のファイルには `AIDLC_KIRO_ACP_LIVE=1` を設定します。端末のファイルには `AIDLC_KIRO_TUI_LIVE=1` と `AIDLC_TUI_LIVE=1` を設定します。ネイティブの Bun 端末バックエンドが Windows の入力と画面の取得を扱います。これらのファイルは実行前に CLI、アカウント、選択した端末バックエンドを確認し、対応する各プラットフォームで同じジャーニーのアサーションを行います。

**再現可能な MR10 Windows EC2 実行手順:**

1. SSM アクセス付きの使い捨て Windows Server 2022 ホストを立てる。

   ```bash
   aws cloudformation deploy \
     --stack-name aidlc-windows-test \
     --template-file tests/harness/windows/windows-test.cfn.yaml \
     --capabilities CAPABILITY_NAMED_IAM \
     --parameter-overrides VpcId=vpc-... SubnetId=subnet-...
   ```

2. テスト対象のコミット済み Git ツリーを同期する。

   ```bash
   bun tests/harness/windows/sync.ts --stack-name aidlc-windows-test HEAD
   ```

3. ホスト上でリポジトリの開発依存関係をインストールする。

   ```bash
   bun tests/harness/windows/ssm-run.ts --stack-name aidlc-windows-test -- \
     powershell -ExecutionPolicy Bypass -File C:\aidlc\tests\harness\windows\setup.ps1 -ProjectDir C:\aidlc
   ```

4. ライブ TUI を有効にした Windows の `--all` ゲートを実行する。

   ```bash
   bun tests/harness/windows/ssm-run.ts --stack-name aidlc-windows-test -- \
     powershell -ExecutionPolicy Bypass -File C:\aidlc\tests\harness\windows\run-all.ps1 -ProjectDir C:\aidlc -Parallel 8
   ```

5. ホストを破棄する。

   ```bash
   aws cloudformation delete-stack --stack-name aidlc-windows-test
   ```

SSM の観測処理は、API の照会とポーリングにまたがって 1 つの期限を共有します。
期限切れの場合はリモートの終了を未確認として報告します。遅れて届いた終端の応答が、期限切れの観測を成功した実行に変えることはありません。

`run-all.ps1` は、`bun tests/run-tests.ts --all --debug -P <N>` を呼ぶ前に `AIDLC_BUN_BIN` と `AIDLC_TUI_LIVE=1` をエクスポートします。
その preflight は、Bun を通じて共有の `selectedTuiBackend` と `tuiUnavailableReason` のヘルパーを呼び、選択したバックエンドの前提条件を確認します。Node は引き続きフルスイートのツールの前提条件です。前提条件の検査がジャーニーをスキップした場合、ライブのオプトインだけではカバレッジは成立しません。取得したファイルごとの結果を確認してください。ネイティブインストーラーは、CloudFormation の UserData のブートストラップを実行したユーザー（EC2Launch v2 では Administrator）の下に `claude.exe` を置くため、スクリプトは `C:\Users\Administrator\.local\bin` と systemprofile のホームの両方で Claude のバイナリを探します。

スタックの既定は、フル `--all -P 8` のライブ実行向けに **`c5.4xlarge`** です。
より小さなホストでは並列負荷の下で競合が増えます。`InstanceType` を下げる場合は、より軽い層の選択を使ってください。前述の共有のタイムアウトの最終防御は、1 つのホストで観測された所要時間を性能要件として扱うことなく、ランナーのばらつきを許容します。

## ターミナルドライバー

`tests/harness/tui-drive.ts` は、名前付きのセッションを通じて対話型の CLI を駆動します。
`tests/harness/tui-runtime.ts` の共有のセレクターは、`AIDLC_TUI_BACKEND` からバックエンドを選びます。

| 選択 | プラットフォームと前提条件 |
|-----------|----------------------------|
| 未設定または `auto` | Linux、Windows、macOS ではネイティブの `bun` |
| `bun` | Linux、Windows、macOS。**Bun >=1.3.14**、`Bun.Terminal`、`bun:ffi`、`@xterm/headless` が必要。ネイティブの封じ込めは x64/arm64 に対応する。Linux は pidfd によるシグナル送信と待機のために glibc、procfs、カーネル >=5.4 が必要。Windows は ConPTY が必要。macOS は libSystem のプロセスの識別子と継承された所有トークンを使う（環境変数を消す場合の制限は[クロスプラットフォーム対応](#クロスプラットフォーム対応)を参照） |
| `tmux` | Linux/macOS での明示的な代替。ドライバーの実行に Bun が、`PATH` に `tmux` が必要 |

`auto` はプラットフォームで選び、前提条件が欠けていても別のバックエンドへフォールバックしません。空文字を含む未知の値は構成エラーです。`AIDLC_BUN_BIN` は `bun` と `tmux` のバックエンドの Bun 実行ファイルを上書きします。1 つのセッションでは、コマンド間で同じバックエンドの選択を保ってください。ネイティブの Bun バックエンドは tmux を必要としません。

`tests/harness/tui-bun-backend.ts` のネイティブデーモンは、`Bun.spawn` のインラインの `terminal: { ... }` オプションを使って PTY とその出力のコールバックを所有します。`tests/harness/tui-screen.ts` はそれらのバイト列を `@xterm/headless` で解析し、エミュレーターの応答を PTY に返します。コマンドは Linux ではローカルソケット、Windows では名前付きパイプでデーモンに届くため、PTY と画面は別々のドライバーの呼び出しをまたいで存続します。

各ネイティブセッションは、それぞれ独自のデーモン、PTY、画面、認証された IPC のエンドポイントを持ちます。並列のワーカーには、別々のセッション名、プロジェクト、`CLAUDE_CONFIG_DIR` のプロファイルを与えてください。テストランナーは、端末セッションの数とは独立に Bedrock の同時実行数を制限しなければなりません。

`tests/harness/tui-bun-process.ts` は、Linux の subreaper と pidfd による所有、または Windows の Job Object で子孫を監督します。`kill` は、確認されたプロセスのクリーンアップとデーモンの退役を待ちます。`wait-dead` はデーモンのプロセスの識別子を確認します。開始ロックは OS が所有し、中断された起動者が終了すると解放されます。フィクスチャのクリーンアップも、ネイティブセッションのクリーンアップが未確認の間は、そのプロジェクトの削除を拒否します。

セッションの記録と最終的なスナップショットは `AIDLC_TUI_BUN_ROOT`（既定: OS の一時ディレクトリを使う `$TMPDIR/aidlc-bun-tui`）の下に残ります。既定のルートも明示的なルートも非公開でなければなりません。POSIX では現在のユーザーが所有するモード **0700** の実ディレクトリ、Windows では現在のユーザーの所有者 SID を持ち、Everyone、BUILTIN\Users、Authenticated Users への許可 ACE がないことです。
シンボリックリンク、ジャンクション、その他の Windows のリパースポイントは拒否されます。ドライバーは欠けているルートを非公開の権限で作成し、安全でない既存のルートは権限を変えずに拒否します。POSIX では、明示的なルートのすべての祖先が現在のユーザーまたは root の所有で、sticky でない限りグループ／その他の書き込みビットを持たない必要があります。暗黙のルートの一時ディレクトリの親は、現在のユーザーの所有かモード **1777** でなければなりません。ファイルシステムがそれらの祖先をサンドボックスの uid の所有と報告する管理されたテストホスト（たとえば `/` が `nobody` に属するオーバーレイファイルシステム）では、`AIDLC_TUI_ALLOW_UNTRUSTED_ANCESTORS=1` を設定すると所有権の要件だけを飛ばせます。書き込みビットの規則と、ここでの他のすべての検査は引き続き強制されます。
Windows はルート／セッションの所有者と DACL を検証しますが、祖先の ACL の信頼性はまだ検証しません。後述の世代のハンドシェイクは引き続き強制されます。事前に作られた安全でないルートを削除するか、`AIDLC_TUI_BUN_ROOT` を信頼できる祖先の下の非公開ディレクトリに向け、コマンド間でその設定を一貫させてください。

テストランナーは、ログディレクトリの権限とは独立に、信頼できる OS の一時ディレクトリの下で各ファイルに別々の非公開のネイティブルートを与えます。トランスポートのクリーンアップが確認された後、セッションの記録とスナップショットをファイルの `tui-bun/` 成果物にアーカイブし、一時的なネイティブルートを削除します。クリーンアップが不確かな場合は、診断のためにライブの名前空間を保持します。

起動の記録は、ルートとセッションのディレクトリのファイルシステム上の識別子に固定された非公開の通常ファイルです。クライアントとデーモンはどちらも、それを信頼する前に所有権、権限、セッションの識別子を検証します。デーモンはさらに、PTY やスーパーバイザーを作る前に、起動者が argv で渡した新しい世代を持つ **starting** の記録を要求し、コマンドを解放する直前に記録された両方のディレクトリの識別子を再確認します。再生された完了済みの記録がコマンドを認可することはできず、診断情報が信頼できないディレクトリに書かれることはありません。

対象の終了ステータスと PTY の終了ステータスは別物です。Bun は、Linux の通常のスレーブのクローズによる EIO を PTY のステータス `1` として報告します。ドライバーは、スーパーバイザーの終了とクリーンアップが確認された後にそのステータスを受け入れます。Bun のコールバックは、他の POSIX の読み取りエラーを区別する errno を公開しません。
到達できないセッションと未確認のクリーンアップは、引き続きエラーです。

取得は、キューに入った出力が解析された後の、現在のアクティブなビューポートを読みます。プレーンテキストはソフトラップされた行を結合し、末尾の空行を取り除きます。ANSI の取得は、パレットと RGB の色を含め、現在のセルとその属性から再構築されます。スクロールバックと以前に消去された出力は除外されます。JSON は、空のセルや全角文字の幅ゼロの継続セルを含め、物理的なグリッド全体を保持します。

既存の `start`、`send`、プレーンな `capture`、`startup`、`wait` のコマンドは、呼び出し規約を保ちます。`send --keys "<text>" --literal` はリテラルのテキストを送ります。`--literal` がない場合は名前付きのキーが解釈され、`1`/`2` のような任意のテキストはリテラルのままです。`--no-enter` が設定されていなければ Enter が追加されます。`wait --stable-ms N` は画面の安定条件を保ち、`startup --ready-pattern "<regex>"` は起動時のナビゲーションの振る舞いを保ちます。

Bun バックエンドは次の取得と入力のコマンドをサポートします。

| コマンド | 振る舞い |
|---------|----------|
| `resize --session <name> --width N --height N` | PTY とエミュレーターの両方のサイズを変える。列 2〜500、行 1〜200、最大 40,000 セル |
| `paste --session <name> --text "<text>"` | **暗黙の Enter なし**でテキストを貼り付ける。ブラケットペーストのマーカーは、アプリケーションがそのモードを有効にしている場合だけ使う。CRLF と単独の LF は CR になり、既存の単独の CR は保持される |
| `capture --session <name> --physical` | 物理的な表示行のプレーンテキストを返す。既定の論理的な取得の API は保たれる |
| `capture --session <name> --json` | 完全なセルのデータを持つ一貫した `TuiSnapshot` を返す |
| `capture --session <name> --ansi` | セルの色とスタイルを ANSI シーケンスとして持つ現在のビューポートを返す |

メニューの検出は常に物理的な行を使います。Bun は `text`、ラップのフラグ、ANSI を変えずにスナップショットのセルからそれらを導出し、tmux はこれらの読み取りで `-J` を省きます。これにより、ConPTY のラップのメタデータが、表示されているメニューの選択肢を前の行に結合することを防ぎます。外部の自動化は、`--json` や `--ansi` とは別に `capture --physical` を選べます。

`wait --pattern` と `startup --ready-pattern` の既定は `--view auto` です。まず物理的なテキストを試し、同じフレームの論理的なテキストをフォールバックにします。これにより、本物のソフトラップにまたがるリテラルのパターンを保ちつつ、行に固定された UI のパターンをサポートします。1 つの解釈を選ぶには `--view physical` または `--view logical` を使います。Bun は両方を 1 つのスナップショットから得て、tmux は両方を 1 つの同期的なコマンドリストで取得します。メニューの操作は、パターンのビューの選択にかかわらず、常に物理的なビューを調べます。安定性は、全体の期限を再開始することなく、一致したビューで測られます。

ライブの待機は、時計だけでなく、画面が示す内容で終わります。待機がエージェントの作業（そのステータスのスピナーと経過タイマー、バックグラウンドエージェントの待機、実行中のサブエージェントの行、実行中のコマンドのバックグラウンドのヒント）を見た後、Claude の空のプロンプトが 30 秒間変わらなければ、ターンは終わっています。パターンが一度も描画されなければ `wait` は最後のペインとともに失敗し、メニューが現れず終端条件が満たされなければ `answer-gate` は失敗し、改訂の復旧は、そのアイドルのプロンプトでだけ自由記述のフィードバックを入力します。ドライバーが認識しない画面は作業中とみなされるため、ハングの最終防御は引き続き適用されます。記録されたセッション全体で、ターン内でアイドルに見える最長の一時停止は 0.5 秒未満でした。`wait --through-turn-end` はターンの終わりを越えて待ち続けます。`answer-gate` がメニューに答えるのは、強調表示された選択肢からフッターまでのその行が 0.5 秒間同じに読める場合だけです。そのため、描画途中で捉えたメニューにその前半で答えることはありません。5 秒後も行が変わり続けている場合は、メニューの待機に戻ります。メニューに答えた後は、そのメニューの強調表示された選択肢からフッターまでの行が、自身のキーが動かすキャレットとチェックボックスの印を除いて変わらない間、最大 5 秒待つため、遅い描画や部分的な再描画に 2 回答えることはありません。それらの行が再描画されるか終端条件が満たされると待機を止め（`--stop-at-approval-gate` では再描画だけが終わらせる）、5 秒後もそのまま残っているメニューには再び答えます。

`resize`、`paste`、`capture --json` には Bun バックエンドが必要です。ANSI の取得は tmux でも利用できます。`--json` と `--ansi` は同時に指定できません。

これらは同じドライバーで呼び出します。たとえば次のとおりです。

```bash
bun tests/harness/tui-drive.ts resize --session demo --width 120 --height 40
bun tests/harness/tui-drive.ts paste --session demo --text "draft input"
bun tests/harness/tui-drive.ts capture --session demo --json
```

`TuiSnapshot` は `tests/harness/tui-screen.ts` で定義されています。`sequence`、`cols`、`rows`、0 始まりの `cursor: { x, y }`、`buffer`（`normal` または `alternate`）、`text`、`ansi`、`lines` を含みます。各行は `wrapped` のフラグと `cells` の配列を持ちます。各セルは `chars`、`width`、`fg`/`bg` の色（`mode: default|palette|rgb`、数値の `value`）、真偽値の `bold`、`dim`、`italic`、`underline`、`inverse`、`invisible`、`strikethrough` の属性を持ちます。シーケンスは解析された出力やサイズ変更の後に進み、変化のない取得では進みません。ラップが保留されている場合、カーソルの `x` は `cols` と等しくなることがあります。

ユニットスイート `tests/unit/t-tui-runtime.test.ts` と `tests/unit/t-tui-screen.test.ts` は、ランタイムの選択と端末のトランスクリプトについての決定論的な検査を定義します。画面のスイートは、次の UTF-8 のリグレッションを含みます。

- ちょうど 85 バイトの ANSI/Unicode の preflight のペイロードを、空の端のチャンクを含め、86 通りすべての 2 チャンクの分割位置で分割する。
- 1 から 85 バイトまでの各固定チャンクサイズで、書き込みの間にパーサーを排出する。テキスト、物理的なセル、幅、色、ANSI が一致しなければならない。
- `0x80` の継続バイトを含む、選んだ 2、3、4 バイト文字のすべてのバイト分割。
- 残りのバイトが届くまで、`flush()` の呼び出しをまたいで保持される不完全な UTF-8。
- 黙って消えるのではなく、`U+FFFD` の置換セルとして描画される不正な UTF-8。

画面は xterm の文字列 API の前に増分の `StringDecoder` を使います。xterm 5.5 のバイトデコーダーは、断片化したエムダッシュ（`E2 80 94`）のように、保存された継続バイトが `0x80` の場合に文字を失うことがあります。

`tests/unit/t-tui-bun-process-linux.test.ts` は実際の Linux の監督を検証し、`tests/integration/t-tui-bun-lifecycle.test.ts` は Windows の Job Object、シグナル、子孫のクリーンアップをカバーします。`tests/unit/t-tui-process-identity.test.ts` は、中断された起動者を含め、識別子とロックの解放をカバーします。
`tests/integration/t-tui-bun-backend.test.ts` は、トークンを使わない対象に対して公開の CLI を実行し、8 つの同時セッション、入力、ANSI/セルの取得、サイズ変更、貼り付け、再起動、IPC のエラー、デーモンの退役をカバーします。

TUI の preflight は、選択したバックエンドを調整します。ネイティブのライフサイクルには上記の別のカバレッジがあります。ライブのモデルのジャーニーは既存のオプトインを保ちます。
一時的な Claude のフィクスチャは、開発用の指示や外部インポートのプロンプトを継承しないよう、リポジトリの祖先ディレクトリの外に置いてください。

## 事前検証

フィルターなしでライブ実行可能なレベル（integration または e2e）を実行する前に、ランナーはゲートとして `tests/integration/t19.test.ts` を実行します。これは **Claude Agent SDK**（integration 層が使うものと同じライブ経路）で小さな実ターンを 1 回流し、決定論的なサーフェスだけに対してアサートします。preflight がスキップされた場合、既定の実行を失敗させずに Claude のゲートを閉じます。`AIDLC_CLAUDE_SDK_LIVE=1`、`AIDLC_TUI_LIVE=1`、`--require-coverage` の場合は、代わりにスキップのない完全な合格の証拠を要求します。preflight の実際の失敗、タイムアウト、クリーンアップのエラーは、どのモードでも実行を失敗させます。preflight がスキップしても失敗しても、決定論的なファイルは引き続き実行され、Claude に依存するファイルにはファイル単位の `SKIP` のエントリが付きます。

SDK ドライバーは `driveAidlc()` の呼び出しごとに一時的な `CLAUDE_CONFIG_DIR` を与え、セッションの永続化を無効にします。そのためライブテストは、コマンドのサンドボックス内でホームディレクトリが読み取り専用の場合も含め、ユーザーの `~/.claude.json` と Claude のトランスクリプトに一切触れません。呼び出しごとの `env.CLAUDE_CONFIG_DIR` は、個別の調整用に引き続き使えます。

1 回の駆動は 1 つのセッションで、既定では最初のターンの結果で終わります。利用者の次のメッセージを必要とするジャーニーは `nextMessage` を渡します。ターンが終わると、それはターン番号と、その時点までの駆動の累計（ピッカー、ツールの結果、Stop フック。1 ターン分は前のターンの累計を差し引く）を受け取り、同じセッションに送るメッセージを返します（何も返さなければ駆動を終えます）。`chatAboutQuestionWhen` は、Claude Code の「Chat about this」ボタンと同じようにピッカーに答えるため、質問は開いたままです。`answerScript` の指定 `{ text }` は利用者自身の言葉をピッカーに入力します。`captureStopHooks` は、各 Stop フックの判定をそのターンとともに記録します。`stopWhen` は、その時点までのツールの結果が条件を満たした時点で駆動を終えます。これは、複数の結果を必要とする停止（作業を作る手順の前にも後にも届き得るエンジンの行）のためのものです。

Claude Code のセッション内（`CLAUDECODE=1`）から起動したスイートは、そのセッションの `ANTHROPIC_DEFAULT_*_MODEL` の既定値を駆動に渡しません。SDK に同梱された Claude Code はセッションのモデルより古く、それを拒否することがあるからです。
駆動の最終的なプロバイダーが Bedrock の場合、プロジェクト設定やテストが設定していないモデルには CI の固定モデル（`scripts/ci-credential-broker.ts` の `CI_BEDROCK_MODELS`）が、そうでなければ同梱の既定値が与えられます。CI を含め、他のシェルからの実行では環境は変わりません。

| アサーション | サーフェス | 失敗時 |
|-----------|---------|---------|
| AWS 認証情報が有効 | `aws sts get-caller-identity` が終了コード 0（`aws` CLI がなければスキップとして合格） | 中止 — Bedrock は IAM 認証を要する |
| ライブのターンが終端の結果に到達する | SDK の実行が `undefined` でない `resultEvent` を生成する（その層が必要とするバイナリが存在し到達可能） | 中止 — 実行基盤／API に到達できない |
| ターンがエラーなしで完了する | `resultEvent.is_error === false`（`claude -p` の終了コード 0 の決定論的な等価物。124/137 のハングでは未定義のまま） | 中止 — API が応答しない |
| 応答が空でない | 実行が*何らかの*出力を取得した — `tool_result` またはアシスタントのテキスト（存在のみで内容は見ない） | 中止 — API が何も生成しなかった |

ここで赤になるのは、常に実環境の発見事項（`claude` がない、認証情報の期限切れ）であり、ならすべき不安定さではありません。これは下流の LLM 層を素早く打ち切るという、ゲート本来の役目です。

## テストレジストリ

このスイートは**登録制ではなく発見制**です。`bun tests/run-tests.ts` は 4 つのレベルディレクトリ（`tests/{smoke,unit,integration,e2e}/`）を走査し、見つかったすべての `t*.test.ts` を実行します。同期を保つべき手書きのテストごとの表はありません。テストファイルを追加するだけでランナーが拾います。

各テストが*何をカバーするか*は、`tests/gen-coverage-registry.ts` が、テストファイル先頭のコメントブロックにある `covers:` ヘッダ（通常は 1 行目。正当に何も宣言しないファイルも少数あり、それらはカバレッジの主張を持たないだけです）から機械的に追跡します。ジェネレーターは、フレームワークの単位を 7 つのクラス（`function`、`audit`、`scope`、`stage`、`hook`、`subcommand`、`render-surface`）にわたって列挙し、各 `covers:` の主張を列挙された単位へ対応付け、単位ごとに主張と状態を持つエントリを 1 つ構築します。

レジストリは**決してコミットされません**。コミットされたコピーはほぼすべての PR で変わったため、キューに入った PR がそこで衝突するか、リベースのたびに再生成する必要がありました。代わりに CI が毎回新しく構築します。必須の `Tests (smoke + unit)` チェックの一部である、統合された **Checks** ジョブのカバレッジのステップが `--check --base HEAD^1` を実行します。これは、テスト対象のコミットと、その最初の親（PR のベース、またはキューで前にあるエントリ）についてレジストリを構築し、親については一時ディレクトリでその親自身のパッケージャーとジェネレーターを使います。そして、親がカバーしていて、コミットにまだ存在するがもうカバーされていない各単位を示して失敗します。カバレッジは増えることしかできません。主張のない新しい単位は列挙されますが失敗にはならず、コードが削除または名前変更された単位は損失になりません。テストがなくなるときに単位をカバーしたままにするには、それを検証する別のテストにその `covers:` の主張を追加してください。

```bash
bun tests/gen-coverage-registry.ts                             # write tests/.coverage-registry.json locally (gitignored)
bun tests/gen-coverage-registry.ts --check                     # the anti-rot guards on a fresh build
bun tests/gen-coverage-registry.ts --check --base origin/main  # and fail if a unit main covers lost its claim
```

ジェネレーターは、パッケージされた `dist/claude` ツリーから単位を読みます。そのツリーがチェックアウトと異なるソース（`core/`、`harness/`、`plugins/`、またはパッケージャー自身のスクリプト）からパッケージされていた場合、どちらのコマンドも 1 行で拒否します。先に `bun scripts/package.ts` を実行してください。`package.ts` は、ハーネスごとの入力の内容フィンガープリントを `dist/.package-sources.json` に記録するため（`scripts/package-sources.ts`）、編集を元に戻すだけなら再ビルドは不要です。入力が変わった最中のビルドは記録されず失敗し、再実行するよう伝えます。ジェネレーターの `AIDLC_COVERAGE_*` のシームからの一時ツリーは `core/` を持たず、確認されません。

ある関数、監査イベント、スコープ、ステージ、フック、サブコマンド、描画サーフェスをどのテストが検証するかを調べるには、レジストリをローカルに書き出して読むか、`covers:` ヘッダを直接 grep してください。unit 層はすべてのツリーで `--check` を実行するため、壊れた列挙処理はゲートを赤にします。

> **注記:** t19 は unit（`tests/unit/t19.test.ts`、ジャンプ CLI ツール）と integration
> （`tests/integration/t19.test.ts`、ライブの preflight ゲート）の両方に存在します。
> このような衝突は、裸の ID ではなくレベル／ファイルパスで区別します。

L1 は Git の pre-commit フックで強制できます。`bun tests/run-tests.ts || exit 1`

必須の `Tests (smoke + unit)` ステータスは、統合されたチェックのジョブも要求します。パッケージの決定性、型検査、lint、インストーラーの ShellCheck、Linux のスモーク、production guard です。契約検査とテストのマトリクスは並行して実行され、集約は両方を待ちます。その名前は変わらないため、リポジトリの必須ステータスチェックがそれらをまとめて覆います。

GitHub ホストのランナーの障害だけが原因でマージキューが PR を外した場合、`merge-queue-notice.yml` がその旨を述べるコメントを PR に 1 件投稿し、ジョブを示し、メンテナーがそれを再び追加できることを伝えます。これは各マージキューの CI 実行の後に `workflow_run` で実行され、既定のブランチだけをチェックアウトし、`actions: read`、`checks: read`、`contents: read`、`pull-requests: write` を持つ組み込みのトークンを使います。`.github/scripts/merge-queue-notice.ts` が、GitHub の記録から読み取る署名を所有します。

- `failed_checks` による除外では、赤いすべてのジョブが、ランナーを失った（"The hosted runner lost communication with the server"、失敗したステップなし）か、"Could not resolve host: github.com" でチェックアウトに失敗した。
- `checks_timed_out` による除外では、除外の時点でまだ開いていたすべてのジョブが、ランナーを待っていたか、まだ "Prepare unit test substrates" にあった。

テストの失敗、競合、手動の除外、`.github/` を変更する PR、すでにキューに戻っている PR、すでに説明済みの実行については何も投稿せず、キューへの追加・削除やマージを行うことは決してありません。`t-ci-merge-queue-notice` は、`tests/fixtures/merge-queue-notice/` にある実際の除外の切り詰めた記録でこれを固定します。

PR CI は厳格なままです。失敗したファイルは再試行なしに PR で赤になるため、不安定さは持ち込まれた場所で見えます。マージキューは異なります。1 つの不安定なファイルが PR を外し、その後ろにキューされたすべてのグループを再ビルドさせるからです。そこでは、`ci.yml` がスモーク、ユニット、integration の各レッグに `retry-once` を渡し、それらは `--file-retries 1` で層を実行します。最初の試行がアサーションで失敗したファイル（失敗したケースがあり、JUnit の証拠が完全で、ファイルのタイムアウトもクリーンアップの失敗もなく、最大 10 分で、実行に少なくとも 5 分残っているもの）は、新しいプロセスと一時ディレクトリでもう一度実行されます。自身のケースのタイムアウトを超えて実行されたケースは失敗したケースであり、失敗がそのようなケースのタイムアウトだけのファイル（遅い Windows のランナーでケースがタイムアウトした場合）は、最大 45 分実行していても 1 回の再試行を受けます。`retries.json` はそれを `caseTimeoutsOnly` と記します。この規則は `tests/lib/file-retry.ts` にあり、隔離されたライブの再試行と共有されます。失敗したケースのないクラッシュや非ゼロの終了、ケースを 1 つも実行しなかったファイル、期限を超えて実行したファイル、2 回目の失敗は決して再試行されません。利用者ターンの失敗も同様です。駆動の `PersonTurnError`（`tests/harness/person-turns.ts`。利用者の返答の裏付けなしに利用者のものとして記録された判断、または利用者が答える前に始まった作業）で失敗したケースは、そのファイルを `NO RETRY` の行とともに赤のままにします。2 回目の試行での合格は、利用者が出会うはずの不具合を隠してしまうからです。最初の失敗を置き換えるのは、最初の試行が実行したすべてのケースに合格した再試行だけです。2 回目の失敗や、それらのケースのいずれかを飛ばした、またはケースを 1 つも実行しなかった再試行は、失敗のままです。
再試行は、最初の試行の証拠を丸ごと脇に移した後でだけ始まります。その一部でも移せなければ、そのファイルは再試行されません。
2 回目の試行での合格が黙って扱われることはありません。ジョブは `Flaky test` の警告（"<file> passed on its second attempt (merge queue)"）を示し、ステップのサマリーは "Passed on retry" の下にそれを列挙し、ファイルの `summary.txt` の行は `PASS` のままで、その下に "passed on retry" の行が付きます。実行のログディレクトリの `retries.json` は、不安定さの切り分けのためにすべての再試行を記録します。最初の試行のログと JUnit は、2 回目の横に `<file>.attempt-1.*` として残ります。隔離された e2e と Full Suite がこのフラグを取ることはありません。`t-runner-production-guards` と `t-ci-retry-report` が、規則、ランナー、レポートをカバーします。

macOS のランナーはホスト型ランナーの中で最も遅く数も少ないため、マージキューのペースを決めます。macOS のユニット一式はマージグループごとに約 245 ジョブ分を要します。
キューでだけ、`ci.yml` は macOS のユニットシャードに `macos-merge-selection` を渡し、`scripts/ci-macos-unit-selection.ts` が、ソースに macOS または darwin の名前を含むユニットファイル（毎回計算し、保持された一覧は使わない）と、最初の親（キューで前にあるエントリ）に対して変更が触れたユニットファイルを選び、重みに応じてキューの 2 つの macOS ユニットジョブに分散させます。全体で約 60 ジョブ分です。選ばれたファイルは、そのアフィニティグループの残りを伴います（t249 は t238 がビルドしたバイナリを読みます）。
各シャードは自身の分担を 1 つの完全なシャードとして実行し（`--shard 1/1`。そのため必須のコンパイル済みカバレッジなどのシャードの規則が成り立つ）、他のファイルは `--exclude` で除外します。そのため macOS でスキップするファイルは、完全なシャードと同様に `SKIP` のままです。選ばれたファイルがないシャードは、インストールの前に止まります。変更の差分を取れない場合、選ばれた名前がテストファイルの文法から外れる場合、選択が失敗した場合は、シャードは完全に実行されます。
macOS のスモーク、integration、隔離された E2E、ネイティブ端末のユニット、Linux と Windows、PR CI、毎晩の Full Suite は、すべてのファイルを実行します。`t345` がこれを固定します。

`main` は本番ではありません。PR CI とマージキューは上記の高速なゲートのままで、必須のホスト型のライブ層は `full-suite.yml` で実行されます。`preview-release.yml` は毎晩、preview のソース SHA について、それを別の実行としてディスパッチします。その失敗は、preview のワークフローを失敗させることなく、その実行と preview のノートで見えるままです。契約検査に合格すると、preview のネイティブのスモーク、ビルド、成果物の検証が Full Suite と並行して実行されます。公開は、検証済みの成果物と完了したテストレポートの両方を待つため、preview のリリースノートには Full Suite やアップグレードの警告が残ります。
ソースが変わっていない場合も、ビルドと公開は飛ばしつつ、契約検査と Full Suite は実行されます。

stable の昇格は、公開済みの preview のソースを選び、バージョンのメタデータと固定された公開の制御だけを加えます。CI や Full Suite は繰り返しません。preview の以前の結果は、失敗も含めて見えるままで、昇格を選ぶのはメンテナーの判断です。新しくビルドされた stable のバイナリは、公開の前に引き続きパッケージ、インストーラー、ライフサイクル、更新の検査に合格します。[昇格の手順](../../DEVELOPERS.md#4-promote-a-preview-to-production) を参照してください。

同じワークフローの ref と同じ検証の選択による新しいディスパッチは古い実行を取り消すため、プッシュ後にライブ検証を再ディスパッチすると、以前の head の実行が置き換えられます。
リリース目的のディスパッチは `ref` 入力もキーにし、preview が呼び出した Full Suite の実行がこの方法で取り消されることはありません。

`ci.yml` と `full-suite.yml` は、同じ再利用可能な `.github/workflows/deterministic-tests.yml` を呼び出します。呼び出し側は、不変の `ref`、ランナー、層、ユニットまたは integration のシャード、任意のファイルの `filter` と `exclude`（どちらも既定は空なので、層全体が実行される）、成果物のラベルを選びます。どちらも integration を 6 つのジョブに分けます。スコープ実行（`filter`、`t-scope-run-*`。classic の own-file ファイルを `exclude`）、それらの classic の own-file ファイル（`own-file-moves`）、スコープとホストの実行（`filter`、`t-scope-host-*`）、所要時間を均衡させた 2 つのシャードのガードマトリクス（`filter: ^t-guard-matrix-`、`integration-shard: 1/2` または `2/2`）、それ以外のすべて（3 つすべての `exclude`）です。PR CI は Linux のスモーク、10 の重み付きユニットシャード、そして `own-file-moves` 以外のすべての integration のジョブを選びます。`own-file-moves` はマージキューだけが加えます。`full_verification` の Full Suite は、Linux/macOS/Windows でスモーク、OS ごとに 16 のユニットシャード、6 つの integration のジョブ、隔離された E2E を選びます。毎晩の Full Suite は決定論的な層を実行せず、その `scope_runs` ジョブが、3 つすべての OS でスコープ実行、`own-file-moves`、スコープとホストの実行、ガードマトリクスのために共有ワークフローを呼び出します。integration と E2E は OS ごとに独立したジョブとして、それぞれ新しい Bun のランナープロセスで実行されます。
各呼び出しは新しいチェックアウトを持ち、Bun 1.4.2 の下で固定された依存関係をインストールし、配布物を 1 回だけ再生成し、`--debug -P 8 --no-llm` で Bash ラッパーを呼び出します。E2E の実行は `--isolated-e2e` を保ち、スモークは各チェックアウト内で直列のままで、ユニットも macOS のシャードを除いて直列のままです（[ユニットテストのシャード分割](#ユニットテストのシャード分割)）。ワークフローの共有は、コマンドとセットアップを共有するものであり、以前のテスト結果を共有するものではありません。

CI は、コードの契約、インストーラーの ShellCheck、カバレッジのラチェット、PR の変更履歴の保持、Linux のスモーク、production-guard の検査を 1 つのジョブにまとめます。スモークと production guard は別々のランナープロセスとログディレクトリを使い、共有するのは依存関係のインストールと生成された配布物だけです。macOS と Windows は独自のスモークのジョブを保ちます。Linux のスモークは、マージキューの再試行と不安定なテストの報告の方針を保ちます。各検査は独自のステップと失敗を保ち、独立した検査は前の検査が失敗した後も続きます。カバレッジは引き続き最初の親と比較し、変更履歴の保持は固定された PR のベースを使います。必須の `Tests (smoke + unit)` ステータスは、この統合されたジョブの合格を要求します。PR CI は 17 のランナーを割り当て、マージキューは既存のプラットフォームの選択のまま 51 を割り当てます。ライブのハーネスとネイティブビルドのマトリクスは変わりません。

リポジトリの `default-branch` ルールセットは、マージキューのビルドの同時実行を 8 から 2 グループに制限します。この設定はこれらのワークフローとは別に GitHub で管理され、制限するのはマージグループのビルドの同時実行数であり、マージのバッチに入る PR の数ではありません。必須のチェックは引き続き各グループのコミットで実行されます。

Full Suite は、手動の決定論的なマトリクスを同時 12 ジョブに、毎晩のスコープ／ガードのマトリクスを同時 3 ジョブに制限します。69 の手動の決定論的なジョブと 12 の毎晩のスコープ／ガードのジョブは、引き続きすべて実行されます。スイートの軸が先に来るため、ジョブの作成は Linux、macOS、Windows を交互に並べます。この順序はプラットフォームごとの割り当てではなく、どのジョブが一緒に実行されるかはランナーの空きとジョブの所要時間で決まります。ライブのシャードは、Linux 4、macOS 2、Windows 3 ジョブという既存の制限を保ちます。これらはマトリクスごとの制限であり、組織の割り当てではありません。並行するワークフローは引き続きホスト型の容量を共有します。同時実行を下げると、PR やキューとの競合が減る一方で、Full Suite の実行が長くなることがあります。

単独の決定論的、ネイティブ端末、production-guard のテストジョブは、5 時間のジョブの最終防御と 270 分の実行ステップを使います。ランナーは、スモークと隔離された決定論的な E2E を含め、呼び出し全体で 4 時間の作業期限を共有し、ファイルごとに 2 時間の期限を持ちます。
この階層により、作業が止まった後に、プロセスの退役、レポートの仕上げ、ログの無害化、証拠のアップロードのための時間が残ります。ユニットの作業は重複なしに分割されたままです。CI では 10 の Linux シャード、16 の Windows シャード、マージキューでは選ばれた 2 つの macOS シャード、拡張された手動の CI では 16 の macOS シャードです。Full Suite のフル検証は OS ごとに 16 を使います。コンパイル済みの生成側／利用側のアフィニティは保たれます。

統合された CI のチェックのジョブは、チェックアウトの前に共有の 270 分の作業期限を開始し、5 時間のジョブの上限のうち 30 分をプロセスの後片付けと証拠の収集に残します。チェックアウトと Bun のセットアップはそれぞれ 15 分の上限を持ち、合わせても作業の枠を使い切ることはできません。その後のすべてのセットアップと契約のコマンドは `scripts/ci-check-budget.sh` を通じて実行され、これはプロセスグループのタイムアウトで残りの期限を強制し、期限が切れた後は開始を拒否します。独立した検査は引き続き失敗を集め、Bun が使える限り、コマンドが失敗した後も無害化は実行対象のままです。
スモークは残りの作業時間の最大半分を受け取り、残りの半分を production guard のために取っておきます。guard は、そのステップが始まった時点で実際に残っている時間を受け取ります。各呼び出しは 4 時間の上限も保ちます。
予算を使い切ると、テストを起動する前にそのステップが失敗します。既存のケースとファイルの上限は、各呼び出しの残り予算の中で引き続き適用されます。

同じ階層は、マージキューのネイティブ端末の検査、Full Suite のネイティブの義務、production-guard の検査にも適用されます。これらの経路は、より小さなケース、ファイル、実行、ステップの上限を黙って再導入してはいけません。いずれも、取得された `--debug -P 8` のラッパーの実行と証拠の収集を保ちます。
認証情報を持つライブのジョブは、別個の 1 時間の認証情報の境界を保ちます。70 分のステップと 80 分のジョブの中で 60 分のファイルです。その入れ子のドライバーの操作は、ファイルの残り予算から割り当てられます。

対象を絞った決定論的な再現には、候補のブランチで `deterministic-tests.yml` を直接ディスパッチします。

```bash
gh workflow run deterministic-tests.yml --ref '<candidate-branch>' \
  -f 'ref=<exact-source-sha>' -f runner=windows-latest -f tier=unit \
  -f unit-shard=1/1 -f 'diagnostic_filter=^t-tui-runtime$'
```

`diagnostic_filter` は手動専用のファイル名の正規表現で、再利用する CI の呼び出し側には公開されません。unit 層は `unit-shard=N/M` を必要とし、`1/1` は絞り込みの前にすべてのユニットファイルを選びます。smoke、integration、e2e では `unit-shard` を省きます。その既定値は空です。integration では、絞り込んだ一覧の 1 つの分割を再現するために、さらに `integration-shard=N/M` も使えます。各再現は、モデルのゲートを閉じた新しいランナー 1 つと、同じ不変のチェックアウト、制限されたランナー、無害化された証拠のパスを使います。
既定の成果物は `ci-deterministic-probe-<OS>` です。これらの対象を絞った診断は、フルスイートやリリースの条件を満たしません。

POSIX のユニットジョブには tmux が必要です。共有のセットアップはまず `command -v` を確認し、欠けている場合にだけ Linux では apt、macOS では Homebrew を使います。Linux のユニットジョブは、zsh がなければそれもインストールします。ツールが欠けている場合は、互換性のケースをスキップするのではなく、セットアップが失敗します。

共有ワークフローは、チェックアウトしたコミットを呼び出し側の SHA に束縛します。
リリース目的の Full Suite の実行は計画ジョブで `main` に対してその SHA を認可し、手動の検証は代わりに選択したワークフローの head に束縛します。
PR CI は、ライブの認証情報を受け取らずに PR のマージコミットをテストできます。
各実行は、チェックアウトのルートの `tmp/ci-deterministic/run.log` に stdout/stderr を取得し、そのパスと実際のログのスタンプを出力し、無害化が成功した後にこの取得と `tests/logs/` の両方を保持します。
成果物は呼び出し側のラベルと実際のランナーの OS を使い、証拠を 90 日間保持します。どのワークフローも `ci-deterministic-*` の成果物をダウンロードしないため、`ci.yml` は `evidence-optional: true` を渡します。アップロードの失敗はジョブで報告されますがジョブを失敗させないため、アップロードのタイムアウトが、テストに合格した PR をキューから外すことはありません。テストのステップ自身の終了コードは引き続きジョブを失敗させます。CI の `ci-native-*` と `ci-check-evidence` のアップロードも同じ規則に従います。
Full Suite はこの入力を渡さないため、手動のフル検証の実行の `full-suite-deterministic-*` のアップロードは必須のままです。その実行は人に証拠を渡すために存在し、それを待つキューの PR はないからです。

毎晩の修正が入る前のプラットフォームの検証には、`gh workflow run ci.yml --ref <branch> -f platform_regressions=true` をディスパッチします。これは既存の決定論的なマトリクスを 3 つの OS すべてに広げ、integration と並べて隔離された E2E のジョブを追加します。先に Linux のパスを実行したり、別の広範なリグレッションのスライスを追加したりはしません。完全なユニットシャードには tmux、パス、ワークスペースのフィクスチャ、macOS のリグレッションが含まれ、t238/t249 は重み付きのアフィニティグループに保たれます。
これらは毎晩のテストと同じ POSIX のプロビジョニングと取得の経路を使います。
対象を絞ったネイティブ、production guard、OS 隔離の検査は引き続き必須です。
手動の CI はモデルを呼び出さず、Full Suite の結果も生成しません。

## ステージテストの追加方法

1. テストするステージを選び、それが必要とする状態フィクスチャを特定する（状態はそのステージを現在または次のステージとして示す必要がある）。
2. `tests/fixtures/` に状態フィクスチャを作成するか、既存のものを再利用する。
3. `tests/integration/tNN-stage-SLUG.test.ts` を作成し、シェルの TAP ヘルパーではなく、共有の TypeScript ハーネスのヘルパー（`tests/harness/fixtures.ts`、`tests/harness/sdk-drive.ts`、`tests/harness/tui-drive.ts`、`tests/harness/plugin-kit.ts`、`tests/harness/exec-drive.ts`）を使う。
4. `bun tests/run-tests.ts --integration`、または直接 `bun test tests/integration/tNN-stage-SLUG.test.ts` で実行する。

## 受け入れテストのアサーション追加方法

`tests/e2e/` 配下の既存の e2e ワークフローテストに成果物のアサーションを追加するには、次のようにします。

1. 現在のテストを読み、すでに何を確認しているかを理解する。
2. 既存の `test(...)` ブロック内に `expect(...)` のアサーションを追加する（bun:test は呼び出しそのものからアサーションを数えるため、同期すべき `plan` の行はない）。
3. 柔軟なパターンを使う。正確な文字列ではなく、`readFileSync` の内容に対して `/[Tt]odo/` を照合する。
4. 非決定的な LLM の出力形式に依存するアサーションには、`test.skipIf(...)` または早期リターンを使う。
5. サイズの下限の確認には `expect(statSync(path).size).toBeGreaterThan(minBytes)` を使う。

## アサーション設計原則

- **キーワードのクラス** — 大文字小文字を区別しない正規表現を使う: `[Tt]odo`、`[Rr]eact`、`[Bb]rownfield`
- **柔軟な検出** — 正確な名前を確認するのではなく、`find` + `wc -l` でファイル数を数える
- **サイズの下限** — 最小の内容量には `statSync(path).size` と `toBeGreaterThan()` を使う
- **段階的な劣化** — アサーションが非決定的な LLM の出力に依存する場合は `skip` を使う
- **内容より構造** — 内容を確認する前に、Markdown の見出し（`^#`）、ファイルの存在、ディレクトリの作成を確認する

## CLI リファレンス

```bash
# Entrypoints
bun tests/run-tests.ts        # Native cross-platform runner
bash tests/run-tests.sh       # POSIX compatibility wrapper

# Level flags (combinable)
--smoke         # Structural validation
--unit          # Unit directory, including existing process and workflow contracts
--integration   # Cross-component contracts and stage/CLI utilities
--e2e           # Full lifecycle, worktree, and rendered terminal journeys

# Profile flags (shortcuts)
(default)       # smoke + unit + integration
--ci            # smoke + unit + integration
--release       # smoke + unit + integration + e2e
--all           # Same as --release

# Output modifiers
--production-guards # Run selected tests with guard bypasses and direct authority
                    # off; neutralize inherited off-switches. Default: fixture.
--verbose       # Write per-test logs to tests/logs/
--no-llm        # Force all live-model gates closed while deterministic
                # integration/e2e tests still run. Also via AIDLC_NO_LLM=1.
--debug         # Implies --verbose; streams per-test output and writes SDK/TUI
                # driver traces to tests/logs/
--filter PAT    # Only run tests whose filename matches extended regex PAT
--exclude PAT   # Leave out tests whose filename matches PAT; the rest run as an ordinary tier
--parallel N    # Run up to N test files concurrently within a tier (alias: -P N).
                # Default: 1 (serial). Smoke is always serial; unit is too, except
                # a --shard run on a platform the unit weights cap (macOS).
--file-timeout N  # Independent file ceiling in seconds for every tier; caps isolated E2E too.
                  # Default: 7200 outside isolated E2E.
--run-timeout N   # Shared work deadline in seconds across setup and all selected files.
--shard N/M     # Run one duration-balanced unit or integration shard.
                # Requires --unit or --integration with no other tier/profile.
--isolated-e2e  # Run e2e in independent checkouts; -P sets worker count.
--e2e-plan      # Print selected files/resources without builds or test execution.
                # Requires --e2e; implies --isolated-e2e, not --e2e.
--bedrock-parallel N  # Concurrent Bedrock test files (default 2).
--kiro-parallel N     # Concurrent Kiro test files (default 2).
--ide-parallel N      # Concurrent IDE files, also charged to Kiro (default 1).
--e2e-file-timeout N  # Outer isolated-file deadline in seconds (default 10800).
--e2e-timings FILE    # Prior runner summary.txt for duration-based ordering.
--e2e-cancel-file FILE # Create this file to request cancellation on any platform.
```

`--no-llm`（または `AIDLC_NO_LLM=1`）は、導出される Claude のゲートを閉じ、すべてのライブモデルのオプトイン（Claude TUI、Kiro ACP/TUI/IDE、Codex exec、opencode run）を強制的に `0` にします。これらの層の決定論的なテストは、トークンを使わない TUI の実行基盤の preflight を含め、引き続き実行されます。これにより、CLI がインストールされていてライブの変数が `1` として継承されていても、ライブモデルのコストや不安定さなしに、全層の決定論的なプロファイルを CI に提供します。

ライブの SDK と TUI のハーネスのドライバーは、既定でプロジェクト自身の Claude 設定ソースを使います。SDK のドライバーはコピーされたテストの `.claude/` のプロジェクト設定とフックを読み込み、TUI のドライバーはさらに、人による AI-DLC のステータスラインの選択が置かれる、そのプロジェクトの `.claude/settings.local.json` も読み込みます。どちらも開発者のユーザーレベルのフック／設定は除外します。これはインストールされたフレームワークの表面を再現し、ローカルの対話的な好みがテストの振る舞いを変えるのを防ぎます。明示的なドライバーのオプションや `AIDLC_TUI_SETTING_SOURCES` は、調整のための逃げ道として残ります。

`--all --debug`（および `--release --debug`）は、環境がすでに設定していない限り、既定で `AIDLC_TUI_LIVE=1` にします。これにより、「すべてをトレース付きで」のプロファイルは、トークンを消費するライブの TUI ジャーニーを既定で実行します。それらのファイルをテスト内の SKIP の経路に留めるには、`AIDLC_TUI_LIVE=0` を明示的に設定してください。

`--exclude` は同じ名前に一致しますが、何も選びません。一致したファイルは層から除外され、残りは後述の通常の、絞り込みのない規則を保ちます。`--shard` と組み合わせた場合は、先にシャードが選ばれ、その後で一致したファイルがそこから除外されます。

スコープ実行、スコープとホストの実行、ガードマトリクス（`t-scope-run-*`、`t-scope-host-*`、`t-guard-matrix-*`）はファイルごとに数分かかるため、`--filter` のない実行はそれらを除外し、その旨を伝えます。完全な `--release` と `--all` の受け入れテストはそれらを含みます。CI のジョブと同様に、`--integration -P 8 --filter '^t-(scope-run|scope-host|guard-matrix)-'` でそれらだけを実行できます。

明示的な **`--filter` は、選択した各ファイルでの実行を要求します**。すべてのケースがスキップされた（またはケースを宣言しない）ファイルは、選択した別のファイルが合格しても実行を失敗させます。一部がスキップされたファイルは、少なくとも 1 つのケースが正常に実行されれば合格します。`expect()` の数は実行の指標ではありません。一致しないフィルターも失敗し、失敗したテストをでっち上げるのではなく、`Test files: 0` と `failures.txt` の説明を保持します。

絞り込みのないスイートは任意のスキップを保ち、すべてスキップされたファイルを `SKIP` と報告します。`--no-llm`（または `AIDLC_NO_LLM=1`）は、混在した選択から Claude に依存するファイルを引き続き意図的に除外します。明示的なフィルターがそれらの除外されたファイルだけを選んだ場合は、ケースが実行されなかったため実行は失敗します。`--no-llm` がない場合、明示的に選ばれた Claude のファイルは、その実行基盤が利用できなければ失敗します。すべてのケースがスキップされたと報告する、明示的に絞り込まれた他のライブのファイルも失敗します。文書化されたライブの変数を有効にし、必要な CLI／認証を用意してください。ライブのオプトインだけでは実行の証拠になりません。

サマリーとファイルごとのログは、実行されたテストケースとスキップされたテストケースの数を、従来の `Total assertions` のフィールド（スキップを含む JUnit のテストケースを数える）とは別に報告します。`--verbose` / `--debug` は、Bun が出力した場合、Bun の `<test-name>.junit.xml` をファイルごとのログの横に保持します。
カバレッジの失敗は、`summary.txt` と `failures.txt` でファイルと対処を示します。スキップされたケースについてアサーションの失敗がでっち上げられることはありません。

## ガードプロファイル

既定の **fixture** プロファイルは、合成的なテストのセットアップを簡便に保ちます。テストの子プロセスで `AIDLC_SKIP_ARTIFACT_GUARD`、`AIDLC_SKIP_HUMAN_PRESENCE_GUARD`、`AIDLC_SKIP_SUMMARY_CONFIRMATION_GUARD`、`AIDLC_SKIP_REVISION_BACKSTOP`、`AIDLC_ALLOW_DIRECT_AUDIT_EVENTS` を `1` に設定します。継承された他の変数は既存の振る舞いを保ちます。

本物のガードの証拠を用意し、所有するコマンドやフックを検証するテストには、**`--production-guards` を `--filter` と組み合わせて**使います。これは呼び出しが選択したすべてのテストに適用され、層の選択やライブモデルのゲートは変えません。たとえば、ランナー自身のプロファイルの契約を検証するには次のようにします。

```bash
bash tests/run-tests.sh --debug -P 8 --unit --production-guards \
  --filter '^t-runner-production-guards'
```

production の子プロセスは、既知のガードのスキップ、監査／状態への直接の権限のスイッチ、そしてアンサンブルの証拠、計画承認、レビュアーのスコープ、レビュー凍結、使用量の追跡を含む記録可能なバイパスについて `0` を受け取ります。継承された `AIDLC_SKIP_*`、`AIDLC_DISABLE_*`、`AIDLC_ALLOW_DIRECT_*` の変数もすべて `0` に強制されます。これはランナーが `.claude/settings.json` の環境の値を読み込んだ後に行われるため、シェルやプロジェクト設定の無効化スイッチが、子プロセスの初期のガードプロファイルを黙って変えることはできません。記録可能なバイパスに対する明示的な 0 は、`aidlc.settings.json` / `aidlc.settings.local.json` のバイパスの一覧よりも優先されます。変数を単に削除すると、そのフォールバックを許してしまいます。

ランナーは起動時と標準出力のサマリーで `Guard profile: fixture (...)` または `Guard profile: production (...)` を出力し、`--verbose` や `--debug` では同じラベルを `summary.txt` とファイルごとのログに書きます。テストは、ガードを検証する前に `process.env.AIDLC_TEST_GUARD_PROFILE === "production"` をアサートできます。継承されたマーカーがプロファイルを選ぶことはありません。

これは子プロセスの起動環境の契約です。テストのコードとハーネスのヘルパーは、引き続き自身の環境を上書きしたり、設定を書いたり、合成的なフィクスチャを組み立てたりできます。特に `resetAidlcEnv()` が削除するのは `AWS_AIDLC_DEFAULT_SCOPE` と `AIDLC_SKIP_SOURCE_FRESHNESS` だけです。プロファイルのマーカーや他のガードの設定は保持し、テストがそれらを変えた後に production の 0 を復元することはありません。production プロファイルのラベルだけでは、個々のテストが production のガードの証拠を使ったことの証明にはなりません。その主張の一部として、選択したテストの環境の上書きとセットアップをレビューしてください。

PR ワークフローの統合された `check` ジョブ（`Checks (contracts + smoke + production
guards)`）は、production のガードを有効にして、決定論的なランナーと復旧の契約を独自のステップで実行します。

```bash
bash tests/run-tests.sh --debug -P 8 --production-guards --unit --integration \
  --no-llm --filter '^(t-runner-production-guards|t-guard-recovery-production)' \
  > "$GITHUB_WORKSPACE/tmp/ci-guard-contract/production-run.log" 2>&1
```

このジョブはそのログディレクトリを作成し、テストが失敗しても、無害化の後にスモークと guard のログと `tests/logs/` を `ci-check-evidence` として集めます。アップロードの失敗はジョブを失敗させません。既存の `test` の集約（`Tests (smoke + unit)`。必須チェックの名前として保持）は、すべてのトリガーで、スモーク、すべてのユニットシャード、決定論的な integration とともに `check` の成功を要求し、PR へのプッシュ以外ではネイティブ端末とライブの OS 隔離のマトリクスも要求します。production-guard のスライスは PR へのプッシュのたびに実行され、マージキューでは両方のクロス OS のマトリクスがそれに加わります。

この絞り込んだコマンドから `--production-guards` を外すと失敗します。`t-guard-recovery-production.test.ts` は fixture プロファイルではジャーニーを 1 つも実行しないからです。ランナーのユニットテストが合格しても、その欠けたカバレッジを隠すことはできません。
preview の `full-suite.yml` にある絞り込みのない決定論的な integration のジョブは、意図的な fixture プロファイルを保ち、production のジャーニーのファイルを `SKIP` と報告します。PR CI と Full Suite の必須の production のジョブがそれらのジャーニーを検証します。Full Suite はさらに、その選択について完全なカバレッジを要求します。

## 並列実行

`--parallel N`（または `-P N`）は、層内で最大 N 個のテストファイルを同時に実行します。既定は直列（`1`）です。

**効く場面。** ライブの integration と e2e のテストは、実時間の多くを CLI の起動とモデルのターンに費やします。integration のヘルパーはテストごとに新しいプロジェクトを作ります。共有のプロファイルや生成された出力を持つ E2E の系統には、さらに後述の隔離されたチェックアウトのモードが必要です。

**スパイク結果（2026-05-06、Bedrock 経由の Opus 4.7）:**

| シナリオ | 直列 | `--parallel 4` | `--parallel 8` |
|---|---|---|---|
| 4 × `/aidlc --help` | 56s | 16s (3.5x) | — |
| 8 × `/aidlc --help` | — | — | 31s |

8 つの並列呼び出しのすべてで `cache_read=73789` が観測されました。この過去の help コマンドの調査では、スロットリングや破損なしにプロンプトキャッシュの再利用が観測されましたが、完全なワークフローを同時に実行する容量を示すものではありません。

**直列のままのもの。** スモークの層は `--parallel` を無視し、1 つのチェックアウト内で直列に実行します。ユニットの層も同じですが、`tests/unit-shard-weights.json` が上限を設けるプラットフォーム（macOS。[ユニットテストのシャード分割](#ユニットテストのシャード分割) を参照）での `--shard` の実行は例外です。ユニットの CI は隔離されたシャードで実時間を短縮します。共有ワークフローの各呼び出しが新しいチェックアウトを持ちます。PR CI は Linux で 10 の重み付きユニットシャードを使い、integration には 8 つのワーカーを使い、最も長い integration のファイルから始めます。手動の Full Suite の `full_verification` は、Linux、macOS、Windows のそれぞれで 16 のシャードを使います。スモークは OS ごとに 1 回実行され、決定論的な integration と隔離された E2E は、それぞれ 8 つのワーカーを持つ別々のジョブで実行されます。スモーク／ユニットを組み合わせたコマンドに `-P 8` を加えるだけでは、それらの層は並列化されません。preflight のゲート（`tests/integration/t19.test.ts`）も、LLM の層がその終了ステータスに依存するため直列に実行されます。

**並列時の出力。** `START` マーカーはライブで流れ、最初の `DONE` の前に複数が現れることがあります。通常／詳細モードでは、TypeScript のコーディネーターが各テストの TAP の本文をバッファし、そのファイルが終わったときに 1 つのブロックとして書きます。`--debug` モードでは、Bun の stdout/stderr がライブで流れつつ、各テストのログにも書かれます。並列のデバッグ出力にはファイルのベース名が接頭辞として付くため、重なり合うワーカーでも帰属がわかります。SDK/TUI/Kiro-ACP のドライバーのトレースは、ログの横に `$LOG_DIR/sdk-drive-*.ndjson`、`$LOG_DIR/tui-drive-*.ndjson`、`$LOG_DIR/kiro-acp-drive-*.ndjson` として書かれます。隔離された E2E は、それらをファイルの成果物のディレクトリの下に置きます。ランナーは起動時と各テストの開始時にそれらのパスを出力します。Kiro-ACP のトレースは、ツールの呼び出しと更新、出力のプレビュー、権限の回答、プロセスの stderr、result/timeout/end のイベントを含むため、タイムアウトを保持された証拠から調査できます。

**ワーカーの協調。** TypeScript のランナーは、ファイルごとに 1 つの Bun のテストのサブプロセスを起動し、アクティブな promise を追跡します。並列の上限に達すると、ファイルが終わるのを待ってから次を受け入れます。完了した各ファイルは `$LOG_DIR/_results/` に `.meta` のサイドカーを得て、ランナーはそれらの記録を読んでサマリーの表を埋めます。シェルのラッパーは、すべてのプラットフォームでこのランナーへ委譲します。

**指針。** 隔離された E2E では、チェックアウトの容量として `-P 8` を使い、`--bedrock-parallel 2` のような小さな明示的なプロバイダーの上限から始めてください。そのプロバイダーの許容量は、同時に動くジョブやマシンの間で分けてください。スロットリング、遅延、失敗について代表的なワークフローを測定してから引き上げてください。個々の失敗を調べるには `--filter` を使います。

## 隔離された E2E ワーカー

`--e2e --isolated-e2e` は、ワーカーの容量とライブのプロバイダーの容量を分離します。
`-P` はチェックアウトのワーカー数を制御します。既知の TUI、Codex exec、Kiro ACP/IDE、opencode の直列ファイルは、各ワーカーが自身のチェックアウト、生成ツリー、アプリケーションのプロファイル、一時フィクスチャ、端末の名前空間、出力ディレクトリを所有するため、同時に実行できます。未知の `.serial.` の系統は、その共有リソースがレビューされるまで排他的な実行を保ちます。

一時プロジェクトは、リポジトリの探索がランナーのソースツリーを継承しないよう、Git のチェックアウトの外に置かれます。失敗したフィクスチャは、プロセスのクリーンアップの後、ログの横に保持されます。新しい Claude のプロファイルは初回実行の準備を受けます。所有している起動時のモデルのアップグレードの提案は、出荷されたモデルの固定を保つため、表示される「No」の選択で断ります。

各ファイルは、信頼できる OS の一時ディレクトリの下に非公開の `AIDLC_TUI_BUN_ROOT` を受け取ります。確認されたセッションの記録とスナップショットは、その後プロファイルとログの横にアーカイブされます。
ワーカーのクリーンアップは、ネイティブのドライバーの認証されたセッションの制御を使い、中断された起動を含めデーモンの退役を確認します。これは成功、タイムアウト、取り消しの後に、一時ファイルが削除されたりワーカーが再利用されたりする前に実行されます。クリーンアップが未確認の場合はディスパッチを止め、証拠を保持します。tmux のクリーンアップは、ワーカー自身のトランスポートに限定されたままです。

コーディネーターは、コミットされていない変更を含め、現在の作成済みファイルのスナップショットを取り、独立したワーカーのチェックアウトを作る前に、生成された配布物を一度だけコピーします。既定のローカルの Git のクローンは、可能な場合はオブジェクトファイルをハードリンクし、ファイルシステムをまたぐ場合はコピーし、参照の連鎖を延ばさずに既存の代替ストアを保持します。代替ストアを持つリンクされたワークツリーは、相対的なオブジェクトの参照が正しく解決されるよう、最初のスナップショットに Git のトランスポートを使い、選択したリビジョンは保たれます。インストールされた依存関係は共有され、作業ファイルと Git のインデックスは独立しています。テストは引き続き同じファイル、フィクスチャ、ライブのオプトイン、アサーションを実行します。テスト内の手順は既存の順序を保ちます。スナップショットの準備中にソースを編集したり配布物を再生成したりしないでください。

相対的なシンボリックリンクは、壊れたリンクを含め元のターゲットを保つため、フィクスチャの別名を通じた書き込みはそのワーカーの中に留まります。スナップショットの準備は、絶対パスのリンクとソースのルートから逃れるリンクを拒否します。共有の依存関係のディレクトリは明示的な例外です。追跡されている子孫は、サイズの計算やコピーの前に、構成要素ごとに確認されます。祖先の位置にあるシンボリックリンクやジャンクションは、その末端が通常ファイルに見える場合でも、たどらずに拒否されます。相対的な IDE のシードのパスと、パスを値とする実行ファイルの上書きは、ワーカーの開始前にソースのチェックアウトに対して解決されます。IDE は引き続きシードを非公開のプロファイルにコピーします。

ビルドや CLI の起動なしに、選択全体を確認できます。`--e2e-plan` を `--e2e` と組み合わせてください。これは `--isolated-e2e` を含意しますが、e2e の層自体は選びません。

```bash
bash tests/run-tests.sh --debug -P 8 --e2e --e2e-plan
```

明示的に有効にした Claude TUI の選択の例:

```bash
AIDLC_TUI_LIVE=1 bash tests/run-tests.sh --debug -P 8 \
  --e2e --isolated-e2e --filter 't-tui-(?!kiro)' \
  --bedrock-parallel 2 \
  --e2e-timings tests/logs/<previous-stamp>/summary.txt
```

`--e2e-timings` は任意です。過去の所要時間はスケジュールの順序を決めるもので、選択を決めることはありません。新しいファイルも引き続き実行されます。履歴がない場合は、ソースのタイムアウトの値が大まかな順序の手がかりになります。対象となる最長のファイルが最初に始まり、飽和したリソースを必要としない作業は空いているワーカーを使えます。Bedrock、Kiro、IDE の上限は独立しており、IDE のファイルは Kiro の枠と IDE の枠の両方を消費します。

これらの上限が数えるのは HTTP のリクエストではなく**テストファイル**です。ワークフローは内部で、モデルを使う複数のエージェントを起動することがあります。Claude SDK/TUI、Codex、既定の opencode の実行は、設定されたリージョンが異なる場合でも Bedrock の予算を共有します。
Kiro ACP/TUI/IDE は Kiro の予算を共有します。アカウントの認証は引き続きホストが提供します。生成された IDE のシードはオンボーディングを準備しますが、引き続きサインイン済みのホストが必要です。
予算は 1 つのコーディネーターに適用されます。各ジョブに許容量全体を与えるのではなく、アカウントの予算を同時に動くジョブやマシンの間で分けてください。
これらのプロバイダーの上限は、隔離された E2E のディスパッチに適用されます。integration は引き続き通常の層ごとのスケジューラーを使います。別のホストと並べて実行する場合は、絞り込んだファイルのレーンでライブの SDK の integration を制限し、決定論的な integration は別のチェックアウトに保ってください。パッケージングのテストがそのチェックアウト内で共有の出力を再生成するため、ユニットのシャードにも別々のチェックアウトが必要です。

ネイティブの Windows の Codex のファイルは、`windows-codex` の直列グループも共有します。新しいプロファイルは[文書化された昇格された Windows のサンドボックス](https://learn.chatgpt.com/docs/config-file/config-basic#windows-sandbox-mode)を選び、そのセットアップはホストのアカウントを使います。プロファイルをまたぐ同時の初期化はまだ検証されていません。
無関係なハーネスが空いているワーカーとプロバイダーの枠を使える一方で、Codex のファイルは一度に 1 つずつ実行されます。Windows のホストでは Codex のコーディネーターを 1 つだけ実行してください。これらのネイティブの実行には、ログインした対話型のセッションを使ってください。検証済みのランタイムのサンドボックスのコマンドは、SSH のサービスセッションからは起動できませんでした。Linux と macOS の Codex のファイルは、引き続き Bedrock の上限を使います。

Windows では、同じネイティブのランナーを `--e2e --isolated-e2e --filter 't-ide-kiro'` で使い、`AIDLC_KIRO_IDE_LIVE=1` を設定し、`--ide-parallel` を選びます。
各 IDE の起動はシードを非公開のプロファイルにコピーし、Electron にデバッグのポートを割り当てさせます。親は、PID を使ってポートを選ぶのではなく、その子プロセスのエンドポイントを待ちます。1 つの IDE ファイルから始め、その後で観測したメモリーと完了時間を使って 2 つと比較してください。ネイティブのコマンドは `bun tests/run-tests.ts --debug -P 8 --e2e --isolated-e2e ...` です。この経路は、古い Windows のラッパーの固定のインストールディレクトリに依存しません。
Windows のプロファイルは、Electron の入れ子のデータベースとログのパスがパスの上限に収まるよう、ファイルごとの短い一時ディレクトリを使います。テストの成果物は元のパスを保ちます。解体は、所有するブラウザーの CDP のエンドポイントを通じてクローズを要求し、子プロセスが閉じるのを待ちます。クリーンアップの失敗はプロファイルを保持し、それ以前のテストの失敗とともに見えるままです。
IDE のアダプターは、プロンプトの送信時にイベントが提供したセッション ID も保持するため、ワークスペースの起動のコールバックが観測されなかった場合でも、セッションの識別子は利用可能なままです。セッション ID のないプロンプトは、既存のフォールバックの状態を保ちます。

GUI の実行では、Windows のデスクトップセッションをログインしたままにしてください。インストールされた IDE を認証済みとみなす前に、使い捨てのプロファイルでアカウントのパネルを確認してください。
IDE と CLI には別々のログインの検査があり、サインイン済みの IDE が Kiro CLI や Cursor CLI のゲートを満たすことはありません。プロファイルのシードは Windows のホストに置き、テストの結果とトレースは、そのユーザーデータのディレクトリとは別に収集してください。

ランナーは、タイムスタンプ付きのログディレクトリの下に次の追加の成果物を書きます。

- `e2e-plan.json`: 選択された正確な一覧、見積もり、リソースの要件。
- `e2e-events.ndjson`: ディスパッチ／完了のイベント、ワーカーの ID、キューの時間。
- `e2e-results.json`: 選択されたファイルと前提条件のファイル、ソースのリビジョン／dirty の状態、ワーカーの割り当て、ケースの合格／失敗／スキップの数、所要時間、タイムアウト／クリーンアップの結果、診断用のスロットリングのパターンの数。
- `e2e-artifacts/<test>/`: 保持された JUnit と、隔離された SDK/TUI/IDE のトレース。
- `e2e-artifacts/<test>/deferred-cleanup.json`（隔離されたファイルの実行では `attempt-N/` の下）: コーディネーターがネイティブのプロセスの退役を確認した後の、Windows の Codex のフィクスチャの保持。これらのフィクスチャは成功時でも `retained-fixtures/` に移されます。保護されたサンドボックスのファイルの最終的な削除はホストが担います。ボリュームをまたぐコピーでは元のものも保持されます。
- `failed-fixtures/<label>-<pid>-<n>/`: 失敗したライブの SDK のフィクスチャ（t183、t193）の制限付きのスナップショット。フィクスチャ自体はホスト型ランナーが破棄する OS の一時ディレクトリの下にあるため、`tests/harness/failed-fixture.ts` が取得します。`aidlc/` の下のワークフローの記録が最初にコピーされます。リンクは決してたどらず、`node_modules/` と `.git/` は飛ばし、ファイルごと、ファイル数、合計サイズ、走査の上限が適用されます。`retained-fixture.json` は除外したすべてのエントリを理由ごとに数え、その最初のものをパスで列挙します。
  ライブの収集処理はそれをログツリーの残りとともにコピーし、無害化処理がアップロードの前に墨消しします。
- `e2e-artifacts/<test>/attempt-N/leg-evidence/`: 合格かどうかにかかわらず、すべてのライブの系統が保持するもの。プロジェクトがまだディスク上にある間に、各ドライバー自身の終了時点（SDK の駆動、TUI のセッションの kill、Codex の exec、Copilot や opencode のターン）で `tests/harness/leg-evidence.ts` が取得します。`audit/<project>/` は、その系統が駆動したすべてのプロジェクトの各監査シャードのコピーを、プロジェクト内でのそのパスに保持します。`words-*.ndjson` は、エージェントが利用者に示したテキストごとに 1 行（`ts`、`harness`、`turn`、`text`）を、SDK のメッセージ、TUI のセッションの Claude Code のトランスクリプト、または Copilot と opencode の出力から保持します（Codex は自身の exec のログに言葉を保持します）。8 KiB を超えるテキストと 256 KiB を超えるシャードは、先頭と末尾を保持し、その間に切り詰めたことを記します。1 つの系統がここに保持するのは最大 1 MiB で、それに達したときは `not-kept.txt` が一度だけそう伝えます。2 週間分の毎晩の実行では、系統あたり約 20 KB でした。無害化処理はこのフォルダーをドライバーのトレースとして扱います（後述）。
- `e2e-worker-storage.json`: チェックアウトのプールの場所、見積もったスナップショットのサイズ、チェックアウトのコピーを保持したかどうか。Windows のプールは、深いレポートのパスがフィクスチャのコピーを壊さないよう、システムの一時ディレクトリの下の短い非公開のパスを使います。

Kiro のレビュアーのジャーニーは、アサーションの前に主要な成果物と一致したレビューの受領記録を保存します。スコープ除外のジャーニーは、タイムアウト時も含め、最終的な状態と監査を保存します。そのジャーニーは、ワークフロー全体の完了とスコープから導出された禁止ステージの検査を保ちつつ、完全に指定された小さなセキュリティパッチを使います。セットアップと 2 回の SDK の駆動は、元のケースの期限を共有します。

ファイルごとの出力は逐次保存されます。外側の期限切れや中断された実行は失敗／未完了の結果のままで、合格した再試行に変換されることは決してありません。
verbose/debug の実行は、すべての層について、ファイルごとの JUnit と、実効的なカバレッジのゲートの `.execution.json` の記録を保持します。これらの記録はカバレッジの制御を含むもので、プロセスの環境全体や認証情報は含みません。
すべてのテストファイルは、通常のスモーク／ユニット／integration の実行を含め、所有されたプロセスのスーパーバイザーの下で実行されます。デバッグログの書き込みに失敗すると、以降のディスパッチを止め、受け入れたテストのプロセスを退役させ、ランナーの結果を非ゼロにします。
通常のファイルも非公開の一時ディレクトリと端末の名前空間を受け取るため、ランナーはテストが中止された後にネイティブのセッションを退役させられます。
結果のボリューム自体に書き込めない場合、欠けた取得は未完了のままです。それらが成功したカバレッジを確立することはできません。

Codex のライブテストは `tests/harness/codex-test-lifecycle.ts` を使い、クリーンアップの時間を予約しつつ、元の失敗と exec の出力全体を保持します。Windows では、検証済みのランナー所有のフィクスチャは、コーディネーターがそのプロセスツリーを退役させた後にだけ削除されます。失敗した場合は、それらのフィクスチャを診断の成果物とともに保持します。
exec のドライバーは、Codex exec が処理できない対話型の `request_user_input` 機能を無効にし、スキルの文章による承認のフォールバックを検証します。
承認のアサーションとサンドボックスの権限は引き続き必須です。

Windows のプロビジョニングのフィクスチャは、戻る前にその一時的なアカウントとプロセスが退役していることを要求します。Windows のサービスがまだ保持しているプロファイルのハイブは、GitHub ホストのランナーでだけ VM の破棄のために記録されます。永続的なホストは、制限されたクリーンアップの操作の中でそれを削除しなければなりません。
Windows の決定論的な E2E のジョブは、チェックサムで固定された Codex のコマンドランナーをダウンロードし、`AIDLC_CODEX_RUNNER_PROBE` を設定するため、ネイティブのブートストラップのリグレッションが既存のファイルシステムとアカウントのテストと並べて実行されます。これはモデルを呼び出しません。ローカルの診断では、その変数を検証済みのランナーの実行ファイルに向けます。任意で `AIDLC_CODEX_RUNNER_PROBE_ONLY=1` を設定すると、ブートストラップとランチャーの検査を選びます。
その診断の選択は他のプロビジョニングのケースを飛ばし、完全なカバレッジの結果にはなりません。

ワーカーの準備は、スナップショットとチェックアウトのコピーのための空き容量に加え、512 MiB の予備を確認します。隔離された各ファイルは、開始前に予備を確認します。
`AIDLC_E2E_MIN_FREE_BYTES` は予備をバイト単位（負でない整数）で上書きします。
この受け入れ検査は、実行時のフィクスチャの増加をすべて予測できるわけではありません。通常のアサーションの失敗はフィクスチャと診断の記録を保持し、その後で使い捨てのチェックアウトのプールを解放します。`AIDLC_KEEP_TEMP=1` や未確認のプロセスのクリーンアップは、調査のためにチェックアウトのコピーを保持します。
スケジューリングがライブのワークフローの期限を延ばすことはありません。端末の実行基盤の preflight は、絞り込んだ選択を含め、選択された TUI の作業の前に実行されます。通常のアサーションの失敗が、無関係なファイルの実行を妨げることはありません。

改訂ループの TUI テストは、クリーンなジャーニーと却下／改訂／承認のジャーニーを、別々のプロジェクト、Claude のプロファイル、端末セッションで同時に実行します。
どちらも、クリーンアップの時間を予約したうえで、1 つの 60 分のファイル予算の中で同じ完了のマイルストーンに到達しなければなりません。各ジャーニーは、それぞれの端末の状態、ネイティブの忠実度の証拠、クリーンアップの結果を保持します。

このテストは、新しい Claude のトランスクリプトで、確認済みで完了したルートの HTTP 5xx の失敗があった後も待機を止めます。プロバイダーのエラーとネイティブのトランスクリプトを記録し、所有する answer-gate のクライアントを止め、通常の端末のクリーンアップを行います。これはモデルを再試行したり、失敗を消したり、健全なワークフローの期限を変えたりはしません。ツールの出力、サブエージェントのエラー、復旧された履歴、テストの完了のマイルストーンの後のエラーは、この早期の失敗を引き起こしません。

コントローラーが可搬な取り消しを必要とする場合、特にプロセスを終了しても POSIX のシグナルが届かない Windows では、`--e2e-cancel-file <path>` を使ってください。そのファイルを作成すると、ディスパッチを止め、アクティブな所有するワーカーを終了します。
POSIX の SIGINT/SIGTERM も同じクリーンアップの経路を使います。ホスト／プロセスの強制終了ではクリーンアップを実行できませんが、逐次保存された結果は引き続き未完了のファイルを示します。

従来のサマリーと、失敗したファイルの終了の規約は引き続き利用できます。失敗の終了コードは 255 で頭打ちになるため、256 の未完了のファイルを持つ実行が一周して成功のプロセスステータスになることはありません。サマリーは完全な失敗の数を保持します。
必須の毎晩のゲートには `--require-coverage` を追加してください。スキップされたケース、空のファイル、実行されなかった選択済みのファイル、空の選択は非ゼロの終了を生みます。
すべての verbose の実行は、選択された一覧とケースの数を含む `coverage.json` を書き、テストの失敗とは別に `Coverage: COMPLETE` または `INCOMPLETE` を出力します。必須のゲートにはプラットフォーム固有の選択を使ってください。広範な探索の実行での意図的なプラットフォームのスキップは、それらを満たしません。
実効的な一覧には、狭いファイル名のフィルターの下でも、自動的に必要となる preflight が含まれます。`requestedFiles` は元の選択を数え、`selectedFiles` はそれらの前提条件を 1 回ずつ含みます。端末の前提条件は、TUI のジャーニーを始める前に、スキップされたケースのない、有効で空でない合格の証拠を生成しなければなりません。
JUnit の証拠は、スイートの合計が testcase の記録と一致する完全な文書でなければなりません。切り詰められたレポートの肯定的なヘッダーがゲートを満たすことはできません。最終的なクリーンアップ／公開のエラーは、testcase の結果とは独立に、実行を `ERROR` にします。
`e2e-results.json` はさらに、すべてスキップされたファイルを実行されたカバレッジと区別し、スキップされた、空の、または未完了のファイルについては `coverageComplete` が false になります。no-LLM やプラットフォーム固有の実行では、ライブのカバレッジが正当に不完全になることがあります。毎晩の完全なカバレッジを主張する前に、想定されるプラットフォーム／プロバイダーのジョブを集約してください。スロットリングのパターンの数は出力の中の診断上の一致で、引用されたテキストを含むことがあります。プロバイダーのクォータの失敗を確立するものではありません。

## プラットフォームをまたぐ必須ジョブ

`tests/native-terminal-profile.json` は、決定論的な端末の制御を Linux/Bun、macOS/Bun、Windows/Bun、Linux/tmux のジョブに割り当てます。可搬な制御は 3 つの OS すべてで実行され、ネイティブの Linux と macOS の封じ込め、Windows の Job Object と共有ハンドルの検査、互換バックエンドには明示的な所有者がいます。このプロファイルは Linux arm64、macOS arm64（`macos-15`）、Windows x64 を対象にしています。別のアーキテクチャには、別途対応する義務を宣言してください。
プラットフォーム固有の制御は、別々に選択できるテストファイルにあります。それらのアサーションは、プロファイルによって引き続き必須です。プロファイルが名前を挙げるファイルにケースを追加したら、そのファイルを実行する各ジョブにも追加しなければなりません。Linux では unit 層の `t-native-terminal-profile.test.ts` が、それらのファイルのすべてのケースを実行せずに列挙し、プロファイルが列挙していないケースがあれば失敗するため、PR は Full Suite より先にそれに出会います。

ディスパッチの前に、すべてのホストが受け取る作成済みのソースを使って、計画を 1 つ準備します。

```bash
bun tests/reconcile-tests.ts prepare \
  --profile tests/native-terminal-profile.json --cohort "nightly-$(date -u +%Y%m%dT%H%M%SZ)" \
  --repo . --output tmp/native-plan.json
```

計画には、正確なジョブ／ファイル／testcase の一覧、コホートの ID、コミットされていないバイト列を含む作成済みのソースのダイジェストが含まれます。同じソースのバイト列と計画を他のホストにコピーしてください。計画と結果は、ignore された場所か外部のストレージに置いてください。
ルートのパス、タイムスタンプ、Git のコミット ID だけでは、ソースの識別子にはなりません。

各ジョブは、対応する層／フィルターのフラグと宣言されたバックエンドで実行します。たとえば、ネイティブのプロファイルの Linux のジョブについて正確なフィルターを導出するには次のようにします。

```bash
TEST_MATRIX_PLAN=tmp/native-plan.json
TEST_MATRIX_JOB=linux-bun
TEST_MATRIX_FILTER=$(bun -e '
  const plan = await Bun.file(process.argv[1]).json();
  const job = plan.jobs.find(job => job.id === process.argv[2]);
  if (!job) throw new Error("unknown matrix job");
  const names = job.files.map(({path}) => {
    const parts = path.split("/");
    if (parts[0] !== "tests") throw new Error("expected native-profile test path");
    return `${parts[1]}-${parts.at(-1).replace(/\.test\.ts$/, "")}`
      .replace(/[.*+?^${}()|[\]\\]/g, "\\$&");
  });
  console.log(`^(?:${names.join("|")})$`);
' "$TEST_MATRIX_PLAN" "$TEST_MATRIX_JOB")
AIDLC_TUI_BACKEND=bun bash tests/run-tests.sh --debug -P 8 \
  --unit --integration --e2e --no-llm --isolated-e2e \
  --filter "$TEST_MATRIX_FILTER" \
  --matrix-plan "$TEST_MATRIX_PLAN" --matrix-job "$TEST_MATRIX_JOB" \
  > tmp/native-linux-run.log 2>&1
```

`--matrix-plan` と `--matrix-job` は厳格なカバレッジを含意します。ランナーはディスパッチの前に、実際のソース、プラットフォーム、アーキテクチャ、選択したバックエンド、実効的なファイルの一覧を検証します。クリーンアップとレポートの公開の後に `test-matrix-receipt.json` を封印し、実際の Bun のバージョン、許可リストにあるライブのゲート、JUnit のハッシュ、検証済みの testcase の結果を記録します。ソースの変更、欠けたケース、スキップ、確定処理の失敗は、成功した受領記録を妨げます。
隔離されたジョブは、そのチェックアウトを再利用または削除する前に、各ファイルの前後でワーカーの作成済みソースのハッシュも取ります。その観測は `matrix-worker-source.json` に残ります。照合処理は、その計画、受領記録、参照される JUnit の証拠を上書きする出力パスを拒否します。
Windows では、Bun 1.3.14 が非同期の一時停止の後に同期的な子プロセスを早すぎるタイムアウトにすることがあります。ソースの検証は、読み取り専用の Git の照会からの早期の `ETIMEDOUT` だけを、最大 1 回、元の残り予算で再試行します。
その復旧はログに記録されます。本当の期限切れ、他のエラー、テストの失敗は、この仕組みでは再試行されません。`t-test-source-timeout.test.ts` は、予算の契約と、実際の非同期の隙間のリグレッションの両方を確認します。

各受領記録を、相対的な JUnit のパスを保ったままそのスタンプのディレクトリとともに収集し、必須のすべてのジョブを照合します。

```bash
bun tests/reconcile-tests.ts reconcile --plan tmp/native-plan.json \
  --receipt "<linux-bun-stamp>/test-matrix-receipt.json" \
  --receipt "<darwin-bun-stamp>/test-matrix-receipt.json" \
  --receipt "<windows-bun-stamp>/test-matrix-receipt.json" \
  --receipt "<linux-tmux-stamp>/test-matrix-receipt.json" \
  --output tmp/native-matrix-result.json
```

終了コード 0 になるのは、完全に一致するマトリクスだけです。欠けたジョブ、誤ったソース／コホートやバックエンド、変更された JUnit、本当の失敗、矛盾する受領記録は失敗のままです。後の合格した受領記録が以前の失敗を消すことはできません。明示的に除外されたプロファイルの義務は `NOT_REQUESTED` として現れ、満たされたカバレッジとしては扱われません。

このプロファイルは、端末のドライバーと保持された互換性の制御を検証します。
定期実行の preview は `full-suite.yml` を呼び出し、それがネイティブの受領記録を照合して、宣言されたすべてのジョブの合格を要求します。スキップされたライブのジョブはスイートを失敗させ、文書化された除外の系統はテストされないままです。

### 毎晩のフルスイートのマトリクスとプロビジョニング

`Full Suite` は明示的な `ref` で呼び出すことができ、手動でディスパッチすることもできます（既定は `main`、両方の検証フラグは false）。通常の計画は、マージされていない PR を含め、要求されたブランチまたはコミットを受け付け、一度だけ解決します。
マトリクスのすべてのレッグがその不変の SHA をチェックアウトします。preview と stable のリリースのワークフローは、それぞれ独自の公開ソースの方針を強制します。Full Suite は、テストするだけのためにコミットが `main` 上にあることを要求しません。
定期と手動の `preview-release.yml` の実行は、パッケージングの決定性、型検査、lint、インストーラーのシェル検査の後に、ソースにすでに公開済みの preview がある場合でもそれを呼び出します。preview は PR CI のテストマトリクスを再び呼び出しません。Full Suite がそのテストカバレッジを担います。Full Suite が失敗しても preview のビルドは止まりません。`Release tests` ジョブは、`scripts/ci-preview-test-report.ts` で、失敗したレッグ、失敗したジョブ、失敗したテストケースのレポートを生成します。
レポートは実行のサマリーと `preview-test-report` の成果物に書かれます。
合格でも失敗でも、レポートの最後には answers コーパスの毎晩の読み取り（`### Answers corpus`）が付きます。合格した返答、種類ごとの取りこぼし（setup。エージェントが質問を一度も示さなかったときの検査自身のもの。record、question、words）、取りこぼした各項目の ID で、ライブの検査が `full-suite-live-*` の成果物に残す要約から作られます。要約がなければ、なかったという 1 行になります。このセクションはレポート専用で、公開されるノートには決して入りません。
公開される preview のノートは、冒頭に警告を置き、末尾にそのレポートを載せます。
計画されたノートは丸ごと保たれます。先に譲るのはレポートで、それでも余地がない場合は警告です。そのため、計画されたノートが GitHub のリリースの 125,000 文字の上限に収まる preview を、失敗したスイートが止めることはありません。
`update-from-previous` ジョブ（`scripts/ci-update-from-previous.ts`）は、Linux、macOS、Windows で、最後の stable リリースのインストールを候補に更新し、すべてのハーネスのプロジェクトのフック、refresh、doctor を実行します。各プロジェクトは、人自身がコミットしたアプリ、`.gitignore`、`AGENTS.md` を持ち、その作業はゲートで待っています。更新の前に、最後のリリース自身のエンジンとフックの上で、スクリプト化された代役（`tests/harness/work-open.ts`。そのツールのスコープのホスト上）が bugfix を始め、Requirements の質問に答え、開いた Requirements のゲートでその日の作業を止めます。これを 7 つのプロジェクトすべてで並べて行います。refresh の後、人は新しいチャットで `/aidlc --resume` と入力して承認します。ゲートが戻ってこない、ステージが再び実行される、回答が再び求められる、承認が人の返答に裏付けられていない、次のステージが始まらない、コミットしたファイルが AI-DLC の印の付いた部分の外で変わった、のいずれかで検査は失敗します。代役が最後のリリースで作業を開いたままにすることがそもそもできないときは、検査は独自の行でそう伝えます。ジョブの 2 つ目のレッグ（`--channel copy`）は、コピーのチャネルについて同じことを行います。各プロジェクトは最後のリリースのコピーのランタイムからコピーした `runtime/<harness>/` で、その `.sha256` と照合され、それ自身の `config --from` でセットアップされ、ガイドの Copy Channel が述べるとおり、候補のコピーのランタイムからそのコマンドで refresh します。どちらかのレッグが失敗しても preview は公開され、そのノートは冒頭に警告を置き、レポートにはその行が加わります。`release.yml` は、これに失敗した stable リリースを公開しません。
`Release result` は、preview の公開の成功または意図的なスキップを要求します。Full Suite は別に実行されます。preview はその実行 ID を記録し、その実行の証拠をダウンロードして本当の結果を報告しますが、その失敗を伝播させることはありません。
変更のないソースは公開をスキップしますが、テストレポートは引き続き受け取ります。stable の昇格は、選んだ preview のソースと新しいバージョンのコミットを検証し、その後、ソースの CI や Full Suite を繰り返さずに、ネイティブバイナリ、インストーラー、ライフサイクルのフロー、アップグレード、チェックサム、来歴をビルドして検査します。決定論的なソースの層と production guard は、PR／マージの CI と手動の `full_verification` に残り、通常のリリース目的の Full Suite はそれらを省きます。preview も契約検査と Full Suite を一度実行し、公開の重複排除は、その後のビルドと公開のチェーンにだけ適用されます。

マージされていない PR を利用者の承認のもとで完全に検証するには、そのブランチを選び、`ref` をそのブランチの正確なワークフローの head の SHA に設定します。

```bash
gh workflow run full-suite.yml --ref '<candidate-branch>' \
  -f 'ref=<exact-workflow-head-sha>' -f full_verification=true
```

フル検証は、認証情報を受け取らないすべてのジョブを実行します。ネイティブの義務と照合、すべての決定論的な層、production guard、Windows のリリース契約です。マージされていないコードを選ぶことがあるため、3 つの `live_prepare_*` ジョブ、`live_linux`、`live_macos`、`live_windows`（OIDC と AWS の認証情報を要求するジョブ）は決して実行しません。候補のライブの系統は、別に認可されたモードである後述の `live_verification` でカバーしてください。Full Suite のすべてのチェックアウトは `persist-credentials: false` を設定するため、候補のコードがディスク上でリポジトリのトークンを見つけることはありません。それ以外は、通常の Full Suite の実行と同じファイルのマトリクス、アサーション、タイムアウトを使います。別個の `full-suite-verification-result` の成果物は、`purpose: "full-verification"` を持つ `full-suite-result.json` を含みます。`passed` は、他のすべてのジョブの成功、6 つのライブ／準備のジョブが `skipped` であること、`verificationFamily: "all"`、そして `omittedLegs` がちょうどその 6 つのジョブを示すことを要求します。
候補がマージされた後でも、preview と stable のどちらの公開もこの結果を使いません。

`full_verification` は `workflow_dispatch` にだけ存在します。チェックアウトした SHA が選択したワークフローの head と等しいことを要求し、`live_verification` とは同時に指定できず、系統／ファイルのフィルターを拒否します。プッシュやプルリクエストのイベントが特権付きのフル検証を自動的に始めることはありません。

利用者の承認のもとでライブだけの候補の検証を行うには、候補のブランチで `live_verification=true` を付けて Full Suite を手動でディスパッチし、`ref` をそのブランチの正確なワークフローの head の SHA に設定します。

```bash
gh workflow run full-suite.yml --ref '<candidate-branch>' \
  -f 'ref=<exact-workflow-head-sha>' -f live_verification=true
```

他のカバレッジがすでに実行中の間に 1 つの系統だけを繰り返すには、`-f verification_family=codex` を追加します。手動の選択肢は `all`（既定）、`claude-sdk`、`claude-tui`、`codex`、`copilot`、`opencode` です。`all` 以外の系統には、ライブ検証のモードと、同じ手動のイベント／正確な head の検査が必要です。
これは Linux/macOS/Windows でその系統の行だけを選び、元のプラットフォームごとの N/M のシャード番号を保ちます。範囲を絞った検証では、別個の Windows のリリース契約のジョブは省かれます。再利用の呼び出し側には系統のセレクターは公開されず、通常のリリース目的の実行は `all` を使わなければなりません。

1 つのテストファイルについては、その正確なリポジトリのパスも渡します。

```bash
gh workflow run full-suite.yml --ref '<candidate-branch>' \
  -f 'ref=<exact-workflow-head-sha>' -f live_verification=true \
  -f verification_family=claude-sdk \
  -f verification_test=tests/integration/t238-user-stories-mob.sdk.test.ts
```

ファイルは選択した系統に属していなければなりません。未知のパスや系統の不一致は計画で失敗します。ファイルは宣言されたプラットフォームで実行されます。可搬なテストは 3 つの OS すべてを使い、Windows 専用のケースは Windows を使います。準備はそれらのランナーだけをカバーします。元のシャードの識別子はそのまま保たれ、結果は `verificationTest`、`verificationPlatforms`、省略されたジョブを明示的に記録します。
この選択は stable の公開では使われません。

これらの検証の入力は `workflow_dispatch` にだけ存在し、`workflow_call` には決して存在しません。
認可には、そのイベントと、チェックアウトした SHA が `github.sha` と等しいことが必要です。`main` でワークフローを選んでも、別のブランチのソースを認可することはできません。プッシュやプルリクエストのトリガーが特権付きの検証を始めることはありません。
このモードは `plan`、3 つの `live_prepare_*` ジョブ、`live_linux`、`live_macos`、`live_windows`、`release_contract_windows` を実行します。ネイティブ端末／照合、決定論的な層、production guard は意図的にスキップするため、決定論的な CI を繰り返しません。既存のプロバイダーのオプトイン、厳格なライブのカバレッジ、認証情報の隔離は引き続き有効です。

別個の `full-suite-live-verification-result` の成果物は、`purpose: "live-verification"`、`verificationFamily`、`omittedLegs` にある省略されたジョブ、`complete: false` を持つ `full-suite-result.json` を含みます。その `passed` は、すべてのライブのジョブの成功と、意図的に省略したすべてのジョブが `skipped` であることを要求します。欠けた、失敗した、取り消された、予期せず実行されたジョブは失敗します。`main` についての成功した検証であっても、stable の公開では使われません。通常の Full Suite の実行は `full-suite-result` の成果物の名前を保ち、明示的に省略された決定論的なジョブと production-guard のジョブを除くすべてのジョブを要求します。リリース目的を持たない古い成果物は、Full Suite の結果の方針を満たしません。

3 つの独立した `live_prepare_*` ジョブは、contents-read の権限だけで `live-prepare.yml` を呼び出し、依存関係をインストールし配布物をパッケージします。各ライブの OS のジョブは、自身のプラットフォームの準備だけを待ちます。POSIX の準備は公式の Node 22.23.2 を選び、その完全なインストールプレフィックスを固定された CLI とともにパックします（`ci-live-deps.py pack --cli ... --node-runtime ...`）。検証済みのアーカイブは `bin/node` とそのライブラリのディレクトリの両方を要求します。隔離されたランタイムは、そのプレフィックスを root 所有のツールツリーにコピーし、`node/bin` を PATH に置いて、ローダー相対のライブラリを保ちます。Node と CLI の起動は、ランナーのディレクトリを保護した後に確認されます。Homebrew の実行ファイルだけをコピーすると `@rpath/libnode` のような依存関係が失われるため、サポートされません。
Windows の CLI のインストールは、その隔離されたユーザーの中に留まります。
これで [#1306](https://github.com/awslabs/aidlc-workflows/issues/1306) が解決します。インストーラーが OIDC のスコープ内で実行されることはなく、認証情報を持つレーンは準備済みのバイト列を検証して展開するだけです。認可されたすべての Full Suite の実行は、既存の `ai-pr-review` 環境を使って準備とホスト型のライブのジョブを実行します。このリリースのワークフローには、別個のライブのオプトインのスイッチはありません。前提条件の欠落、スキップされたジョブ、失敗したテストは、通常の Full Suite の実行を失敗させます。
それらは preview の公開を妨げません。preview は引き続きビルドされ、そのノートは Full Suite の失敗レポートで終わり、別個の Full Suite の実行だけが赤のままになります。stable の昇格はそれらの結果と警告を preview のページに保ち、警告の行を昇格の記録に保持し、stable のページはその preview にリンクします。スイートを繰り返すことも、以前の失敗が合格したと主張することもありません。stable の公開には、引き続き新しいバイナリがインストールとアップグレードの検査に合格することが必要です。認証情報を使わない Windows のリリース契約のジョブも実行されます。

宣言されたカバレッジは次のとおりです。

- 手動の `full_verification` だけ: Linux、macOS、Windows での決定論的なスモーク、16 の独立したユニットシャード、integration、隔離された E2E。integration と E2E は別々のジョブで、それぞれ 8 つのワーカーと独自のランナーのプロセスと証拠を持ちます。すべてのユニットファイルは OS ごとに 1 つのシャードに割り当てられ、各シャードは独自のデバッグログと結果を保持します。
- 手動の `full_verification` だけ: Linux の production-guard のスライスが、ランナーと復旧の契約について `--production-guards` と `--require-coverage` を選びます。そのため、通常の fixture モードの層がそれらのケースをスキップしても、それらは検証されます。
- Linux arm64/Bun と tmux、macOS arm64/Bun（`macos-15`）、Windows/Bun での、ソースに束縛されたネイティブ端末の義務。ホスト型の Windows は他のツール用に Node を提供し、Bun が固定された依存関係をインストールします。
- ホスト型の Linux/macOS/Windows での Claude SDK、Claude TUI、Codex、Copilot CLI、opencode、リリースのエンドポイントの契約。厳格な SDK のレッグでの Claude プラグインの呼び出しを含みます。
  Copilot CLI は、認証情報のブローカーに対して独自モデル（BYOK）のモードで、Codex が使う Mantle のモデル上で実行されるため、GitHub のサインイン、Copilot のシート、トークンは関わりません。そのリリースのジャーニー（`tests/e2e/t-exec-copilot-release-journey.serial.test.ts`）は、人が初日に行うことです。コピーのチャネルでのセットアップ、doctor、文書化された最初の手順、計画の質問、Reverse Engineering の承認で、入力したすべての行についてメッセージ記録があります。2 つ目のケースはフォルダーを信頼しないままにし、doctor が信頼の修正を示すことを要求します。Codex の golden ジャーニー（`tests/e2e/t-exec-codex-journey-golden-bugfix.serial.test.ts`、Linux と Windows）は、同じ greeter を最初の行から Code Generation の承認まで修正し、計画の質問はその日に残して新しいセッションで承認します。Copilot のもの（`tests/e2e/t-exec-copilot-journey-golden-bugfix.serial.test.ts`、Linux だけ。Windows では再試行が許す 25 分を超えて実行されるため）は、そのリリースのジャーニーのコピーのチャネルのインストール上で同じことを行います。opencode のもの（`tests/e2e/t-run-opencode-journey-golden-change.serial.test.ts`、Linux と Windows）は、同じ依頼を Reverse Engineering まで進め、そこで人が自分の言葉で 1 つの変更を求めて改訂を承認します。出荷された権限の表の上で行います。
- Kiro ACP、TUI、IDE は、専用の隔離された Windows デスクトップのホストができるまで、宣言された除外です。ローカルのライブの実行が引き続きそのカバレッジの経路です。
- Cursor は除外されます。ベンダーの CLI がエージェントの環境から API キーを読むため、認証情報の分離ができないからです。どの除外も、成功したカバレッジとしては報告されません。

`scripts/ci-live-filter.ts --list` は、発見された系統の分割を出力します。
認可と依存関係のインストールの後、計画は `--matrix linux`、`--matrix macos`、`--matrix windows` を、`live_linux`、`live_macos`、`live_windows` のジョブの動的なマトリクスとして出力します。各行の `shard: N/M` は、その系統／プラットフォームについて所要時間の均衡が取れたグループを選びます。各 OS は、Claude SDK のシャードを 2 つ（golden ジャーニーを実行し、answers コーパスを実行する唯一の OS である Linux では 5 つ。コーパスはそれ専用のシャード。golden ジャーニーも実行する Windows では 3 つ）、Claude TUI を 3 つ、Codex を 1 つ（Codex の golden ジャーニーを実行する Linux と Windows では 2 つ）、Copilot を 1 つ、opencode を 1 つ持ち、全体で 30 のライブのハーネスのジョブになります。golden ジャーニーは、そこで再試行が許す 25 分未満で済む限り、Linux と Windows で実行されます。`tests/live-shard-weights.json` のタイミングの重みはスケジューリングの手がかりです。
探索は引き続き、対象となるすべてのファイルをプラットフォームごとにちょうど 1 回割り当てます。各 OS は独自の同時実行の上限を持ち、ライブのジョブは Linux で 4 つ、macOS で 2 つ、Windows で 3 つです。
すべてのシャードは最大 2 つのファイルワーカーを持ち、Windows の Codex のファイルは直列のままです。
Windows のリリース契約のカバレッジは、シャードに分けない別個のジョブに留まります。

`--isolated-files` は、各ワーカーの次のファイルの前に、生成物と Git の状態を含め、元のチェックアウトのスナップショットからそれを復元します。各ファイル／試行は、新しい HOME/USERPROFILE、一時ディレクトリ、Claude/Codex/opencode と XDG のプロファイル、非公開の Git の設定、ブローカー専用の AWS の設定の非公開のコピーを受け取ります。
インストールされたツールと依存関係は再利用されます。枠を再利用する前に、既存のプロセス／トランスポートの退役の検査が成功しなければなりません。クリーンアップが不確かな場合はディスパッチを止め、残りのファイルを未完了と記します。

出荷時の権限設定: 2 つの golden ジャーニーは、Claude Code を既定の権限モードで、プロジェクトの出荷時の設定（設定ソースは user、project、local。user は駆動のスクラッチの設定フォルダー）とともに駆動し、すべてのプロンプトに yes と答えます。AI-DLC 自身のコマンドや記録（`aidlc/` や `.claude/` を示すもの）についてのプロンプトや、プロジェクトの外への書き込みはジャーニーを失敗させます。ほかのすべてのプロンプトはそのログに列挙されます（`tests/harness/stock-permissions.ts`）。ほかの Claude SDK の駆動は `bypassPermissions` を保ちます。Codex の `--json` のジャーニーは出荷時の `workspace-write` のサンドボックスで実行され、サンドボックスが拒否した `.codex/` や `aidlc/` を示すコマンドはそのターンを失敗させます。Copilot CLI は `--allow-all-tools` で実行され（AI-DLC は Copilot CLI の許可ルールを出荷しないため、人自身の `--allow-tool` のルールが決めます）、Claude のターミナルのジャーニーは権限のプロンプトを飛ばし、opencode はすでに `--auto` なしで実行されます。

`--file-retries 1` は、確認されたクリーンアップの後に、短い失敗したファイルだけを新しい状態で再試行し、両方の試行を `e2e-artifacts/<file>/attempt-N` の下に保持します。
（`--isolated-files` がない場合、同じフラグはスモーク、ユニット、integration のファイルを新しいプロセスで再試行します。マージキューは前述のとおりそれを使います。）
タイムアウト、不完全な証拠、クリーンアップの失敗、利用者ターンの失敗は再試行されません。利用者ターンの失敗は `Person-turn failure` のエラー行も出力します。再試行で合格すると `Flaky live test` の警告を出力します。モデルのサービスが失敗したために失敗したファイル（SDK の駆動の `ModelApiError`。Claude Code が 429、5xx、切断された接続で実行を終えた場合で、リクエストが原因の 4xx は決して含まない）は 1 回の再試行を保ち、`Model service failure` の警告を出力します。失敗したケースがすべてサービスのものであるとき、`failures.txt` と preview のレポートのその行は "the model service failed, not AI-DLC: infrastructure,
not a test result" となり、本当の失敗がそれと並ぶ場合は、ファイルの通常の理由が保たれます。Windows のライブのジョブは隔離された子の出力をログに入れないため、これらの行は収集した `e2e-results.json` から（`bun scripts/ci-retry-report.ts --live
tests/logs`）、決まった言葉とテストファイルの名前だけで伝えます。合格したファイルは再実行されません。各シャードは、認証された隔離と必須の機能の preflight を保ちます。手動の `--family FAMILY --test <repository-path>` は、シャードの識別子を保ったまま、宣言されたプラットフォームでそのファイルだけを選びます。
依存関係の準備は高速な gzip 圧縮を使い、起動を短くするため、生成されたアーカイブを 2 回目の圧縮なしにアップロードします。

Full Suite のすべてのジョブ名は、ランナーの OS を先頭に置き、その後にレーンとマトリクスの項目を続けます。たとえば `Linux / claude-tui 3/3`、`macOS / deterministic unit-3`、`Windows / native-terminal bun`、`Windows / release-contract` です。そのため Actions の UI は実行のジョブを OS ごとにまとめます。結果の `legs` はジョブ ID を保ち、preview のレポートは失敗したジョブを OS とレーンごとにまとめます。

認証情報を持つ各ジョブは、既存のロールから 3,600 秒のセッションを要求します。
ジョブには 80 分、ライブのテストステップには 70 分の上限があります。すべてのライブの系統は、通常の integration/SDK のファイルを含め、3,600 秒の共有のランナー予算と独立したファイルの期限を受け取ります。ドライバーの作業は、その枠の中でクリーンアップのために最大 5 分を予約します。収集は失敗やタイムアウトの後も続きます。古いジャーニーのより長いローカルのタイムアウトが、ホスト型の予算を延ばすことはありません。使い切った場合は、カバレッジが未完了の目に見える失敗になります。

`bun scripts/ci-live-filter.ts claude-tui --platform linux` は、アンカー付きのランナーのフィルターを出力します。探索は、各ファイル自身の integration/e2e のライブのゲートの変数、導出された Claude の実行基盤の一覧、ユニットのリリース契約のオプトインを使います。汎用のプラグインのヘルパーを使っても、それがサポートするすべてのプロバイダーのカバレッジを主張することにはなりません。
ユニットのゲートのフィクスチャのテストは決定論的で、ライブの系統ではありません。`PLATFORM_ONLY` は、一部のプラットフォームでだけ実行されるファイルと、プラットフォームの指定がなければ、どのライブのジョブも設定しない独自のスイッチでだけ開く要求に応じた検査（入力コーパスの検査）の名前を挙げます。選ばれたファイル内のスキップされたケースを隠すことは決してありません。すべてのライブのプロバイダーのレッグは `--require-coverage` を使います。リリース契約のファイルはプラットフォーム条件付きのケースを保ち、そのフラグを使いません。

ネイティブのプロファイルの外では、決定論的な結果とリリース契約の結果はジョブの結果であり、個々のケースのすべてが OS のマトリクスのどこかで実行されたことの証明ではありません。
それらのデバッグの成果物は、ファイルごとのケースの数、スキップされたケース、JUnit を保持します。
そのようなケースのすべてを該当する OS に割り当て、ジョブをまたいでそれらの受領記録を照合する、ソースに束縛された一覧はありません。各層全体に `--require-coverage` を適用すると、正当にプラットフォームに該当しないケースまで拒否してしまいます。緑のジョブがそれらのスキップを合格に変えることはありません。OS をまたぐ完全なケースのカバレッジは、その一覧と照合ができるまで、明示的な欠落として残ります。

`--args` を加えると、完全なランナーの引数を 1 行に 1 つずつ出力します。スクリプトが層の選択を担います。選ばれたファイルのある層だけを出力し、各系統の厳格なカバレッジの方針を適用します。ライブの integration と E2E のファイルは `--isolated-files` を使い、ユニットのリリース契約は既存の実行経路を保ちます。
production-guard のジャーニーは、fixture プロファイルのファイルとシャードを共有する場合も含め、独立して production のプロファイルを受け取ります。ワークフローは `--run` を使ってリポジトリのルートからランナーを直接起動し、シェルの単語分割や Bash のバージョン固有の組み込みコマンドなしに、各引数を保ちます。

```bash
bun scripts/ci-live-filter.ts claude-sdk --platform linux --run -- --debug -P 8
```

e2e のファイルを含む選択では、テストを実行せずに計画を確認するために `--e2e-plan` を追加します。integration だけやユニットだけの選択には追加しないでください。そのモードは空の e2e の選択を意図的に拒否します。決定論的な `--no-llm` の実行は、閉じた Claude のヘルスの preflight を省き、そのファイルをスキップとして記録します。意図的なスキップを前提条件の失敗として扱うことはありません。

成果物は `full-suite-native-plan`、`full-suite-native-<job>`（完全なログのスタンプのディレクトリと JUnit）、`full-suite-native-result`、`full-suite-production-guards`、`full-suite-deterministic-<suite>-<OS>`（suite は `smoke`、`unit-1` から `unit-16`、`integration`、`scope-runs`、`own-file-moves`、`scope-hosts`、`guard-matrix-1`、`guard-matrix-2`、`e2e`）、`full-suite-scope-runs-<OS>`、`full-suite-own-file-moves-<OS>`、`full-suite-scope-hosts-<OS>`、`full-suite-guard-matrix-1-<OS>`、`full-suite-guard-matrix-2-<OS>`（リリースの `scope_runs` ジョブ）、`full-suite-live-<family>-<slice-number>-<OS>`、`full-suite-live-release-contract-Windows`、そして目的別の結果（90 日間保持）です。`purpose: "release"` には `full-suite-result`、`"live-verification"` には `full-suite-live-verification-result`、`"full-verification"` には `full-suite-verification-result` です。最終的な JSON は、`sha`、`runId`、`runAttempt`、`purpose`、`verificationFamily`、`coveragePolicy`、`passed`、`complete`、`legs` にあるすべてのジョブの結果、`disabledLegs: []`、`omittedLegs`、そして並べ替えた `excluded` の一覧にある `hosting: "excluded"` と宣言されたライブの系統を記録します。`required-hosted-live-shards-v3` の下の `purpose: "release"` では、`passed` は 40 桁の 16 進のコミット ID、省略されスキップされたのがちょうど `deterministic` と `production_guards` であること、そして `scope_runs` を含む宣言された他のすべてのジョブの成功を要求します。
欠けた、失敗した、取り消された、予期せずスキップされた必須のジョブは失敗します。`disabledLegs` は、Full Suite の結果の方針が過去の disabled-live のレポートを拒否できるように保持されています。`complete` はさらに除外された系統がないことを要求します。文書化された Kiro と Cursor の除外があるため false のままで、preview の公開の条件ではありません。それらの除外はスイートを失敗させずに警告し、無効化された必須のジョブはスイートを失敗させます。
任意の検査器である `scripts/ci-full-suite-evidence.ts check` が結果を受け入れるのは、`sha` が要求されたコミット、`runId` がその結果の出所の実行、`purpose` が `"release"`、`verificationFamily` が `"all"`、`coveragePolicy` が `required-hosted-live-shards-v3`、`passed` が true、`disabledLegs` が空、`omittedLegs` がちょうど 2 つの決定論的／production-guard のジョブ ID である場合だけです。それらのジョブはスキップされていなければならず、宣言された他のすべてのジョブと追加のレッグは成功していなければなりません。
`complete` は要求しないため、文書化された除外は警告になるだけです。昇格はこの検査器を呼び出さず、それが合格することも要求しません。
ジョブの成功もこの方針のマーカーも、OS をまたぐ完全なケースのカバレッジを主張するものではありません。

ネイティブのジョブは、`--debug -P 8` と変わらないマトリクスの計画／ジョブのセレクターで Bash ラッパーを使います。その成果物には、`tests/logs/` に加え、無害化されたルートの `tmp/full-suite-native/` の取得とリテラルのスタンプのパスが含まれます。ネイティブの受領記録の照合は、引き続き受領記録を再帰的に発見します。

共有の決定論的な成果物は、`tests/logs/<stamp>/` と `tmp/ci-deterministic/`（完全な stdout/stderr とリテラルのスタンプのパス）を含みます。CI の成果物は `ci-deterministic-<suite>-<OS>` を使い、suite は、拡張された macOS/Windows の実行での smoke、Linux での unit-1 から unit-10、Windows と手動の macOS での unit-1 から unit-16、マージキューの macOS での unit-1 から unit-2、integration、scope-runs、own-file-moves（拡張されたマトリクスだけ）、scope-hosts、guard-matrix-1、guard-matrix-2、または e2e（拡張されたマトリクスだけ）です。
Linux のスモークと production-guard の証拠は、代わりに `tmp/ci-smoke/`、`tmp/ci-guard-contract/`、`tests/logs/` を含む `ci-check-evidence` を共有します。
アップロードには、失敗したテストコマンドの後も含め、両方のログの場所が無害化に合格することが必要です。

Kiro ACP/TUI/IDE のライブの系統は、毎晩のフルスイートでの宣言された除外で、警告として出力され、`complete: false` のままにします。それらには、別の低権限の識別子で Kiro を実行する、専用の隔離された Windows デスクトップのホストが必要です。
`AIDLC_KIRO_ACP_LIVE=1`、`AIDLC_KIRO_TUI_LIVE=1`、`AIDLC_KIRO_IDE_LIVE=1` でのローカルの実行が、引き続きカバレッジの経路です。ホスト型のレーンは後続の課題で追跡されています。

stable の昇格のために preview を選ぶ前に、メンテナーは選んだソース SHA について記録された Kiro CLI のリリースのジャーニーの結果を、Kiro のツリーごとに 1 つずつ確認します。セットアップが "Kiro CLI (V2)" と表示する `kiro` と、セットアップが "Kiro" と表示し、その `.kiro/settings/cli.json` が Kiro CLI を v3 エンジンに固定する `kiro-ide` です。どちらも Kiro CLI で実行され、どちらも Kiro IDE を駆動しません。その SHA についての結果がなければ、サインイン済みの Kiro CLI があるマシンで、preview のソースのコミット上でジャーニー（`tests/e2e/t-tui-kiro-release-journey.serial.test.ts`。Copilot のレーンと同じジャーニーを、対話型の `kiro-cli chat` のターミナルで、ツリーごとに 1 回）を実行します。

```bash
bun scripts/package.ts
AIDLC_KIRO_TUI_LIVE=1 AIDLC_TUI_LIVE=1 bun tests/run-tests.ts --e2e --production-guards \
  --require-coverage --filter t-tui-kiro-release-journey
```

`--require-coverage` は、どちらかのツリーのジャーニーがスキップされたときに実行を失敗させます。一方のツリーにはその SHA についての結果がすでにあり、もう一方が欠けているか失敗している場合は、コマンドの前に `AIDLC_KIRO_RELEASE_TREE=kiro` または `AIDLC_KIRO_RELEASE_TREE=kiro-ide` を置きます。そのツリーのジャーニーだけが実行され、`--require-coverage` はそのツリーだけを覆います。Linux では Kiro にスクラッチのホームを与えつつマシンのサインインを保つため、`~/.kiro` には触れません。各ジャーニーは約 5 分かかり、クレジットは Kiro CLI が使うモデルに従います（Kiro CLI 2.32.0 の `claude-opus-5.5` でそれぞれ約 33）。ツリーごとに 1 行を出力します。例えば `Kiro CLI 2.32.0 (kiro-ide) release journey on <commit>: PASS (5.1 min of
turns, 33.23 credits, 3 permission prompts)` で、両方の行は完全なソース SHA を含めて、昇格の前に選んだ preview の GitHub のリリースノートに記録されます。そのソースについての既存の結果は再利用され、昇格のワークフローが新しいメタデータのコミット上でジャーニーを再実行することはありません。ワークフローの中にこれらの手動の結果を読むものはありません。メンテナーが [preview を本番に昇格する](../../DEVELOPERS.md#4-promote-a-preview-to-production) の手順 2 でそれらを確認します。修正は、昇格のために選ばれる前に別の preview で出荷されます。

ライブのジョブは既存の `ai-pr-review` 環境とロールを使います。Full Suite を実行する前に、次の前提条件を確認してください。

- 環境 `ai-pr-review` がシークレット `AWS_AI_PR_REVIEW_ROLE_ARN` を提供する。
  `live_linux`、`live_macos`、`live_windows` はその環境を選び、シークレットはそれらのジョブの中で解決される。`full-suite.yml` を呼び出すワークフローは `secrets: inherit` を渡さなければならない。これがないと、呼び出された実行ではシークレットが空として解決され、すべてのライブのジョブが "Assume nightly Bedrock role" で失敗していた。各ライブのジョブは、今では最初にシークレットを確認し、`secrets: inherit` を示すメッセージとともにすぐに失敗する。
  Kiro/Cursor の API キーのワークフローのシークレットや、ホスト型のベンダーキーのレッグはサポートされない。
  AWS のロールの OIDC の信頼は、このリポジトリの `environment:ai-pr-review` のサブジェクトにスコープされていなければならない。各 assume は 3,600 秒を要求し、既存の 1 時間のロールの有効期間の範囲内に収まる。ワークフローは、IAM のセッションの有効期間を変えずに、作業を制限されたファイルのジョブに分割する。
- ロールには、`scripts/ci-credential-broker.ts` の CI 専用のモデルの表に対する Bedrock の invoke/stream のアクセスが必要。`us-east-1` の Claude Fable 5、Opus 4.8、Sonnet 4.6、Haiku 4.5 の推論プロファイル、同じリージョンでの opencode の既定の Sonnet 4.6、そして `us-east-2` の Bedrock Mantle を通じた Codex の `openai.gpt-5.5` で、これは Copilot CLI の独自モデルのモードも使う。
  この表はブローカーの許可リストと Claude のクライアントの別名を固定する。出荷されるユーザー設定はプロバイダーに中立なままである。

環境へのアクセス、ロールの信頼、モデルの権限、必須のライブの実行基盤が欠けている場合は、準備の確認で失敗します。ワークフローは新しい環境やロールを作成しません。

Claude Code、Copilot CLI、opencode の npm のバージョンはワークフローで固定されています。レジストリと互換性を確認した後に、意図的にそれらの固定を更新してください。CLI／認証の preflight は、存在しない実行基盤が合格したライブテストに見せかけるのを許さず、はっきりと失敗します。

#### 認証情報の隔離とアップロードされる証拠

ライブのモデルはリポジトリの内容を受け取り、ツールを呼び出せるため、そのシェルとツールの結果のトレースは、認証情報にとって信頼できない流出先として扱ってください。AWS のアクションは、AWS の認証情報を後続のステップにエクスポートせずに、マスクされたステップの出力を返します。信頼できる起動用のヘルパーは、それらの値を自身のステップの環境でだけ受け取り、切り離されて環境を消したブローカーのプロセスに stdin で JSON を送り、ライブのエージェントが実行される前に終了します。ブローカーは認証情報をメモリーにだけ保持し、起動時に署名付きの STS の `GetCallerIdentity` を実行します。ブローカーの外に出るのは、秘密でないアカウント、ARN、ループバックのポートだけです。認証情報を返す経路、credential process、認証情報のファイル、認証情報を持つエージェントの環境はありません。

ループバックのプロキシが受け付けるのは、設定されたモデルの ID と `POST /model/<id>/(invoke|invoke-with-response-stream|converse|converse-stream)`（任意で `/bedrock` の下）、そして `model: openai.gpt-5.5` を伴う Codex の Mantle の `POST /openai/v1/responses` だけです。クライアントの認証ヘッダーを取り除き、上流への各リクエストに署名します。成功したストリームはバイト単位でそのまま転送されます。他の経路は禁止され、リダイレクトはたどらず、AWS のエラーは署名を反映し得るため、上流のエラーの本文は抑止されます。
Mantle の経路では、署名の前にリクエストから `reasoning.summary` を取り除きます。Mantle の `openai.gpt-5.5` は、推論の要約を求めるレスポンスを、モデルが推論を始めると停滞させ、Copilot CLI はすべてのリクエストでそれを求めるためです。Codex のもののように要約を求めないリクエストは、送られたとおりに転送されます。ブローカーはリクエストごとに 1 行を `tests/logs/credential-broker.log` に追記します（メソッド、パス、受け付けたモデル、ステータス、所要時間、最後のバイトの時刻、バイト数、回答が終わったかどうか）。ヘッダーや本文は決して記録しないので、停滞したストリームはアップロードされたログに現れます。
上流がヘッダーの後 2 分間データを送らないレスポンスは終了されます（その行の `end=idle-timeout`）。SSE の `:` のキープアライブのコメントはデータではありません。Mantle は停滞中も含めて 15 秒ごとにそれを送ります。

Claude は文書化された `ANTHROPIC_BEDROCK_BASE_URL` と `CLAUDE_CODE_SKIP_BEDROCK_AUTH=1` を使います。その t19 の preflight は、ブローカーの起動時の識別子を確認し、続いて実際の SDK のターンを行います。Codex 0.151.0 は、ループバックのエンドポイントに対して検証された、`/openai/v1` で終わるプロバイダーの `base_url` を使います。サービス固有の Bedrock Runtime の上書きだけでは、Codex の Mantle の通信はリダイレクト**されません**。
compose、workspace、memory のジャーニーを含め、すべての一時的な Codex のホームが共有の Bedrock の設定レンダラーを使います。隔離された CI のランタイムの外では、`AIDLC_CODEX_AWS_PROFILE` を未設定または空のままにすると `config.toml` からプロファイルが省かれ、EC2 のインスタンスロールを含め、AWS SDK の既定の認証情報チェーンが認証情報を解決できるようになります。既存の名前付きプロファイルを使い続けるには、`AIDLC_CODEX_AWS_PROFILE=codex`（または実際の名前）を設定してください。`codex` という名前のプロファイルが暗黙に選ばれることはもうありません。`AIDLC_CODEX_AWS_REGION` の既定は引き続き `us-east-2` です。
隔離された CI のランタイムは、Linux、macOS、Windows でダミーの `broker` のキーを選ぶために、明示的に `AIDLC_CODEX_AWS_PROFILE=codex` を設定します。opencode のプロファイルもダミーのキーだけを含みます。opencode は、前提条件の検査がそのプロファイルを認識するように `AWS_PROFILE=broker` を選び、文書化されたプロバイダーの `endpoint` の上書きが AI SDK のリクエストをプロキシ経由にします。
Codex のシェルの方針は、プロバイダー／ブローカー／API／GitHub／Actions の変数を除外し、ランナーはライブテストを起動する前に CI のコントロールプレーンの認証情報を取り除きます。

ホスト型の Linux/macOS のライブのエージェントは、非公開のチェックアウトのコピーの中で、明示的な `sudo ... env -i` の環境と root 所有の読み取り／実行可能なツールを使い、別の特権のない `aidlc-live` ユーザーとして実行されます。起動プロセスの procfs の環境、ランナーのホーム、元のチェックアウト、Actions のコマンドファイルは読めません。

Linux の Codex の準備は、ディストリビューションの `bubblewrap` をインストールし、その AppArmor のアタッチメントを保つため、`/usr/bin/bwrap` への root 所有のシンボリックリンクをライブの PATH に公開します。
Ubuntu が特権のないユーザー名前空間を制限している場合、準備は既存の `/etc/apparmor.d/bwrap-userns-restrict` のプロファイルを読み込むか、`apparmor-utils` とともに `apparmor-profiles` からディストリビューションの追加プロファイルをインストールします。グローバルな制限は変えてはいけません。これは公式の [Codex のサンドボックスの前提条件](https://learn.chatgpt.com/docs/sandboxing#prerequisites)に従うもので、Codex は `workspace-write` を保ちます。
AWS のセットアップの前に、環境を消したライブのユーザーは、bubblewrap のユーザー名前空間を作成し、Bun を実行し、その非公開の一時ディレクトリに書き込めなければなりません。その名前空間の中で root であっても、ランナーのホーム、元のチェックアウト、Actions の環境ファイル、起動プロセスの環境、一時的なランナー所有／root 所有の目印のファイルを読めてはいけません。
この証明はブローカーの起動後に繰り返され、失敗するとライブの実行を妨げます。

Windows は、`C:\aidlc-live` の下に、標準の Users だけのアカウントと、ACL で隔離された work/home/tools を作成します。タスクスケジューラーは、その識別子の下で Limited のバッチログオンで各本体を起動し、ランナーのセッションのデスクトップの ACL を避けます。準備は、既存のプリンシパルを保ちつつ `SeBatchLogonRight` だけを付与し、その後、実際のバッチログオンのタスクを検証します。Git やスモークのプローブを含む準備のタスクの既定は 30 分です。認証情報を持つテストのタスクは、ワークフローの 70 分のライブのテストステップの中で 64 分の上限を保ちます。
ネイティブの起動の 5 分の最終防御の間に始まらなかったタスクは、スケジューラーの状態と最後の 20 件の運用イベントとともに失敗します。明示的な安全な環境と、UTF-8 の識別子／cwd／出力のログは残り、タスクは完了後に登録解除されます。
セカンダリログオンの `Start-Process` は、タスクの登録自体が失敗した場合にだけの、報告されるフォールバックです。バッチのセッションはセッション 0 を使うことがあります。証明には、正しいユーザーの識別子と、起動側のモジュール／`PROCESS_VM_READ`、ランナーのディレクトリ、非公開の認証情報の状態へのアクセス拒否が必要です。
ブローカーはランナーの識別子の下に留まり、ライブのユーザーの環境に渡るのは秘密でない経路とモデルの固定だけです。隔離の証明に失敗すると実行を妨げます。

Windows の Codex は、2 つのネイティブのサンドボックスの識別子もプロビジョニングし、新しいテストのホームを使って両方を検証します。非ゼロで終了したプロビジョニングの実行は、同じ新しいホスト上でもう一度だけ実行され、そのログは最初の実行のログの横に保持されます。タイムアウトや、出力の吸い出しが終わらない場合は、引き続きすぐにフェイルクローズします。準備の確認のコマンドは、実際のサンドボックスの下で PowerShell と Bun を通じて実行されます。シェルはプロジェクトで始まらなければならず、Bun はそのパスを正準化しなければならず、ワークスペースの外での認証情報の読み書きは拒否されたままでなければなりません。サンドボックスの識別子は、フィクスチャの上にある 3 つの非公開のコンテナーについてディレクトリのメタデータと走査のアクセスを受け取り、その内容を一覧したりファイルを読んだりする継承された権限は持ちません。
準備の確認は、stderr の固定のフェーズの診断とは独立に、ネイティブの初期化処理の終了ステータスを確認します。ステータスが欠けているか非ゼロであれば実行を妨げます。
ネイティブのランチャーは、ホスト型の Windows のコールドスタートのばらつきに対応するため、新しいホームの初期化に 5 分を与え、その期限が切れると実行を拒否します。
各ネイティブの CLI のプロセスは、再開される前にそれぞれの Windows のジョブに割り当てられます。CLI の終了後、ランチャーは stdout と stderr を排出する前にそのジョブの子孫を退役させるため、継承されたパイプのハンドルが呼び出しを開いたままにすることはありません。
POSIX の収集は、管理者によるコピーの前に専用のアカウントのプロセスを止めます。macOS では、サービスの再起動を止めるために、まずそのアカウントの launchd の user/GUI のドメインを退役させます。ゾンビのエントリは実行できません。それ以外のプロセスが残っている場合や一覧の取得に失敗した場合は、収集を拒否します。失敗には残っている PID／状態の行が含まれます。影響を受けるのは、このジョブで新たに作成されたアカウントだけです。

すべてのマージキューの実行は、プロバイダーの認証情報なしに、同じ準備と証明のスクリプトに加えてサンドボックスの識別子の下での `--smoke --filter '^t01'` を使い、3 つの OS すべてで `test_live_isolation` を実行します。認証情報を使わない Windows のリリース契約のユニットは、引き続き別に実行できます。ホスト型の Windows のライブのモデルのカバレッジは本物で、オプトインのスタブや同じユーザーでの例外ではありません。

エージェントは、ジョブのタイムアウトまで、許可リストのプロキシを通じて引き続き費用を使えます。IAM のモデルの権限、クォータ、ランナーのアクセスを制限してください。この境界はホストのカーネルと管理者を信頼します。OS の権限昇格は対象外です。
Cursor は、その CLI がエージェントのツールのシェルに API キーを露出するため、引き続き除外されます。
Kiro は、ワークフローが注入する API キーなしに、専用の CI の識別子の Windows ホストの既存のサインインだけを使います。ランナー所有の収集は、アップロードの前に無害化のために完了したログをコピーし戻します。サンドボックスが作成したコードは実行しません。

Windows のサンドボックスのプロセスが止まった後、テストのログと起動のログは独立に収集されます。テストツリーのコピーに失敗しても、検証済みの起動の stdout/stderr は `tests/logs/windows-launch-<uuid>/` の下に保持されます。公開されるのは完全で検証済みのツリーだけで、どちらかのコピーが失敗すると収集は失敗のままです。`tests/logs/windows-collection-<uuid>.json` はソースごとの完了と、失敗時には操作、安全な相対パス、例外のコードを記録します。例外のメッセージ、絶対パス、機密のパスの構成要素は省きます。アップロードされた収集のレポートやフォールバックのログは、テストが合格したことを確立するものではありません。

Windows のライブのレッグは、進行しなくなったフックについての証拠も保持します。
`scripts/ci-live-sandbox.ts` はすべての Windows のライブの系統について `AIDLC_TEST_HOOK_TRACE=1` を設定し、ランナーは `AIDLC_HOOK_TRACE_DIR` を各ファイルの試行の `e2e-artifacts/<file>/attempt-<n>/hook-trace/` に束縛します。そのため、その試行のすべてのフックのプロセスがそこにフェーズを書きます（[フックのフェーズトレース](06-hooks-and-tools.md#フックのフェーズトレース)を参照）。ライブの実行のスケジュールされたタスクが実行されている間、`.github/scripts/prepare-live-runtime.ps1` のランナー側の待機ループは 1 分に 1 回プロセスの一覧を確認します。隔離されたアカウントが所有し、コマンドラインに `engine hook ` または `engine adapter ` を含むプロセスが 10 分間実行されていると、停止したプロセスのツリー（その隔離されたアカウントの親とすべての子）とそのスレッドの状態を含む `hook-stall-<time>.json` を 1 つ、`tests/logs/windows-launch-<uuid>/hook-stalls-run-<id>/` に、プロセスごとに 1 回書きます。読むのはプロセスのメタデータだけで、所有権を確認するのは停止したプロセスとその親だけです。すべての照会は、60 秒のスナップショット予算の残り（最大 15 秒）で制限されます。スキップされた、失敗した、タイムアウトした照会は、スナップショットを `truncated` と記します。所有者を確認できなかった停止したプロセスは、別のアカウントに属する可能性があるため、その id、名前、開始時刻だけ（コマンドラインや子なし）で `ownerUnknown` の下に列挙されます。これが実行を失敗させることは決してありません。フックのトレースの `.ndjson` のファイルは、後述のトレースの保持の規則に従います。
Linux と macOS のレッグはどちらも有効にしません。

フルスイートのすべての `tests/logs/` のアップロードは、まず `scripts/ci-sanitize-logs.ts` を実行し、無害化に失敗するとブロックされます。フルスイートと共有の決定論的なジョブは、ツールの呼び出し、完了の境界、タイムアウトの振る舞いを診断に使えるよう、対象となるドライバーの NDJSON、`sdk-drive*`、`tui-drive*`、`e2e-artifacts/**/traces`、`leg-evidence/` を既定で保持します。リポジトリ変数 `AIDLC_NIGHTLY_UPLOAD_TRACES=0` でトレースの保持をオプトアウトできます。単体の無害化処理は、その `AIDLC_NIGHTLY_UPLOAD_TRACES` の環境変数が `1` でない限り、引き続きこれらのトレースを削除します。不正な UTF-8、UTF-16、NUL を含むファイル、その他のテキストでないファイルは常に削除され、その相対パスと理由が `sanitizer-report.json` に記録されます。バイナリ／スクリーンショットの許可リストはありません。残った UTF-8 のテキストは、AWS の認証情報、ベンダーのキー、bearer トークン、Anthropic のキーについて墨消しされます。リンクはターゲットをたどらずに削除されます。墨消しは多層防御であり、エンコードされた秘密に対する証明ではありません。生のテキストのトレースを保持すると、その残存リスクが高まります。

### すべてのライブの系統を読む: トレースの監査

合格した系統にも、利用者が出会う摩擦が現れていることがあり、毎晩の実行はそのトレースを保持します。`scripts/trace-audit.ts` は、メンテナーのために、メンテナー自身のマシン上で、分けて保たれた 2 つの層でそれらを読みます。

- `bun scripts/trace-audit.ts extract --run <full-suite run id>` は、メンテナー自身の `gh` で、その実行の `full-suite-live-*` の成果物をダウンロードします（または `--dir <folder>` で、ダウンロード済みの実行、`tests/logs` のフォルダー、ローカルのセッションのフォルダー、つまり使い捨てのプロジェクト、Claude Code の設定フォルダー、Codex のホームを読みます）。記録されたイベントとフィールドを数えて照合するだけで、読むフォルダーの外に、`table.txt` と `table.json`（検査の所見、ガードの拒否、エンジンのエラー、利用者に再び渡された質問、承認後に書かれたステージのファイル、10 分以上の沈黙、再試行、エージェントのツールのエラーごとに 1 行。それぞれ、その実行、ハーネス、OS、テスト、ステージ、証拠のファイルと行を示す）と、系統ごとに 1 つの `legs/<leg>/story.md` を書きます。後者は、利用者が入力し選んだもの、尋ねられたもの、エージェントが実行し言ったものを時間順に、サイズの予算に合わせて切り詰めて示し、利用者のために記録された各判断を、その人の返答を隣に置いて示すので、読み手は各返答をその記録と突き合わせて判断できます。
- `bun scripts/trace-audit.ts judge <out>`（`scripts/trace-audit-judge.ts`。指示は `scripts/trace-audit-judge.md`）は、各テストの系統を、メンテナー自身の `claude` に print モードで渡します。読むこと（`Read`、`Grep`、`Glob`）だけができ、判定する系統自身のフォルダーの中だけで、セッションのフォルダーが置かれたホームは決して読めません。既知の一覧（`--known`）と、未解決の issue とプルリクエスト（`--issues`）も渡します。モデルは摩擦の項目を JSON で返します。ツールは各項目がいくつの系統で出会われたかを数え、`JUDGE.md` を書きます。`--dry-run` は各グループの入力を書き、モデルを呼びません。`--max-usd` と `--budget-kb` が各呼び出しを制限します。

抽出器は実行が保持したものだけを読みます。SDK の駆動のトレースは各ツールの返答の最初の 240 文字を保持し、各系統の `leg-evidence/` フォルダーは、それが駆動したすべてのプロジェクトの監査と、エージェントが利用者に伝えたことを保持し、ストーリーはそれらを系統の他のイベントの間に時間で配置します。系統がどちらも保持しなかった場合、ストーリーはその冒頭でそう伝えます。

## Kiro のプロンプトフックのトランスポート制御

Kiro の agent-v1 のプロンプトフックは、シェルツールの出力予算とは独立に、既定の `max_output_size` が 10 KiB です。アダプターは、ステアリング以外のディレクティブを注入する前に、説明文を含む UTF-8 の事前ディスパッチのパケット全体を数えます。大きすぎるパケットとすべての `load-steering` ディレクティブは、既存の正確な引数の転送ラッチを使うため、エンジンの完全な JSON は実際のツール呼び出しを通じて返されます。`--single` はフックの事前ディスパッチを完全に飛ばし、その最初の発行をそのツール呼び出しに任せます。事前ディスパッチされるのは、エンジンが正確に読む行だけです（`readNextLine`）。エンジンがエージェントに渡すはずのものは、手を加えずにエージェントへ渡されるため、この継ぎ目が、誰かが読む前に人の言葉に基づいて動くことは決してありません。

`t147-kiro-hook-adapter.test.ts` は、マルチバイトの内容、ネイティブのシェルの別名、保持された端末のガード、実際のマルチパートのエンジンの往復で、10 KiB の境界を確認します。届けられたすべてのルールのバイト列を再構築し、不透明な継続トークンをそれぞれ変更せずに渡します。トークンだけが残っていても、ルールが完全に届いたことの証明にはなりません。切り詰められたルールの前にそれを移すことは有効な修復ではありません。

これらの決定論的な制御は、アダプターとエンジンの stdout をテストします。ネイティブの Kiro のリリースのツールチャネルの上限を調整するものではありません。そのトランスポートの予算を変える前に、対応する各ネイティブのプラットフォームで、上限に近い完全なペイロードを検証してください。フックの設定された `max_output_size` を引き上げる場合にもその調整が必要です。それはこのアダプターの保守的な注入の方針を変えません。

## ユニットテストのシャード分割

`--unit --shard N/M` は、検出したすべてのユニットファイルを、所要時間の均衡が取れた `M` 個のシャードのちょうど 1 つに割り当てます。割り当ては決定論的で、各ファイルの OS ごとの所要時間を記録した `tests/unit-shard-weights.json` を使います。現在のプラットフォームでの測定値が優先し、そこで測定されていないファイルは最も遅い OS の代替値を使います。一覧にないファイルには 1 秒の既定の重みが与えられるため、新しいテストはコマンドを変えずに最も負荷の軽いシャードに入ります。`M` が割り当て可能なグループの数を超えると、ランナーは終了コード 2 で終わるため、有効なシャードのコマンドが 0 ファイルを実行して成功を報告することはありません。

シャードはファイルを 1 つずつ実行します。ただし、重みのファイルが `parallel` の下で上限を設けるプラットフォーム（macOS。そのマージキューのユニットシャードがキューの進む速さを決める）は例外です。そこでは、シャードは一度にその数までのファイルを始め、`-P` を超えることはありません。それ以上は役に立ちません。最も重い単一のファイルが下限を決めるためです。
並べて実行する場合、アフィニティのグループが最初に単独で、その順序で実行されます。t238 は t249 が読むバイナリをビルドし、そのリリースのパッケージング（`scripts/package-release.ts`）は共有の `dist/` と `dist-release/` をその場で再生成するため、その瞬間にそれらを読むファイルは、それらが欠けているのを見ることになります。他のファイルは、そのプラットフォームの重みで長いものから順に、それぞれ独自のプロセスと独自の一時フォルダーで始まります。
`AIDLC_TEST_UNIT_PARALLEL=<n>` は、どのプラットフォームでも 1 回の実行の上限を設定し、macOS 以外での試行に使います。CI では何もそれを設定しません。`--shard` のない実行は直列のままです。

別々のシャードは、別々のチェックアウトまたは CI のジョブで実行してください。`AIDLC_TEST_PACKAGE_READY=1` のないランナーは、最初のファイルの前に `dist/` を再生成し、同じツリーでの他の実行の読み手の下でそれを行います。

アフィニティの一覧は、ファイルをまたぐ前提条件を明示的に保ちます。現在、ネイティブバイナリのビルダーのテストは、同じシャード内で Copilot のコンパイル済みアダプターのカバレッジより前に実行されます。ネイティブのビルド／インストールのアサーションがすべて合格した後、t238 は検証済みの実行ファイルと隣接する `runtime/` を、ランナー所有の `AIDLC_TEST_COMPILED_DIR` にコピーします。その非公開のビルド／インストールのフィクスチャは引き続きテスト後に削除され、公開されたコピーはランナーのクリーンアップまで存続します（または verbose のログとともに保持されます）。各ランナーは新しい引き継ぎのディレクトリを割り当てるため、共有の `build/binaries` の出力が上書きされたり、以前の実行から借用されたりすることはありません。
シャードでのユニットの実行では、t249 がこの引き継ぎを解決することが必要です。成果物が欠けている場合は、明示的な実行ファイルや古いリポジトリのビルドが存在しても、コンパイル済みのケースを黙ってスキップせずに失敗します。シャードを使わない直接の t249 の実行は、引き続き `AIDLC_TEST_COMPILED_EXECUTABLE` やローカルのネイティブビルドの結果をオプトインで使えます。
スモークのランナーの契約は、10 と 16 のシャードの割り当てがどちらも空でなく、互いに重複せず、ユニットの一覧全体を網羅し、生成側／利用側の順序を保ち、生成側が絞り込みで除外された場合はコンパイル済みのカバレッジを失敗させることを検証します。

複数のワーカーがある場合、integration の層は `tests/integration-weights.json`（サマリーの行の名前をキーにする）に基づいて並列のファイルを長いものから順に開始するため、長いファイルが最後に始まって層の実時間を決めることはありません。重みのないファイルと同点のものは名前順を保ちます。読み取れる重みのファイルがない場合、ファイルは名前順に始まります。直列のファイルとスモークの層は影響を受けません。複数のワーカーを持つユニットシャードは、上記のとおり、ユニットの重みでファイルを並べます。

`--integration --shard N/M` は、同じ integration の重みを使って、絞り込んだ integration の一覧を均衡させます。絞り込みは分割の前に行われ、除外はその後に適用されるため、ファイルを除外しても他のファイルがシャード間で移動することはありません。2 つのガードのジョブは、同じフィルターでこのモードを使います。ホスト型のジョブの数とワーカーの上限は変わりません。

重みはファイルの均衡と順序を決めるだけで、ファイルを選んだり、スキップしたり、失敗させたりすることはありません。
`scripts/ci-test-weights.ts refresh <dir>` は、`gh run download <run-id> -p 'ci-deterministic-*' -D <dir>` でダウンロードした決定論的な CI の証拠から、両方の重みのファイルを書き直します（緑のマージグループの実行を複数使ってください。各ファイルは OS ごとの中央値を取り、最も遅い中央値はその代替値も更新します）。refresh に含まれないプラットフォームの測定値は保持されます。最初のプラットフォームの重みは、成功したマージグループの実行 `39029896320` から収集しました。スケジューリングの改善は、その学習用の測定だけでなく、その後の実行に対して確認しなければなりません。
各ユニットと integration のジョブの後、助言用の "Report outdated test weights" ステップが `scripts/ci-test-weights.ts report` を実行します。1 分を超えて実行され、かつ重みの 1.5 倍を超えたファイルには、警告の注釈と、refresh のコマンドを示すジョブのサマリーの行が付きます。このステップは常に成功するため、古い重みは CI を遅くしますが、ジョブを失敗させたりマージキューから PR を外したりすることは決してありません。`t-ci-test-weights.test.ts` は、refresh、レポート、チェックインされた重みのファイルをカバーします。
