# アイデア創出フェーズ — ステージリファレンス（1.1〜1.7）

## フェーズの概要

アイデア創出フェーズは、AI-DLC ライフサイクルを構成する 5 つのフェーズのうち 2 番目です。技術作業を開始する前に、意図を捉え、実現可能性を検証し、スコープを定義し、承認を得ることで、取り組み全体の基盤を築きます。エンタープライズと機能追加では、このフェーズはステージ 1.1 から 1.7 を実行し、インセプションフェーズへの移行を制御する実行／中止ゲートで完了します。

7 つすべてのステージ本体はインラインで実行され（ステージの作業は会話の中で行われ、サブエージェントはありません）、承認ゲート、質問形式、完了メッセージについて標準の `stage-protocol.md` に従います。意図の収集とラフモックアップはレビュアーとしてプロダクトリードも指名しており、レビューが `none` に設定されていない限り、プロダクトリードは別のサブエージェントとしてゲート前に助言的なパスを 1 回実行します。オーケストレーターは、プランが実行するステージを順番に処理します。

**アイデア創出フェーズの主な特性:**

- すべてのステージはインライン実行モード（ユーザーとの直接対話）を使用します。
- 各ステージは、意図のレコードディレクトリにある `<record>/ideation/<stage-name>/` 配下に成果物を生成します。ここで `<record>` は `aidlc/spaces/<space>/intents/<YYMMDD>-<label>/` です（`audit/` のシャードディレクトリ、ステージごとの `memory.md`、検証レポートも同じレコードディレクトリに置かれます）。
- ステージ 1.1 以外のすべてのステージは、先行ステージの出力に依存します。
- ステージ 1.7 は、それを実行するスコープ（エンタープライズと機能追加）で、インセプションへ引き継ぐ前にフェーズ境界検証チェックを実行します。
- 意図の収集、スコープ定義、承認と引き継ぎは ALWAYS ステージで、他の 4 つは CONDITIONAL です。ALWAYS が成り立つのは、そのステージを含むスコープの中だけです。最小実用製品は承認と引き継ぎを実行せず、概念実証は意図の収集だけを実行します。

**スコープに応じたステージの採用:**

スコープのコンパイル済みプランは、そのステージを順番に並べます。最小実用製品では、アイデア創出はラフモックアップで終わり、その承認、または該当しないときに記録されるスキップが、インセプションへ引き継ぎます（出力は省略しています）:

```text
$ aidlc engine graph scope mvp

workspace-detection
state-init
intent-capture
feasibility
scope-definition
rough-mockups
reverse-engineering
practices-discovery
requirements-analysis
...
```

|----------|------------------|

## ステージ 1.1: 意図の収集とフレーミング

### メタデータ

| 項目 | 値 |
|------|----|
| フェーズ | アイデア創出 |
| ステージ番号 | 1.1 |
| 条件 | ALWAYS — アイデア創出を実行するすべてのスコープ（エンタープライズ、機能追加、最小実用製品、概念実証）の最初のステージ。 |
| 主担当エージェント | AIDLC プロダクトエージェント |
| 支援エージェント | AIDLC アーキテクトエージェント（技術的コンテキスト） |
| レビュアー | AIDLC プロダクトリードエージェント（ソース接地とプロダクト品質のレビュー） |
| モード | インライン |
| 完了絵文字 | 💡 |

### 目的

意図の収集は、アイデア創出を実行するすべてのスコープの最初のステージです。ビジネス上の課題を収集し、ステークホルダーを特定し、成功指標を設定します。プロジェクト種別（グリーンフィールドまたはブラウンフィールド）は、ワークスペース検出ですでに設定されています。生成される意図ステートメントとステークホルダーマップは、以降のすべてのステージがその上に構築される基盤となります。

本人による作業の説明そのものがシードです。このステージは `project-description` ユーティリティでそれを読むため、依頼を改めて尋ねることはありません。

### 入力

- `project-description` ユーティリティから得られる正式なプロジェクト説明（`$ARGUMENTS` や監査の `Request` から組み立て直すことはありません）、および本人が指名した文書（`document-input` で読み取ります）
- 以前のセッションにおける既存の `<record>/` 成果物（存在する場合）
- `aidlc/spaces/<active-space>/memory/` にあるガードレール

### 手順

1. **既存コンテキストを読み込む** — `project-description` からプロジェクト説明を読みます（指名された文書は `document-input` で読みます）。既存の成果物を確認し、ガードレールを読み込みます。
2. **明確化の質問を生成する** — 初期の説明、ワークフローで選択されたスコープ、使用したアクティブメモリのルールを載せる `## Sources` レジスターを持つ `<record>/ideation/intent-capture/intent-capture-questions.md` を作成します。ビジネス課題、顧客、成功指標、取り組みの契機、ステークホルダー、意思決定権限、コミュニケーションニーズ、そしてこの最初のバージョンで扱わないもの（ワークフローで選択されたスコープは選択済みとして明示し、改めて質問しません）を質問します。A〜E の選択肢（Claude Code では A〜D）に加え X（その他）を持つ `[Answer]:` タグ形式を使用します。3 モードの質問フローを提供します。
3. **回答を収集して分析する** — すべてのタグが入力されたことを確認します。曖昧さ・矛盾の分析を実行します。
4. **接地された成果物を生成する** — 意図ステートメントとステークホルダーマップを作成します。実質的な内容を持つすべての段落・リスト項目・表のデータ行には、インラインの `[desc]`、`[scope]`、`[Q<n>]`、`[memory:<id>]`、`[assumption]` のいずれかのタグを付けます。両ファイルに `## Assumptions & Open Questions` を含めます。
5. **仮定を解決する** — いずれかの成果物に仮定が残っている場合、ユーザーにその受け入れか、追加質問への変換を求めます。受け入れても仮定ラベルは維持され、主張が事実に昇格することはありません。
6. **完了を準備する** — プロダクトリードレビューを実行し、両方の成果物を検証して、ゲートの結果を `aidlc-orchestrate.ts` を通じて報告します。
7. **完了を提示して承認を求める** — 標準の 2 選択肢ゲートを提示します。

### 出力

| ファイル | 内容 |
|----------|------|
| `intent-statement.md` | ソースタグ付きの問題ステートメント、対象顧客、成功指標、取り組みの契機、およびワークフロー選択とユーザー確認を区別した初期スコープシグナル。仮定セクションは必須 |
| `stakeholder-map.md` | ソースタグ付きのステークホルダーと関心事項、意思決定者と影響者の区別、コミュニケーション要件。仮定セクションは必須 |
| `intent-capture-questions.md` | 許可ソースのレジスター、`[Answer]:` タグを持つ明確化の質問、必要な場合は仮定の確認 |

### 注記

- アイデア創出を実行するすべてのスコープの最初のステージです。本人の入力以外の先行成果物はありません。
- `project-description` で読み取った本人の説明がシードコンテキストとなります。
- 選択されなかった選択肢は、除外事項でも要件でもありません。裏付けのない内容は、省略するか、フォローアップで聞き出すか、明示的な仮定としてのみ保持します。
- 意図ステートメントは、後続するすべてのアイデア創出ステージに入力され、インセプションへも引き継がれます。

## ステージ 1.7: 取り組みの承認と引き継ぎ

### メタデータ

| 項目 | 値 |
|------|----|
| フェーズ | アイデア創出 |
| ステージ番号 | 1.7 |
| 条件 | ALWAYS — インセプション前の最終アイデア創出ゲート（エンタープライズ、機能追加）。 |
| 主担当エージェント | AIDLC デリバリーエージェント |
| 支援エージェント | AIDLC プロダクトエージェント（完全性を検証） |
| モード | インライン |
| 完了絵文字 | ✅ |

### 目的

すべてのアイデア創出成果物を単一の取り組み概要にまとめ、すべての決定を記録し、フェーズ境界検証を実行して、実行／中止ゲートを提示します。

### 入力

ステージ 1.1〜1.6 からのすべてのアイデア創出フェーズ成果物。

### 手順

1. AIDLC デリバリーエージェントのペルソナとナレッジを読み込みます。
2. すべてのアイデア創出フェーズ成果物を読み取ります。
3. 承認質問を生成します。
4. 取り組み概要（すべての出力を統合した 1 ページ資料）を作成します。
5. フェーズ境界検証を行います（意図 -> スコープ -> 意図バックログの整合性）。
6. 引き継ぎ成果物とフェーズ境界の成果物を検証します。ライフサイクル状態を直接編集してはいけません。
7. 3 選択肢の承認ゲートを提示します。承認されたら結果を報告し、エンジンがステージ完了とインセプションへの移行を不可分に実行します。

### 出力

| ファイル | 内容 |
|----------|------|
| `initiative-brief.md` | すべてのアイデア創出出力を統合した 1 ページの要約 |
| `decision-log.md` | アイデア創出中に行われたすべての決定の記録 |
| `approval-handoff-questions.md` | `[Answer]:` タグを持つ承認質問 |

フェーズ境界検証:

| ファイル | 内容 |
|----------|------|
| `<record>/verification/phase-check-ideation.md` | アイデア創出からインセプションへのトレーサビリティチェック |

### 承認ゲート

特別な 3 選択肢ゲート:

- **承認** — インセプションフェーズへ進みます。
- **変更を要求** — 修正フィードバックを提供します。
- **取り組みを却下** — ワークフロー全体を終了します。

### 注記

- フェーズ境界ステージです。ステージプロトコルのガバナンスに従って検証を実行します。
- 取り組み概要は、アイデア創出フェーズ全体のエグゼクティブサマリーとして機能します。

---

## フェーズの要約

### 主な出力

1. **意図ステートメント**（1.1）— 問題ステートメント、対象顧客、成功指標、取り組みの契機、初期スコープシグナル。
2. **ステークホルダーマップ**（1.1）— 主なステークホルダー、意思決定者、コミュニケーション要件。
3. **競合分析**（1.2）— 市場での位置付け、内製と購入の比較（該当する場合）。
4. **実現可能性評価と RAID ログ**（1.3）— 技術的実現可能性、リスク登録簿、制約（該当する場合）。
5. **スコープ文書と意図バックログ**（1.4）— 正式なスコープ境界、優先順位を付けた作業単位の原型リスト。
6. **チーム計画**（1.5）— スキルマトリクス、モブ構成、キャパシティ配分（該当する場合）。
7. **コンセプトモックアップ**（1.6）— ワイヤーフレーム／ユーザーフロー、またはシステムコンテキスト図（該当する場合）。
8. **取り組み概要**（1.7）— すべてのアイデア創出出力を統合したエグゼクティブ向け 1 ページ資料。
9. **フェーズ境界検証**（1.7）— トレーサビリティチェックの結果。

### インセプションへの引き継ぎ

プランが実行する最後のアイデア創出ステージ（エンタープライズと機能追加では 1.7、最小実用製品では承認されたかスキップとして記録されたかにかかわらず 1.6、概念実証では 1.1）が承認されると、フレームワークはインセプションフェーズに移行します。ブラウンフィールドの作業では、インセプションはステージ 2.1 のリバースエンジニアリングから始まります。グリーンフィールドの作業では、エンタープライズ、機能追加、最小実用製品ではステージ 2.2 のプラクティス発見から、概念実証ではステージ 2.3 の要件分析から始まります。概念実証はプラクティス発見を実行しません。
