# 構築フェーズ -- ステージリファレンス（3.1～3.7）

## フェーズの概要

構築フェーズでは、インセプションで作成した設計成果物を、動作しテスト済みの
ソフトウェアへと変換します。機能設計、非機能要件と設計、インフラストラクチャ
設計、コード生成、ビルド／テスト検証、CI パイプライン設定にわたる 7 つの
ステージ（3.1～3.7）で構成されます。

構築は AI-DLC 方法論における 5 フェーズのうち第 4 フェーズです。コンパイル
済みのスコープグリッドにより、実行するステージとスキップするステージが
決まります。ランタイムのユニットバッチは `unit-of-work-dependency.md`
（ステージ 2.7）に由来します。デリバリー計画（ステージ 2.9）は承認済みの
実行単位計画を作成します — これは計画の内容であり、ウォークの情報源では
ありません。

すべてのステージは、承認ゲート、質問形式、完了メッセージ、状態追跡について
`stage-protocol.md` に従います。

> **パス規約。** 各ワークフローの成果物は、対応する**意図レコードディレクトリ**
> `aidlc/spaces/<space>/intents/<YYMMDD>-<label>/` に格納されます（`<space>` は
> 非デフォルトのスペースを使用していない限り `default` です。
> `<YYMMDD>-<label>` は意図ディレクトリを示し、`260624` のような短い UTC 日付
> プレフィックスと、レコードを時系列に並べられる短いケバブケースのラベルで
> 構成されます）。以降の `<record>/` はこのディレクトリの短縮表記です。たとえば
> `<record>/construction/{unit-name}/functional-design/` は
> `aidlc/spaces/default/intents/<YYMMDD>-<label>/construction/{unit-name}/functional-design/`
> に展開されます。ディレクトリ名は人が読めるラベルであり、正規の識別子は
> `intents.json` レジストリ行に保存された UUIDv7 です。（意図ごとのレイアウト
> より前に作成されたプロジェクトではフラットツリーを使用しており、エンジンが
> 初回実行時に移行します。）

## 構築のウォーク

[実行単位](../../guide/glossary.md) は、デリバリー計画で記録された計画上のデリバリースライスです。Definition of Done、確信度仮説、所有権を持つ 1 つ以上のユニットで構成されます。ランタイムの順序は、`bolt-plan.md` のまとめ方ではなく、`unit-of-work-dependency.md` と記録済みの反復の選択に従います。

ユニット分解と、スコープ内でソースを生成するユニット単位ステージを含む新しいソロのワークフローは、既定で `Construction Checkpoints: enabled`、`Construction Iteration: unit-major`、`Construction Execution: serial` になります。1 つのユニットの該当する設計ステージとソース生成ステージを終えてから次のユニットへ進みます。明示的なステージ優先（stage-major）の選択は保持します。設計のみのワークフローとユニットの無いワークフローは既存のステージの流れを保ち、チーム所有の作業は `unit_gate` を使います。チェックポイント設定を持たない既存のワークフローは、従来の最初のステージのレビューを保ちます。その遅れて発火するステージ承認は、チェックポイントがオフの作業と同様に、1 つの質問になります。

skeleton-on の対象となるチェックポイント作業では、最初の DAG ユニットが、動作する最小の統合スライスです。stage-major を選んでいても、後続のユニットより前に、コード生成を含む該当ステージを完了します。実際のエンドツーエンドのプロジェクト検査に通り、検証済みのそのスケルトンを人が承認しなければなりません。従来の最初の構築ステージの承認はステージのレビューにすぎず、統合スケルトンが構築されたことを示すものではありません。

ユニット／バッチのチェックポイントはすべて、インテントに記録された、人が許可した `Construction Verification Command` を再利用します。デリバリー計画がプロジェクトのスキャンからそれを提案します。コマンドを提示する前に、ハーネスのファイル書き込みツール（Write/edit）で `<record>/verification-command.txt` へ書き込みます。シェルの `echo` や heredoc は決して使いません。リポジトリ由来のコマンド文字列をシェルの行へ埋め込んではなりません。承認前に置換が実行されうるためです。`log decision` と `log answer` はどちらも `--checkpoint verification-command --command-file verification-command.txt` を取り、実行中のセッションを自分で見つけます。
`decision` ツールの JSON 出力の `command` フィールドから、正規化された完全なコマンドをそのまま検証コマンドの質問のコードスパンへ写します。決して省略しません。コマンド内のバッククォートを保てる区切りを選びます。人は `<record>/verification-command.txt` を開くこともできます。正規化されたコマンドは、空白でない 1 行・最大 1024 文字です。制御文字と表示を偽装する文字（ゼロ幅文字や双方向制御を含む Unicode の書式文字、行／段落区切り、ノーブレークスペース U+00A0）は拒否されます。
人の **Approve** / **Request Changes** の回答が、保留中のコマンドに回答を結び付けます。尋ねたチャットでも、それが最新の質問である間は新しいチャットでもかまいません。受領記録を許可するのは **Approve** だけです。無関係な回答、**Request Changes**、別の質問への回答は許可になりません。人が選んでいない限り `--details "Approve"` を書いてはならず、選んだ場合にだけ `state set-construction-verification-command --command-file verification-command.txt` を実行して、対応する Runtime State フィールドを書きます。実行できる検査がまだ無い場合、人は延期でき、その場合は最初のチェックポイントが尋ねます。実行を許可するのはフィールドだけではなく、現在の承認の受領記録です。変更には新しい受領記録と型付きのセッターが必要で、汎用の `state set` や自動の選択は決して使いません。

skeleton-off では構築の開始時に、skeleton-on では実際のスケルトンのチェックポイントの後に、**Continue automatically** / **Review each checkpoint** を提示します。自動的に尋ねるのは、記録済みの選択が無い状態で提示が出力された場合だけです。オンデマンドの依頼で、構築中に選択を変えられます。その回答は通常の完了の質問を制御します。計画の承認、検証コマンドの選択、有効な要約確認を与えることも、失敗した検査の検証を成功させることも決してありません。

```text
Eligible new source-producing solo Unit workflow:
  Default: unit-major + serial + verified Unit checkpoints
  Skeleton-on: first whole integrated Unit → real check → human approval
  When offered: Continue automatically / Review each checkpoint
  Remaining Units: applicable stages → checks → completion per recorded policy
  Completion-only stage directives: bookkeeping over recorded Unit approvals

Existing, design-only, no-Unit, or team-owned workflow:
  Preserve its recorded path and applicable stage or Unit-gate policy

After the per-unit work:
  Build and Test, then CI Pipeline if included, run once across the solution
```

**本体より先にチェックポイントをルーティングする。** `construction_checkpoint` ディレクティブは、既存のユニット作業を検証して承認するもので、コード生成を再実行しません。それが `rereview` を運ぶ場合、そのレビューの依頼を尋ねずに直ちに実行し、その後で検証して 1 つの承認の質問をします。`rereview` は 3 つの場合のいずれかを示します。完了したレビューの後にユニットのコードや文書が変更された場合、ユニット自身のレビューが完了していない場合（`unfinished`: まだ判定が無いか、パスが残った NOT-READY）、またはユニットの作業のこの実行でまだ一度も依頼されていない場合（`first`）です。完了したレビューの後の変更を再確認するのは Guard Policy が `strict` の場合だけです。`relaxed` と `off` ではその変更は 1 行で受け入れられ、ユニットの承認はそのまま有効ですが、完了していないレビューや一度も依頼されていないレビューは引き続き示されます。レビューがオフの場合も同様で、その 1 行は次のチェックポイントの `verify` または構築ステージ自身の検査から、承認の質問とその人の回答の間に行われた変更についてはその人の `approve` から出ます。
`command_authorized: false` の場合は、どの `verify` よりも前に検証コマンドの質問を尋ね、人の decision／answer／セッターの手順を完了してから、`next` を呼びます。承認の質問には「Verified with `<full command>` (exit 0)」を表示します。`verification_command` は記録済みの正規化された完全なコマンドであり、省略したラベルでは決してありません。
`swarm_checkpoint` は、後続のバッチ作業の前に、完了したバッチを扱います。検証、承認、却下の後は `next` を呼び、1 つのユニットやバッチのためにステージ全体を承認することは決してしません。
`verify` が `verified: true` を報告し、現在のチェックポイントが `ready: true` になった後でだけ、`aidlc engine bolt checkpoint --action ask --unit "<unit>" --kind <unit|skeleton>` で人のユニット／スケルトン承認の質問を開きます。`ask` は準備できていない、または未検証のチェックポイントを拒否します。人に尋ねるバッチの質問では、status が `ready: true` を報告した後でだけ `aidlc engine bolt swarm-checkpoint --action ask --batch <N> --units "<Units>"` を実行します。
ユニットの `ask` が `earlier_reply` を返した場合、ユニットのレビューが走っている間にその人がこのチャットですでに回答しています。質問を表示せず、その人の言葉が選んだとおりに `approve` または `reject` を実行します。その言葉が何にも答えていない場合は、質問を表示して待ちます。それ以外の場合は **Approve** / **Request Changes** を提示して待ちます。このチェックポイントの質問に対する人の回答が、コンダクターがそこから読み取る操作を許可します。そのチャットでも新しいチャットでもかまいません。自分の質問を持たない新しいチャットの回答は、別のチャットが尋ねたチェックポイントの質問への回答として保持されます。ただし、それが最新の質問で、まだ開いている間に限ります。無関係な回答、エージェント自身の言葉、別の質問への回答は許可になりません。これらのコマンドは自分のセッションを見つけます。人が選んでいない `--user-input` は決して渡しません。同意は 1 回限りで、現在のチェックポイントのフィンガープリント、検証証明の ID、許可されたコマンドのダイジェストに結び付きます（バッチの質問はフィンガープリントとユニットごとの `Command SHA-256` の集合に結び付きます）。
`verify` やスウォームの `finalize` を再実行すると、このインテントの開いているチェックポイントの質問と、取り込まれたチェックポイントの回答が、どのセッションのものでもすべて撤回されます。再検証し、`verified: true`（バッチではソースの着地後に `ready: true`）を確認してから、もう一度尋ねます。古い回答で新しい証跡を承認することはできません。自動承認（`human_required: false`）には `ask` も `--user-input` も不要です。人による却下には、常にこの検証済みの質問と回答の手順が必要です。

`construction_policy.completion_only: true` と `human_completion_required: false` を持つステージは、本体、質問、レビュアー、学習のプロンプトを飛ばし、でっち上げたユーザー入力なしで `awaiting-approval` と `approved` を報告します。その他の完了ゲートは `human_completion_required` に従います。ポリシーを持たない従来の経路は、既存の人によるゲートの手順を保ちます。

バージョン 4 のチェックポイント証明は、コマンドの `command_sha256` と `command_label` 内の正規化された完全なコマンドに加え、終了ステータス、stdout／stderr の全バイト数と SHA-256 ダイジェスト、各ストリームの末尾 2 KiB を `stdout_tail` と `stderr_tail` に保持します。これらの末尾はチェックポイントの CLI の JSON にも現れます。先頭の不完全なマルチバイト列を落としたうえで UTF-8 としてデコードされ、改行とタブ以外の制御文字は U+FFFD に置き換えられます。出力の全文は保持されません。プロジェクトの検査コマンドは秘密情報を出力してはなりません。末尾は秘密情報の伏字処理を受けないためです。末尾は失敗の説明に使います。それ以上の診断には、新たに選んだコマンドではなく、同じ許可されたプロジェクト検査を使います。従来のバージョン 1〜3 の証明は、ユニットを承認できるようになる前に `aidlc engine bolt checkpoint --action verify --unit "<unit>" --kind <unit|skeleton>` による再検証が必要です。`GATE_APPROVED` は `Verification Command SHA-256` を証明のダイジェストに結び付けます。
検証ツールは、証明ファイルとともにツール所有の `CHECKPOINT_VERIFICATION_RECORDED` 受領記録を記録し、承認にはその受領記録が必要です。手書きの証明ファイルでユニットを検証済みにすることはできません。証明ファイルがまったく無いチェックアウト（新しいクローンや別のマシン）では、すでに承認済みで証跡が変わっていないユニットについて、その受領記録が証明の代わりになるため、何も再実行されません。

`plan_approval` がオンの間、コード生成の計画の承認は、すべてのユニットについて、生成前に人が止める地点のままです。まとめた計画の承認は、正確なライブのスウォームのユニット集合をまとめて提示できますが、受領記録は引き続き個別に記録します。生成前の要約確認が必要なのは、`directive.ceremony.summary_confirmation === "on"` の場合だけです。チェックポイントと承認のコマンドは [構築のコマンド](../../guide/12-cli-commands.md#construction-order-and-execution) を参照してください。

**反復と実行は別物です。** ユニット優先（unit-major）は直列です。対象となるチェックポイント作業でスウォームを明示的に選ぶには、stage-major を選び、そのうえで `Construction Execution: swarm` を選びます。ガイド付きと自動の完了はどちらもサポートされます。自律の回答は、実行方式も反復順序も変えません。すでに承認済みのインラインのユニットが、後のスウォームで再構築されることはありません。実行設定を持たない従来のワークフローは、既存の自律に基づくスウォームの経路を保ちます。

**チーム所有のゲート。** `Unit Ownership: team` の場合、`per-stage` リズムは、決着した `(stage, Unit)` ごとに、その Unit が前へ進む前にゲートを開きます。`unit-end` は、その Unit の最後の該当するユニット単位ステージの後に 1 回だけゲートを開きます。これらはソロのチェックポイントの方針とは別のままです。エンジンは `Unit Progress` を更新し、各ゲートの報告はその Unit を名指しするため、判断とレシート下限はその作業にだけ影響します。

チームモードのクレームは `claim/<intent-id8>/<unit>` の ref を compare-and-swap 更新で
使います。クレームに成功すると gitignore 済みのチェックアウトスタンプが書かれます。その
チェックアウトはスタンプされた Unit だけをルーティングし、ライフサイクル・レビュー・
ゲート・フォークの各証跡にクレーム世代を載せます。クレームが有効な間、スコープの付いて
いないメインは終端のファンアウト通知を出力します。`aidlc-unit.ts release <unit>` は ref を
削除する代わりに tombstone を書き、履歴を保ちながら古い試行を無効化します。参加者の
クローンは `aidlc-unit.ts participate` で 1 回だけガイド付きクレームピッカーへオプトイン
します。ファシリテーターのメインは、意図的にこのマーカーを持ちません。スコープ付きの
ルーティングとレシート書き込みはオフラインファーストです。クレーム時のスタンプが権威で
あり、レジストリの生存確認はフォーク／リリースのようなクレームに敏感な境界でのみ再実行
されます。リモートが利用できない場合は警告のうえスタンプに基づいて続行し、オンラインで
古い、あるいは解放済みと分かった試行は拒否されます。

完了したチームはコミットして `aidlc unit publish <unit>` を実行します。続いてスコープの
付いていないメインが、クレーム ref の正確な OID をピン留めし、ワークツリーを実体化せずに
その成果物・レシート・ゲート・レビューおよび Plan Approval を検証し、人間によるマージ
ゲートを 1 回記録して、`aidlc unit land` で候補を着地させます。Git のコンテンツは Unit 行が
畳み込まれる前に着地します。メインが所有する状態／実行時マーカーは保持され、チームの
新しい監査シャードが試行キー付きのレシートを運び、`UNIT_MERGED` がその行を印付けます。
ソースの衝突は状態変更の前に中断します。最後のマージ済み行の後、ビルドとテスト、および
CI パイプラインがメイン上で 1 回だけ実行されます。

**ユニット単位バッチウェーブ（任意、ステージ優先のみ）。** 記録されたステージ優先の
経路では、エンジンは 4 つのインライン設計ステージ（3.1〜3.4）のいずれかに
対して `directive.wave` を発行することが **できます**（MAY）。ウェーブは自己修復
された 1 つの DAG スナップショットから導出され、コンダクターが
`runtime-graph.json` を読んだり兄弟パスを導出したりすることはありません。
コード生成（3.5、`workspace_requires: true`）は **決してウェーブ対象になりません**。
並行するビルダーが共有ワークスペースへの書き込みで衝突するためであり
（スウォーム経路のユニットごとのワークツリーは、まさにこの分離のために存在します）、
また `plan_approval` がオンの間、その最初の計画の承認はあらゆる実行モードで必須の停止地点であり、エンジンからその人への質問をビルダーの戻りメッセージへ折り畳めないためです。`plan_approval` がオフの場合（express と poc の既定）、エンジンは計画を名指しする 1 行の後、書かれたとおりに計画を構築し、`PLAN_APPROVAL_SKIPPED` を記録します。Guard Policy が `relaxed` または `off` の場合、計画の再承認のフェンスは指示されていない作業については脇へ退き、拒否する代わりに `GUARD_STOOD_ASIDE` を記録します。
承認後、同じ対象と試行に対する内容の編集は、下記のコード生成の実効フェンスの規則に従います。フェンスが下げられていれば、計画の承認でもう一度止まらずに継続できます。

各エントリは、種別に応じて解決された `consumes`、存在しない `consumes` の明示、
すべての `produces`、該当する必須の部分集合、ユニットローカルの日誌パス、ビルド
状態、対レビューの状態、そしてウェーブ完了受領記録がまだ必要かどうかを運びます。
ビルダーは親のステージファイル、インラインコンテキストのロスター、警告、蓄積された
ステアリング内容をそのまま受け取ります。ブロックされたビルダーが差し止めるのは
該当する必須パスであり、任意パスや種別上免除されたパスではありません。ビルドと
レビューの後、`unit complete --wave` がライブエントリを検証し、ユニット日誌の
エントリを親日誌へ冪等に集約し、`UNIT_COMPLETED` を発行します。エンジンは、該当
するすべてのユニットがそれらの証跡を揃えるまで現在のバッチを保持し、その後に依存
する後続バッチまたは単一のステージゲートを許可します。ウェーブは
`Construction Iteration: unit-major` では決して適用されず、並列ディスパッチの
プリミティブを持たないハーネスはエントリを直列に処理します。完全な契約は
`stage-protocol-wave.md` §「ユニット単位バッチウェーブ」を参照してください。

**並列バッチ。** エンジンが出力した、依存関係の準備が整った正確なユニットに従います。明示的なステージ優先／スウォームの実行では、対象となるコード生成のユニットを並行してディスパッチできます。チェックポイントが有効なワークフローでは、完了した各バッチが、後続の作業の前にガイド付きまたは自動の完了のための `swarm_checkpoint` を返します。従来のスウォームの決着は、既存のステージゲートを保ちます。`BOLT_STARTED` / `BOLT_COMPLETED` はスウォーム経路でユニット／ワークツリーごとに発行され、`SWARM_COMPLETED` がバッチを閉じます。直列のインライン作業は、ユニットのライフサイクルとチェックポイントの受領記録を使います。

新しい実行単位のワークツリーはそれぞれ、ブランチ `bolt-<id8>_<slug>` 上の `.aidlc/worktrees/bolt-<id8>_<slug>` です。インテントのレジストリ UUID の接尾辞 `<id8>` はユニットのクレームと共有されるため、並行するインテントは、ブランチや保持／保留された ref を共有せずにユニットのスラッグを再利用できます。レジストリ UUID の無いインテントでの作成は拒否されます。構築の前にインテントを採用し直すか作り直してください。命名と、アップグレード前の従来の実行単位を、古い形の新しい実行単位を作らずに完了させる来歴の検査については、[Bolt の識別](../../../core/knowledge/aidlc-shared/worktree-info-schema.md#bolt-identity) を参照してください。クリーンアップは、別のワークツリーのパスでチェックアウトされているブランチを拒否し、その所有者のブランチと ref を保持します。

メインのチェックアウトが初期化したサブモジュールは、新しい実行単位のワークツリーそれぞれにも、ベースが記録するコミットで、メインのチェックアウト自身のコピーからクローンして（ネットワークも認証情報も不要）用意されます。初期化されていないサブモジュールは空のディレクトリのままです。着地では、そこにあるサブモジュールのコピーに未コミットの変更や、メインのチェックアウトのコピーに無いコミットがある場合、ワークツリーを保持し、そのサブモジュールを名指しします。コミット済みソースの検査は、初期化されたサブモジュールを、ライブのソース走査と同じように、そのコミットとファイルとして読みます。そのため、サブモジュールを持つクリーンなチェックアウトは、自分自身の `HEAD` と一致します。

最初の保護された prepare の前に、すべてのユニットが、現在の承認または許可された承認後の継続と、コミット済みで再現可能な親アプリケーションのソースについて、読み取り専用の事前検査を受けます。これは従来の自律にも新しいチェックポイントにも当てはまります。未コミットの承認済みソースのスナップショットは、子を作る前に拒否されます。それをコミットする明示的な許可を得てから再試行します。インラインのスケルトンの承認済みソースは、後の並列バッチの前にコミットしなければなりません。prepare がそのコミットを自動で行うことは決してありません。

`resume_existing: true` の却下されたバッチは `prepare --resume-existing` を使います。却下によって以前の承認が退役した場合は、その改訂の新しい計画の承認を得ます。その承認後の再試行は、同じインテント、対象、試行について、下げられたフェンスでの継続を使えます。`execution_allowed: true` は `ok: false` でもそれを許可し、古い試行の承認を復活させることはありません。
残っているワークツリーはソースを保持し、以前のメタデータをアーカイブします。ネイティブなソースの着地で子が取り除かれた場合、必要な着地の証跡があれば、ツールはすでに着地した親のソースから子を再作成でき、却下の改訂を保持します。マージ後のすべての子が保存されることは約束しません。[Swarm prepare](../../guide/12-cli-commands.md#aidlc-engine-swarm-prepare-prepare-a-reproducible-batch) を参照してください。

**失敗時の処理。** コード生成の失敗は自律モードにかかわらず、常に構築を停止します。
選択肢は再試行（失敗したユニットだけを再実行）、スキップ（`[S]` を記録して続行。
依存するユニットも失敗する可能性があります）、または中止です。並列バッチ内で成功
した兄弟の実行単位は、`[x]` の状態と成果物を維持します。正規の手順については
`stage-protocol-checkpoint.md` と、`stage-protocol-construction.md` の §「Halt-and-ask on failure」を参照してください。
通常の失敗プロンプトの Abort は、ワークツリーを保持したまま構築を一時停止します。代わりに `--discard` を明示的に伴う、古いレビューからの回復の中止は、追跡対象のファイルと無視されていない未追跡ファイル、レビュー済みのソース ref を保留し、そのうえでライブのチェックアウトとブランチを削除します。人の選択を得たら、返された中止コマンドを変更せずに実行します。中止結果の `restore_operation` がある場合、そのルートは `worktree` で、保存したスラッグ、スタンプ、リポジトリ（`--repo <name>` または `--repo .`）を選ぶ正確な引数を持ち、その後に `--intent <record-dir-name> --space <space>` が続きます。これにより、アクティブなインテントが変わった後も、回復はそのインテントに結び付いたままです。人が復元を依頼したら、列挙された各引数を別々の argv 引数としてそのまま渡して `{{INVOKE}} engine worktree <args...>` を呼び出し、シェルのコマンドに連結することは決してしません。復元は `.aidlc/restored/bolt-<id8>_<slug>-<stamp>` 内のファイルを `restore/bolt-<id8>_<slug>-<stamp>` 上に回復し、新しいライブの実行単位を上書きすることも、古い試行のレビュー権限を復活させることもありません。`restore_hint` は人向けの表示用の任意のテキストにすぎず、実行の入力ではありません。安全な描画に失敗した場合、ヒントは省かれ、操作は残ったまま `restore_hint_error` がその理由を説明します。復元の提案はヒントではなく操作に基づいて行います。レビューの証跡だけが残っていた場合、`evidence-only` の記述子には、復元の操作、ヒント、ヒントのエラー、除外のいずれもありません。作業ファイルは保存されておらず、復元は拒否され、doctor は削除だけを提案します。
[回復の手順](../../guide/15-troubleshooting.md#保留したboltのファイルを取り戻す) は、何が保留されたか、除外、正確な復元の選択、情報としての doctor の一覧と削除の選択肢を説明します。従来の復元は従来の名前を保ち、選択したインテントの正確な `WORKTREE_DISCARDED` の `Parked ref` の来歴を必要とします。

## ステージ 3.1: 機能設計

### メタデータ

| 項目 | 値 |
|------|----|
| ステージ | 3.1 |
| フェーズ | 構築 |
| 実行 | CONDITIONAL（実行計画に従う） |
| 条件 | 新しいデータモデル、複雑なビジネスロジック、またはビジネスルールの設計が必要。新しいビジネスロジックのない単純なロジック変更ならスキップ。 |
| ユニット単位 | はい |
| 主担当エージェント | AIDLC アーキテクトエージェント |
| 支援エージェント | AIDLC 開発者エージェント |
| モード | インライン |
| 入力 | 作業ユニット定義、ストーリーマップ、ストーリー（生成されていれば）、要件、ドメイン設計成果物 |
| 出力 | `<record>/construction/{unit-name}/functional-design/` — 機能仕様、ルール、エンティティ、traceability.json、条件付き: フロントエンドコンポーネント（ユニットの種別による） |

### 目的

単一の作業ユニットについて、ビジネスロジック、ドメインモデル、ルールを設計します。
AIDLC アーキテクトエージェントが主導し、AIDLC 開発者エージェントが技術的実現可能性の
入力を提供します。

### 入力

- `<record>/inception/units-generation/unit-of-work.md` からのユニット定義
- `<record>/inception/units-generation/unit-of-work-story-map.md` からの割り当て済みストーリー
- `<record>/inception/user-stories/stories.md` からの、それらのストーリーの受け入れ基準（生成されていれば）
- `<record>/inception/requirements-analysis/requirements.md` からの要件
- `<record>/inception/domain-design/` からのドメイン設計成果物

### 手順

1. **ユニットコンテキストを読む** — ユニット定義、割り当て済みストーリーとその受け入れ基準、
   要件、ドメイン設計成果物を読みます。

2. **機能設計計画を作成する** — ユニットのスコープを分析し、コンテキストに適した
   質問と `[Answer]:` タグを用いて、次の場所に質問ファイルを作成します。
   `<record>/construction/{unit-name}/functional-design/functional-design-questions.md`
   着目点:
   - ビジネスロジックのワークフローとアルゴリズム
   - ドメインモデルとエンティティ関係
   - ビジネスルール、制約、検証ロジック
   - データフローと変換
   - 他ユニットまたは外部システムとの統合点
   - エラー処理とエッジケース（Standard と Comprehensive の深さでは、product エージェントの
     `corner-checklist.md` に照らしてコンポーネントごとに洗い出す。要件ですでに決着した
     端のケースはそのまま引き継ぐ）
   - フロントエンドコンポーネント（コンポーネント階層、プロパティ／状態、
     操作フロー、フォーム検証）
   - ビジネスシナリオ（エンドツーエンドのユーザージャーニー、正常／異常パス、
     並行性のエッジケース）

3. **回答を収集して分析する** — `stage-protocol.md` の質問フローに従って回答を
   収集します（対話モードの選択を提示し、回答を集め、ファイルへ書き戻す）。
   曖昧さの分析は必須です。
   - 曖昧な回答を特定する（「混在」「わからない」「場合による」「おそらく」など）
   - 回答間の矛盾を確認する
   - 成果物生成に必要な欠落詳細に印を付ける
   - 曖昧さが 1 つでもあれば、フォローアップ質問を作成し、解決してから進む

4. **成果物を生成する** — 次を
   `<record>/construction/{unit-name}/functional-design/` に生成します。
   - **機能仕様**: ユニットのビジネスロジック向けの詳細な
     アルゴリズム、ワークフロー、データ変換、処理順序、決定木
   - **ルール**: 決定ルール、検証ロジック、制約、ポリシー、条件付き
     振る舞い、ビジネス不変条件
   - **エンティティ**: エンティティ、関係、データ構造、属性、
     ライフサイクル状態、エンティティ相互作用パターン
   - **フロントエンドコンポーネント**（条件付き — ユニットにフロントエンド／UI が
     含まれる場合のみ）: コンポーネント階層、プロパティ／状態設計、操作フロー、
     フォーム検証ルール、API 統合点

5. **完了を準備する** — ユニットの機能設計成果物を検証します。状態は編集せず、
   ゲート結果を `aidlc-orchestrate.ts` を通じて報告します。

6. **完了** — 完了メッセージと承認ゲートを提示します。

### 出力

| 成果物 | 説明 |
|--------|------|
| 機能仕様 | アルゴリズム、ワークフロー、データ変換、処理順序、決定木 |
| ルール | 決定ルール、検証ロジック、制約、ポリシー、条件付き振る舞い |
| エンティティ | エンティティ、関係、データ構造、属性、ライフサイクル状態 |
| フロントエンドコンポーネント | （条件付き）コンポーネント階層、プロパティ／状態、操作フロー、フォーム検証、API 統合 |
| traceability.json | 各ストーリーのすべての受け入れ基準をユニットに対応付けたもの（stories.md が無ければストーリーマップにあるユニットの FR 行、ストーリーマップも無ければすべての FR。下位要件を持つ要件はその `FR{n}.{m}` ID で）。それぞれ、rules.md の `BRx.y` ルールへの `OK`、理由付きの `N/A` または `Deferred`、あるいは `GAP` |

ユニットが受け取るファイルはその種別に従います。`ui` ユニットにはエンティティもルールも無く、フロントエンドコンポーネントを受け取るのは `ui` ユニットだけで、`packaging` ユニットはどれも受け取りません。

### 承認ゲート

厳格な 2 選択肢: Approve / Request Changes。

### 注記

- 質問ファイルはステージ成果物と同じ場所に置きます。
  `<record>/construction/{unit-name}/functional-design/functional-design-questions.md`
- フロントエンドコンポーネント成果物は、ユニットにフロントエンド／UI 作業が
  含まれる場合のみ生成します。
- すべての質問は 3 モード対話フロー（Guide me / I'll edit the file / Chat）を
  使用します。

## ステージ 3.2: NFR 要件

### メタデータ

| 項目 | 値 |
|------|----|
| ステージ | 3.2 |
| フェーズ | 構築 |
| 実行 | CONDITIONAL（実行計画に従う） |
| 条件 | パフォーマンス、セキュリティ、スケーラビリティ、信頼性、または可観測性の要件が必要、あるいは技術スタック選定が必要。NFR 要件がなく技術スタックが既に決まっている場合はスキップ。 |
| ユニット単位 | はい |
| 主担当エージェント | AIDLC アーキテクトエージェント |
| 支援エージェント | AIDLC 開発セキュリティ運用エージェント、AIDLC コンプライアンスエージェント、AIDLC 品質エージェント |
| モード | インライン |
| 入力 | 機能設計成果物、要件、リバースエンジニアリング成果物 |
| 出力 | `<record>/construction/{unit-name}/nfr-requirements/` — パフォーマンス要件、セキュリティ要件、スケーラビリティ要件、信頼性要件、可観測性要件、技術スタック決定、traceability.json（ユニットの種別による） |

### 目的

単一ユニットについて、パフォーマンス、セキュリティ、スケーラビリティ、信頼性、
可観測性、技術選定にわたる非機能要件を定義します。AIDLC アーキテクトエージェントが主導し、
AIDLC 開発セキュリティ運用エージェントがセキュリティ入力、AIDLC コンプライアンス
エージェントが規制入力、AIDLC 品質エージェントがテスト容易性と測定可能性の入力を
提供します。

### 入力

- `<record>/construction/{unit-name}/functional-design/` からの機能設計成果物
  （存在する場合）
- `<record>/inception/requirements-analysis/requirements.md` からの要件
- `aidlc/spaces/<active-space>/codekb/<repo>/` からのリバースエンジニアリング成果物
  （存在する場合）

### 手順

1. **先行成果物を読む** — 機能設計成果物（存在する場合）、要件、
   リバースエンジニアリング成果物を読みます。

2. **NFR カテゴリを評価する** — 次の NFR カテゴリでユニットを分析します。
   - **パフォーマンス**: 応答時間、スループット、レイテンシ目標、リソース使用率
   - **セキュリティ**: 認証、認可、データ保護、コンプライアンス要件
   - **スケーラビリティ**: 負荷処理、成長予測、スケーリング戦略
   - **信頼性**: 可用性目標、耐障害性、災害復旧、データ耐久性
   - **可観測性**: 監視、ログ、アラート、トレーシング要件

3. **質問を生成する** — 不明な NFR 領域について `[Answer]:` タグを用いて、次の場所に
   質問ファイルを作成します。
   `<record>/construction/{unit-name}/nfr-requirements/nfr-requirements-questions.md`
   定量的な目標と具体的な制約に焦点を当てます。

4. **回答を収集して分析する** — `stage-protocol.md` の質問フローに従って回答を
   収集します。曖昧さの分析は必須です。
   - 曖昧な回答を特定する（「十分速い」「高可用」「セキュア」など）
   - NFR 目標間の矛盾を確認する
   - 欠落している定量目標に印を付ける
   - 曖昧さが 1 つでもあれば、フォローアップ質問を作成し、解決してから進む

5. **成果物を生成する** — 次を
   `<record>/construction/{unit-name}/nfr-requirements/` に生成します。
   - **パフォーマンス要件**: 応答時間目標、スループット要件、レイテンシ予算、
     リソース制約、ベンチマーク
   - **セキュリティ要件**: 認証要件、認可モデル、データ保護、コンプライアンス、
     脅威の考慮
   - **スケーラビリティ要件**: 負荷予測、スケーリング契機、キャパシティ計画、
     データ成長、同時実行目標
   - **信頼性要件**: 可用性目標（SLA／SLO）、耐障害性要件、バックアップ／復旧、
     グレースフルデグラデーション
   - **可観測性要件**: 監視要件、ログ標準、分散トレーシングの必要性、
     アラートしきい値、ダッシュボード要件、SLI／SLO 定義
   - **技術スタック決定**: 技術選定とその根拠 — 言語、フレームワーク、
     データベース、インフラツール、各選択の正当化

6. **完了を準備する** — ユニットの NFR 要件成果物を検証します。状態は編集せず、
   ゲート結果を `aidlc-orchestrate.ts` を通じて報告します。

7. **完了** — 完了メッセージと承認ゲートを提示します。

### 出力

| 成果物 | 説明 |
|--------|------|

## ステージ 3.5: コード生成

### メタデータ

| 項目 | 値 |
|------|----|
| ステージ | 3.5 |
| フェーズ | 構築 |
| 実行 | ALWAYS（ユニット単位） |
| 条件 | 実行計画内のすべてのユニットで常に実行します。 |
| ユニット単位 | はい |
| 主担当エージェント | AIDLC 開発者エージェント |
| 支援エージェント | （なし — 実装に集中） |
| モード | サブエージェント（`Task` ツールの `subagent_type="aidlc-developer-agent"`） |
| 入力 | このユニットの先行設計成果物すべて |
| 出力 | アプリケーションコード（ワークスペースルート）＋ `<record>/construction/{unit-name}/code-generation/` — コード生成計画、コード生成質問、ユニットテスト指示、コードサマリー、traceability.json、加えてエンジン必須の随伴ファイル source-manifest.json（ユニット作業のみ） |

### 目的

単一の作業ユニットについて、アプリケーションコード、テスト、設定をすべて生成します。
このステージを含むすべてのスコープで、すべてのユニットについて実行されます。infra はコード生成もビルドとテストも実行しません。そのコンパイル済みの計画が示すとおりです。

```text
$ aidlc engine graph scope infra
workspace-scaffold
workspace-detection
state-init
practices-discovery
requirements-analysis
nfr-requirements
nfr-design
infrastructure-design
ci-pipeline
deployment-pipeline
environment-provisioning
deployment-execution
observability-setup
```

コードはワークスペースルートに書き、`<record>/` には書きません。

### 重要な規則

- アプリケーションコードはワークスペースルートへ。決して `<record>/` へは置かない。
  開発者がそこで行う唯一の変更は、各ステップを終えるたびに計画のそのステップの
  チェックボックスに印を付けることである
- ブラウンフィールド: ファイルをその場で変更する。次のような複製は作らない
  `ClassName_modified.java`
- この作業が作成していない、プロジェクトにすでにあるファイル（README、LICENSE、
  ドキュメント、設定）は、新規プロジェクトであってもその人のものである。そのまま残し、
  その周りにコードを構築する。何を使って構築したか、どう実行するかについてのこの作業
  自身のメモは `code-summary.md` に書き、テストコマンドはすでに
  `unit-test-instructions.md` にある。それらのファイルを変更するのは、その人が求めた
  場合か、それなしでは作業を構築できない場合（ブラウンフィールドでは、作業が変更する
  コード）だけである。その変更を計画で名指しし、ゲートで一度、ファイルとそこで何を
  変えたかを名指しして伝える。元に戻す方法は、ある場合にだけ伝える
- テスト自動化のため、対話的な UI 要素に `data-testid` 属性を付ける
- 次の順序で作業する: 計画（手順 2）、手順 3（その人の計画の承認。計画の承認が
  オフなら、その 1 行の通知だけ）、生成（手順 4）、手順 5 のファイル、そして
  レビュー（ディレクティブが `reviewer` プロトコルモジュールを列挙している場合）と
  完了（手順 6）。レビューは完成した作業を確認する。レビュアーが手順 5 のファイルが
  存在する前に実行されることは決してない。ディレクティブがすでに
  `plan_approval.status: "approved"` を運んでいる場合（再開または継続したビルド）、
  ディスク上の計画とテスト指示は承認済みのものである。手順 2 と 3 を飛ばし、
  そのまま構築する。承認済みの計画やそのテスト指示を書き直してはならない。
  変更するのは、その人が求めた場合だけである
- ユニット（`directive.unit` がある場合）では、手順 5 でレビューの前に、このユニットが
  作成・変更・削除したアプリケーションソースのパスをすべて列挙する、エンジン必須の
  随伴ファイル `source-manifest.json` を書く。シェルコマンド、スキャフォールディング、
  ジェネレーターが書いたファイルも含める。ユニットを伴わない作業は
  `source-manifest.json` を書かない
- NFR 要件、NFR 設計、および Testing Contract のカバレッジ床に由来する測定可能な
  品質目標は、入力であって提案ではない。ステップを通すために、定義済みの目標を
  緩和・引き下げ・無効化してはならない（テストやビルド設定のしきい値設定を含む）。
  代わりにギャップを表面化させる。

### 入力

- `<record>/construction/{unit-name}/functional-design/` からの機能設計
  （存在する場合）
- `<record>/construction/{unit-name}/nfr-requirements/` からの NFR 要件
  （存在する場合）
- `<record>/construction/{unit-name}/nfr-design/` からの NFR 設計（存在する場合）
- `<record>/construction/{unit-name}/infrastructure-design/` からの
  インフラストラクチャ設計（存在する場合）
- `<record>/inception/domain-design/` からのドメイン設計
- `<record>/inception/units-generation/unit-of-work.md` からのユニット定義
- `<record>/inception/units-generation/unit-of-work-story-map.md` からの
  ストーリーマップ

### 手順

このステージは**二部構成**です。計画の後に生成を行います。

#### 第 1 部 — 計画（手順 1～3）

1. **ユニット成果物をすべて読む** — 現在のユニットの設計成果物をすべて読みます
   （機能設計、NFR 要件、NFR 設計、インフラストラクチャ設計、ドメイン設計、
   ユニット定義、ストーリーマップ）。

2. **コード生成計画を作成する** — 各実装ステップにチェックボックスを付けた詳細計画を
   次の場所に作成します。
   `<record>/construction/{unit-name}/code-generation/code-generation-plan.md`
   ストーリーからコードステップへの追跡可能性を含め、各計画ステップを実装する
   ユーザーストーリーへ対応付けます。

   `aidlc-testing-posture.ts render` を実行し、その完全な
   `## Testing Contract` JSON ブロックを計画へ貼り付けます。リゾルバは
   org/team/project の Testing Posture セクションを加法的に読みます。プロジェクトの
   カバレッジや統合に関する注記は適用されたままですが、チームの方法論を消し去る
   ことはありません。矛盾する、より狭い方法論は拒否されます。

   この契約は、方法論固有の計画プロファイルを提供します。

   - **TDD** — 該当するすべてのテスト可能な層（データ、リポジトリ、ビジネス
     ロジック、API、フロントエンド）に対する Red/Green/Refactor。
   - **BDD** — 観測可能な機能スライスの前に実行可能な振る舞いシナリオを書き、
     その後に層をまたぐ実装、シナリオのグリーン化、リファクタリングが続きます。
     層ローカルの TDD へは変換されません。
   - **ATDD** — 層をまたぐ完全な機能実装の前に実行可能な受け入れテストを書き、
     その後に受け入れテストのグリーン化とリファクタリングが続きます。
   - **カスタム／混合** — 確認済みの正確な順序がそのまま維持されます。シナリオ
     ファーストの BDD と、実装後の下位レベルユニットテストのような組み合わせも
     含みます。
   - **テスト後書き** — 該当するすべてのテスト可能な層に対して、実装の後に
     テストを書きます。

   グリーンフィールドの計画は、最初の Red／シナリオ／受け入れステップの前に
   最小限の実行可能なテストコマンドをブートストラップします。ブラウンフィールドの
   計画は、既存のコマンドを先に検証します。選択されたテスト戦略が量／種類を
   与え、スコープがその床（カバレッジ/CI、対象を絞った回帰、または追加の床
   なし）を加えます。どちらの義務も他方を置き換えません。Minimal の下では、
   バグ／セキュリティの対象を絞った回帰が、欠陥を再現できる最も狭いレベルで
   ある場合に限り、統合/E2E テストを 1 つ追加できます。

   **計画へのテストファイル含有は必須です。** 計画には必ず次のステップを含めます。
   - ユニットテストファイル（主要振る舞いをカバーするコンポーネント／モジュールごと）
   - テスト設定（テストランナー設定、または同等）

   計画がテストファイルのステップを省略している場合、ユーザーへ提示する前に
   追加しなければなりません。テストはビルドとテストへ先送りしません。あの
   ステージは検証と拡張であり、ゼロからの作成ではありません。

   明確な実行順序と追跡性のため、各計画ステップに連番を付けます
   （手順 1、手順 2、など）。

   コード生成の記録ディレクトリはディレクティブから 1 つに解決します。
   `directive.unit` があれば
   `<record>/construction/<directive.unit>/code-generation/`、無ければ Unit を伴わない
   ステージディレクトリ `<record>/construction/code-generation/` です。あわせて、
   計画の承認より前に、そこへ `unit-test-instructions.md` も作成します。有効なテスト
   戦略に合わせます。
   - **Minimal**: 要件駆動のユニットテスト（要件ごとに 1 テスト、コンポーネント
     ごとに正常系の下限）、合計でおよそ 5～15 テスト
   - **Standard**: コンポーネントごとに 5～8 テスト、主要な振る舞いをカバー
   - **Comprehensive**: コンポーネントごとに 10～15 テスト、網羅的にカバー

   テストフレームワークのセットアップと設定、最初のテストファーストサイクルの
   前に利用可能な正確な実行可能コマンド、期待するカバレッジ目標、モック／スタブの
   指針、テストデータ管理を含めます。
   すべての実行コマンドは、正確なテストファイルパスまたは正確なユニットフィルタに
   より、このユニットへスコープを限定しなければなりません。ビルドとテストは
   すべてのユニットのコマンドを実行するため、`npm test` のようなプロジェクト全体を
   対象とする素のコマンドは許容されません。プロジェクト全体に設定されたカバレッジの
   下限は、これらのコマンドではなく、ビルドとテストがフルスイートで測定します（1 つの
   ユニットのテストでは、他のユニットのテストがカバーするソースでランナーのしきい値が
   失敗することがあります）。ファイルはその下限を名指しし、ユニットの実行を通すために
   プロジェクトのカバレッジ設定にある下限のしきい値を変更することは決してありません。
   下限のしきい値で失敗しうるコマンドは、そのしきい値による終了で止まってしまう後続の
   ステップを持ちません。ビルドとテストは、終了によって後のステップを止めたコマンドを
   免除しないためです。ユニットまたはそのパスの 1 つに設定されたカバレッジ目標には、
   ユニットにスコープを限定した独自のチェックがあります。

   計画は短い `## Summary`（Builds、Touches、Tests の各行）で始まり、エンジンは
   承認を求めるときにそれをその人に見せます。

3. **計画の承認** — エンジンが尋ねます。両ファイルが書かれたら、コンダクターは
   `next` を実行します。準備のできた計画（空でない計画と指示、有効で最新の
   Testing Contract、読み取れるワークスペースのソース）では、`next` はビルドの代わりに
   `plan-approval` の質問を返します。質問、各対象のサマリーと計画のパス、そして
   **Approve Plan**、**Request Changes**、**I'll edit the files** です。エンジンは
   `code-generation-questions.md`（質問、両タグ、空欄の `[Answer]:`）を書き、保護された
   ランタイムディレクトリに質問を記録します。コンダクターはそれを表示してターンを終えます。
   human-turn フックは、この作業に関するどのチャットからでも、質問の後のその人の返答を
   すべて保持し、入力された言葉からは何も選び取りません（質問ボックスでの選択はホスト
   自身の構造です）。コンダクターは、返答がどの質問に答えているかを読み取り、
   `answer --checkpoint plan-approval` でその人の選択を記録します。
   これはその時点のファイルのフィンガープリントを取り、回答、受領記録、その人の言葉を
   含む `PLAN_APPROVAL_RECORDED` の行を書きます。その人は代わりに、質問ファイルが促す
   とおりにファイル自身の `[Answer]:` 行へ回答を書き、そう伝えてもかまいません。エンジンは、
   同じ質問が立っている間、その人がそこに書いた回答を決して上書きしません。その人が
   そう伝えたときは、どんな言葉でも（「done」、「I put my answer in the file」）、コンダクターは
   その行を読んで、その人がした選択を記録します。行そのものは何も承認せず、承認するのは
   エンジンの受領記録です。質問が開かれたこのチャットでのその人のメッセージがすでに変更を
   求めていて（「go back to code generation: also accept -S」。完了済みの作業でも、また変更を
   名指しする 1 つのユニットのステップのやり直しでも）、それが求めたやり直しやジャンプ以外の
   どの判断もそれを使っていない場合、コンダクターはそれをその質問の Request Changes として、その人の
   言葉とともに記録します（`--message` が読むとおり、メッセージの記録が証明です）。承認には
   引き続き質問の表示後の返答が必要で、改訂された計画の質問にはそれ自身の返答が必要です。
   次の `next` は、
   `plan_approval.status: "approved"`（ビルド）、`revise`（その人の言葉付き）、`repair`
   （編集で壊れた Testing Contract）、`plan`（ファイルを仕上げる）のいずれかの run-stage を
   返します。編集モードでは、その人がファイルを変更するか、質問ファイルに回答を書いて
   完了を伝え、コンダクターはその人が書いたものを読んで選択を記録します。その間、
   ガードはそれらのファイルへのコンダクターの書き込みを拒否します。準備のできていない
   計画について尋ねることは決してありません。`next` は代わりに修復を名指しします。

   同じ対象と試行に対する承認後の計画、指示、Testing Contract の編集は、Guard Policy が
   `strict` の場合は改めて尋ねます。`relaxed` または `off` の場合、ビルドは更新された内容で
   継続します。元の証跡は保持します。編集された内容がそれによって承認されたわけでは
   ありません。Testing Posture、スコープ、戦略、プロジェクト種別の変更も同じ規則に
   従います。承認後にそれ以外のコードが動いても、どの Guard Policy でも改めて尋ねることは
   決してありません。ビルドは、ファイルを名指しする `change_notices` の 1 行とともに継続
   します。`strict` の下のスウォームは、その人自身のファイルについての例外です。prepare は
   計画が改めて承認されるまで拒否し、ソースの着地は、同じ変更が元に戻されるか Guard Policy
   が `relaxed` になるまでそれを拒否します。別のインテントや対象、新しい試行、実際の最初の承認が欠けている場合は、引き続き
   それ自身の承認が必要です。却下されたゲート（コード生成の完了ゲート、ユニットの
   チェックポイント、スウォームのバッチのチェックポイント）の後、計画が以前に承認された
   ままであれば、`next` はまずそのゲートでのその人の言葉付きで `revise` を返すため、
   続く質問は改訂された計画を示します。`/aidlc --stage code-generation`（`Reopen: jump`）または
   Redo（`Reopen: redo`）でステップを開き直すと新しい試行が始まり、任意の編集を求める
   ことなく、現状の計画について尋ねます。
   `Reopen: change` とゲートの Request Changes は、引き続きその人のフィードバック付きで
   `revise` を返します。`next` の再実行や、同じ対象と試行に対する
   ディレクティブの再発行で承認が再開することは決してありません。その間にエンジンが
   何を言ったかでも再開しません。圧縮されたチャット、保留して再開した作業、ガードの
   回復の質問がそうです。`next` は、置き換えるディレクティブではなく、ルーティングした
   ディレクティブが構築する計画についての承認を読みます。転送ループの継続は決して
   承認ではありません。

   `testing-posture verify` は、継続が許可される場合、`ok: false` が現在の内容は未承認だと
   伝えていても、`execution_allowed: true` を exit 0 で報告します。その実行の結果を
   使います。`begin` と `brief` もそれに従います。分かりやすい `reason` が継続を説明し、
   `approval_reason` は古くなった結び付きの詳細を保持するもので、新たな承認の停止地点では
   ありません。内容とソースの両方が変わった場合、読み取り専用の `verify` は
   `change_notices` でソースの変更も事前に示します。生成の開始（ガードのディスパッチと
   スウォームの準備を含む）は、受け入れたソースの変更を記録して告知し、下げられた
   フェンスの下でソースの来歴の基準を取り直します。元の承認のフィンガープリント、回答、
   セッションは変わりません。既存の委任されたワーカーは、検証済みの親インテントのライブな
   フェンスに従います。後で下げたり上げたりした場合も同じです。
   成果物の欠落や、不正または構造的に不完全な Testing Contract は、実行の前に修復が
   必要です。自動で新しい承認の手続きになるわけではありません。
   `obligations.strategy` は `test_strategy` と一致しなければならず、`strategy_volume` と
   `scope_floor` の両方が空白でない義務を含まなければなりません。
   フェンスを下げても実行の来歴は必須のままです。生成が始まる前に、結び付けられない
   ソースや、ランタイム／監査の公開の失敗があれば、操作は止まります。その運用上の失敗を
   修復し、同じ承認とフェンスの設定で再試行します。人が発行した有効な break-glass の
   受領記録は、既存のソースの結び付けの例外を保ちます。
   作業ごとのフェンスを下げても、本物の最初の承認、実行可能な成果物、現在の対象／試行の
   権限の代わりにはなりません。直接の書き込みと開発者のディスパッチは、生成の開始を
   公開する前に、選択したすべての対象を検証します。それらの実行要件が満たされない間も、
   計画の記録の修復は引き続き行えます。
   複数の対象を選択するディスパッチは、開始全体にわたって生成の権限のロックを保持します。
   いずれかの対象が失敗するか、公開中にソースが変わった場合、そのディスパッチが新たに
   開始したすべての受領記録が元に戻されます。再試行では現在のソースを改めて確認します。
   元の承認と下げたフェンスの設定は変わりません。

#### 第 2 部 — 生成（手順 4～7）

4. **コードを生成する** — ディレクティブの `narration` が、このビルドについてユーザーに
   伝える 1 行で、委任の前に 1 度だけ伝えます。エンジンは計画ファイルから計画を数え、
   両方の行について 1 度だけ数えます。開始時は
   "Generating unit-2's code for 9 plan steps. This may take several minutes
   depending on project complexity. I'll show a summary when complete."、中断した
   ビルドが再開する地点では ("Picking up unit-2's code at step 5 of 9 (1-4 done)."。
   コードが書かれていて印の付いたステップが無い場合は "Picking up unit-2's code: the plan
   marks none of its 9 steps done, checking what is built.") です。計画がタスクを「Step N」の見出しの下にまとめている場合、両方の行はタスクを
   数えて見出しを名指しします（"Generating unit-2's code for the 19 tasks in 4 plan
   steps ..."、"Picking up unit-2's code at task 7 of 19, in Step 3 (tasks 1-6 done)."）。
   エージェントが自分でステップを数えることは決してありません。

   `Task` ツールで AIDLC 開発者エージェントのサブエージェント
   （`subagent_type="aidlc-developer-agent"`）へ委任します。

   **サブエージェントへ渡すコンテキスト:**
   - 先頭に `aidlc-testing-posture.ts brief --unit <unit>`、Unit を伴わない場合は
     `--stage-level` の出力をそのまま渡します。1 行目は対象マーカー
     `AIDLC-UNIT: <directive.unit>` または `AIDLC-STAGE: code-generation`、
     2 行目は現在の計画の `AIDLC-TESTING-CONTRACT: <contract_sha256>` です。
     フェンスがオンなら、ディスパッチガードは欠落・相違・古いハッシュを拒否します。
     文脈上の依存関係に追加の対象マーカーは付けません。
   - **現在のユニットのみ**の設計成果物（全ユニットではない）
   - インセプションフェーズ成果物それぞれの 1～2 行サマリーとファイルパス
     （要件サマリー、ストーリーサマリー、ドメイン設計サマリー）— 全文が必要なら
     サブエージェントが個別ファイルを読めます
   - 上記の出力に、承認内容の投影を使って含まれる現在の計画と `unit-test-instructions.md`。
     計画は末尾の `## Review` 付録を除き、タスクマーカーをリセットして空白を正規化した形、
     指示は元のバイト列そのままです。fingerprint は付録を除外するため、付録は実行する
     作業ではありません。フェンスがオンなら、それを引用する引き継ぎをディスパッチガードが
     拒否します。許可された承認後の編集の後は、その編集を承認済みと呼ばずに現在の
     ブリーフを使います
   - 同じ計画のビルドが中断していた場合、その出力はマーカー行の後に
     `## Progress before the interruption` 節も運びます。計画ファイルで印の付いた
     ステップ（印が無い場合は、ビルド開始後に名指しされたファイルが変わったステップ）、
     完了したステップがコードスパンで名指しするファイルのうちプロジェクトに無いもの
     （素のファイル名は、その名前のファイルがプロジェクト内のどこかにあれば数えます）を、
     ワーカーが判断する事実として述べ、続行するステップを示します。印も名指しされたファイルも
     何が完了したかを示さない場合は、ビルドがコードを書いたのに計画がどのステップにも印を
     付けていないことを述べ、完了した各ステップに印を付けるよう求めます。これが現れるのは、
     ビルドがすでに現在の計画と指示のままで始まっていた場合だけです（この対象、
     ステージ試行、承認済み内容の受領記録が `generation` にあり、ディスク上の内容が
     承認済みの内容であるか、承認後に編集された計画についてフェンスが下げられていた
     場合は、生成の開始がその受領記録に保持した編集後の内容である場合）。Redo、
     却下されたゲート、新しい承認、ビルド開始後に編集された計画では、ステップは新たに
     始まります。新しい承認の下でビルドが始まると、エンジンは計画ファイルのタスク
     マーカーを `[ ]` に戻します（ファイルのそれ以外は変わらず、フィンガープリントも同じ
     です）。そのため以前の印が数えられることはありません。スウォームのバッチは独自の
     継続規則を保ちます。この節はヒントであり、ゲート、レビュー、受領記録の証跡では
     決してなく、印はフィンガープリントの外にあります
   - プロジェクトワークスペースの詳細（言語、フレームワーク、規約を
     `aidlc-state.md` から）
   - 各計画ステップを順に実行し、完了時にチェックボックスを付ける指示。
     進捗の節がある場合は、その節が示す地点から始める
   - 現在のブリーフにある Testing Contract が正典です。サブエージェントは独立して
     memory を再解決せず、その契約の TDD、BDD、ATDD、テスト後書き、または
     カスタム／混合プロファイルをそのまま実行します。
   - NFR 要件、NFR 設計、および Testing Contract のカバレッジ床に由来する
     測定可能な品質目標は、入力であって提案ではありません。サブエージェントは、
     ステップを通すために、定義済みの目標（テストやビルド設定のしきい値設定を
     含む）を決して緩和・引き下げ・無効化してはならず、代わりにギャップを
     表面化させなければなりません。

   **コンテキスト予算:** 現在のユニットの設計成果物だけを渡し、全ユニット分の設計成果物は渡しません。
   インセプション成果物は全文埋め込みではなく、ファイルパス付きで要約します。
   サブエージェントはワークスペース内にすべてのコード、テストファイル、設定
   成果物を生成します。

5. **コードサマリーとソースマニフェストを生成する** — サブエージェント完了後、
   次を作成します。
   `<record>/construction/{unit-name}/code-generation/code-summary.md`
   記載内容:
   - 作成／変更したファイル
   - 主要な実装上の決定
   - テストカバレッジの要約
   - 計画からの逸脱

   ユニット（`directive.unit` がある場合）では、あわせて
   `<record>/construction/<directive.unit>/code-generation/source-manifest.json`
   も作成します。これは厳格なバージョン 1 の JSON 随伴ファイルであり、宣言された
   `produces[]` 成果物ではありません。`stage: "code-generation"`、正確なユニット名、
   そしてこのユニットが作成・変更・削除したアプリケーションソースのパス
   （シェル、スキャフォールディング、ジェネレーターが書いたファイルを含む）を
   すべて含む `writes` 配列を記録します。パスは POSIX 相対で、グロブや `..` は
   使いません。末尾の `/` は生成されたディレクトリツリーを主張します。メイン
   ワークスペースのマルチリポジトリ実行では、各エントリが記録済みの `repo` を
   名指しします。実行単位をホストするワークツリー内では、パスは選択された
   リポジトリからの相対で、`repo` は省略します。

   ステージファイルが示す形は次のとおりです。

   ```json
   {
     "stage": "code-generation",
     "unit": "u1-auth",
     "version": 1,
     "writes": [
       { "path": "src/auth/login.ts" },
       { "path": "src/auth/generated/" },
       { "repo": "repo-a", "path": "src/api/routes.ts" }
     ]
   }
   ```

   エンジンはこのスキーマを検証し、これがない終端のユニット単位レビューの記録を
   拒否します。そのバイト列と主張は `Unit Source Fingerprint` に組み込まれます。
   Guard Policy が strict の場合、新鮮なレビュー済みマニフェストのいずれにも含まれない
   ステージソースパスの変更は完了をブロックします。relaxed または off の場合、それらは
   保持され、ユニットの外で変わったファイルがその人に 1 度だけ伝えられます。

   ユニットを伴わないディレクティブ（`directive.unit` が無い場合）は
   `source-manifest.json` を書かず、そのためのユニットディレクトリも作りません。
   エンジンがマニフェストを読むのはユニットの場合だけで、ユニットを伴わない
   レビューは代わりにワークスペースのソース全体を結び付けます。その手順 5 の
   ファイルは `<record>/construction/code-generation/code-summary.md` と
   `<record>/construction/code-generation/traceability.json` です。

6. **レビューし、そのうえで完了を準備する** — ディレクティブが `reviewer`
   プロトコルモジュールを列挙している場合、`stage-protocol-reviewer.md` の
   12a 節に従い、アーキテクチャレビュアーがまず完成した作業（計画、テスト指示、
   コードサマリー、トレーサビリティ、そしてユニットでは `source-manifest.json` が
   主張するソースパス）を確認します。レビューはステージの `review_artifact` である
   `code-generation-plan` に対して記録されます。これはレビューの記録先を示すもので、
   構築前の計画のレビューではありません。ユニットでは、手順 5 のファイルが存在する
   まで、エンジンはレビューの依頼を拒否します。そのうえでユニットのコードと
   サマリー成果物を検証します。状態は編集せず、ゲート結果を
   `aidlc-orchestrate.ts` を通じて報告します。

7. **完了** — 完了メッセージと承認ゲートを提示します。

### 出力

| 成果物 | 説明 |
|--------|------|
| コード生成計画 | チェックボックス、ストーリー追跡性、手順順序付きの詳細計画 |
| コード生成質問 | 永続化された Plan Approval の質問と明示的な人間の回答 |
| ユニットテスト指示 | ユニットごとのセットアップ、スコープ限定の実行コマンド、カバレッジ、モック、テストデータ |
| コードサマリー | 作成／変更ファイル、決定、テストカバレッジ、計画からの逸脱 |
| traceability.json | 割り当てられた上流 ID をコード／テスト対象でカバーする構造化データ |
| source-manifest.json | エンジン必須の厳格な随伴帰属インデックス。ユニット作業のみ。意図的に `produces[]` には含めない |
| （アプリケーションコード） | ワークスペースルートへ書き出された全ソース、テスト、設定 |



### 承認ゲート

厳格な 2 選択肢: Approve / Request Changes。

### 注記

- **二部構成**: 計画フェーズ（手順 1～3）はユーザー対話と計画承認付きでインライン
  実行します。生成フェーズ（手順 4～7）は `Task` ツール経由で AIDLC 開発者
  エージェントのサブエージェントへ委任します。構築の大半のステージが完全に
  インラインである点と異なります。
- **開発者エージェントのサブエージェント**: コード生成はインライン実行ではなく、
  `subagent_type="aidlc-developer-agent"`（`Task` ツール経由の委任）を使います。
  構築でサブエージェントを使う唯一のステージです。AIDLC 開発者エージェントは
  `tools:` 許可リストを宣言せず、`Task` を拒否します。
- **コンテキスト予算**: サブエージェントへ渡すのは現在のユニットの設計成果物のみです。
  インセプションフェーズ成果物は 1～2 行とファイルパスで要約し、必要なものだけを
  選択的に読ませます。
- **テストファイルの必須含有**: テストファイルはコード生成計画の一部でなければ
  なりません。ステージ 3.6（ビルドとテスト）はテストを検証・拡張しますが、
  ゼロからは作成しません。
- **ソースマニフェストの強制**（ユニット作業のみ）: `source-manifest.json` はエンジンが検証するもの
  であり、Markdown の `required-sections` の対象ではありません。その厳格な
  スキーマと `Unit Source Fingerprint` が、正確パス／ディレクトリのソース主張
  すべてを拘束します。エンジンは、これが欠落または無効な場合に終端レビューを
  拒否し、Guard Policy が strict の場合は、新鮮なレビュー済み主張の和集合の外でソースが
  変更されたときにステージ完了を拒否します。
- **ユニットスコープの実行**: ユニットごとのテスト指示ファイルは、正確なテスト
  パスまたは正確なユニットフィルタを使うため、ユニット横断の実行ステージが
  ユニットごとにプロジェクト全体のスイートを再実行することはありません。
- **ブラウンフィールドへの配慮**: ブラウンフィールドでは、サブエージェントは
  複製を作らず既存ファイルをその場で変更します。

## ステージ 3.6: ビルドとテスト

### メタデータ

| 項目 | 値 |
|------|----|
| ステージ | 3.6 |
| フェーズ | 構築 |
| 実行 | ALWAYS（すべてのユニット完了後） |
| 条件 | すべてのユニット単位ステージ完了後に一度だけ常に実行します。 |
| ユニット単位 | いいえ（全ユニットに対して一度実行） |
| 主担当エージェント | AIDLC 品質エージェント |
| 支援エージェント | AIDLC 開発セキュリティ運用エージェント |
| モード | インライン |
| 入力 | 全ユニットのコード生成出力すべて |
| 出力 | `<record>/construction/build-and-test/` — ビルド手順、ビルドとテストのサマリー、テスト結果。テスト戦略によるもの（`optional_produces` に宣言）: 統合テスト手順（Standard 以上）、パフォーマンステスト手順とセキュリティテスト手順（Comprehensive で、その種類の NFR がある場合）、およびその他の条件付きテスト手順ファイル |

### 目的

ユニット横断のテスト手順を生成し、ユニットごとのユニットテスト指示を取り込んだ
うえで、シェル経由でビルドとテストを実際に実行します。このステージは**全ユニット
横断**で動作し、ユニット単位ではありません。AIDLC 品質エージェントが主導し、
AIDLC 開発セキュリティ運用エージェントがセキュリティテストの専門知識を提供します。

### 入力

- `<record>/construction/*/code-generation/code-summary.md` からの全ユニットの
  コード生成出力
- `<record>/construction/*/code-generation/unit-test-instructions.md` からの
  ユニットごとのテスト指示
- 各ユニットの `nfr-requirements/` および `nfr-design/` ディレクトリ配下の
  該当するすべての成果物
- ステージレベルまたはユニット単位の `code-generation-plan.md` にある、
  現在のすべての `## Testing Contract`。下げられた計画の再承認のフェンスで
  許可された承認後の編集と、計画の承認をオフにして構築した計画も含みます。
  どちらも人が承認したものとは記述しません。CI の義務（契約の「Run the selected
  tests in CI before merge.」の行、または memory の注記の「CI execution before
  merge」）が対象になるのは、計画が CI パイプラインを実行する場合（`aidlc-state.md` で
  `ci-pipeline` が `EXECUTE` として列挙され、`[S]` ではない場合）だけです。そうでなければ
  その理由とともに `N/A` と記録され、失敗には決してなりません。CI パイプラインがまだ先に
  ある（`[ ]`）間は、その対象は CI パイプラインが満たすものです。担当ステージ
  `ci-pipeline` と、計画の後のほうで CI パイプラインがマージ前にこれらのテストを実行する
  CI を用意するという理由とともに `N/A` と記録され、失敗には決してなりません

### 手順

1. **テスト要件を分析する** — 全ユニットのコード生成サマリーとユニットごとの
   テスト指示を読みます。NFR 要件、NFR 設計、および現在のすべての
   Testing Contract に由来する測定可能な目標について、ソースを網羅した
   インベントリを構築します。各目標について、安定した ID、ソースのパス／
   セクション、期待値、実際の値を得るためのチェック、そしてその目標を所有する
   後続の検証ステージ（あれば）を記録します。必要なテスト種別をすべて一覧化
   します。

2. **ビルド手順を生成する** — 次を作成します。
   `<record>/construction/build-and-test/build-instructions.md`:
   - 依存関係のインストール手順
   - 環境整備（環境変数、設定ファイル、ローカルサービス）
   - ビルドコマンド（コンパイル、バンドル、トランスパイル）
   - ビルド検証手順
   - よくあるビルド問題のトラブルシューティング

3-7. **追加のテスト手順を生成する** — 有効なテスト戦略を参照し、対応する
   ユニット横断の手順ファイルを生成します。
   - **Minimal**: 追加ファイルは生成しません。ユニットテストはコード生成が
     ユニットごとにカバーします。
   - **Standard**: 主要な境界とユニット横断の相互作用について
     `integration-test-instructions.md` を生成します。
   - **Comprehensive**: 統合テスト手順に加え、パフォーマンス NFR がある場合は
     `performance-test-instructions.md` を、セキュリティ NFR がある場合は
     `security-test-instructions.md` を生成します。
   - いずれの戦略でも、プロジェクトの文脈が求める場合は、契約、エンドツーエンド、
     アクセシビリティ、その他の名前付き手順ファイルを追加します。

   すべてのファイルは `<record>/construction/build-and-test/` に置きます。
   各ファイルには、フレームワークのセットアップ、実行コマンドとフィルタ、
   カバレッジ目標、テストデータまたは環境の準備を含めます。

8. **ビルドとテストのサマリーを生成する** — 次を作成します。
   `<record>/construction/build-and-test/build-and-test-summary.md`:
   - 全体のビルド状態と前提条件
   - テスト種別インベントリ（生成したテスト種別）
   - プロジェクトと各ユニットのカバレッジ期待値
   - Target ID、Source、Expected、Actual、Evidence、Owning Stage、Verdict を
     持つ目標検証マトリクス（Target Verification Matrix）
   - 該当する目標は `Pending` で開始します。`N/A` が有効なのは、ソースを網羅した
     インベントリが該当する測定可能な目標を見つけられなかった場合か、計画によってここでは
     該当しなくなる目標（CI パイプラインを実行しない、またはそれがまだ先にある計画の CI の
     義務）の場合だけです
   - 準備状況の評価（ビルド準備、テスト準備、デプロイ準備）
   - 既知の制限や未解決事項

9. **ビルドとテストを実行する** — 手順ファイルに記載したビルドおよびテスト
    コマンドを**シェル経由で**実行を試みます。

    a. **ビルド**: ビルド手順からビルドコマンドをシェルで実行し、出力を捕捉します。
    b. **ユニットテスト**: ステージレベルの
       `<record>/construction/code-generation/unit-test-instructions.md`（存在する場合。
       Express を含む）と各ユニットの
       `code-generation/unit-test-instructions.md` からコマンドを収集し、同一の
       コマンドを重複排除して、異なるコマンドごとに一度だけ実行します。コマンドは
       ユニットにスコープされているはずです。プロジェクト全体を対象とするコマンドが
       含まれる場合は一度だけ実行し、ユニットごとには実行しません。二重計上せずに
       ユニットごとの合否を報告します。
       プロジェクト全体にカバレッジの下限が設定されている場合、プロジェクトの
       フルスイートのカバレッジコマンドを、それ自身のカバレッジ設定で一度だけ実行します
       （複数リポジトリのインテントでは、下限が適用される各リポジトリで一度ずつ実行し、
       その行の Evidence にリポジトリを名指しします）。その実行が、目標検証マトリクスに
       あるプロジェクト全体の下限の行の証拠になります。あるリポジトリの実行が、別の
       リポジトリの下限の証拠になることは決してありません。ユニットにスコープされた
       コマンドは、新しいファイルのものでも承認済みのファイルのものでも、その出力が、
       選択したテストがすべて合格し、非ゼロ終了の唯一の原因がプロジェクト全体の下限の
       しきい値（ランナーがファイルごとに確認する場合でも、測定対象のソース全体に対する
       1 つのしきい値）であることを示していれば、合格として数え、その終了コードと理由を
       test-results.md に記録します。これが当てはまるのは、その終了がコマンドの後続の
       ステップを何も止めなかった場合だけです。後のステップがそのために実行されなかった
       場合（`… && <lint>` のように連結されたもの、コマンドが呼び出すスクリプトや
       ライフサイクルフックの中のもの、ビルドツールの後続のタスクやフェーズ。コマンドが
       実行するスクリプト、フック、タスクやフェーズの定義と、その出力から判断します）、
       そのコマンドは免除されず、その非ゼロ終了は失敗したコマンドです。それ以外の非ゼロ
       終了（1 つのパスやユニットに設定されたしきい値を含む）は失敗です。1 つのユニットに
       設定された目標には、ユニットにスコープを限定した独自の証拠が必要です。
    c. **統合テスト**（該当する場合）: 統合テストコマンドを実行し、結果を捕捉します。
    d. **その他の該当するチェック**: パフォーマンス、セキュリティ、契約、E2E、
       アクセシビリティ、その他の生成済み手順ファイルにある該当するコマンドを
       すべて実行します。先送りできるのは、デプロイ済みまたは本番相当の環境を
       必要とし、かつ現在の実行計画に所有する検証ステージが名指しされている
       チェックだけです。そのステージと期待される証拠パスを記録します。その目標は
       `Unverified` のままであり、このステージを成功にすることはできません。
       予定された所有ステージがなければ、単に `Unverified` です。
    e. **最終化して結果を報告する**: あらゆる終了経路で、次を作成または更新します。
       `<record>/construction/build-and-test/test-results.md` と
       `build-and-test-summary.md`
       - ビルド状態（成功／失敗＋出力）
       - テスト結果（合計、成功、失敗、スキップ）
       - 失敗の詳細（テスト名、アサーション、スタックトレース）
       - カバレッジレポート（テストフレームワークが対応する場合）
       - 最終化された目標検証マトリクス。該当するすべての目標が、実際の値、証拠、
         所有ステージ、そして最終的な `Met`、`Not Met`、`Unverified` のいずれかの
         判定を持ちます。手順 9 の後に `Pending` の判定は残りません。
       - `## Loop-Back Log`（失敗エスカレーションはしごの段 3 または段 4 が
         ループバックを発火させた場合のみ）: 試行ごとに 1 つの
         `### Loop-back N -- <ISO timestamp>` エントリ（診断／根本原因ステージ／
         計画された修正／推定影響）。追記専用で、再実行後も残ります
         （ループバック再入時は Modify であり、決して Redo ではありません）。

    **失敗エスカレーションはしご:** ビルドまたはテストのコマンドが失敗した場合、
    あるいは該当する目標が `Not Met` または `Unverified` の場合、このステージは
    失敗しています。どの失敗種別でも、同じはしごへ入る前にマトリクスとサマリーを
    最終化します。目標の引き下げ・緩和・無効化は、決して許容される修正では
    ありません。

    1. **ステージ内修正（最大 2 回）** — このステージ自身の担当範囲内にある
       根本原因（テスト設定、ビルドスクリプト、環境整備、または実行可能な目標
       チェック）向け: 証拠を読み、失敗している設定や足場を特定し、修正を適用し、
       失敗したステップを再実行し、目標マトリクスを更新します。
    2. **分類して影響を見積もる** — ステージ内の試行を使い果たしたとき、または
       診断が上流を指すとき: 根本原因が生成されたソースまたはテストコードに
       あるのか — 欠陥の大小を問わず — あるいはコード生成のアプローチ選択
       （ライブラリ／バージョン、コンテナイメージ、インスタンスタイプ、
       アルゴリズム、フラグ）にあるのかを判断します。交換可能な次元での修正を
       見つけ、その影響（工数、金銭的コスト、リスク）を必ず見積もります。
       影響を見積もっていない工数の思い込みで、実行可能な経路をスコープ外と
       宣言してはなりません。
    3. **自律的な有界ループバック** — `Construction Autonomy Mode:
       autonomous` であり、影響見積もり済みの修正が存在し、`## Loop-Back Log`
       のエントリが 3 件未満の場合: 診断＋影響見積もり済み修正を記録し、
       修正が名指しするユニットについて（原因がすべてのユニットにまたがる場合だけ
       全ユニットについて）エンジン経由でコード生成を開き直し、ループバックプロトコル
       モジュール（`aidlc-common/protocols/stage-protocol-loopback.md`）の
       「Build-and-Test failure loop-back」に従った確定認識ルートで前方へ
       リプレイします。失敗した実行のゲートは提示されず、有効な学びの手続きは
       最終的に成功する実行へ委ねられます。learnings モジュールがなければ日誌も手続きも実施しません。
    4. **停止して確認（halt-and-ask）** — ゲート付き／未設定モード、上限の
       使い果たし、または特定可能な修正がない場合: 失敗を記録し、ループバック
       プロトコルモジュール
       （`aidlc-common/protocols/stage-protocol-loopback.md`）の
       halt-and-ask 質問を提示します — 候補の修正が存在する場合は影響見積もり
       付きの 3 選択肢バリアント（Retry with fix [推定影響] / Accept failure /
       Abort）、段 2 で修正が見つからなかった場合は修正なしの 2 選択肢
       バリアント（Accept failure / Abort）です。

    **ループバックのリプレイ経路:** 構築のチェックポイントがオフで、コード生成が
    ユニットのライフサイクル受領記録を一度も使用していない場合、保持された成果物は
    全カバー済みの `gate: true` ファストパスを取れます。そのゲートの前に、計画された
    修正と決定論的な Modify/Keep の判断を適用します。チェックポイントがオンの場合
    （最初のユニットから受領記録が必要）、またはライフサイクル行が 1 つでも
    存在すると、受領記録モードは固定化され、ジャンプはユニット単位の作業を
    再発行します。`unit start` / `unit complete` を再発行し、対象ユニットへ
    Modify を、残りへ Keep を適用し、宣言されたレビュアーをユニットごとに
    実行します。開き直しはそれらのユニットの以前のレビューを無効化するため、
    どちらの経路も、確定／承認ゲートの前に、開き直したすべてのユニットについて
    現在試行の新しい `REVIEW_COMPLETED` を必ず記録しなければなりません。修正が
    名指ししないユニットは、作業と承認を保ちます。unit-major の下ではスウォームは
    決して発火せず、リプレイは直列のユニット単位ウォークに従います。改訂した
    コード生成の計画には、引き続き人の新しい計画の承認が必要です。

    リプレイは新しいステージ試行としてコード生成計画を修復するため、以前の承認は適用されません。
    差分を Loop-Back Log に記録し、修復した計画を書きます。そのうえで `next` が、
    修正コードを生成する前に、その人に計画の承認を改めて求めます。ゲートの「Retry with fix」はジャンプの許可であり、
    改訂した計画そのものの承認ではありません。

    **スウォームの安価な経路:** ジャンプは新しい正確なステージ試行の
    `Run floor` 境界トークンを生成するため、古い収束行はカウントされません。
    古い worktree／ブランチを保留または破棄し、新しい `prepare` を実行します。`finalize`
    は現在の prepare スタンプを要求するため、それらを新しい試行へ引き継ぐことは
    できません。
    保存された中止結果または doctor の `restore_operation` がある場合、それは保留した
    ファイルを別に回復するもので、現在試行の権限は回復しません。列挙された各引数を
    そのまま argv として渡してその `worktree` エンジンルートを呼び出し、シェルの
    コマンドに連結することは決してしません。ヒントと描画されたコマンドは人向けの
    表示用テキストにすぎず、描画のエラーで型付きの操作が取り除かれることはありません。
    証跡のみの試行には、復元の操作も復元するファイルもありません。まず `check` を実行します。グリーンなユニットはビルダーの
    ターンをスキップできますが、`finalize --claimed` へ入る前に、新しい
    worktree 内で終端の現在試行レビュアー受領記録が依然として必要です。
    `finalize` は、その受領記録の現在の成果物フィンガープリントと試行スタンプの
    両方を検証します。

    単一ステージ実行（`--single`）は段 2 で停止します — 移動すべき
    メインワークフローの位置が存在しないためです。影響見積もり済みの選択肢は
    記録され、その実行の分離実行サマリーで提示されます。

    **成功時:** 成功の準備状況判定には、すべてのコマンドが成功し、該当する
    すべての目標が `Met` であること — または該当する目標がない場合は説明付きの
    単一の `N/A` 行 — が必要です。

10. **ユニット横断の最終カバレッジゲート** — `aidlc engine sensor-traceability --stage build-and-test`
    を実行します。これは `requirements.md` のすべての `FR` と `NFR`（下位要件を持つ要件は
    その `FR{n}.{m}` ID で）と、`stories.md` のすべての `AC`（User Stories が実行された場合）を
    報告し、それぞれ、ステージレベルまたはユニット単位のコード生成の `traceability.json` が、
    存在する対象ファイルとともに `OK` でカバーしていれば構築済みとします。下位要件を持つ
    要件は、各ユニットがそれ自身の下位要件（その NFR 要件が書いた `NFR1.x`。`NFR1` だけの
    行はそれらをカバーしません）を構築したときに構築済みです。そうでなければ、それ自身の
    行によって、または User Stories が実行された場合は、User Stories がそれを追跡した
    ストーリーのすべての受け入れ基準を通して構築済みになります。何も構築しないものは、
    それを追跡した最新のステージ（User Stories、NFR 要件、次にコード生成）が、そこでそれを
    列挙するすべての表で理由付きの `N/A` を付けていれば決着済みです。理由の無い `N/A` は
    決着済みではありません。その出力から、判定、ID ごとのカバレッジ、カバーされていない
    すべての ID を含む `cross-unit-traceability.md` を書きます。カバーされていない ID は、
    承認ゲートで示される所見です。

11. **完了を準備する** — ビルド／テストの証拠を検証します。ステージや
    フェーズの状態は編集せず、報告されたゲート結果が遷移を所有します。

12. **完了** — 完了メッセージと承認ゲートを提示します。

### 出力

| 成果物 | 説明 | 条件 |
|--------|------|------|
| ビルド手順 | 依存関係インストール、環境整備、ビルドコマンド、トラブルシューティング | 常時 |
| 統合テスト手順 | 前提条件、ユニット横断テスト、外部依存、データ準備 | Standard／Comprehensive |
| パフォーマンステスト手順 | 負荷テスト、NFR シナリオ、ベースライン、ストレス／ソーク | NFR パフォーマンスがある場合 |
| セキュリティテスト手順 | SAST／DAST、認証テスト、インジェクションテスト、コンプライアンス | NFR セキュリティがある場合 |
| 契約テスト手順 | コンシューマ駆動契約、スキーマ検証、API 互換 | マイクロサービスの場合 |
| エンドツーエンドテスト手順 | ブラウザ自動化、ユーザージャーニー、クロスブラウザ | UI 主導の場合 |
| アクセシビリティテスト手順 | WCAG 準拠、スクリーンリーダー、キーボード操作 | ユーザー向け UI の場合 |
| ビルドとテストのサマリー | 全体状態、テストインベントリ、カバレッジ、準備状況評価 | 常時 |
| テスト結果 | 実際のビルド／テスト実行結果、合否、カバレッジ | 常時 |
| ユニット横断トレーサビリティ | すべてのユニットにわたる FR／NFR／AC のカバレッジ、判定、カバーされていない ID | 常時 |



### 承認ゲート

厳格な 2 選択肢: Approve / Request Changes。

### 注記

- **実際のシェル実行**: このステージはテスト手順を文書化するだけでなく、シェル経由で
  ビルドとテストコマンドを実際に実行し、実結果を捕捉します。コードベースに対して
  実コマンドを実行する数少ないステージのひとつです。
- **品質目標の証拠**: ソースを網羅したマトリクスは、あらゆる終了経路で最終化
  されます。デプロイ環境が必要なチェックは後続の所有ステージを名指しできますが、
  `Unverified` のままです。`Not Met` と `Unverified` はどちらも失敗のはしごへ
  入ります。
- **失敗エスカレーションはしご**: ステージ内修正は 2 回までに制限されます。
  根本原因が上流の生成コードまたはコード生成のアプローチ選択にある場合、この
  ステージは修正を分類してその影響を見積もり、コード生成への有界な自律
  ループバック（最大 3 回、test-results.md の追記専用 `## Loop-Back Log` で
  カウント）を実行するか、影響見積もり付きの halt-and-ask 質問を提示します。
  ループバックプロトコルモジュール
  （`aidlc-common/protocols/stage-protocol-loopback.md`）の
  「Build-and-Test failure loop-back」を参照してください。再入は確定認識型で、
  `plan_approval` がオンの間は修復された計画について改めて計画の承認を求め（以前の承認は
  前の試行に属します）、該当するすべてのコード生成ユニットが現在試行の新しい
  レビューを得るまでゲートに到達できません。
- **条件付きテスト種別**: パフォーマンステスト、セキュリティテスト、契約テスト、
  エンドツーエンドテスト、アクセシビリティテストは、関連条件が満たされる場合のみ
  生成します（NFR 要件の存在、マイクロサービスアーキテクチャ、UI 主導アプリ、
  ユーザー向けインターフェース）。
- **ユニット横断スコープ**: ユニット単位のステージ 3.1～3.5 と異なり、ビルドとテストは
  すべてのユニットが生成したコード全体に対して一度実行します。個別ユニットではなく、
  統合されたコードベースを検証します。
- **フェーズ完了**: このステージ（該当すれば 3.7 とともに）が構築フェーズの終わりを
  示します。最終の承認済み報告により、エンジンが構築を完了としてマークし、
  運用への遷移を原子的に行います。

## ステージ 3.7: CI パイプライン

### メタデータ

| 項目 | 値 |
|------|----|
| ステージ | 3.7 |
| フェーズ | 構築 |
| 実行 | CONDITIONAL（十分な CI が既にある場合はスキップ） |
| 条件 | CI パイプラインの作成または大幅な変更が必要な場合に実行 |
| ユニット単位 | いいえ（全ユニットに対して一度実行） |
| 主担当エージェント | AIDLC パイプライン・デプロイエージェント |
| 支援エージェント | （なし） |
| モード | インライン |
| 入力 | ステージ 3.5 のコード生成出力、ステージ 3.6 のビルド／テスト結果 |
| 出力 | `<record>/construction/ci-pipeline/` — CI 設定、品質ゲート、CI パイプライン質問 |

### 目的

品質ゲート、成果物管理、ビルド／テスト自動化を備えた CI（継続的インテグレーション）
パイプラインを設定します。AIDLC パイプライン・デプロイエージェントが主導し、
支援エージェントはありません。

### 入力

- `<record>/construction/build-and-test/` からのビルド／テスト結果
- `<record>/construction/infrastructure-design/` からのインフラストラクチャ設計
  （存在する場合）
- 既存の CI 設定のためのワークスペースプロファイル

### 手順

1. **先行コンテキストを読み込む** — ビルド／テスト結果、インフラストラクチャ設計
   （存在する場合）、既存 CI 設定のためのワークスペースプロファイルを読みます。

2. **明確化の質問を生成する** — 次の質問を含むファイルを作成します。
   `<record>/construction/ci-pipeline/ci-pipeline-questions.md`
   - 使用中の CI ツールは何か（CodePipeline、CodeBuild、GitHub Actions、
     Jenkins）？
   - ブランチ戦略は何か？
   - マージ前に必要な品質ゲートは何か？
   - 使用する成果物リポジトリは何か（ECR、CodeArtifact、S3）？

   `stage-protocol.md` の質問フローに従います。

3. **回答を収集して分析する** — 既存インフラとチーム能力に対して CI の選択を検証します。

4. **成果物を生成する** — CI パイプライン設定（buildspec.yml、ワークフロー YAML、
   または同等）、品質ゲート定義、成果物リポジトリ設定を作成します。

5. **フェーズ境界検証** — 構築から運用への検証チェックを実行します。
   - アーキテクチャからコード、テストへの整合
   - すべてのコードが設計へ追跡できること
   - 受け入れ基準に対するテストカバレッジ
   - 結果を `<record>/verification/phase-check-construction.md` へ書き出す

6. **完了を準備する** — CI と境界の成果物を検証します。ステージや
   フェーズの状態は編集せず、報告されたゲート結果が遷移を所有します。

7. **完了** — 完了メッセージと承認ゲートを提示します。

### 出力

| 成果物 | 説明 |
|--------|------|
| CI 設定 | CI パイプライン設定（ビルド仕様、ワークフロー YAML など） |
| 品質ゲート | マージ／昇格のための品質ゲート定義 |
| CI パイプライン質問 | 回答付きの明確化の質問 |



### 承認ゲート

厳格な 2 選択肢: Approve / Request Changes。

### 注記

- **フェーズ境界検証**: これは構築フェーズの最終ステージです。構築から運用への
  フェーズ境界検証チェック（`stage-protocol-governance.md` のセクション 13）を実行し、
  アーキテクチャがコードへ、コードがテストへ追跡できることを検証します。結果は
  `<record>/verification/phase-check-construction.md` に書き出します。
- **条件付き実行**: プロジェクトに十分な CI パイプラインが既にある場合、この
  ステージはスキップされます。計画（スコープと、その人が行うスキップや追加）が到達するかどうかを
  決め、ステージはそれでも自身の条件を適用します。デリバリー計画が計画するのは Bolt であり、
  ステージではありません。
- **ユニット後実行**: ステージ 3.6 と同様、すべてのユニット単位作業の完了後に
  一度実行し、ユニット単位ではありません。

## フェーズのまとめ

構築フェーズは、段階的な構築フローにより、インセプションの設計を動作する
ソフトウェアへ変換します。

**ユニット単位ステージ（3.1～3.5）:**
- 3.1 機能設計 — ビジネスロジック、ドメインモデル、ルール（アーキテクト主導）
- 3.2 NFR 要件 — パフォーマンス、セキュリティ、スケーラビリティ、信頼性、
  可観測性、技術スタック（アーキテクト主導）
- 3.3 NFR 設計 — NFR カテゴリ向けの具体パターン（アーキテクト主導）
- 3.4 インフラストラクチャ設計 — デプロイ、サービス、監視、CI／CD
  （AWS プラットフォーム主導）
- 3.5 コード生成 — 計画＋生成の二部構成をサブエージェント経由（開発者主導）

**ユニット後ステージ（3.6～3.7）:**
- 3.6 ビルドとテスト — 手順生成＋失敗診断付きの実際のシェル実行（品質主導）
- 3.7 CI パイプライン — CI 設定＋フェーズ境界検証（パイプライン・デプロイ主導）

**主な特性:**
- ステージ 3.1～3.4 は CONDITIONAL、3.5～3.6 はそれらを含むすべてのスコープで実行（infra はどちらも持たない）、3.7 は CONDITIONAL
- どの条件付きステージに到達するかは、デリバリー計画ではなく計画（スコープと、その人が行うスキップや追加）から決まる。各ステージはそれでも自身の条件を適用する
- ソースを生成する新しいソロのユニットのワークフローは、既定で unit-major・直列実行・
  検証済みユニットチェックポイント。明示的な反復の選択と、既存の従来・設計のみ・
  ユニットなし・チーム所有の経路は保持する
- NFR 成果物は上流リファレンスより粒度を拡張（要件 6 つの Markdown ファイル、設計 6 つ。それぞれ
  `traceability.json` 付き）
- インフラストラクチャ設計は 3 つの Markdown 成果物（監視と CI／CD の専用ファイルを含む）と
  `traceability.json` を生成
- コード生成はコンテキスト予算制御付きで AIDLC 開発者エージェントのサブエージェントを使用
- ビルドとテストは実コマンド実行と自動失敗診断を行う
- CI パイプラインは運用へ移行する前にフェーズ境界検証を含む

**上流リファレンスからの意図的な逸脱:**
- NFR 要件: 6 つの Markdown ファイルと traceability.json（リファレンスの 2 から拡張）
- NFR 設計: 論理コンポーネントを含む 6 つの Markdown ファイルと traceability.json
  （リファレンスの 2 から拡張）
- インフラストラクチャ設計: 3 つの Markdown ファイルと traceability.json。統合された
  `infrastructure-specification.md`（デプロイ＋サービス＋共有）に加え、専用の
  `monitoring-design.md` と `cicd-pipeline.md`
- 計画／質問ファイルをステージ成果物と同じ場所に配置
