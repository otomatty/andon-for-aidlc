# Kiro IDE フックペイロード — 実測リファレンス

Kiro IDE がコマンドフックへコンテキストを渡す方法です。0.12-main（標準入力・引数配列・環境全体をダンプするプローブ用 `.kiro.hook` ファイル）、1.0.165（プローブ用 v2 フック JSON ファイル。上流 #543/#555）、1.0.242（Windows 上の UserPromptSubmit / PreToolUse プローブ）でライブ実測しました。これは `harness/kiro-ide/` アダプターの根拠となる証拠であり、CLI ハーネス（`harness/kiro/`）は別の kiro-cli 形の stdin 機構を使います。

秘匿処理済みのネイティブ Windows の前後キャプチャは
[`research/kiro-windows-output-encoding/`](research/kiro-windows-output-encoding/) に保管されています。

## チャネルは IDE 世代間で変わった

| | Kiro IDE 0.12 | Kiro IDE 1.x（>= 1.0.1xx） |
|---|---|---|
| フック登録 | `.kiro/hooks/*.kiro.hook`（`{"version":"1.0.0","when":{...},"then":{...}}`） | `.kiro/hooks/*.json` v2 スキーマ（`{"version":"v1","hooks":[{name,trigger,matcher,action}]}`、PascalCase トリガー）。レガシーの `.kiro.hook` ファイルは**何の表示もなく無効** — 決して実行されない。 |
| コンテキストチャネル | 環境変数 `USER_PROMPT`（JSON 文字列） | **stdin**（JSON。書き込まれてクローズされる）。`USER_PROMPT` は空で届く。 |
| stdin の挙動 | 開かれるが書き込みもクローズもされない — 素の読み取りはハングする | 書き込まれてクローズされる — 読み取りは速やかに解決する |
| フィールド命名 | camelCase: `{ toolName, toolArgs, toolResult, toolSuccess }` | snake_case: `{ session_id, hook_event_name, cwd, tool_name, tool_input, tool_response }` — **成功フラグなし** |

1.0.165 でライブ捕捉した PostToolUse の、フィールドそのままの例:

```json
{"session_id":"sess_…","hook_event_name":"PostToolUse","cwd":"/path/to/project","tool_name":"execute_bash","tool_input":{},"tool_response":"Output:\n…\nExit Code: 0"}
```

アダプターは、空でない `USER_PROMPT` を即座に使います（0.12 チャネル。その stdin は決してクローズされません）。この変数が空の場合は、Kiro がクローズするまで 1.x チャネルの stdin を読むので、Kiro が遅れて渡したメッセージ（混み合ったマシン）も丸ごと読まれます。60 秒の安全上限（Kiro 自身のコマンドフックの既定の予算）が終わらせるのは、決してクローズされないチャネルだけです。正の `AIDLC_IDE_STDIN_TIMEOUT_MS` の値が、診断やテストのためにこれをミリ秒単位で上書きします。どちらのチャネルにも何もないまま上限が過ぎると、`record-human-turn` はターンもメッセージも記録しません（本人が何も入力しなかったと記録に残すものはなく、Kiro 自身のものだったかもしれないメッセージに存在の印を発行することもありません）。`kiro-adapter.drops` の行が `doctor` のためにそれを名指しし、エージェントは本人に伝える 1 行を受け取ります。「The last message in this chat did not reach AI-DLC's record, so if it answered one of its questions, you will be asked that question again」（誰が送ったものでも正しい文です。ペイロードがなければ、それが本人のものか Kiro が作ったものかは誰にもわかりません）。両方のフィールド綴りが受け入れられます。取得はペイロード依存のターゲットに限定されます。`plan-approval-guard`、`review-freeze`、`state-transition-guard`、2 つのターミナルコマンドターゲット、それぞれの最新の `session_id` のための `session-start` と `continue-workflow`、そして承認応答そのものを受け取る `record-human-turn` です。それ以外のすべてのターゲットはどちらのチャネルにも触れず、ゼロレイテンシの経路を保ちます。

レガシーの環境変数名は生のユーザーテキストを意味しません。実測された 0.12 の契約は camelCase の JSON です。したがって `prompt` フィールドを持たない promptSubmit ペイロードはレガシーのターンクロックを進めるだけで、ターミナルユーティリティは後から、対応する preToolUse イベントの `toolArgs.command` から認識されます。生の `/aidlc ...` テキストは、それを直接公開するより新しい Kiro 世代では引き続き受け入れられますが、0.12 互換性の主張ではありません。

`VSCODE_IPC_HOOK` / `VSCODE_PID` も IDE のフックプロセスには存在します（CLI にはありません）。エージェント自身のシェルコマンドはどちらも持たず、代わりに `TERM_PROGRAM=kiro` と `KIRO_SESSION_ID` を持ちます（Kiro IDE 1.2.37 で計測。#2167）。エンジンの「answer was not recorded」の行とフック無効時の手順は、これによって Kiro IDE の中にいることを知ります。別の `TERM_PROGRAM`（VS Code のターミナルでの Kiro CLI は `vscode`）は、VS Code 自身の `VSCODE_PID` が並んでいても Kiro IDE を除外します。レガシーの Plan Approval は、これら実測されたホストインスタンスの値をランタイムのセッション同一性へハッシュ化するため、1 つのワークスペースで開いた 2 つの IDE ウィンドウがチャレンジ／レスポンスのファイルを共有することはありません。その他のアダプターのルーティングは、引き続き上記のペイロードチャネルをキーにします。

## イベント別キャプチャ

結果の文言は両チャネルで同一です（0.12 では `toolResult`、1.x では `tool_response`）。

| イベント | ツール名 | ツール入力 | 結果の文言 | 復元可能か |
|-------|-----------|-------------|--------------|--------------|
| UserPromptSubmit（1.0.242） | n/a | `{prompt:""}` | n/a | prompt: 不可。session id: 可 |
| UserPromptSubmit（1.2.37、Workflows on） | n/a | 本人のメッセージにも Kiro 自身のメッセージにも `{cwd, hook_event_name, prompt, session_id}`。Kiro 自身のものは、ワークフロー作成者の `<original_user_request>` ブリーフ（チャットの session_id）、各ステップのブリーフ（ステップ自身の session_id。環境変数 `KIRO_SESSION_ID` はチャットのまま）、`A workflow you launched (...) completed. ...` の完了通知（チャットの session_id。Kiro の記録は `syntheticUserMessageReason: agent-initiated-prompt` と印を付ける） | n/a | 誰が送ったか: 記録または文から（後述） |
| PreToolUse（シェル、1.0.242） | `execute_pwsh` | `{command,cwd,run_in_background,timeout}` | n/a | コマンド: 可 |
| PostToolUse（書き込み）— 作成 | `fs_write` | `{}`（空） | `Created the <PATH> file.` | パス: 結果の文言からのみ |
| PostToolUse（書き込み）— 編集 | `str_replace` | `{}`（空） | `Replaced text in <PATH>` | パス: 結果の文言からのみ |
| PostToolUse（書き込み）— 追記 | `fs_append` | `{}`（空） | `Appended the text to the <PATH> file.` | パス: 結果の文言からのみ |
| PostToolUse（シェル） | `execute_bash` | `{}`（空） | `Output:\n<stdout>\n\nExit Code: 0` | コマンド: 復元**不可**（stdout のみ） |

UserPromptSubmit が入力されたフェンスや Guard Policy の切り替えを運ぶとき、アダプターはそれをコアの human-turn フックへ転送します。フックはペイロードのセッションでメッセージを記録し、何も適用しません。エージェントが `next` の名指す設定コマンドを実行し、シェルの設定コマンドはアダプター内では実行しません。
本人の行が `/aidlc` だけの場合、またはこのチャットのワークフローにまだ記録がないときに `/aidlc` の後に言葉だけ（エンジンが受け取るフラグや動詞なし）が続く場合、`verb-intercept` メンバーは最初の手順 `engine orchestrate next` を名指しする文脈の行を 1 つ出力します。そうすることで、aidlc スキルを自身の判断でしか読み込まない Kiro の Default エージェントが、その行に自分で答えるのではなく AI-DLC を始めます。エンジンの `next` は記録された行を読みます（takePersonsOwnLine）。プランの名前だけを入力した場合（`/aidlc bugfix`）も同じ行を受け取りますが、名指すのは `engine orchestrate next <plan>` で、これは aidlc エージェントのスキルがそれに対して取る手順です。裸の `next` は単独で名指されたプランを読まないからです。その手順は作業の目的を尋ねます。メンバー自身が実行するユーティリティ（`/aidlc --status`）、フラグ付きの行、`/aidlc-<runner>` の入力、普通の言葉、そしてチャットのワークフローが記録済みのときに入力された言葉（その場合、裸の `next` は作業の継続となり、ステージの未回答の質問への普通の返答を除いて、記録された行を読みません。aidlc エージェントのスキルが言葉を自分で渡します）には、そのような行は出ません。
Kiro が作ったプロンプトは本人のターンではありません。Kiro 自身のチャット記録（`~/.kiro/sessions/<workspace>/<session>/messages.jsonl`。ペイロードのセッション）が `_meta.kiro.syntheticUserMessageReason` で印を付けたメッセージ、または Kiro が印を付けない Workflows のブリーフで、その冒頭の文を丸ごと先頭に固定して照合したものは、`origin: {kind: "host"}` 付きで転送されます。コアフックは `HOST_TURN` を記録し、本人のものは何も記録しません。アダプターはそれに対してセッションを開始せず、チャットを覚えず、ターンも開きません。チャットのターンが閉じたあとなら、それはターミナルコマンドの同一ターンの保持を終わらせます（後述）。記録が `_meta.kiro.userMessageTag` を付けたメッセージは、その言葉が何であれ本人のものです。未知のものもすべて本人のものとして扱い、チャットの `KIRO_SESSION_ID` と異なるペイロードの `session_id` も、それだけでは同様です（その変数はステップのプロンプトでもチャットを名指していたので、メッセージがどのタブから来たかを名指さないことがあります）。
IDE 1.0.242 のような空プロンプトのビルドでは、ターンごとの `prompt-empty` マーカーにより、アダプターは引き下げるシェルコマンドを拒否します（終了コード 2、理由は stderr）。環境変数を前置した呼び出しや、要約確認の `off` も対象です。また `verb-intercept` は、そのビルドでは進行中の作業を引き下げられないことを説明し、プロンプトに対応した IDE へ更新するか、既定値の低いスコープから新しい作業を始めるよう案内する機能の注記を、セッションごとに一度出します。要約確認と計画承認については、どちらの注記も、作業の実行中でも使える本人のプロジェクト全体のターミナルコマンド `<invoke> config flags --bypass AIDLC_DISABLE_SUMMARY_CONFIRMATION --local --yes` または `--bypass AIDLC_DISABLE_PLAN_APPROVAL_GUARD` を示します（`--clear-bypass` で元に戻せます）。`strict` への引き上げや、フェンスや要約確認を `on` にすることは引き続き可能です。
空のプロンプトを転送する前に、アダプターは単独の廃止済み `Change Control: relaxed|off` 行を、値と出所のラベルを変えず、ポリシーの監査行も出さずに、自動で `Guard Policy` へ改名します。一部のビルドはコアフックの出力を捨てるので、移行の注記はアダプター自身が出力します。

### 重要な制約

1. **PostToolUse の書き込み／シェルのキャプチャは、両チャネルともツール入力が空**です。したがって書き込まれたパスは結果の文言からパースする必要があり、シェルコマンドは存在しません（stdout と終了コードのみ）。これは IDE の普遍的なルールではなく、配送の仕方も世代間で一様ではありません。後期の 1.x ビルドは一部の PreToolUse 入力と委譲入力を埋めます（#543）。課題 #763 は、Kiro IDE 1.0.309 が PreToolUse のサブエージェントディスパッチに `prompt` と `explanation` を、シェル／書き込みのマッチャーに `command`、`cwd`、`run_in_background`、`timeout` を、さらに PostToolUse の入力も埋めたと報告しています。この 1.0.309 の観測は報告されたものであり、本リポジトリで計測したものではありません。計測に基づく土台は、上記で述べた 0.12、1.0.165、1.0.242 のキャプチャと、後述の「ツール呼び出しのブロック」にある 1.1.14 の PreToolUse のキャプチャです。
2. **1.x は成功フラグを運びません。** 整形式の書き込みを監査から落とすのは 0.12 チャネルの明示的なブール値 `toolSuccess: false` だけです（#417）。フィールドが無い 1.x ペイロードはパス検査へフォールスルーします。このチャネルは構造的に失敗を報告できないため、1.x での失敗した書き込みはエラー文言としてのみ届きます。そこでアダプターは記録前に分類します。失敗と**認識できた**文言は `hookDebug`（フックデバッグが有効なときだけ書かれます）へ送られます。監査すべき成果物が存在しない以上、転送しないことは decay ではなく正しい振る舞いです。認識できない文言は引き続き可視のフックドロップを記録します。こちらが本当の機能低下を示すケースです。レガシーの 0.12 チャネルでは、明示的な `toolSuccess: true` が引き続き権威を持ち、失敗文言の推論をバイパスします。存在する非 null のペイロードフィールドが実行時型として不正な場合は malformed として扱われます。助言的フックは正常終了し、可視のドロップを記録し、監査イベントもサブエージェントイベントも転送しません。`null` はフィールド不在と同様に扱われ、チャネル既存の absent-value 契約に一致します。
3. **結果の文言中のパスはワークスペース相対**ですが、コアフックは絶対のレコードルートと比較するため、アダプターは転送前に絶対パスへ解決します。

### ツール呼び出しのブロック（PreToolUse）

Kiro IDE 1.1.14（Windows）で、`execute_pwsh` と `fs_write` にプローブ用フックを付けてライブ計測しました。

| フックの出力 | ツール呼び出し | モデルが受け取るもの |
|-------------|-----------|-------------------------|
| 理由を stderr、終了コード 2 | Kiro の承認カードより前にブロックされる | stderr のテキスト。ツールが実行されなかったことを伝える Kiro の「Tool ... was intercepted by PreToolUse hooks before execution」というメッセージの中に入る |
| 理由を stdout、終了コード 2 | 承認カードのあとに実行される | フックからは何も届かない |
| stdout と stderr、終了コード 2 | ブロックされる | stderr のテキストだけ |
| 理由を stderr、終了コード 1 | 実行される | フックからは何も届かない |
| stdout に `{"decision":"block","reason":...}` または `hookSpecificOutput.permissionDecision: "deny"`、終了コード 0 | 実行される | フックからは何も届かない |

したがって、拒否は理由全体を stderr に出し、終了コード 2 で終わらなければなりません。ツール呼び出しを拒否するアダプターの経路はすべてそうしており、転送したコアフックが終了コード 2 で終わればその stderr を中継します。PreToolUse フックの stdout がモデルに届くことはありません。複数の PreToolUse フックはファイル名の順に次々と実行され、前のフックがブロックしたあとでもすべて実行されます。2 つのフックの間にあるフックのブロックも、その理由が届きます。Kiro IDE はフックの実行ごとに「Run Command Hook」カードを 1 つ表示するので、AI-DLC は 4 つのツール呼び出し検査を 1 つのフック `aidlc-guard-tool-call` として登録します。このフックは、Kiro が個別のフックを実行していたのと同じように検査を実行します。同じ順序（`plan-approval-guard`、`review-freeze`、`state-transition-guard`、`terminal-command-guard`）で、それぞれ自身の登録が選んでいたツールに対して、前の検査が拒否したあとでもすべてを実行します。いずれかの検査が拒否すれば呼び出しは拒否され、各拒否のテキストは 1 回ずつ示され、通した検査からは何も示されません（#2022）。そのマッチャーが除外するのは、アダプターのツール名表にある読み取りだけです。読み取りは承認に答えることもワークスペースを変えることもできないためです。表が知らない名前（Kiro 自身のバックグラウンドの `memory` ツールなど）は、引き続き検査に届きます。1.1.14 では PreToolUse の `fs_write` の入力は `{path, text}` で、シェルの入力は上の 1.0.242 の行と一致します。

### 書き込みやコマンドの後: 次のカードが行う

Kiro IDE 1.2.37 がフックの stdout をエージェントへ渡すのは、終了コード 0 の `SessionStart` と `UserPromptSubmit` の場合だけで、stderr を渡すのは `PreToolUse`、`UserPromptSubmit`、`PreTaskExec` のフックが終了コード 2 で終わった場合だけです（そのフック実行器の終了コード表）。`PostToolUse` フックが出力したものは、エージェントにも本人にも届きません。そのため、AI-DLC が書き込みの後に行う作業（監査行とセンサー）とコマンドの後に行う作業（後述の監査末尾を読む 2 つのフック）には、それ自身のカードがありません。`aidlc-guard-tool-call` は呼び出しを通すとき、それを `aidlc/.aidlc-sessions/kiro-ide-pending/` の下に書き留めます。監査対象の書き込みでは対象ファイルのその時点の状態（サイズ、時刻、内容のハッシュ）を、コマンドではコマンドとすべてのスペースのレコードフォルダを書き留めます。どのみち実行される次のカード（次のガード、本人の次のメッセージ、またはターンの終わり）が、`catch-up` でまずその作業を行います。ファイルが変わった書き込みは、書き込み後のカードが渡していたのと同じ入力と、その書き込み自身の `session_id` とともに `write-audit-log` と `run-sensors` へ送られます。ファイルが変わっていない書き込みは、別の呼び出しが始まる間は後のカードを待ち（まだ書き込み中かもしれないため）、メッセージやターンの終わりでは捨てられます。コマンドは同じ前段ゲートの後ろで `aidlc-after-shell` の 2 つのフックを実行し、その実行中に現れたレコードフォルダは `Intent created: <record> (space: <space>)` として rebuild に渡されます。書き留めた各呼び出しはファイルの改名で取得されるので、2 つのチャットのカードが同じ作業を二度行うことはありません。フックファイルがまだ `aidlc-write-audit-log` や `aidlc-after-shell` を登録しているプロジェクトでは、それらのカードが引き続き作業を行い、ガードはそれらについて何も書き留めません。

## 各フックへの帰結

- **write-audit-log / run-sensors** — 復元可能: 結果の文言からファイルパスを抽出し、絶対パスへ解決し、Claude 形の `{tool_input:{file_path}}` をコアフックへ渡します。パスを抽出できない場合、アダプターは両方を記録するのではなく 2 つのケースに分けます。**失敗した**書き込みと認識された文言は `hookDebug`（フックデバッグが有効なときだけ書かれます）へ送られ、成果物が存在しないため転送されません。この推論はペイロードに構造化された成功フラグが無いときにだけ走ります。明示的な `toolSuccess: true` と、その他の一致しない文言は可視のフックドロップを記録します（黙った no-op には決してなりません）。こちらが、ドロップログが可視化するために存在する「見えない機能低下」のケースです。この 2 つを混同していたため、健全なワークスペースでも `--doctor` が機能低下を報告していました。
- **rebuild-stage-graph** — シェルコマンドは復元不能なので、IDE 経路はコマンドフィルターを捨て、監査末尾だけでゲートします（mtime による冪等ガード付き。たとえば `WORKFLOW_COMPLETED` 後に残った遷移が、以後のシェルコマンドのたびに再コンパイルを起こさないように）。シェルの結果とセッション識別子は引き続き転送されます。最新のイベントはそのままの `session_id` を使い、レガシーチャネルは SessionStart が保持するホスト由来の識別子を使います。結果が成功した `intent-create` を示す場合、共有フックはそのセッションを作成されたレコードへ束縛します。
- **sync-workflow-state** — IDE はタスクペイロードを渡さないため、監査末尾の最新の `STAGE_STARTED` から現在ステージを導出します。これは**前進のみ**のミラーです。`Current Stage` を完了済み／スキップ済みステージへ巻き戻すことはなく、ワークフローが `Running` でないときは発火しません（完了したワークフローの蘇生を防ぎます）。また、その `STAGE_STARTED` の後に、または別のクローンの監査ファイルで同じ秒に、Unit の再オープンが作業を現在のステージへ戻していた場合も、`Current Stage` には手を付けません（再オープンの行は `Moved From` を持ちます）。この移動は自身の開始を書かないため、最後の開始は作業が離れたステージを指しているからです。IDE には sync がパースできるタスクイベントがないため、監査末尾を読む両フックは `execute_bash`、Windows の `execute_pwsh`、`shell` エイリアスにマッチさせています。
- **監査末尾を読む 2 つのフックの前段ゲート**: これらはシェルコマンドごとに 1 回、次のカードの `catch-up` の中で（フックファイルが古いプロジェクトでは `aidlc-after-shell` カードとして）実行されるので、`catch-up` とディスパッチャーの `engine adapter kiro-ide` 経路が、エンジンを読み込まずに先に確認します（`core/tools/aidlc-hook-front-gate.ts`）。どちらかのフックがレコードのファイルからすることが何もないと判断すると、そのレコードの `.aidlc-engine/hooks-health/` に `<hook>.noop` を残します。ゲートがフックを省くのは、すべてのスペースのすべてのレコードがその印を持ち、それが、フックがそこで読むすべて（監査シャードと状態ファイル。rebuild ではさらに `runtime-graph.json`）より少なくとも 5 秒新しい場合だけです。省いた rebuild は、完全なフックと同じように既存の `rebuild-stage-graph.last` のハートビートを書き直します。リンク、スペース導入前のフラットなレイアウト、フックデバッグ、時計より先のタイムスタンプ、マージン内の変更のいずれかがあれば、完全なフックを実行します。カードが省かれるのは、両方のフックが省かれる場合だけです。ガード、書き込み、プロンプト、その他すべてのターゲットは常に完全に実行されます。
- **log-subagent** — ペイロード依存。IDE 0.12 は `invoke_sub_agent` を送り、1.x（1.0.89〜1.0.138）は代わりに `subagent_<agent>` を送りました。いずれも空の `subagent_response` シェル（`"Response recorded."`）が先行します。そのため登録マッチャーは広く（`^(?!subagent_response$)(subagent_.+|invoke_sub_agent|orchestrate_subagent)$`）取られ、空のシェルにはカードを出さずに、すべての委譲名がアダプターへ届きます。アダプターはそれ以外のすべての入口で `subagent_response` を落とします — このシェルは文言を運ぶものの身元を持たず、転送すれば `Agent Type: unknown` の `SUBAGENT_COMPLETED` 行を捏造してしまいます。身元は構造化された 1.x の `subagent_<agent>` ツール名を優先します（#543） — プラットフォーム提供のため、エージェントが書いた結果文言が監査行を誤帰属できません — 。フォールバックは #459 の `**Reviewer:**` / `**Agent:**` 結果マーカーで、これは 0.12 の `invoke_sub_agent` 形における唯一の身元信号です。
- **review-freeze / state-transition-guard**: それぞれ `aidlc-guard-tool-call` カードの中で、自身のマッチャーで実行されます。マッチャーは、アダプターが転送する書き込みとシェルのツール（`write`、`fs_write`、`create_file`、`str_replace`、`fs_append`、`delete_file`、`apply_patch`、`edit_file`、`execute_bash`、`execute_pwsh`、`shell`）をちょうど名指しするので、読み取り、検索、`memory` の呼び出しはどちらの検査にも届きません。`create_file`、`apply_patch`、`edit_file` のペイロードはキャプチャされていません。それぞれアダプターが読むパスのフィールドで検査し、それが 1 つも無いもの（パスがテキストの中にしかない patch）は後述のとおり拒否します。アダプターが認識する書き込みツールは、Write（`fs_write` は `text` を `content` として、kiro-cli 2.6.1 の `write` は `content` をそのまま）または Edit（`fs_append` は `text` を `new_string` として、`str_replace` は `oldStr`/`newStr` を `old_string`/`new_string` として、`delete_file` は `targetFile` をパスとして）として転送します。シェルのツールは Bash として、呼び出し自身の `cwd`（とコマンド中のリテラルな `cd` や `pushd` が残すすべてのディレクトリ）から判定して転送します（`execute_pwsh` には `aidlc_shell: "powershell"` を付けるので、両方の検査がそれを PowerShell として読みます）。ペイロードの `session_id` も一緒に渡します。それ以外のツールは転送しません。Kiro は委譲されたエージェント自身の呼び出しにもプロジェクトの PreToolUse フックを、コンダクターの `session_id` 付きでエージェントの身元なしに実行し、そこでも終了コード 2 を尊重します（IDE 1.2.4 で `invoke_sub_agent` 越しに `fs_write` で計測）。そのため両方のガードは、委譲先の呼び出しをコンダクターの呼び出しとして判定します。サポート対象のビルド（Kiro IDE 1.1.70、Kiro CLI 2.24.1 以降）のすべての PreToolUse ペイロードはツールを名指しし、その入力を埋めるので、どちらのガードも読めない呼び出し（ペイロードなし、不正なフィールド、ツール名なし、アダプターが読むパスのフィールドを持たない書き込みツール、コマンドのないシェルのツール）は、ワークフロー、Guard Policy、`AIDLC_DISABLE_REVIEW_FREEZE_HOOK` にかかわらず、どちらかが実行される前に終了コード 2 で拒否します。拒否はそれらのビルドを名指しし、古い Kiro を更新するよう伝えます。レガシーの引数なしのペイロードもそのような呼び出しの 1 つです。何も書き込まない読めるコマンドは引き続き転送します。
- **plan-approval-guard** — 引数が埋まっている `PreToolUse` の引数は、共有の対象認識ガードへ転送します。シェルの呼び出しは上記と同じく自身の `cwd` から判定します。Kiro IDE 0.12 はツールを識別しますが引数オブジェクトは空なので、アダプターは仲介された計画時ソースのプロトコルを使います（これはこのガード自身の扱いです。この行では上記の review-freeze と state-transition の登録がそのような呼び出しを拒否するので、このガードが通す計画の書き込みは実行されず、開いた書き込みウィンドウは後述のとおり復旧のラッチのまま残ります）。計画作業中に利用できるのは計測済みの `fs_write` と `str_replace` だけで、シェル・追記・削除・patch・エイリアス・独自の変更ツールは承認前に停止します。正規の計画書き込みの後、アダプターは現在の Testing Contract を注入します。正規の質問ファイル書き込みの後は、対象に結び付く `[Approval Fingerprint]` を差し替え、現在のワークスペースソースを `[Planned Source]` に記録し（レガシーチャネルではフィンガープリントコマンドを実行できないため、両タグをアダプターが管理します。ワークスペースにソースフィンガープリントがなければ `unbindable`）、予約された decision または answer ツールを自ら呼び出します。ステージのラーニング日誌、コンポーザの提案、本人の回答テキスト、または `aidlc/.aidlc-request-text/` に直接置く本人の依頼の書き込み（計画の待機中に共有ガードが認めるレコードファイル）は、計画の書き込みではありません。アダプターはその書き込みウィンドウをクリアし、違反を記録しません。Kiro は PostToolUse の stdout を捨てるため、成功時の書き込みフックは何も出力しません。decision または answer の手順が拒否された場合は、それを捨てずに拒否理由を stderr に出して終了コード 2 で終わります。書き込みウィンドウのラッチは、人間が復旧するまで解除されないためです。ワークスペースソースは、回答経路と同様に記録済みの `[Planned Source]` と照合します。計画時ソースが記録される前は比較対象がなく、記録されたあとに差分があれば、対象を判別できないツールを「計画を再提示する」という対処とともにブロックします。その対処を実行できるよう、正規の計画書き込みは引き続き許可します。
  呼び出し元の `next`、または最後のステアリング `continue` が、Code Generation ディレクティブに `legacy_plan_approval_choices` の権能を 1 つ載せます。ランタイムが保存するのはそのハッシュだけで、平文のラベルはそのチャットのツール結果に残ります。人間の後続の `promptSubmit` は、正確なラベルをちょうど 1 つ運ばなければなりません。無関係なプロンプトに権能は与えられません。所有権は、受信セッションを辿って引くのではなく、アクティブなインテント／リビジョンに対してグローバルです。復旧は人間ゲート付きです。所有ウィンドウがまず型付きの復旧問い合わせを受け取り、エージェントはそれを平易な言葉で尋ねます。以後の `next` がオファーやチャレンジをローテーションする前に、エージェントは本人の承諾を、どのような言葉であれ `log answer --checkpoint plan-approval --details 'Recover Plan Approval'` で記録します（問い合わせの後に本人の返答が来ていれば、エンジンは自身の選択から応答を書き込みます）。別の生存中ウィンドウからの要求は拒否されます。置き換えのウィンドウが同じ人間による復旧を要求できるのは、記録された所有者 PID が消えた後、または IPC のみの所有者のエンドポイントが消えた後だけです。引き継ぎは保留中のチャレンジをローテーションし、その直前の応答をクリアします。共有の質問ファイルは正規のまま保たれ、監査は選択肢を伏せます。オファー／チャレンジのファイルが欠落・破損しても権威が消えることはありません。PostToolUse が一度も届かない場合、書き込み前ウィンドウそのものが孤児復旧のラッチとして働き、PostToolUse が走った場合は、一致する書き込み違反がそのラッチを継続させます。新規の公開は、本人の復旧への承諾が記録されるまでブロックされたままです。アダプターは復旧問い合わせを保持し、成功後は、置き換えのオファーを削除するのではなく違反／書き込みウィンドウだけをクリアします。各書き込みの前にラッチが作られます。権威ある `toolSuccess: false` と認識済みの失敗文言は、変更が起きていないためこれをクリアし、結果が不明な場合はラッチを保持して復旧を要求します。
  引数を持たない計画書き込みの前に、アダプターは現在の対象／リビジョンを保護された書き込みウィンドウへ保存します。その書き込みが状態、アクティブマーカー、あるいは別の権威ファイルを削除・破損した場合、PostToolUse は保存されたリビジョンを poison し、生きている権威をもはやパースできない場合でも、以後の変更呼び出しはブロックされたままになります。アダプターが所有する `next` の復旧がその poison をクリアするのは、エンジンが有効な非エラーのディレクティブを返した後だけです。生の監査追記に権威はありません。アダプターが所有する復旧と decision／answer の仲介は、`aidlc-runtime-paths.ts` の共有ヘルパー `aidlcEngineCommand` を使います。これはオーケストレーターの state 子プロセスも使うものです。ネイティブモードは（`AIDLC_COMPILED_EXECUTABLE` を尊重して）コンパイル済み実行ファイルを解決し、`engine orchestrate next`／`continue` または `engine log decision`／`answer` を起動します。ソースモードは Bun の実行ファイルと、`aidlc-orchestrate.ts` または `aidlc-log.ts` の絶対パスを使います。どちらのモードも既存のプロジェクト／セッションの引数、作業ディレクトリ、継承した環境を保ちます。失敗した子プロセスの呼び出しは実際のエラーを保持し、不正な JSON や error ディレクティブで復旧のラッチを解除することはありません。新しいステージの試行は承認を失効させますが、同じ対象・同じ試行に対する新しいディレクティブでは失効しません。生成の開始時に計画が結び付くソースの基準を取り直しますが、それより先にワークスペースソースが動いていれば、記録を削除せず拒否します。
  共有の `ask_type: "guard-recovery"` ディレクティブは、レガシーの復旧問い合わせとは別の契約です。選ばれた対処の `interaction` に従い、必要な人間の選択のあと、返された `command` をそのとおりに実行し、`human-input` の Request Changes の対処では、正確なフィードバックを別に受け取ります。ネイティブの restart／abort コマンドは構造化された操作から得ます。ネイティブの abort が Plan Approval の前提条件の例外を受けるのは、出力されたとおりの引数の形の場合だけです。所有するツールは引き続きライフサイクルの許可判定を強制します。[ガードの許可判定と復旧質問](12-state-machine.md#ガードの許可判定と復旧質問) を参照してください。
- **session-start** — 最新の `session_id` を読み取り、gitignore 対象のランタイムセッションディレクトリ配下に永続化します。レガシーチャネルは代わりに、`VSCODE_IPC_HOOK` / `VSCODE_PID` からホストインスタンス単位の安定した ID を導出します。Kiro IDE 1.1.14（Windows でライブ確認）は新しいチャットで SessionStart フックを実行しないので、後述の record-human-turn の経路が、チャットの最初のプロンプトでこの作業を行います。
- **ターミナルコマンド** — 送信された `/aidlc ...` プロンプトを公開するより新しいビルドは、UserPromptSubmit で決定論的なユーティリティを実行します。IDE 1.0.242 は空のプロンプトを公開するため、フォールバックは PreToolUse で厳密に一致する `execute_pwsh` の `aidlc-orchestrate.ts next` 呼び出しを認識し、分類済みユーティリティを 1 回だけ実行し、重複するシェル呼び出しを拒否します。どちらの経路もイベントの `session_id` をセッションとしてユーティリティに渡すので、このフックが record-human-turn によるそのチャットの開始より前に走った場合でも、`/aidlc intent <name>` や `/aidlc space <name>` は、それを入力したチャットを結び付けます。どちらの経路も UTF-8 を明示的にデコードし、ターミナルのプロトコル／制御バイトはプレーンテキストの中継からのみ取り除きます。構造化されたフック JSON や無関係な拒否経路は書き換えません。最新のターン／ラッチ状態は `session_id` のハッシュをキーとするため、並行するチャットが互いの出力を再利用することはできません。セッション識別子を持たないペイロードは、ホスト由来の識別子か保持済みのセッションを使い、どちらもなければ明示的なレガシーのバケットを使います。0.12 の camelCase フォールバックは、コマンドを `toolArgs.command` から読み取ります。
- **ターミナルコマンドの後のシェル呼び出し**: 同じターンの中では、上記のフォールバックは、シェル経由で再び入力されたターミナルコマンド、引き下げるガード設定、ツールファイル `aidlc-orchestrate.ts`、`aidlc-utility.ts`、`aidlc-knowledge.ts` を名指す呼び出しも拒否します。あるチャットのターンでターミナルコマンドが実行されると、エージェントはその出力を中継して止まるよう伝えられ、`terminal-command-guard` はそのターンのそのチャットの他のすべてのシェル呼び出しも拒否します。ツール入力を読めない呼び出しも含め、終了コード 2 で、出力を中継してターンを終えるよう述べる固定の 1 行を stderr に出し、コマンドが運んでいたものは何も引用しません。ペイロードが名指すチャットについては、固定の呼び出しを求める拒否（単独のキャリッジリターン、ファイルへ送られた AI-DLC の返答、cmd.exe が分割する値、引数の中の PowerShell コード）より前にこれを判定するので、エージェントが呼び出しをもう一度実行するよう言われることはありません。再び入力されたターミナルコマンド、ツールファイルを名指す呼び出し、引き下げる設定コマンドは、そのような文字を含む場合も、代わりにフォールバックの拒否とその出力を受け取ります。本人のメッセージを隠すビルドでは、引き下げる設定コマンドはそれ自身の拒否を受け取り、その拒否が抜け道を名指します。対象は、任意の引数を付けたディスパッチャーやネイティブの `aidlc`、任意のプロジェクト、実行時にシェルが組み立てる名前、そして AIDLC をまったく名指さない呼び出しです。どの呼び出しが無害かを、コマンドの読み取りで決めることはありません。シェルでないツールはこの検査の対象外です。ターンが進むのは本人のメッセージ（`UserPromptSubmit`）があったときだけです（Kiro が自ら作ったプロンプトは `HOST_TURN` として記録され、ターンを進めません。ただし、ターミナルコマンドが保持していた実行がその Stop で終わったあとなら、そのチャットに対するそのようなプロンプトはそれ自身の実行を始め、保持を終わらせます。その実行が開いている間や、ワークフローのステップ自身のセッションでは、保持は残ります）。本人のメッセージなしに Kiro が始めたエージェントの実行はターンを保ち、本人の次のメッセージがそれを解放します。同一ターンのシェル検査が判定するのは、ペイロードの `session_id` が名指すチャットだけで、そのチャットが記録したターンに対してです。ペイロードにセッションがない場合、別のチャットのラッチ、または後のターンでは、何も拒否しません。ターン数は整数としてだけ読まれ、やり直しが必要になったとき（欠落または読めない）はいつでも、その横のラッチは捨てられます。ラッチを削除できないときは、新しい数はそのラッチのターンより先から始まります。数を書き込めないときはラッチも一緒に取り除かれるので、そのターンのターミナルコマンドはラッチを残さず、そのシェル呼び出しは実行されます。数を書き込めず、かつラッチを削除できない場合にだけ、どちらかを再び変更できるようになるか本人が新しいチャットを開くまで、ラッチは一致し続けます。ペイロードがセッションを名指さない場合、ターミナルコマンドの拒否は引き続きホストのセッションか保持済みのセッションに従います。これに対するエンジン自身のガード（Branch 0）が読むのは agent-v1 のプロジェクト全体のラッチだけで、これらのチャットごとのラッチは読みません。エンジンがあるチャットのラッチと別のチャットのラッチを見分けられるのはプロセスの祖先関係を通じてだけで、1 つの Kiro IDE ウィンドウのチャットは 1 つのプロセスを共有するからです。
- **cmd.exe のメタ文字**: ネイティブ Windows の `aidlc` は `aidlc.cmd` なので、cmd.exe は Windows PowerShell 5.1 がそれのために組み立てるコマンドラインを読みます。空白を含む値は、値自身のダブルクォートをそのままにしてダブルクォートで囲まれ、cmd.exe はクォートの外の `&`、`|`、`<`、`>`、`^` に反応します。そのため `--details 'Use "R & D" team'`（`\"` を使った同じもの）は、`D" team"` を別のコマンドとして実行します。`terminal-command-guard` は何よりも先に、これらの文字のどれかがクォートの外で cmd.exe に届く `aidlc` または `aidlc.cmd` の `execute_pwsh` 呼び出しや、値に `%NAME%` の組を含む呼び出しを拒否します（終了コード 2、理由は stderr）。cmd.exe はクォートの中でも、それを同名の環境変数の値に置き換えるからです。単独の `%` は通り、`10% and 20%` の中のもののように、名前が空白で始まるか終わる組も通ります。理由は、問題の値を持つフラグ（または「A value」）と、その文字または「a %NAME% pair」を名指しする固定の文で、値そのものは決して繰り返さないので、値の中のテキストが行を加えることはできません。`orchestrate next` の後のテキストが変更を求められることはありません。そのテキストが、そのような文字、`%NAME%` の組、ダブルクォートやタイポグラフィックなクォート、改行、または空白を含む値の末尾のバックスラッシュを持つとき、理由は代わりに依頼ファイルを名指します。エージェントはそれを `next --request-file` 用に自身のファイルツールで書きます。また理由は、フラグの値はそのファイルを通せないことも述べます（エージェントは、メタ文字を含む 1 語の値はシングルクォートの中のダブルクォートで書き、自分で書いた値からはその他の文字を外し、本人が与えた値については本人に尋ねます）。通るのはその 1 つの形だけです。`%`、ダブルクォートやタイポグラフィックなクォート、末尾のバックスラッシュを含まない、ダブルクォートで囲んだ 1 語（`--report '"scan&review.json"'`）で、`next` が任意の値で受け取るフラグ（`nextTokenKind`）の後に置かれ、かつエンジンが `next`（または先頭の `compose`）の後に受け取る語がフラグとその値である間に限ります。`--` の印、語、先頭の名詞、エンジンが受け取らないフラグ、変数、またはエンジンがそのフラグの値として受け取らない値（空、`--` で始まる、またはフラグが列挙するものでない）があると、そこで終わります。エンジンが行から最初に取り除く `--request-file`、`--project-dir`、`--aidlc-attempt-id` は、その値ごと読み飛ばされます。他の語のどれが依頼かはエージェントが知るべきことで、フックはそれを読みません。検査は PowerShell 5.1 の引数の渡し方（空の引数は落とし、空白やタブを含む値はダブルクォートで囲む）と cmd.exe のクォートの切り替えを模擬し、`#` コメントと閉じた `<# ... #>` ブロックコメントの先を読み、バッククォートの継続（CRLF、LF、CR）で終わる行を次の行とつなげます。`(...)`、`$(...)`、`@(...)`、`@{...}`、`{...}` のグループの中の文も、入れ子かどうかにかかわらず読むので、`(aidlc engine orchestrate next 2>$null | Select-Object -Last 1)` のような `aidlc` の呼び出しも、他と同じように検査されます。ダブルクォートの文字列の中の `$(...)` は読みません。リダイレクト（`2>$null`、`*>$null`、`>$null`、`2>&1`、`> file`）が `aidlc` の値になることはありません。`aidlc.cmd` が実行される前に PowerShell が解決する本人の言葉も拒否します。cmd.exe に何が届くかを検査で見られないからです。対象は `--details`、`--decision`、`--rationale`、`--reason`、`--user-input`、`--feedback`、`--override`、`--arguments` の値、または `next` の後の依頼を、`$x` や `$env:X` のような変数、`$(...)` のような式、`$` やバッククォートを含むダブルクォートの文字列で与えたものです。理由は、値が PowerShell の変数や式から来ていることを述べ、値そのものをシングルクォートで渡すよう求めます。他のフラグや位置トークン（`continue $obj.receipt` のレシートなど）に対する変数は、それ自身のテキストがメタ文字や `%NAME%` の組を含まない限り通ります。他のコマンドの中の変数も同様です。最後まで読めない文（停止解析トークン `--%` を使う文や、閉じていないクォートやブロックコメントを含む文）は、その位置までの語からわかる範囲で、プログラムが `aidlc` または `aidlc.cmd`（裸、パス指定、`&` や `.` の後）なら拒否します。他のプログラムを実行する文は、データとして aidlc に触れていても通ります。`bun .kiro/tools/...` の呼び出しやその他のプログラムは検査しません。
- **stop** — 最新の Stop イベントの `session_id` を読み取り、ワークスペース全体の SessionStart マーカーより優先します。これにより並行するチャットはそれぞれ自身の作成後と切り替え後の引き継ぎレシートのみを消費します。レガシーの agentStop や壊れた最新チャネルは、保持済みの識別子にフォールバックします。
- **record-human-turn** — 最新の `session_id` と回答ペイロード、またはレガシーの `USER_PROMPT` を読みます。ディレクティブが発行した正確な選択肢を送信できますが、別のチャットの保護された権能を明かすことも、ローテーションすることも、移譲することもありません。プロンプトの `session_id` が直前のイベントから保持したものでない場合、またはアダプターにそのセッションを開始した記録がない場合、アダプターは先にコアの session-start を実行し（そのセッションを以前に開始していたか、セッションがすでに結び付きやインテントの刻印を持っていれば `resume`、そうでなければ `startup`）、プロンプトフック自身の文脈の前にその文脈を出力します。そのため新しいチャットでも `AIDLC Runtime Session:` の行が得られ、以前のチャットに戻ると結び付けし直されます。記録は、セッションのハッシュ化したターン／ラッチのディレクトリにある `session-started` ファイルで、session-start が成功したあとにだけ、この経路か、実際に実行された SessionStart フックから書かれます。保持した ID だけでは開始の証拠になりません。以前のアダプターはすべてのプロンプトの ID を開始せずに保持していたので、更新をまたいで開いているチャットは次のプロンプトで開始されます。開始済みで保持されたセッションからのその後のプロンプトは、何も開始しません。
- **session-end / block** — ペイロード不要で、stdin を決して読みません。session-end は SessionStart が永続化した識別子を再利用し、レガシーのライフサイクルフォールバックは、承認権限が一切関わらない場合にのみ保持されます。

## toolResult のパス抽出パターン

| toolName | 文言 | 正規ツール |
|----------|---------|----------------|
| `fs_write` | `Created the <PATH> file.` | Write |
| `str_replace` | `Replaced text in <PATH>`（末尾に ` (N occurrences)` が付くことがある） | Edit |
| `fs_append` | `Appended the text to the <PATH> file.` | Edit |

抽出器はマッチ前に末尾の空白／改行をトリムし、`str_replace` 形からは末尾の括弧書きを取り除きます。`fs_write` は `Write` に対応します。`str_replace`／`fs_append` は `Edit` に対応します（どちらも既存ファイルが対象 → コアの write-audit-log は `ARTIFACT_UPDATED` を記録します）。
