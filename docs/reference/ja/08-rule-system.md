# ルールシステム

> 対象読者: 第 2・第 3 層（チーム導入者、フレームワークコントリビューター）。

この章は、ルールシステムに関するスキーマレベルのリファレンスです。ルールファイルがどこに置かれるか、スコープをどう導出するか、継承チェーンがどう解決されるか、どのメタデータフィールドが有効かを定義します。これは、解決器（`aidlc-graph.ts compile`）と診断コマンドのルールドリフト検査が参照する仕様です。ルールは制御ループにおけるフィードフォワード側であり、対になる決定論的検証側は [センサーシステム](07-sensor-system.md) が扱います。学習ループ儀式、銀行業の実例、確認済み学習がどうルールファイルへ着地するかといった利用者向け説明は、ユーザーガイドの [ルールと学習ループ](../guide/09-rules-and-the-learning-loop.md) を参照してください。

## 配置

ルールは、アクティブなスペースのメモリ層 `aidlc/spaces/<active-space>/memory/` に置かれます。ここはワークスペースルートにある、人が直接編集できる単一の集合であり、各ハーネスはそれぞれのネイティブな取り込み機構（Claude の `@` による取り込み用スタブ、Kiro CLI のエージェントリソース、メモリの本文を載せる Kiro IDE の常時取り込みステアリング、Codex ではエンジンによるステップごとのルール配信、Cursor の常時適用ルール `.cursor/rules/aidlc.mdc`、opencode の `instructions` glob、Copilot の `AGENTS.md` による `@` 取り込み）を通じてこれを読みます。ファイル名は中立なスコープ名です。

```
aidlc/spaces/<active-space>/memory/
├── org.md
├── team.md
├── project.md
└── phases/
    ├── ideation.md
    ├── inception.md
    ├── construction.md
    └── operation.md
```

この配置は、チーム著述のハーネス設定（以前は別のプラクティス名前空間にあったもの）と、自己学習型ガードレール（以前は 2 階層だったもの）を、`aidlc/spaces/<active-space>/memory/` という 1 つのアクティブなスペースメモリディレクトリに統合したものです。

## ファイル名から導出するスコープ

ルールファイルは `scope:` メタデータフィールドを**持ちません**。スコープはファイル名から導出されます。

| ファイル名パターン | スコープ |
|---|---|
| `org.md` | `org` |
| `team.md` | `team` |
| `project.md` | `project` |
| `phases/<phase>.md` | `phase`（フェーズ値 = ファイル名） |

組織・チーム・プロジェクト・フェーズのルールは、パススコープ用メタデータを持ちません。関係はステージ側からの取り込みを著述することで置かれます。組織・チーム・プロジェクトの各ルールは、ファイル名由来の共通既定値としてすべてのステージへ適用されます。対応するフェーズルールは、ステージメタデータの `phase: <name>` フィールドが `phases/<name>.md` を取り込むため、自動で付与されます。

## 5 層継承

ルールは、ワークフロー開始時に次の 5 層チェーンで解決されます。

```
org → team → project → phase → stage
```

組織層はフレームワーク既定値を担い、チーム層とプロジェクト層はチームが確認したプラクティスとプロジェクト固有の特殊化を追加します。フェーズ層は直交する層であり、ステージがメタデータに `phase: <name>` をすでに宣言しているため、対応する `phases/<name>.md` を付与します。これは `requires_stage` や `consumes` と同じ著述方向です。ステージルールは将来予約済みです。将来 `aidlc-stage-<slug>.md` が著述されるようになれば、各ステージの `slug:` 宣言経由で付与されます。このチェーンが実装している広い 2 軸設定モデルについては [アーキテクチャの「設定レイヤー」](01-architecture.md) を参照してください。

コンパイル出力では、`stage-graph.json` の各ステージノードにある `rules_in_context` フィールドへ、この解決済みチェーンが焼き込まれます。実行時にチェーンをたどり直すことはありません。解決はコンパイルの責務です。

## 厳密加算の実行時モデル

適用対象のルールは、すべて `rules_in_context` に現れます。組織・チーム・プロジェクトのルールは単純連結され、実行時に落とされるものはありません。フェーズルールは、そのファイル名がステージの `phase:` 宣言と一致したときに付与されます。グロブフィルターも、具体パスの合成もありません。エンジンはアクティブスペースの各実質的ルールファイルを読み、収まる場合はその本文をステージの `run-stage` に並べて `rules_content` として送ります（大半のハーネスの大半のステージ）。収まらない場合は、本文が先に 1 つ以上の有界な `load-steering` ディレクティブで届きます（ディレクティブ予算が小さい Copilot の大半のステージ）。チャットが以前のステップからこれとまったく同じバンドルをすでに保持している場合、`run-stage` はそれを `rules_held` として示し、本文は運びません。継続トークンは、ランダムなマシンローカル秘密鍵による整合性 MAC を運びます。鍵はアクティブなインテントの gitignore 済み `.aidlc-*` ランタイム状態配下（インテントが存在する前はクローンローカルのセッションランタイム配下）にあり、トークンはステージ・ワークフロー状態・ルールバンドル・ルート・次パートを束縛するため、公開プロジェクトパスからは再署名できません。新しい `next` は必要時に鍵を遅延発行します。サイズ理由のパスフォールバックはありません。空のテンプレートは落とされ、読取不能または不正な必須ルールは修復ガイダンス付きで停止します。`default` 以外のスペースでフレームワークのフェーズルールファイルのいずれかが欠けている場合（`space create` がそれらをコピーするようになる前に作られたスペースには一つもありません）、ステージがそれを必要としたときにフレームワークのコピーが与えられます。既存のファイルを上書きすることはありません。配信はステージごとに毎回繰り返されるため、ワークフロー途中で受け入れられた学習も次のステージに届きます。

§13 の学習儀式は、学習が解決器へ到達する前に、メモリゲートで競合（より狭いスコープがより広い方針へ矛盾する場合）を選別するようオーケストレーターへ求めます。この検査はセクション単位です。提案された日付付き学習エントリを書き込もうとする際、オーケストレーターは `memory/project.md`（または `memory/team.md`）への候補を `memory/org.md` の対応見出しと比較します。競合が見つかれば、ユーザーは**修正・スキップ・エスカレーション**を選びます。上書き経路はありません。競合がない、またはユーザーがエスカレーションした選択だけが `aidlc-learnings.ts persist` へ到達します。`persist` は `org.md` を読まず、この比較を独自に判定することもありません。したがってこの検査は監査上の補助であり、決定論的な強制境界ではありません。プラクティス発見の確認ゲートも別の受け入れゲートですが、そちらの昇格は `aidlc-state.ts practices-promote` による決定論的なセクション置換であり、ユーザーの確認によって正当化されます。自動の組織ルール競合チェックは行いません。書き込み後に組織・チーム・プロジェクトの内容がずれた場合は、診断コマンドのルールドリフト行が別途可視化します。

この設計は、以前の `enforcement: enforced` キーワードと `overrides:` ブロックモデルを置き換えます。どちらのキーワードもスキーマから削除されました。メタデータの解析は、下記の未知キー方針のもとでそれらを許容します。エラーなく通過し、解決器はそれらを無視します。

診断コマンドのルールドリフト検査は、後から生じたドリフトをオンデマンドで可視化します。組織ルールが更新された後にチームやプロジェクトの内容がすでにディスク上へ存在している場合、診断コマンドは `memory/team.md` と `memory/project.md` の `##` 見出しのうち、*内容を持つ*組織見出しと重なるものを決定論的に見つけ、各重なりを助言候補として表示します。表示内容はファイル、セクション、引用された組織文です。行は `Rule drift: N team/project rule(s) overlap org policy (review for contradiction)` という形になります。ライフサイクル上 stale なファイル由来の重なりは、この生きた件数から除外し、`Rule drift: N stale-suppressed` として別行で報告します。診断コマンド自体は LLM を使いません。検出は見出しと文字列のバイト再現可能な処理です。矛盾かどうかの判断は、観測時点でそれを消費するオーケストレーター LLM が担う非ブロッキング判断です。人間はその後、修正・エスカレーション・許容を選びます。

## `pairing:` フィールド

ルールは、`.claude/sensors/aidlc-*.md` にある決定論的センサーと対にできます。

```yaml
---
pairing: aidlc-required-sections
---
# or
pairing: feedforward-only
---
```

有効値:

- `feedforward-only` — このルールに対応センサーがないことを明示します。つまりフレームワークでは決定論的に検証できません。
- `aidlc-<sensor-id>` - センサーのマニフェストファイルのステム（拡張子を除いた名前）です。たとえば `id:` が `required-sections` のセンサーには `pairing: aidlc-required-sections` と書きます。`aidlc-` で始まらないその他の値は、ルールの読み込み時に拒否されます。診断コマンドは照合の前に接頭辞を剥がします。

診断コマンドの対カバレッジ行は、対付きルールとフィードフォワード専用ルールを数え、対になっていないルールを網羅率ギャップとして可視化します（[ルールドリフト検出](#ルールドリフト検出) を参照）。

## ライフサイクルフィールド

すべてのルールファイルは、ファイル単位のライフサイクルメタデータを宣言できます（任意）。

```yaml
---
status: active
stale_after: 2026-12-31
---
```

- `status` が受け付ける値は `active`、`deprecated`、`draft` のちょうど 3 つです。`deprecated` はそのファイルを stale にします。`active` と `draft` はしません。
- `stale_after` は `YYYY-MM-DD` 形式の実在する暦日でなければなりません。ファイルが stale になるのは現在の UTC 日付がその値を厳密に超えたときだけなので、`stale_after` に書いた当日はまだ生きています。
- ライフサイクルはファイル全体に適用され、個々の見出しには適用されません。stale なチーム／プロジェクトファイルの組織見出しとの重なりは、生きたルールドリフト件数から、成功扱いの別行 `stale-suppressed` へ移ります。

どちらのフィールドも任意で、不正な値はルール読み込みをエラーで停止させ、そのファイル名を示します。組織・チーム・プロジェクト・フェーズのどのルールファイルでも有効ですが、Tier-1 の決定論的な消費者は意図的に、`/aidlc --doctor` におけるチーム／プロジェクトの重なり抑制だけに限定しています。ライフサイクルメタデータが、厳密加算の実行時バンドルからルールを取り除くことはありません。

## ルールドリフト検出

`/aidlc --doctor` には、ルール / センサー状態を観測する 2 つの助言行があります。どちらも読み取り専用で、見つけた内容は成功扱いです。どちらの検出結果もヘルスチェック終了コードを変えません。検査そのものが実行できない場合（ルールファイルの読み込みや検証に失敗した場合）は、`Rule drift: check failed` または `Paired sensor coverage: check failed` と表示されて失敗し、そのエラーを示します。診断コマンドはコールドセーフです。対カバレッジ検査が出す `GUARDRAIL_LOADED` 監査行は、監査分割記録がすでにある場合にだけ書き込まれます。意図がまだない新しいシェルでは、診断コマンドは行を表示しますが、イベントを出さず、ファイルも作りません。

- **ルールドリフト** — 各チーム / プロジェクトのプラクティスファイル（`memory/team.md`, `memory/project.md`）について、診断コマンドは `memory/org.md` 側にも存在する `##` 見出しを探し、各重なりを候補ペアとして表示します。表示内容はファイル、セクション、そして組織側の最初の文の逐語引用です。組織側の本文が空、たとえばフレームワーク既定の `## Forbidden`, `## Mandated`, `## Corrections` のように HTML コメントしかない見出しは数えません。重なりは双方に内容がある必要があります。生きた重なりは従来どおり「矛盾がないか確認せよ」の行に出ます。ライフサイクル上 stale なファイル由来の重なりは、同じインライン詳細を伴う `Rule drift: N stale-suppressed` という 1 本の別の助言行に出ます。各行の件数 N は、LLM が矛盾と認定した件数ではなく、*構造的* な候補ペア数です。診断コマンドは決定論的に検出するだけで、矛盾判定は観測時点のオーケストレーター LLM が行います（[厳密加算の実行時モデル](#厳密加算の実行時モデル) を参照）。
- **対付きセンサーの網羅率** — `pairing: aidlc-<sensor-id>` を持つ各ルールについて、診断コマンドは `aidlc-` 接頭辞を剥がし、そのセンサーが少なくとも 1 つのステージの解決済みセンサー集合（`sensors_applicable`）に存在するかを確認します。行は `Paired sensor coverage: P/(M-X) guardrails paired (X feedforward-only)` という形式です。M は `pairing:` 値を持つルール総数、X はフィードフォワード専用ルール数、P は名前付きセンサーが実際に解決されるルール数です。対になっていないルール、つまりセンサー ID は書かれているがどのステージにも束縛されていないものは、行内に列挙されます。これは**ファイル存在確認であって意味論チェックではありません**。束縛が解決されるかだけを確認し、そのセンサーがそのルールに適切かまでは見ません。この行は、初期化済みプロジェクトでは 1 実行あたり 1 回 `GUARDRAIL_LOADED` 監査イベントを出します（監査分割記録がない未使用のプロジェクトでは抑制されます。上のコールドセーフ注記を参照）。

## 前方互換ポリシー

ルールメタデータは、加法的拡張に対して前方互換です。

- 新しいフィールドは加法的に追加されます。既存のルール行を書き換える必要はありません。
- コンシューマーは未知のメタデータキーを許容しなければなりません（無視して通す）。これにより、古い `enforcement:` / `overrides:` キーがユーザー拡張オーバーレイに残っていてもエラーなく読み込めます。
- ルール本文の慣習（`## Forbidden`, `## Mandated` のようなセクション）は、既存のガードレール規約に従います。
- 学習儀式（メモリゲート）は、確認済み学習を、その日付付きエントリとして直接スペースメモリファイルへ書き込みます。既定は `memory/project.md`、ワンクリック昇格先は `memory/team.md` です。組織スコープへの書き込みはありません。確認済み学習はそのままプラクティスであり、プラクティス発見が確認するのと同じファイル群へ入ります。別の `*-learnings.md` 面はありません。解決器はこれらを、`SCOPE_PRIORITY` による単純な整数チェーン（組織:0、チーム:1、プロジェクト:2、フェーズ:3）で整列します。1.5 や 2.5 のような中間ティアはありません。上の「厳密加算の実行時モデル」で説明した受け入れ時の競合検査を実行するのはオーケストレーターです（単一の提案日付エントリを `memory/org.md` の対応セクションと比較し、修正 / スキップ / エスカレーションを行う。上書き経路はありません）。その後、`aidlc-learnings.ts persist` が、受け取った選択をこの比較を再実行することなく書き込みます。

- **実際の学習ループ** — `memory.md` の日誌、承認ゲート儀式、銀行業の実例。ユーザーガイドの [ルールと学習ループ](../guide/09-rules-and-the-learning-loop.md) を参照してください。
- **より広い 2 軸設定モデル** — この 5 層チェーンが具体化している原理です。[アーキテクチャの「設定レイヤー」](01-architecture.md) を参照してください。
